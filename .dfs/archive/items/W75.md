**W75.5 Approach**: In `run.sh`, a chain started from the main checkout on a task with no worktree runs `git worktree add .dfs/worktrees/<task> -b dfs/<task> <default branch>` (reusing an existing `dfs/<task>`), moves the task file's uncommitted state there, and launches every session with cwd = the worktree; the run directory, `meta.json` and the runner's log entries stay where the screen reads them. Test in test_chain.py with the stub agent: a chain's node commits land on `dfs/<task>`, main does not move.

**W75.6 Approach**: A `merge` command (in `tree.py` or a new `branch.py`) merges `dfs/<task>` into the default branch (`main`/`master`, local only, no push) with `git merge --no-ff`, keeping the node commits' subjects in history, then removes the worktree and deletes the branch. `run.sh` calls it when a chain stops `done` after a review `ok`; decide whether the author's accept (screen and web) merges too. Test in test_chain.py.

**W75.7 Approach**: On a conflict, `git merge --abort` and add an open node to the task: merge the default branch into `dfs/<task>` in the worktree and resolve, which completes the tree again and earns another review. A merge git refuses before starting because the author's uncommitted edits on main overlap it is a raise naming the paths. Tests for both.

**W75.8 Approach**: Update SKILL.md (a session runs in the item's worktree on `dfs/<task>`), README, `run.sh`'s header and `templates/ROADMAP.md` if it names the default branch. Run the full test suite, and a stub-agent chain in a scratch repo from first session to review `ok` showing the branch merged into main and the worktree gone.

**W75.9 Approach**: In `branch.py merge`, after the task's files are committed and before `git merge --no-ff`, `_rebase` runs `git rebase <default>` in the worktree (skipped when the default branch is already an ancestor). A rebase that conflicts is aborted and `_reopen` adds an open node asking for `dfs/<task>` to be rebased onto the default branch and resolved; a merge that still conflicts afterwards goes the same way. SKILL.md, README and run.sh's header say rebase-then-merge. Tests in test_chain.py: a default branch that moved is rebased onto before the merge (it is an ancestor of the merge's second parent), and a conflicting rebase leaves no `.git/rebase-merge` and reopens the item.

**W75.10 Approach**: `branch.py` `carry_uncommitted` moves an untracked task file (a task just written from the screen, like W76–W84 in this checkout now) into the worktree and unlinks it from the main checkout, but `tree.task_ids()` globs only the main checkout's `dfs_paths.items()`, so `state.items()`, the screen, the web page and the walk stop listing the task until the merge, although `tree.exists()` (routed through `part_tags`) still finds it. Fix: have `task_ids()` also list the tasks found in each item worktree (`dfs_paths.worktree_states()`), or keep a copy of the task's file in the main checkout. Add a test in test_tree.py or test_chain.py: an untracked task is still in `state.items()` after `enter`, and is listed once after the merge.

# W175 · Ending a chat should return to the chat list

## Summary

Archiving a chat from the web page's chat dialog now closes the dialog and shows the Chats list, with the chat under Archived, including when the chat was opened from that list (the list is redrawn at once). The Chats button in the dialog does the same. The terminal already stayed on the chats list after archiving, so it is unchanged. I read "ending a chat" as the Archive button; the browser flow that covers it was extended but could not be run in this environment (no node).

## Goal

Ending a chat should return to the chat list

## Tree

### W175.1 · Archive in the web chat goes to the Chats list
Status: confirmed
Approach:
- **The question**: when a chat is ended with its Archive button, where should the page go next?
- **Why it matters**: today `chatend` in `scripts/web/index.html` archives the chat and leaves the dialog open on "Archived.". The user must press Chats or Back. The Goal says ending a chat returns to the list.
- **What this node does**: after `/api/chat/end` succeeds, `chatend` closes the chat dialog and calls `go("chats")`, as `chatlist` does, then toasts "Chat archived.". The `chat_end` flow in `scripts/ui_flows.mjs` expects the list instead of the open dialog. The terminal is left alone: `E` in its chats pane already stays on the list.
- **How we will know it worked**: the `chat_end` flow clicks Archive and then finds the Chats tab current, the dialog closed and the chat under Archived. The flow cannot run here (no node), so the change is also read against `chatlist`.
Hypothesis: "Ending a chat" means the Archive button in the web chat dialog. Wrong if the author meant ending from the terminal (`E`, which already stays on the chats list), or the agent exiting by itself. .dfs/artefacts/2c635ceb-ea4d-4bd9-b3ce-3c51e2df6de3.html
Evidence:
- for: `chatend` in `scripts/web/index.html` only redraws the dialog, while `chatlist` already does close and `go("chats")`, so the web path is the one that does not return to the list.
- for: terminal `end_chat_row` calls `chat_rows(fresh=True)` and keeps `pane == "chats"`, so it already returns to the list.
- against: the terminal's `E` on an item (not in the chats pane) also stays on the item, which is the right place there since the chat was opened from the item.
Determination: Confirmed: Archive in the web chat now closes the dialog and opens the Chats list, and the `chat_end` flow expects that. The flow could not run here (no node), so it is read, not run; the unit tests in test_web fail the same five ways with and without the change.

### W175.2 · Fix: archiving a chat opened from the Chats list leaves the list stale
Parent: W175.1
Status: confirmed
Approach: In `scripts/web/index.html`, `chatend` now does `$("#chat").close(); go("chats")`. `go` only sets `location.hash`. A chat opened from the Chats list (the `.chatrow` buttons carry `data-act="chat"`) is opened on a page whose hash is already `#/chats`, so no `hashchange` fires and nothing redraws. `S.chats` still holds the old list, so the archived chat shows as in progress above Archived, and a tap on it reopens it. The 4-second poll (`setInterval` near line 2237, paused while `#chat` is open) only fixes it later. The old code redrew the dialog from the server's answer, so this is new. The `chat_end` flow in `scripts/ui_flows.mjs` opens the chat from the task list (`#tabs [data-act=chat]`), so it never meets this. Fix: in `chatend`, when `route().view === "chats"` already after the close, call `render(true)` (or re-fetch) so the list shows the chat under Archived at once; keep `go("chats")` for other routes. Then add a flow step: open the Chats list, open a chat from its row, press Archive, and assert at once, with no wait for the poll, that `#view > .crow` has no row for it and `.endedchats summary` counts it. Run it if node is available; if not, say so.
Determination: Confirmed: `chatend` and `chatlist` now share `toChats()`, which closes the dialog and redraws the list when the page is already on `#/chats` (else sets the hash), and a new `chat_end` step archives a chat opened from the list and expects it under Archived within 2 seconds; the flow could not run here (no node), so it is read, not run.

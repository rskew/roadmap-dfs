# W24 · Remember scroll position on client

## Summary

The web page now remembers where you were scrolled on each screen (task list, a task's tree, assumptions, chats) for the browser tab's session, so going Back to the list or reloading puts you where you left off, and a screen you have not visited opens at the top. The node sheet remembers its scroll per node, and a chat reopens where you had scrolled to, or at its end if you left it there. I took "client" to mean the web page, not the terminal screen, and kept the positions in session storage, so closing the tab forgets them. The browser tests that need a real agent already failed in this environment and still do; the new ones feed the chat a canned conversation.

## Goal

Remember scroll position on client

## Tree

### W24.1 · Save each screen's page scroll in sessionStorage and put it back after the screen draws
Status: confirmed
Approach: In `scripts/web/index.html`, a scroll listener records `window.scrollY` under the screen being shown (`lastView`: `tasks:`, `task:W3`, `assumptions:`, `chats:`) and writes the map to `sessionStorage` (`scroll`); `render()` replaces its `window.scrollTo(0, 0)` on a screen change with a restore of the saved offset once the screen has drawn, and the listener ignores scrolls while a screen is changing so a short fresh page does not overwrite the saved offset with 0. Back from a task to the list, and a reload, then land where the reader was. The browser flow `scroll_memory` in `scripts/ui_flows.mjs` (test in `scripts/test_ui.py`) scrolls the list, opens a task, goes Back and reloads, and asserts the offsets.
Determination: Confirmed: with the change the flow passes; with `index.html` stashed it fails at the reload (0 != 120); the other ten `test_ui.py` failures (browser timeouts) are the same with and without it.
Ask: Is "scroll position on client" the web page's own scroll per screen (list, task, assumptions, chats) kept for the browser tab's session? I chose that, with the chat log and node sheet in a later node, and not the TUI.

### W24.2 · Keep the scroll offsets in memory only
Status: parked
Approach: The same save and restore with the offsets held in a JS object, so Back within a visit restores them but a reload does not.
Determination: Parked: it is the smaller change, but a reload or an installed-app relaunch (the page is a PWA) would drop the reader at the top, and `walkOpen` already sets the precedent of keeping view state in `sessionStorage`; unpark if storage proves unavailable.

### W24.3 · Also remember the chat log and the node sheet's scroll
Parent: W24.1
Status: confirmed
Approach: The chat log (`#chat-log`) and the node sheet body (`.sheet-body`) are their own scroll areas. Keep the chat log's offset per chat scope across closing and reopening the dialog (today it jumps to the end on open), and the sheet's per node (today it resets to 0 when the node changes, which stays for a different node but should restore when stepping back to one already read). The flow `scroll_memory_areas` in `scripts/ui_flows.mjs` (test in `scripts/test_ui.py`) covers both, handing the page a 40-message chat in place of the agent.
Determination: Confirmed: the flow passes; against the previous `index.html` it fails (stepping back to a read node: 0 != 30); the ten `test_ui.py` failures already there are unchanged. The Goal is met for the web page.

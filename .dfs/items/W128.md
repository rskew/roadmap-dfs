# W128 · A review that says issues but adds nothing holds the task open in a loop

## Goal

A finished task whose implementation review ended `review ok` must not be held open by a following `review issues` entry that added no node and no raise. The task is done once its review is ok and its tree is complete, with no author `accept` needed.

What happened (W116, 2026-10-28): each review logged `review ok` with its lesser findings and then an automatic `review issues` reading "none: no node added, no raise". `tree.py` `status_of` takes the last `issues` verdict as "the implementation review found issues; fix them in new nodes" until the author logs `accept`, so the runner handed out a work session with nothing to fix, and the next review did the same: four sessions went this way. W48 and W67 show the same entry in their logs, and W124 went through two such cycles before a review left the entry out and it finished.

Likely causes to settle first: the reviewer's brief (`state.py` review brief, around the `log <task> review ok` and `log <task> review issues` templates) shows both commands under "exactly once, the verdict", and the agent runs both; and `status_of` (`tree.py`, the `rv["args"][:1] == ["issues"]` branch) treats an `issues` verdict as open work whether or not it came with a node or raise. Make a review that logs `issues` with nothing behind it unable to hold a task open (refuse the entry at `log` time, or read it as ok in `status_of`, whichever the code supports), make the brief say one verdict is logged, and add tests in `test_tree` and the state/brief tests: an `ok` then `issues` pair with no node added leaves the task done; an `issues` that did add a node or raise still opens it.

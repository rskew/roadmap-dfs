# W128 · A review that says issues but adds nothing holds the task open in a loop

## Goal

A finished task whose implementation review ended `review ok` must not be held open by a following `review issues` entry that added no node and no raise. The task is done once its review is ok and its tree is complete, with no author `accept` needed.

What happened (W116, 2026-10-28): each review logged `review ok` with its lesser findings and then an automatic `review issues` reading "none: no node added, no raise". `tree.py` `status_of` takes the last `issues` verdict as "the implementation review found issues; fix them in new nodes" until the author logs `accept`, so the runner handed out a work session with nothing to fix, and the next review did the same: four sessions went this way. W48 and W67 show the same entry in their logs, and W124 went through two such cycles before a review left the entry out and it finished.

Likely causes to settle first: the reviewer's brief (`state.py` review brief, around the `log <task> review ok` and `log <task> review issues` templates) shows both commands under "exactly once, the verdict", and the agent runs both; and `status_of` (`tree.py`, the `rv["args"][:1] == ["issues"]` branch) treats an `issues` verdict as open work whether or not it came with a node or raise. Make a review that logs `issues` with nothing behind it unable to hold a task open (refuse the entry at `log` time, or read it as ok in `status_of`, whichever the code supports), make the brief say one verdict is logged, and add tests in `test_tree` and the state/brief tests: an `ok` then `issues` pair with no node added leaves the task done; an `issues` that did add a node or raise still opens it.

## Tree

### W128.1 · status_of reads an issues verdict with nothing behind it as ok
Status: confirmed
Approach: In scripts/tree.py status_of, drop the branch that holds a task open on a last `review issues` verdict. That branch is reached only after the frontier, incompleteness, open-raise and review-due checks have all passed, i.e. when the review's issues left no open node and no raise, so it holds the task open with nothing to fix. A task whose tree is complete and whose review is not due reads done (reviewed). Update test_tree's test_a_tree_a_session_completed_waits_for_its_review, which pins the old behaviour, and add tests: ok then issues with no node leaves the task done; issues with an open node and issues with an open raise still read open; the author's accept still reads done. Check: python3 scripts/test_tree.py.
Determination: test_tree passes with the new tests (ok then issues with no node reads done; an issues with an open node or an open raise still reads open, its fix due a review); its one error, a pre-commit hook permission denial in a temp repo, fails the same without the change.

### W128.2 · log refuses a review issues that added no node and no raise
Status: confirmed
Approach: In scripts/tree.py append_log, when kind is review and the first arg is issues, refuse (ValueError, so the CLI prints it and exits 2) unless the task's tree is incomplete (a live open node, via incomplete) or has an open raise (open_raises). The message tells the reviewer to log ok with the minor findings in the body. Tests in test_tree: the refusal with a complete tree, acceptance with an open node and with an open raise, and ok still accepted. Then run the other suites that call append_log or `log review issues` (test_chain, test_critic) and adjust their fixtures where they log issues on a complete tree. Check: python3 scripts/test_all.py.
Determination: append_log now refuses a review issues when the tree is complete and no raise is open, and logs it with an open node or an open raise; test_tree passes with the new cases, test_review_tree, test_walk, test_critic, test_ui and test_metrics pass, and the failures in test_web and the pre-commit hook error in test_tree are the same without the change; test_chain is skipped wholesale here (every temp directory is noexec), so its one fixture that logged issues on a complete tree was adjusted by reading, unrun.

### W128.3 · The review brief logs one verdict
Status: open

Say plainly that exactly one of the two is logged, never both, and that a review `issues` with no node or raise is refused. Keep the critic's wording (node, backtrack or raise). Add a brief test in the state/brief tests asserting the one-verdict wording and that the review brief no longer presents the two commands as consecutive steps. Check: python3 scripts/test_critic.py and test_all.py.

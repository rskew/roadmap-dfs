# W188 · Bug: sessions hanging on exit

## Goal

---

A work session hangs after its last turn while a background process it started is still running

What happens: a work session finishes normally. It commits, writes its final message, and its Stop hook (inbox.py stop) runs without errors. But the claude -p process doesn't exit, so run.sh keeps waiting and the next run never starts. Nothing times it out.

Cause (shown twice): the session had started the task's backend in the background with the Bash tool. That is a bash -c running ./dist-newstyle/w101-shop-app on port 3041 against a database copy, and it was a direct child of claude -p. Each time, killing that backend made claude -p exit within seconds and run.sh start the next run straight away. I haven't looked into why claude -p waits on that child, only that it does.

**Evidence (task W101, run dfs_run_av66s21u):**

| Run | Turn ended | Process exited | Time lost |
|---|---|---|---|
| run-2 | 00:05:05 | 01:04:27 | about 59 min |
| run-5 | 01:21:57 | 01:40:28 | about 18 min |

The turn-end times come from the session transcript's last end_turn and stop_hook_summary. The exit times are the log's end · work entries.

Side effects:
The end entry in the task log records when the process exited, not when the session finished. That makes sessions look longer than they were and hides the stall.
Work sessions start a backend almost every time, so this hits most runs on any task that does.

Possible fixes, any one of which would stop the hang:
Clean up when the Stop hook fires. run.sh notices the hook (it already writes to the run's inbox) and, after a short grace period, kills whatever the session left running.
Run the session in its own process group. run.sh starts claude -p with setsid and kills the whole group once the JSON result is out.
A watchdog. The Stop hook has fired but the process is still alive N seconds later, so run.sh kills it.
A briefing rule, as a weaker backstop. Work sessions stop any server they start before they finish. A session cut off at its budget can't be relied on to do that, so this can't be the only fix.

Separately, the log's end time should come from the Stop hook, not from the process exiting.

## Tree

### W188.1 · Reproduce the hang with a real claude and a stand-in model
Status: confirmed
Approach: **The question** - Does `claude -p` stay alive after its last turn when the model's Bash call started a background process, and does killing that process make it exit? **Why it matters** - The report says this only from two runs. The fix, and which sibling to take, rests on knowing what claude waits on, and that the Stop hook still fires and finishes while it waits. **What this node does** - A test in `scripts/test_inbox.py` (its `Model` and `RealClaude` harness already runs the real claude under `-p` with run.sh's hooks): the model's first answer is a Bash call that starts background work (`sleep 300 &`), the second is a final text. Run it and look at: does the process exit, is the JSON written, does the Stop hook run. **How we will know it worked** - The test shows the process still alive after the final answer, and exiting when the background process is killed. If claude exits on its own, the hang has another cause and the later nodes are rethought.
Determination: Confirmed with claude-code 2.1.329: a Bash call started with `run_in_background` keeps `claude -p` alive after its final answer and its JSON is not written, and killing that child makes it exit in under a second (a plain `cmd &` with its output redirected does not hang).

### W188.2 · Stop hook marks the stop, run.sh kills what the session left behind
Parent: W188.1
Status: confirmed
Approach: **The question** - Can the Stop hook tell run.sh that the session is over, so run.sh ends whatever the session left running? **Why it matters** - A Stop hook that finds no waiting message is the one signal that the model has finished. A timer alone cannot tell a hung process from a slow turn. **What this node does** - `inbox.py stop BOX MARK`: when it hands nothing over, it writes the time to the file MARK. `inbox.py --settings` takes MARK, and run.sh passes `$RUNDIR/stopped` for claude sessions. - `run.sh run_session` starts claude in the background and watches: once MARK exists and claude is still alive after a grace period (`DFS_STOP_GRACE`, default 20 s), kill claude's descendants (found with `ps`, so it works without `setsid`), TERM then KILL. claude then exits by itself and writes its JSON. If it is still alive after a second grace, kill it. - Ctrl-C and `wait_agent` keep working with the backgrounded claude (`AGENT_PID`). **How we will know it worked** - The reproduction from the first node, run through `run.sh`, ends within the grace period. A session that ends normally is not delayed and not killed.
Determination: The Stop hook now writes a mark file and run.sh ends what the session left running after a grace period (DFS_STOP_GRACE, 20 s), so a chain whose claude is held by a background child finishes in seconds; a session that ends on its own is untouched.

### W188.3 · Run claude in its own process group and kill the group after the JSON result
Parent: W188.1
Status: parked
Approach: **The question** - Can run.sh `setsid` claude and kill the group once its result is out? **Why it matters** - It is one of the fixes the report lists. **What this node does** - Not pursued. `claude -p --output-format json` writes its one result object at exit (`run_session` says so), so there is no result to wait for while claude is stuck. `setsid` is also missing on macOS. Reopen only if claude's result is written before it waits.
Determination: Parked: the JSON result is written only at exit, so there is nothing to wait for while claude is stuck, and `setsid` is missing on macOS.

### W188.4 · A timer-only watchdog with no Stop hook signal
Parent: W188.1
Status: parked
Approach: **The question** - Can run.sh kill a session that has been quiet for N seconds, without the Stop hook? **Why it matters** - It would also catch a claude that hangs before any Stop hook runs. **What this node does** - Not pursued. Quiet is not finished: a long test run or model call looks the same, and killing it loses work. The marker from the Stop hook is the safer trigger. Reopen if a hang is found where the Stop hook never fires.
Determination: Parked: quiet is not finished, so a timer alone can kill a long test run; the Stop hook marker is the safer trigger.

### W188.5 · The log's end time comes from the Stop hook
Parent: W188.2
Status: open
Approach: **The question** - Can the `end` log entry say when the session finished, not when the process exited? **Why it matters** - An `end` entry made after a stall makes a session look an hour long and hides the stall. **What this node does** - After `run_session`, if the stop file exists, `tree_log end` is written with that time (a `tree.py log` timestamp override, still later than every entry) and a note of how long the process lingered after it. Without the file (codex, kiro, opencode, a killed claude) it is written as now. **How we will know it worked** - A test with a stop file older than the exit shows the `end` entry at the file's time and the stall in its note; one with no file is unchanged.

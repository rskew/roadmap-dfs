# W140 · Reorder tasks should not be so big in y axis

## Summary

In the web page's Reorder list, each task row is shorter. The goal and the status tags take one line each, the reason line is not drawn, and the padding is halved. From 600px wide the move buttons sit in the same row as the text and the grip. Every move button and grip is still 44px. On a phone the four move buttons, with the page's own labels, wrap to two lines, so a row is about 165px, down from 187 to 394px with the same labels; on a wide screen a row is 63 to 67px. To keep what places a row, "held by" and "waiting on" now come first among the tags, and the full text of a row, reason included, is in its tooltip. The row layout was checked in headless chromium on a static copy of the row, and the new flow assertions in `scripts/ui_flows.mjs` have not run, because there is no node or playwright here. The reason line and later tags stay cut, which the author can reverse from the answer page.

## Goal

Reorder tasks should not be so big in y axis

### W140.1 · Make the web Reorder rows short
Status: confirmed
Approach: **The question**
- How do we make each row in the web page's Reorder list take far less height without making any button smaller than a thumb target (44px)?

**What this node does**
- In `scripts/web/index.html`, only for `.item.reorder`: trim the padding to `var(--s2)` above and below. Show the goal on one line with an ellipsis. Keep the status and tags on one clipped line. Hide the reason line (`.why`). Keep `.pending-tag` ("saving…") visible.
- From 600px wide, put the moves strip in the same row as the text and the grip, so a row is one 44px line plus padding. Under 600px the moves stay under the text, in one line.

**How we will know it worked**
- A static page with the real `design.css` and the page's CSS, drawn at 360px and 1000px in headless chromium, gives the row heights before and after. Every `.moves .btn` and `.grip` is still at least 44px.
Hypothesis: "Reorder tasks" means the Reorder list of the web page (`data-act=reorder`, rows with `.moves` and `.grip`), and "big in y" means each row is too tall. Wrong if the author meant the TUI's reorder or something else. .dfs/artefacts/29494370-e4db-4a6f-924c-f872ab702df9.html
Evidence:
- for: the only place that names reordering in the UI is `drawTasks` in `scripts/web/index.html`; its reorder row has a wrapping goal, a wrapping tags line, a reason line and a 44px moves strip under them, with 12px padding above and below.
- against: the goal text does not say which UI; the TUI (`scripts/tui.py`) also has `reorder`, but it is a key press (`[` and `]`) on the ordinary list, with no separate view whose rows could be too tall.
- for: headless chromium on a static page with the real `design.css` and the page's CSS, two rows (one long goal with three tags and a reason, one short): at 360px the rows were 242px and 135px high before and 115px and 111px after; at 1000px 191px and 135px before and 67px and 63px after. The smallest move button or grip stayed 44px. At 600 and 720px the rows are 67px and 63px. ![the compact rows at 640px wide](.dfs/artefacts/8ade530e-76d1-48c5-a61a-60208406dde7.png)
Determination: The Reorder rows are now 63 to 115px high instead of 135 to 242px, and every move button and grip is still 44px, so the reading holds and the node is confirmed.

### W140.2 · Hypothesis: a Reorder row may lose its reason line and show its goal and tags clipped
Parent: W140.1
Status: confirmed
Approach: W140.1 made a scope choice it did not mark as a Hypothesis. In `scripts/web/index.html`, `.item.reorder .why` is `display: none` (a blocked or raising task's reason is no longer shown in Reorder), `.item.reorder .goal` is cut with an ellipsis and `.item.reorder .meta` is `nowrap; overflow: hidden`, so tags such as "held by W9", "waiting on W3" or "ready to open a pull request" can be cut off with no ellipsis and no `title`, and no other way to read the rest in that view. The assumption is that a person reordering needs only the id, the start of the goal and the first tags, and that the full text is a tap away on the task's own screen. It would be wrong if the author wants the reason or every tag visible while reordering, or wants the cut text reachable (a `title`, or a wrap on tap). State it as a Hypothesis on W140.1's page, with the evidence that decides it: what the author sees in Reorder for a task with a long goal and several tags, and whether the cut tags carry anything needed to place a row. If the author would choose otherwise, restore the dropped text in the smallest way (for instance `title` on the goal and meta, or keeping `.why` on one clipped line).

**What this node does**
- In `scripts/web/index.html`, the Reorder row's tags `held by` and `waiting on` get the class `hold` and, with the status, are ordered first in the clipped tag line, so they are the last to be cut.
- The Reorder row gets a `title` holding its id, goal, status, hold tags, review tag and reason, so the cut text can be read on hover or long press. The row's height does not change.
Hypothesis: In Reorder, the id, the start of the goal and the first tags are enough to place a row, and the reason and the rest of the text can stay cut. Wrong if the author wants the reason or every tag visible while reordering. .dfs/artefacts/af0ecc64-89d6-4201-b2d5-57be688f902c.html
Evidence:
- against: a harness with the page's real CSS, real labels and a 360px row (headless chromium, DejaVu Sans) cut the tag line on 2 of 5 sample rows. With the tags in the order the page builds them, `held by W9` and `waiting on W3` come last and were the ones cut.
- for: with `held by` and `waiting on` ordered first, the same two rows show them (`blocked / held by W9`, `open / waiting on W3`); what is cut is now the branch and pull request tags.
- for: restoring the rest costs height on the same rows at 360px: +26px for a one-line reason, +52px for wrapping the tags, +78px for both, against rows the author called too tall.
- for: `test_web.py` gives the same 4 failures with and without the change (chat, installable, claude sign-in, readme), so it breaks nothing; no browser flow ran (no node).
Determination: The assumption holds once `held by` and `waiting on` come first and the full row text is in a tooltip, so the node is confirmed; the reason line and the later tags stay cut, and the answer page lets the author choose otherwise.

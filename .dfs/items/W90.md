# W90 · Chat replies show as they arrive, not only after the next message is sent

## Summary

A reply in the web page's chat is no longer hidden below a stale copy of the question: the page drops its echo of a sent message once the transcript holds a new message of the author's. A message sent before an earlier one is recorded stays shown until it is recorded itself, including when its text is inside the earlier message or repeats it, and stopping a chat drops from the page only the messages never typed. These are covered by tests, and the first by replaying the real transcript of the reported chat. A claude chat's first message was once left unsubmitted in claude's input, and a second Enter, pressed when claude draws nothing after the first, now submits it; the cause could not be repeated against the real claude here (it took the message at every start delay tried, with a local fake model), so that fix is a safeguard tested only against a stand-in, apart from checking that the extra Enter does nothing at an empty prompt. Waiting for claude's prompt screen was left out because it would stall every chat whose claude draws no prompt mark, and nothing showed it was the cause.

## Goal

An agent's reply in the chat shows up as soon as it is written, without the author having to submit another message to make it appear.

Today the reply does not show until a new message is submitted, so the chat looks stalled or empty after a question. The cause is not yet known; which surface it happens on (the web page chat, the terminal screen's chat, or both), and under which agent, is for the task's first nodes to establish.

Done looks like:
- After the author sends a message, the agent's reply appears in the chat on its own, streaming or on completion, with no further input.
- A reply already written when the chat is opened or re-opened is shown too.
- A regression test covers the reply appearing without a second message.

Worth doing: a chat that hides its answers cannot be used.

## Tree

### W90.1 · The reply is hidden by the page's echo of the sent message, which never clears
Status: confirmed
Approach: Find the surface and the agent from the chat the bug was reported in: `.dfs/runs/chat/project.log` and the claude transcript of session d9636512, which hold the report itself ("This chat UI is bugging out, agent responses don't show until a new message is submitted"). Then replay that transcript, cut off after the reply the author could not see, through `Chats.state` with the page's pending message set, and print the last three messages it returns.
Determination: The fault is on the web page, chatting through the terminal screen's background claude chat (ptyrelay). The log's `page: message of 8/30/116 characters handed to the screen's chat` lines at 2026-10-19T00:17–00:20 are the transcript's user turns. The first message, "Continue", was typed but never submitted, and claude recorded "ContinueDo all three as separate tasks" as one message. `Chats.state` keeps the page's pending "Do all three as separate tasks" until that exact text appears among the last three messages, which never happens. The replay therefore ends `you | ContinueDo all three… / agent | I created the three tasks… / you | Do all three as separate tasks`: the reply sits above a stale echo of the question. The replay is correct once the next message is sent and matches.

### W90.2 · Pending clears when the transcript has a new message of the author's, whatever its text
Parent: W90.1
Status: confirmed

Exact text fails when the agent records the message merged or reworded. The three-message window fails when the reply runs to three or more text messages before the page asks again. Regression tests in `scripts/test_chat.py` cover a reply to a message claude recorded merged with an earlier one, a reply of several messages read only after it ended, and the same text sent twice. Each shows the reply as the last message with no echo after it.
Determination: `Chats.state` now clears the page's echo once the transcript holds a new message of the author's. The three new tests in `scripts/test_chat.py` fail on the old code and pass on the new. The replay of the real transcript now ends with the reply. test_chat, test_web, test_codex_chat, test_opencode_chat, test_kiro_chat and the page's chat flows in test_ui pass, with TMPDIR inside the repo since /tmp is noexec. barfromchats, already failing on main, is the only failure.

### W90.3 · A message typed into a freshly started claude chat is submitted, not left in its input
Parent: W90.1
Status: confirmed
Approach: `ptyrelay.Relay._typist` typed "Continue" 1.3s after a resumed claude started (`typed 8 characters after 1.3s wait (settled)`). The text reached claude's input but its Enter did not submit it, so it went in only with the next message, and nothing answered until then. Find why: claude has no `READY` prompt text, so one second of quiet counts as ready. Then make the typist wait for claude's prompt, or confirm the message was submitted and press Enter again. A test in `scripts/test_ptyrelay.py` uses an agent that ignores keys until its prompt is drawn. Found so far: in every chat log, the first message typed after a start is the failing one (1.3s after start). The five others went in 9s or more after it and were submitted. This machine has no `claude` binary, so the real TUI cannot be watched here. Chosen: after a claude's first message, if it draws nothing for `SUBMIT_WAIT` (2s) after the Enter, `Relay._resubmit` presses Enter again, which assumes claude ignores an Enter on an empty prompt. Waiting for claude's prompt text was not chosen: its footer wording cannot be checked here and a wrong guess would delay every first message by the 25s timeout. Tests in `scripts/test_ptyrelay.py` use an agent that ignores Enter while it loads (fails on the old code, passes on the new) and check that a message that was submitted gets no second Enter.
Determination: A claude chat's first message is now submitted even when its Enter arrives while claude is still loading. It is confirmed only against a stand-in agent, since there is no real claude here; the real TUI is unwatched.

### W90.4 · Fix: check the second Enter of a claude chat's first message against the real claude, which this machine has
Parent: W90.3
Status: confirmed
Approach: W90.3 rests on "this machine has no `claude` binary", which is false. `/nix/store/*-claude-code-*/bin/claude` holds builds up to 2.1.301, and `$HOME/.claude/.credentials.json` exists. The reviewer started `.../3mqsqnblcr40d9mjdip1skcw6c33m44a-claude-code-2.1.301/bin/claude --dangerously-skip-permissions --resume d9636512-…` in a pty without typing anything. Its output came at 0.2s (64 bytes), at 0.7s and 0.9s (small writes), and at 1.0s (25 KB, the whole resumed screen). The screen ends with the prompt `❯` and the footer `⏵⏵ bypass permissions on (shift+tab to cycle)`, and a fresh claude draws the same. Transcript saving was off under the inherited `CLAUDE_CODE_CHILD_SESSION` marker, so nothing was written. Two things follow. (1) `ptyrelay.Relay._resubmit` presses Enter again only if claude writes nothing for `SUBMIT_WAIT` after the first Enter. A claude that ignored the Enter while it loaded may well draw the rest of its start-up screen after it, and then the second Enter is never pressed. The stand-in `LOADING` agent in `scripts/test_ptyrelay.py` was written to draw nothing while it loads, so its test cannot show this. (2) The alternative W90.3 parked, waiting for claude's prompt screen (e.g. a `READY["claude"]`), was parked because "its footer wording cannot be checked here", and that reason is false: the real TUI draws it, and `.dfs/runs/chat/project.log` holds real claude screens with the same `❯` and footer. To settle it, run the real claude through `ptyrelay.Relay(agent="claude")` (e.g. under `scripts/run.sh --chat`) with a one-word message sent at its start. Watch whether the Enter is taken, whether claude draws after an Enter it ignored, and whether the fix submits the message. Keep `_resubmit`, change its trigger, or wait for the prompt screen, whichever the real TUI supports. Put that in a test against the real claude, skipped when it is absent, as `test_kiro_chat` does for kiro.
Determination: Against the real claude 2.1.301 (scratch HOME, local fake model) the original failure did not reproduce: it took a pasted message and Enter at every delay from 0.5s to 8s after the start, fresh or resuming the real session, and when both came in one write; an Enter at an empty prompt did nothing, idle or mid-turn (scripts/test_claude_chat.py). So `_resubmit` is kept, harmless and unproven, and waiting for claude's prompt screen was not adopted.

### W90.5 · Fix: a message the page sent stays shown until it is recorded, even when one sent before it is recorded first
Parent: W90.2
Status: confirmed
Approach: `Chats.pending` holds one `(message, author messages then)` per scope, and `Chats.state` drops it once the transcript holds more of the author's messages than that. Suppose the page sends "first" and then "second" before "first" reaches the transcript. That happens while a screen chat is starting and the relay's typist holds both, or when they are sent a moment apart. The transcript recording "first" then clears the echo of "second", which has not been typed or recorded. A claude records a message typed while it is busy only when it takes the message up, so "second" is missing from the page for the whole answer to "first", and an author who thinks it was lost will send it again. The reviewer checked this with `screens_live_chat` in `scripts/test_chat.py`: send "first", send "second", record `("you","first"), ("agent","Working on the first.")`. `state` then returns `hi / Hello. / first / Working on the first.`, with "second" gone. The old exact-text rule showed it. Fix by keeping each unrecorded message in a list per scope. The k-th is shown until the transcript holds `before + k` of the author's messages, or its text is within an author message recorded since the first was sent, which is how a merged first message (W90.1's case) still clears both. Regression tests in `scripts/test_chat.py` cover the reviewer's sequence and two messages recorded apart.

### W90.8 · Fix: a message the page sent clears by text only when the author message holding it is not an earlier pending message's own
Parent: W90.5
Status: confirmed
Approach: In `scripts/chat.py` `Chats.state`, an unrecorded page message is also dropped when `any(text in t for t in texts[base:])`, where `base` is the author-message count when the FIRST pending message of the scope was sent. So a later message whose text is inside an earlier one recorded since is cleared before it is recorded: W90.5's fault again, for short replies and repeats. The reviewer checked it with `screens_live_chat` in `scripts/test_chat.py`: send "Can you look at it now", send "no", record `("you","Can you look at it now"), ("agent","Working on it.")`; `state` returns `hi / Hello. / Can you look at it now / Working on it.`, "no" gone (it is in "now"). Sending "yes" twice and recording one "yes" likewise shows only one, the second vanishing while claude answers the first. Fix so a recorded author message clears by text only the pending messages it can stand for: e.g. match recorded messages after `base` to pending messages in order, each recorded message accounting for the pending ones it equals or is the concatenation of, and leave the merged case (W90.1: "ContinueDo all three as separate tasks" clears "Continue" and "Do all three as separate tasks") clearing both. Add both sequences above as regression tests that fail on the current code.
Determination: `recorded_apart` in `scripts/chat.py` now matches each recorded author message to the page's messages in order, each stretch of text once, counting those already cleared by number, so "no" stays after "Can you look at it now" is recorded and two "yes" need two recorded. The two new tests in `scripts/test_chat.py` fail on the old code and pass on the new; test_chat (58), test_web, test_codex_chat and test_kiro_chat pass.

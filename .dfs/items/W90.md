# W90 · Chat replies show as they arrive, not only after the next message is sent

## Goal

An agent's reply in the chat shows up as soon as it is written, without the author having to submit another message to make it appear.

Today the reply does not show until a new message is submitted, so the chat looks stalled or empty after a question. The cause is not yet known; which surface it happens on (the web page chat, the terminal screen's chat, or both), and under which agent, is for the task's first nodes to establish.

Done looks like:
- After the author sends a message, the agent's reply appears in the chat on its own, streaming or on completion, with no further input.
- A reply already written when the chat is opened or re-opened is shown too.
- A regression test covers the reply appearing without a second message.

Worth doing: a chat that hides its answers cannot be used.

## Tree

### W90.1 · The reply is hidden by the page's echo of the sent message, which never clears
Status: confirmed
Approach: Find the surface and the agent from the chat the bug was reported in: `.dfs/runs/chat/project.log` and the claude transcript of session d9636512, which hold the report itself ("This chat UI is bugging out, agent responses don't show until a new message is submitted"). Then replay that transcript, cut off after the reply the author could not see, through `Chats.state` with the page's pending message set, and print the last three messages it returns.
Determination: The fault is on the web page, chatting through the terminal screen's background claude chat (ptyrelay). The log's `page: message of 8/30/116 characters handed to the screen's chat` lines at 2026-10-19T00:17–00:20 are the transcript's user turns. The first message, "Continue", was typed but never submitted, and claude recorded "ContinueDo all three as separate tasks" as one message. `Chats.state` keeps the page's pending "Do all three as separate tasks" until that exact text appears among the last three messages, which never happens. The replay therefore ends `you | ContinueDo all three… / agent | I created the three tasks… / you | Do all three as separate tasks`: the reply sits above a stale echo of the question. The replay is correct once the next message is sent and matches.

### W90.2 · Pending clears when the transcript has a new message of the author's, whatever its text
Parent: W90.1
Status: open
Approach: In `scripts/chat.py` `Chats.send`, store the pending message with the number of "you" messages the transcript held when it was sent. `Chats.state` drops it once the transcript holds more, instead of waiting for its exact text among the last three messages. Exact text fails when the agent records the message merged or reworded. The three-message window fails when the reply runs to three or more text messages before the page asks again. Regression tests in `scripts/test_chat.py` cover a reply to a message claude recorded merged with an earlier one, a reply of several messages read only after it ended, and the same text sent twice. Each shows the reply as the last message with no echo after it.

### W90.3 · A message typed into a freshly started claude chat is submitted, not left in its input
Parent: W90.1
Status: open
Approach: `ptyrelay.Relay._typist` typed "Continue" 1.3s after a resumed claude started (`typed 8 characters after 1.3s wait (settled)`). The text reached claude's input but its Enter did not submit it, so it went in only with the next message, and nothing answered until then. Find why: claude has no `READY` prompt text, so one second of quiet counts as ready. Then make the typist wait for claude's prompt, or confirm the message was submitted and press Enter again. A test in `scripts/test_ptyrelay.py` uses an agent that ignores keys until its prompt is drawn.

# W90 · Chat replies show as they arrive, not only after the next message is sent

## Summary

A reply in the web page's chat is no longer hidden below a stale copy of the question: the page drops its echo of a sent message once the transcript holds a new message of the author's. A message sent before an earlier one is recorded stays shown, on every poll, until it is recorded itself, including when its text is inside the earlier message or repeats it, and stopping a chat drops from the page only the messages never typed. These are covered by tests, and the first by replaying the real transcript of the reported chat. The chat also went unanswered when its first message was typed into claude before claude had started: started through `run.sh` (as the screen does) on the real HOME, 7 of 7 resumed starts left the message sitting unsubmitted in claude's input, because the relay took the progress output of `nix run` for claude's own and typed after a second of quiet. The relay now waits for claude's own first output, and 6 of 6 resumed starts through `run.sh` then submitted it (`scripts/probe_claude_start.py` repeats the check; it spends real model calls). The earlier second-Enter guard stays as a safeguard but was never the fix; that was found only after the first attempt, which started claude directly on a scratch HOME, failed to reproduce the fault.

## Goal

An agent's reply in the chat shows up as soon as it is written, without the author having to submit another message to make it appear.

Today the reply does not show until a new message is submitted, so the chat looks stalled or empty after a question. The cause is not yet known; which surface it happens on (the web page chat, the terminal screen's chat, or both), and under which agent, is for the task's first nodes to establish.

Done looks like:
- After the author sends a message, the agent's reply appears in the chat on its own, streaming or on completion, with no further input.
- A reply already written when the chat is opened or re-opened is shown too.
- A regression test covers the reply appearing without a second message.

Worth doing: a chat that hides its answers cannot be used.

### W90.5 · Fix: a message the page sent stays shown until it is recorded, even when one sent before it is recorded first
Parent: W90.2
Status: confirmed
Approach: `Chats.pending` holds one `(message, author messages then)` per scope, and `Chats.state` drops it once the transcript holds more of the author's messages than that. Suppose the page sends "first" and then "second" before "first" reaches the transcript. That happens while a screen chat is starting and the relay's typist holds both, or when they are sent a moment apart. The transcript recording "first" then clears the echo of "second", which has not been typed or recorded. A claude records a message typed while it is busy only when it takes the message up, so "second" is missing from the page for the whole answer to "first", and an author who thinks it was lost will send it again. The reviewer checked this with `screens_live_chat` in `scripts/test_chat.py`: send "first", send "second", record `("you","first"), ("agent","Working on the first.")`. `state` then returns `hi / Hello. / first / Working on the first.`, with "second" gone. The old exact-text rule showed it. Fix by keeping each unrecorded message in a list per scope. The k-th is shown until the transcript holds `before + k` of the author's messages, or its text is within an author message recorded since the first was sent, which is how a merged first message (W90.1's case) still clears both. Regression tests in `scripts/test_chat.py` cover the reviewer's sequence and two messages recorded apart.

### W90.10 · Fix: a message the page sent stays shown on every poll after an earlier one is recorded, not only the first
Parent: W90.8
Status: confirmed
Approach: `recorded_apart` in `scripts/chat.py` matches the pending entries against every author message in `texts[base:]`, where `base` is the author-message count when the first of them was sent. On the first `Chats.state` after "Can you look at it now" is recorded, both entries are matched together and "no" is kept. But `state` then drops the first entry from `self.pending`, because it is cleared by number (`held < need` fails). On the next `state`, `recorded_apart` sees only "no", and `texts[base:]` still begins with "Can you look at it now". `find("no", 0)` hits "now", so "no" is dropped before claude has recorded it. W90.8's Determination says the code counts "those already cleared by number". It does not. The page polls `/api/chat/<scope>` every 1.5s while the chat is live (`scripts/web/index.html` `chatLoad`), so "no" vanishes within 1.5s. The reviewer checked this with `screens_live_chat` in `scripts/test_chat.py`: send "Can you look at it now", send "no", record `("you","Can you look at it now"), ("agent","Working on it.")`. The first `state` ends `… Working on it. / no`, and the second, with nothing new recorded, ends `… Working on it.`. Sending "yes" twice and recording one "yes" does the same: the second "yes" is shown once, then gone. "first"/"second" survives only because neither text holds the other. W90.8's two tests call `state` once between records, so they pass. To fix it, make the recorded messages that cleared earlier entries unavailable to the entries still pending. For example, advance the remaining entries' `base` past the author messages the cleared ones account for, or keep the cleared entries in the match until every entry of the scope is cleared. W90.1's merged case ("ContinueDo all three as separate tasks" clears both) must still clear both. Extend both W90.8 tests to call `state` again before the second record and assert the later message is still last. Those tests must fail on the current code.
Determination: `Chats.state` now keeps every message the page sent in the scope's pending list until all are recorded and shows only those not yet held, so a recorded message no longer drops out of the matching and "no" stays after "Can you look at it now" is recorded, on every poll. Both W90.8 tests now poll twice before the second record and fail on the old code (2 failures) and pass on the new; test_chat (59), test_web (88), test_codex_chat and test_kiro_chat pass.

# W144 · Show tasks that are draft, even after a break

## Goal

Show tasks that are draft, even after a break

## Tree

### W144.1 · The tui list says "draft" for an open draft behind a break
Status: confirmed
Approach: **The question**
- Why does a draft after a break not read "draft" in the tui?

**Why it matters**
- `row_state` in scripts/tui.py says "draft" only for an open task that is not held. A break (a fence line in .dfs/order.md) sets `waiting_on`, so the cell reads `»W2` and the author loses the draft mark. The plan view (`lines_plan`) and the command palette reuse `row_state`.

**What this node does**
- In `row_state`, let a draft's mark win over a fence (`waiting_on`), but not over an ancestor's raise (`blocked_by`, shown `↳W7`).
- Flip the unit test `test_what_a_held_row_says` in scripts/test_order.py, which currently asserts a held draft reads `»W2`, and add a draft-behind-a-raise case that keeps `↳W7`.
- Add a test in scripts/test_screen.py: a draft row behind a break draws "draft" in bold amber.

**How we will know it worked**
- test_order.py and test_screen.py pass, and fail without the change.
Hypothesis: "After a break" means the fence in .dfs/order.md, and only that hold should give way to the draft mark: a draft under an ancestor's raise keeps its `↳` pointer because answering the raise is the move that can be made now. Wrong if the author wants every open draft to read "draft" whatever holds it (see the parked sibling), or means something other than a break. .dfs/artefacts/e1bc5795-7919-4d92-a660-f289127cb586.html
Determination: A draft behind a break now reads "draft" in the tui list, plan and palette, while a raise above still reads `↳`; the order and screen tests pass and go red without the change.

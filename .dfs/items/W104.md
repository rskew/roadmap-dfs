# W104 · When viewing an active sessions logs in the tui or page, allow injecting a message into the running session

## Summary

While a chain is live, the author can send its running session a line from the terminal screen (`M` in the chain's log) or from the page (a box under a live run's log); it is held in the run's inbox, listed as waiting, and shown as delivered with a time once the session has taken it, or never read if the chain ended first. It works for every agent the chain runs, each by the way it offers: claude and codex through hooks after a tool call and at the stop, opencode through a plugin that sends the session a prompt, and kiro through a hook that holds the next tool call back with the message as its result. A message is read by the session the author is watching and never by a subagent it starts, and the hooks are told their inbox by their own command, so nothing else the agent runs can claim it. The Goal is met; the limits are that a message never interrupts a call or answer already running, that for kiro a message arriving after the last tool call stays waiting since kiro offers no way in at the end of a turn, and that kiro cannot start its own work agent as a sub-agent. The README says which agent takes a message when.

## Goal

### W104.1 · Hand a message to a running claude session through hooks that read the run's inbox
Status: confirmed
Approach: The page or the screen writes the author's message as a file in the running chain's inbox (`.dfs/runs/<run>/inbox/`); run.sh starts each claude work session with `--settings` naming a PostToolUse hook and a Stop hook. The PostToolUse hook drains the inbox into `additionalContext`, so the next model call sees it; the Stop hook blocks the stop with the message as its reason, so a session that was ending takes one more turn. Each delivered message moves to `delivered/`, which is how the screen and page show it arrived. Settled here by a probe: a real claude-code 2.1.308 under `-p --output-format json` against a stand-in model.
Hypothesis: A message landing at the session's next tool call, or when it tries to stop, is soon enough for the author; it never cuts into a tool call or a model answer already running. Wrong if the author needs a message to break into a long tool call or answer at once. .dfs/artefacts/8fbc6922-dbdd-460a-abbc-421a6b853ed6.html
Evidence:
- for: probe, claude 2.1.308 `-p` with a stand-in model, message written while a 3-second Bash call ran: the next model request carried "PostToolUse:Bash hook additional context: The author says: PING-W104 …", and the result was the model's following reply.
- for: same probe, message waiting before the model ended its turn: the Stop hook's block made a second request carrying the message ("Stop hook blocking error from command: …: The author says: PING-W104 one more thing"), and the session's result was the answer to it.
Determination: Confirmed: claude-code 2.1.308 under `-p` takes a message from a PostToolUse hook at the next model call and from a Stop hook as one more turn, so the inbox and hooks are the way in.

### W104.15 · Fix: a message is handed to a subagent's tool call, so the main session never reads it but the log says delivered
Parent: W104.4
Status: confirmed

The reviewer checked this with a real claude-code 2.1.308 against a stand-in `/v1/messages` (the `Model` of test_inbox.py, extended so the main loop's first answer is an `Agent` tool call with a prompt containing a marker, and the subagent, told apart by that marker in its first message, answers `Bash sleep 4` and then text). ### W104.16 · Minor findings from the review
Parent: W104.15
Status: confirmed
Approach: Each of these is small and rides with W104.15:
- The README's section on sending a message says "A chat or a review session takes no message", but a chain's critic and review sessions go through run.sh's `run_session` like work sessions, and the claude branch passes `--settings` for every kind. Name what takes none (`--review` and chat sessions), or say a critic or review session in a chain takes one too.

A tool or test that runs `inbox.py` or opencode under a live session without setting its own would claim that chain's messages, and `inbox.py --opencode-config` run under an opencode session adds the plugin a second time.
- `web.py` `run_message` has no length cap, though the page's box has `maxlength="4000"`.
- The `run_message` UI flow (ui_flows.mjs) was not re-run in this review, for want of playwright. Re-run it with the fixes.

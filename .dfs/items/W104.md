# W104 · When viewing an active sessions logs in the tui or page, allow injecting a message into the running session

## Goal

When viewing an active sessions logs in the tui or page, allow injecting a message into the running session

## Tree

### W104.1 · Hand a message to a running claude session through hooks that read the run's inbox
Status: confirmed
Approach: The page or the screen writes the author's message as a file in the running chain's inbox (`.dfs/runs/<run>/inbox/`); run.sh starts each claude work session with `--settings` naming a PostToolUse hook and a Stop hook. The PostToolUse hook drains the inbox into `additionalContext`, so the next model call sees it; the Stop hook blocks the stop with the message as its reason, so a session that was ending takes one more turn. Each delivered message moves to `delivered/`, which is how the screen and page show it arrived. Settled here by a probe: a real claude-code 2.1.308 under `-p --output-format json` against a stand-in model.
Hypothesis: A message landing at the session's next tool call, or when it tries to stop, is soon enough for the author; it never cuts into a tool call or a model answer already running. Wrong if the author needs a message to break into a long tool call or answer at once. .dfs/artefacts/8fbc6922-dbdd-460a-abbc-421a6b853ed6.html
Evidence:
- for: probe, claude 2.1.308 `-p` with a stand-in model, message written while a 3-second Bash call ran: the next model request carried "PostToolUse:Bash hook additional context: The author says: PING-W104 …", and the result was the model's following reply.
- for: same probe, message waiting before the model ended its turn: the Stop hook's block made a second request carrying the message ("Stop hook blocking error from command: …: The author says: PING-W104 one more thing"), and the session's result was the answer to it.
Determination: Confirmed: claude-code 2.1.308 under `-p` takes a message from a PostToolUse hook at the next model call and from a Stop hook as one more turn, so the inbox and hooks are the way in.

### W104.2 · Feed the session on stdin as a stream-json conversation
Status: parked
Approach: Start claude work sessions with `--input-format stream-json --output-format stream-json`, stdin a pipe the runner holds open, and write the author's message to it as a user message.
Determination: Parked: it changes every work session's output from one JSON result to a stream that run.sh's `result_field`, limit.py and the screen's run view all parse, and the runner would have to close stdin after the last result for claude to exit, all to deliver no sooner than the hook does.

### W104.3 · Stop the session and resume it with the message
Status: parked
Approach: On a message, kill the running agent and start `claude -p --resume <sid> "<message>"` in its place.
Determination: Parked: the only way that cuts in at once, but it loses whatever tool call was in flight; taken only if the author rules the next tool call too late.

### W104.4 · The inbox, the hooks and run.sh's wiring for claude work sessions
Parent: W104.1
Status: confirmed
Approach: `runs.py` gains writing a message into a run's inbox and listing its pending and delivered messages; a new `scripts/inbox.py` is the hook (`post` and `stop`), draining the inbox named by `DFS_INBOX` atomically (rename before read, so two hooks never deliver one message twice); `run_session` in run.sh passes `--settings` with both hooks and exports `DFS_INBOX` for claude. Tests: unit tests for runs.py and inbox.py, and one with a real claude and a stand-in model (skipped where none is installed) proving a message written mid-tool reaches the next request.
Determination: Confirmed: `runs.post_message` and `runs.messages` keep a run's inbox, `scripts/inbox.py` hands it over as PostToolUse context or a Stop block, and run.sh starts every claude work session with both hooks and `DFS_INBOX`; test_inbox.py (8 tests, two of them a real claude 2.1.308 against a stand-in model) and test_chain's stub check pass, and so does the suite (1019 run, UI flows skipped for want of playwright).

### W104.5 · The screen: send a message from a live run's log
Parent: W104.4
Status: confirmed
Approach: In tui.py's view of a live chain's log (`lines_live_agent`), a key opens a one-line prompt and writes the message to the chain's inbox; the view lists the chain's messages as waiting or delivered. A chain under an agent with no way in says so instead. Test in test_screen.py.
Determination: Confirmed: `M` in a live chain's log (`tui.py`, `send_message`) prompts for a line and leaves it in the chain's inbox, refusing an ended chain or a non-claude agent, and the log lists each message as waiting, delivered at a time, or never read; test_screen.py's three new tests and the suite (1022 run, UI flows skipped) pass, and no picture is attached since it is a curses screen the tests read line by line.

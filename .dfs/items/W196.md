# W196 · In another dfs project, work with multiple workers doesn't start new sessions beyond a single session

## Summary

When a work runs several chains at once, each chain's session cap is now the budget left divided by the chains actually started, not by the empty slots. Before, one workable task among four workers got a quarter of the budget and the rest was held for workers with nothing to do, so its chains ran only a session or two each. A lone chain now reserves the whole budget, so a task that becomes workable while it runs starts only when it ends; this is tested and written in the work notes. The other project could not be inspected, so this is the one cause found in the code. If its chains stopped for another reason, such as no worktree being cut, that is a separate fix.

## Goal

In another dfs project, work with multiple workers doesn't start new sessions beyond a single session

## Tree

### W196.1 · Share the budget among the chains a tick starts, not among the free slots
Status: confirmed
Approach: **The question**
- With several workers, why does a work not run more than a session or two on a task?

**Why it matters**
- In `work_tick` (`scripts/work.py`) a chain's cap is `avail // (free - picks.index(item))`. `free` counts empty worker slots, even when no task can fill them. Probe on the test world: budget 8, 4 workers, one workable task gives that chain cap 2 (budget 20 gives cap 5). Each later chain gets a share of what is left, so caps shrink to 1 and every chain ends after a single session.

**What this node does**
- Divides by the number of chains this tick actually starts (`len(picks) - index`), so one workable task gets the whole budget, as with one worker. Adds a test in `scripts/test_worker.py` and `scripts/test_work.py` for fewer workable tasks than workers.

**How we will know it worked**
- The probe gives cap 8 for budget 8, 4 workers, 1 task, and the existing two-task shares (3 and 4 for budget 7) are unchanged. `test_worker.py` and `test_work.py` pass.
Hypothesis: The report comes from fewer workable tasks than workers, so idle slots hold budget back and caps fall to one session. Wrong if the other project had as many workable tasks as workers, or its chains stopped for another reason (no worktree cut, a stop in the run console). .dfs/artefacts/3efc3a8e-b1f3-4efa-8b1d-0a0ab01ae55c.html
Evidence:
- for: probe of `FakeWorker.start(8, 4)` with one open task started `[('W1', '2')]`, and `start(20, 4)` started `[('W1', '5')]`: the cap is a quarter of the budget.
- for: the new tests in `test_worker.py` and `test_work.py` fail without the change and pass with it (cap 2 before, 8 after, for budget 8 and one task).
- against: the other project's run console was not available, so the cause there is not seen; the same words fit a checkout with no worktree, where tasks run one chain at a time.

Determination: Confirmed: a chain's cap is now shared among the chains a tick starts, so one workable task among several workers gets the whole budget; tests pass, the work notes are re-confirmed (.dfs/artefacts/839dc383-c223-47fb-acd9-2675d235e7ff.html), and whether this is the other project's cause is left to the author's ruling.

### W196.3 · Hypothesis: a lone chain may hold the whole budget while idle workers wait
Parent: W196.1
Status: confirmed
Approach: W196.1 changed `work_tick` in `scripts/work.py` so the cap is `avail // (len(picks) - picks.index(item))`. With one workable task and four workers, that chain now reserves the whole budget. A later tick computes `avail = left - sum(caps of live chains)`, finds 0, and returns at `if avail < 1`. So a task that becomes workable while that chain runs (a new task, a raise answered, a task the first one unblocks, one passed over for the shared checkout) cannot start on a free worker until the chain ends. Before W196.1 the idle slots' share was held back for exactly that case. W196.1 made this trade without a Hypothesis, and its Hypothesis covers only the cause of the report. State it as a Hypothesis with its page: trading late-starting parallelism for a full cap is acceptable, and it is wrong if a work is expected to start a task that appears mid-chain on a free worker (then the cap would need to be lowered, as `work_lower` does, or a share kept back). Check whether a test covers a task appearing while a lone chain holds the whole budget (test_work.py line 270 covers a work that is waiting, not one with a live chain), and say in the work notes (`docs/explain/work.json`) that the whole budget can be held.
Hypothesis: A lone chain may hold the whole budget, so a task that becomes workable while it runs waits for it to end, and that is better than holding a share back for it. Wrong if a work is expected to start a task that appears mid-chain on a free worker at once (then the cap would be lowered, as `work_lower` does, or a share kept back). .dfs/artefacts/e72d1017-d7b5-42ef-9997-9a112e443cd6.html
Evidence:
- for: the new test in `test_work.py` (a task appears beside a lone chain whose cap is 8 of 8) shows the tick starts nothing and the work stays on; it passes on the current code, so it records the behaviour and is not a fix.
- for: `test_nothing_is_started_while_the_live_chains_hold_the_whole_budget` already held that live caps summing to the budget block a new chain, so the rule was in place before; W196.1 only makes a lone chain reach it.
- against: before W196.1 the same appearing task started at once with cap 2 of the 6 left (4 workers, budget 8), so late-starting parallelism is lost for the case where tasks appear mid-chain.
Determination: Confirmed: a lone chain now holds the whole budget and a task that appears meanwhile waits for it to end, which is tested and now written in the work notes (.dfs/artefacts/a18d09ca-0bd9-4146-ae97-c53028d131ce.html); the author may rule the other way.

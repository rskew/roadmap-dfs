# W73 · Allow adding images and files to nodes

## Summary

On the web page, every box the author writes in about a task or node (an answer, a correction, a goal, a node's approach) now has an Attach button, and takes a pasted or dropped picture too. The picture or file is kept in `.dfs/artefacts` under a new name and a reference to it goes into the text, so the page draws the picture under the node and the agent working the task is handed its path and told to open it. The Goal asked for images and is met; documents (pdf, txt, md, csv, json, log) can be attached as well and open as links, a pdf as a download because a browser will not show one in the page's sandbox. Attaching from the terminal screen was left out, since it cannot show a picture; it is the alternative to take up if the author wants it.

![the correction form with an attached picture's reference in the text and the Attach button under the box](.dfs/artefacts/061cac33-b2f7-4938-b006-1095ec97208d.png)

## Goal

Allow adding images to nodes

## Tree

### W73.1 · POST /api/attach stores an uploaded picture or file in .dfs/artefacts
Status: confirmed
Approach: In `scripts/web.py`, a new write `POST /api/attach` takes `{name, data}` (base64 in JSON, allowed a body up to `IMAGE_BODY` like `/api/background-image`), checks the type by extension and, for a picture, by its bytes (`paths.image_type`), and writes it to `.dfs/artefacts/<uuid>.<ext>` (`paths._write_atomically`), returning `{file, ref}` where `ref` is `![name](.dfs/artefacts/<uuid>.png)` for a picture or `[name](.dfs/artefacts/<uuid>.pdf)` for a file. GET `/artefacts/<name>` serves the document types too, as their own plain type and never sniffed into a page, and `artefacts_for` lists them. Checked by new cases in `scripts/test_web.py`: a png and a pdf are stored and listed, a wrong type, a picture whose bytes are not one, and an oversize body are refused.
Hypothesis: An attachment belongs in the text the author writes on a node (an answer, a correction, a new or edited node's Approach, a goal) as a markdown reference to a file in `.dfs/artefacts`, added from the web page only, and limited to pictures (png, jpeg, gif, webp) and plain documents (pdf, txt, md, csv, json, log) of 8 MB or less. Wrong if the author wants attachments kept as a list on the node apart from any text, wants to attach from the terminal screen too, or needs other file types. .dfs/artefacts/7366b183-c6df-4c19-bc75-cf495d7da837.html
Evidence:
- for: `scripts/web/index.html` `ART_RE` already draws `![alt](.dfs/artefacts/<name>.png)` found in any prose, and `web.py` `artefacts_for` lists what a task's text names, so a reference in the text needs no new storage.
- for: `check.py` refuses an edit to a determined node, so a field on the node could not take a picture after the node is ruled; a correction or answer can be written at any node.
Determination: `POST /api/attach` keeps a png, jpeg, gif or webp checked by its bytes, or a pdf, txt, md, csv, json or log file, of 8 MB or less, as `.dfs/artefacts/<uuid>.<ext>` and returns its markdown reference; the reference in a task's text lists it among the task's artefacts and `/artefacts/<name>` serves it sandboxed; `test_web.py` passes, 85 tests with the new case for stored, listed, refused and oversize uploads.

### W73.5 · Fix: commit the picture or file the author attached along with the text that names it
Parent: W73.1
Status: confirmed
Approach: `scripts/web.py` `attach` writes `.dfs/artefacts/<uuid>.<ext>` and the page puts its reference in an answer, correction, goal or Approach, but nothing ever brings that file into git. The web server commits nothing; `SKILL.md` tells a session to stage its node's paths by name and the task file, never the author's upload; `tree.py` `uncommitted` watches only `.dfs/items`, and `state.py` `dirty_paths` and the briefing's uncommitted-work notice leave `.dfs/` out. So a session commits the task file whose log quotes `![…](.dfs/artefacts/<uuid>.png)` and leaves the picture untracked: it sits in `git status` as `??` forever, a push or clone loses it, `git clean` deletes it, and another checkout cannot draw it or hand it to the agent. Checked in this repo: `git status` lists untracked files in `.dfs/artefacts`, and no code path stages an artefact. A picture uploaded and then dropped from the text (the dialog cancelled, or the reference deleted) is never named and never swept, so it piles up in `.dfs/artefacts` too. Settle it with a mechanism and a test: for example, the briefing lists the uncommitted artefacts the task's text names and `SKILL.md` says to stage them with the task file, or `check.py` refuses a commit whose staged task file names a `.dfs/artefacts` file that is on disk but not in the index. Decide what happens to an upload no text names (swept after a while, or never committed), with a `test_tree.py` or `test_web.py` case that fails before the fix.
Determination: `check.py` now refuses a commit whose staged task file or archive names a `.dfs/artefacts` file that is on disk but not in the index, and the briefing lists such files under "Attachments to commit" with `SKILL.md` telling a session to stage them with the task file; three new `test_tree.py` cases (refused when unstaged, passes once staged, a never-named upload and a missing file left alone) and the briefing case fail without the change and pass with it (105 tests), while an upload no text names is deliberately left on disk, neither committed nor deleted, since a sweep could delete a session's screenshot.

# W108 · bug report from another dfs project

## Summary

This bug report was filed against an older version. Parts 1 and 3 were already fixed by earlier work: a worktree under a blanket `.*` ignore rule links the main checkout's task files and current `order.md` so the session is briefed, a missing task file stops the chain with its cause recorded, and `init`, the chain start and the screen's header name the ignore rule that hides roadmap files. Part 2 was only half fixed: an old roadmap is adopted by committing it with `DFS_ADOPT=1`, but that did nothing once git already held some task files, as in the reporter's `.*` project. It now grandfathers every staged task file git does not hold yet, never one it does, and a refused commit that adds such a file names the variable. The Goal is met as those fixes shaped it: adoption is declared rather than detected from files with no history, and a file adopted over the size budget still refuses growth until shelved; the hidden-files message was also corrected to say which hidden paths a worktree links and which it lacks.

## Goal

Bug summary for roadmap-dfs (version 141543c)

  1. A walk's worktree is built from git, so it fails when the project doesn't track its roadmap files

  What happens
  - Starting a walk on a task creates a worktree on a new branch from HEAD. The tool symlinks the untracked state (runs, artefacts, theme and so on) into it.
  - items/ and order.md are not symlinked. They come from whatever git tracks.
  - If the project's ignore rules hide the roadmap directory, for example a blanket .* rule, only files someone force-added are tracked. Newer task files and the current
    order.md never reach the worktree.
  - The first session then can't be briefed:
    - dfs_state: no task file for <id>
    - dfs_run: state.py --brief <id> failed; a session cannot be briefed.
  - The run exits with rc=2 and the walk switches itself off with "the chain ended without recording why". The real cause is only in that run's console log.

  Why it looks like corruption
  - The status view lists the task as open with "no nodes yet — plan the task", as if the tree were empty. The file is intact in the main checkout.
  - The worktree's copy of order.md is also stale, and a task's tracked file can lag its working copy.

  Regression: the same project walked fine on the previous version, which didn't use worktrees.

  Expected behaviour
  - Preflight should check that the task file exists in the worktree and name the cause if it doesn't.
  - The tool should take items/ and order.md from the main checkout, or symlink them like the other state.
  - "Ended without recording why" should record the briefing failure as the reason.
  - Missing-file and empty-tree states should show differently.

  2. The pre-commit check judges a first-time commit of old files as new damage

  What happens
  - When previously untracked task files are staged, the check treats every existing violation as introduced by that commit.
  - The size check reports "GREW it (~0 before)" for files that have no earlier version to compare with.
  - Rules added after a task was written fail it retroactively. In one project that was 92 findings across about 40 tasks:
    - a Hypothesis with no artefact page named (29)
    - a Parent that is a task id rather than a node (about 40)
    - artefact pages that are referenced but not staged or not found (6)
    - two files over the token budget
  - The check also requires every referenced artefact to be staged, which pulls in a project's whole artefact directory (about 200 files, 17 MB here).

  Effect: the only ways through are rewriting old tasks to satisfy newer rules or bypassing the hook. Bypassing disables the guard for that commit.

  Expected behaviour
  - Judge only what the commit changes, and treat files with no history as grandfathered.
  - Offer a documented way to adopt an existing roadmap directory, or a stated way to baseline known findings.

  3. Related, smaller

  - Nothing tells the author that the project's ignore rules are hiding roadmap files. Tasks sat untracked for two weeks until a worktree needed them.
  - A roadmap directory's own ignore file only excludes runs/. That suggests the tool expects everything else to be trackable, so the init step could check that git add
    works on the roadmap directory.

## Tree

### W108.1 · Part 1: a blanket `.*` rule no longer stops a worktree's first briefing
Status: confirmed
Approach: In a scratch repo outside this worktree, init a roadmap with the current `scripts/init.py`, add a blanket `.*` to `.gitignore`, force-add one old task file and leave a newer one and the current `order.md` untracked, then run `branch.py enter <newer task>` and `state.py --brief <task>` inside the worktree it prints. Passes if the worktree has the newer task file and the main checkout's `order.md`, the briefing succeeds, `init.py` names the `.*` rule, and with the task file removed from the worktree the chain's stop (`run.sh`'s briefing failure) records the cause and the status view says the file is missing rather than "no nodes yet". The fix was W87 and W89, merged after the reported version 141543c.
Determination: Not reproduced on the current code: in a scratch repo with a `.*` rule and one force-added task, `branch.py enter W2` linked the worktree's `.dfs/items` and `order.md` to the main checkout, which held the untracked W2 and the current order, `state.py --brief W2` exited 0, and the six tests for the missing-file stop, its recorded cause, the walk's reason and the status line pass, so part 1 is met.

### W108.2 · Part 2: a first-time commit of an old roadmap is not judged as new damage
Status: confirmed
Approach: In a scratch repo with the guard hook installed by `init.py`, write old-style task files that break newer rules (a Hypothesis naming no artefact, a `Parent:` that is a task id, an artefact named but not staged, a file over the token budget) and commit them first with `DFS_ADOPT=1`, then commit an unrelated one-line edit to one of them without it. Passes if the adoption commit prints the findings as notes and is not refused, no "GREW it (~0 before)" appears, the later commit is judged only on its change, and README and `init.py` document adoption. The fix was W88, merged after 141543c.
Determination: Not reproduced on the current code: in a scratch repo, two old task files with a task-id Parent, a Hypothesis naming no page, an unstaged and a missing artefact and one at ~42,556 tokens were refused without `DFS_ADOPT` (the refusal says "ADDS it", not "GREW it (~0 before)", and names `DFS_ADOPT=1`), committed with it as printed notes, and a later log line on the clean-budget file committed without it, so part 2 is met as W88 shaped it: adoption is declared, and growing a file adopted over budget is still refused, which README states.

### W108.3 · Part 3: init and the screen say when ignore rules hide roadmap files
Status: confirmed
Approach: In the part-1 scratch repo, check `init.py` names the `.*` rule and file and line for the hidden roadmap parts, that `run.sh`'s chain start prints the same report, and that `state.py`/the screen's header carries `git hides .dfs`; and that a roadmap ignored whole by a `.dfs/` rule is not reported. The fix was W89, merged after 141543c.

### W108.4 · Fix: adopting old task files into a roadmap git already partly holds is refused, even with DFS_ADOPT=1
Parent: W108.2
Status: confirmed
Approach: The reporter's project is the one part 1 describes: a blanket `.*` rule, with some task files force-added and committed and about 40 newer ones untracked. When those 40 are staged, `scripts/check.py` sets `adoptable = from_index and not dfs_paths.ignored() and not head_names("items")`. HEAD already holds the force-added task files, so `adoptable` is False, `DFS_ADOPT=1` does nothing, every old finding refuses the commit, and the "commit it again with DFS_ADOPT=1" hint is not printed. README ("Adopting an existing roadmap") and check.py's docstring both say "A task file added once git already holds others is new work and is judged in full". So for this project, the only ways through are still rewriting the old tasks or `--no-verify`, which is exactly what the Goal's part 2 reports. W108.2's scratch test missed this because git held no task file there. To reproduce: in a scratch repo with the hook from `init.py`, commit a clean `.dfs/items/W1.md` with `git add -f` under a `.*` `.gitignore`, then stage `.dfs/items/W2.md` holding `Parent: W1` on a confirmed node and a Hypothesis that names no artefact. `DFS_ADOPT=1 git commit` exits 1 with both findings, and adding `!.dfs/` after `.*` (the fix `hidden_message` suggests) changes nothing. Fix: when the author declares `DFS_ADOPT=1`, grandfather the findings of any staged task file that has no history at HEAD, not only when HEAD holds no task file. Keep judging in full any task file committed without the variable, and any file HEAD already holds. Update README, check.py's docstring and `init.py`'s text to match, and print the hint whenever a refused commit adds a task file HEAD lacks. It is settled when a `test_tree.Check` test with one task file already committed and an old-style one staged is refused without `DFS_ADOPT` and passes with it, printing the findings as grandfathered.
Determination: Reproduced and fixed: with one task file committed and an old-style one staged, `DFS_ADOPT=1 git commit` was refused with no hint, and now `check.py` grandfathers any staged task file HEAD lacks when `DFS_ADOPT` is set (never one HEAD holds, and still refused without it, printing the hint), with README, the `check.py` docstring and `init.py` updated; the extended `test_a_task_file_new_to_a_tracked_roadmap_is_judged_in_full` and the new `test_adopting_a_new_task_file_never_excuses_one_git_holds` pass with all 135 `test_tree` tests.

### W108.5 · Minor findings from the review
Parent: W108.3
Status: confirmed
Approach: `scripts/paths.py` `hidden_message()` now says every hidden path is linked by "an item's worktree", but `branch.share_ignored_state()` only links top-level `.dfs` entries that git ignores. A page hidden inside a tracked `.dfs/artefacts/` by a `*.html` rule is neither committed nor linked, so it never reaches the worktree. Word the consequence for each case.
  `paths.hidden()`'s docstring ("an item's worktree, cut from git, goes without them") and `scripts/run.sh`'s preflight comment ("a roadmap part git will not add never reaches the item's worktree") are still the old claim, which is false for the `.*` case. Correct them along with the message.
  `test_ignored.test_the_message_names_the_rule` asserts nothing about the consequence wording, so the false sentence could come back without a test failing.
Determination: Fixed: `hidden_message` now says an item's worktree links the main checkout's copy of what a rule hides under an ignored top-level entry and has no copy of a page hidden inside a tracked directory, `hidden()`'s docstring and `run.sh`'s comment say the same, and `test_ignored` asserts both wordings along with the 3 `test_chain` briefing tests, which only fail when `TMPDIR` sits inside the repo.

### W108.6 · Fix: DFS_ADOPT=1 lets a session's first node of any new task past the guard, and the refusal tells it to
Parent: W108.4
Status: confirmed
Approach: `scripts/check.py` `main` now sets `adopting = declared and head is None` for each staged task file, and prints the "commit it again with DFS_ADOPT=1" hint whenever a refused commit adds a task file HEAD lacks (`adds_new`). But every new task's file is first committed with its first node by a session on `dfs/<task>` (`branch.py` `carry_uncommitted`), with HEAD lacking that file. Before W108.4 this window was only open while HEAD held no task file at all; now it is open for every new task. Checked in a scratch repo (`init.py`, clean `.dfs/items/W1.md` committed on main, then on branch `dfs/W2` a staged `.dfs/items/W2.md` whose confirmed W2.1 has `Parent: W2` and a Hypothesis naming no artefact): `check.py --staged` exits 1 with both findings and prints the DFS_ADOPT hint, and `DFS_ADOPT=1 check.py --staged` exits 0 with both grandfathered. So the guard tells a session how to skip it on the first node of every new task. Fix: neither grandfather nor print the hint on an item branch (`dfs_paths.branch_tag()` not None), where an adoption never belongs, and say in README "Adopting an existing roadmap", `check.py`'s docstring and `init.py` that adoption is committed on the default branch. Settled by a `test_tree.Check` test that stages a new task file with those two findings on `dfs/W2` while HEAD holds W1.md: refused with and without `DFS_ADOPT=1`, no hint printed; and the existing adoption tests on main still pass.
Determination: Fixed: `check.py` no longer adopts or prints the DFS_ADOPT hint on an item branch `dfs/<task>` (README, the docstring and `init.py` say adoption is committed on the default branch), and the new `test_an_item_branch_is_never_an_adoption` stages a new task file with a task-id Parent and a Hypothesis naming no artefact on `dfs/W2` while HEAD holds W1.md: refused with and without `DFS_ADOPT=1`, no "grandfathered", no hint, with all 136 `test_tree` tests passing (the one `Branches` hook-exec error appears only when `TMPDIR` is noexec).

# W37 · Artefacts should be path-based links rather than just the filename in a raise

## Summary

The web page now links an artefact a raise names, whether by its path (`.dfs/artefacts/<name>`) or by its bare filename, as an `<a>` with the relative href `artefacts/<name>`, which resolves in the page that shows the raise; the Artefacts tiles and the answer page use the same relative path. Nothing is refused when a raise is written, so the bare filename an agent writes just works. Only a file the task actually has is linked, and a name inside a longer name or path is left as text.

## Goal

Artefacts should be path-based links rather than just the filename in a raise

## Tree

### W37.1 · A raise names an artefact by its path, not its bare filename
Status: confirmed
Approach: In `scripts/tree.py` `append_log`, a raise is refused when it names an artefact that exists in `.dfs/artefacts` by filename alone (`0a1b2c.html` not preceded by `artefacts/` or by the older `localhost:<port>/` URL), or has an `Answer with:` line whose page lacks the `.dfs/artefacts/` path; the error says to write `.dfs/artefacts/<name>`. The web page's `rich()` and the `Answer with:` readers keep accepting old bare forms, so raises already in logs still resolve. SKILL.md's Raising paragraph and docs/artefacts.md say the raise must carry the path. Tests in `scripts/test_web.py` beside the answer-page tests: bare name refused, bare `Answer with:` refused, path accepted, a bare name of a file that does not exist accepted.
Ask: Is "path-based link" the raise text carrying `.dfs/artefacts/<name>` (which the web page then links)? I took it so and enforce it when a raise is written; the alternative is to make the web page also link bare filenames.
Determination: `tree.py log raise` now refuses a raise that names an existing artefact, or an `Answer with:` page, without the `.dfs/artefacts/` path; `test_tree` passes and `test_web` passes with its new test, except the chat test that failed before the change; the Goal is met.

### W37.2 · The web page links an artefact in prose as an <a> with a relative path, bare filename included
Status: confirmed
Approach: In `scripts/web/index.html`, `ART_RE` makes the `.dfs/artefacts/` (or `artefacts/`, or localhost) prefix optional behind a lookbehind that keeps it off a longer name or path, so `rich()` links a bare `<name>.html` or `<name>.png` the task has; its href, the Artefacts tiles' and the answer page's iframe `src` become the relative `artefacts/<name>`. The W37.1 refusal in `tree.py`, its test and its doc lines are reverted. `test_web` gains bare-name cases and its hrefs are relative; SKILL.md and docs/artefacts.md say a bare filename links too.
Determination: `rich()` links a bare artefact filename and a path alike with a relative-href `<a>`, leaving a longer name, a path-prefixed name and a file the task lacks as text; `test_web` passes under node apart from the chat test and the reorder test, both of which fail without this change too; the Goal is met.
Ask: Is "linked via an a element with a relative path" the page rendering the raise's artefact name as `<a href="artefacts/<name>">`? I took it so, and dropped the refusal; the alternative is a raise that carries the markup itself.

# W148 · Tasks on branches should still show in the regular order rather than after all the main tasks

## Summary

An unplaced task begun on a branch (an id like `W1@fx`) now appears right after its base task `W1` in the list, at the same level and behind the same breaks, instead of after every task the author placed. The author can still move it, which writes it into `order.md` as before. The Goal is met on the reading that "tasks on branches" means these tagged tasks; a tagged task whose base is not in the order stays last, and other unplaced tasks still go last because new work belongs at the bottom. The change is in `state.items()`, with three tests in `scripts/test_order.py`.

## Goal

Tasks on branches should still show in the regular order rather than after all the main tasks

## Tree

### W148.1 · An unplaced branch task takes its base task's place in the list
Status: confirmed
Approach: **The question**
- A task begun on a branch has an id like `W1@fx`. Nobody has placed it in `order.md`, so `state.items()` appends it after every placed task, in the last segment. Reproduced in a scratch repo with `order.md` of W1, W2, a break, W3: the list came back `W1, W2, W3, W1@fx`, and `W1@fx` was in segment 1, behind the break.

**What this node does**
- In `scripts/state.py` `items()`, put an unplaced `X@tag` straight after the end of `X`'s subtree, at `X`'s depth and in `X`'s segment. If `X` is not placed (or has no task), it stays last as now. Other unplaced tasks still go last, as `order.sort_key` intends.
- Tests in `scripts/test_order.py` or `scripts/test_walk.py`: the scratch case above gives `W1, W1@fx, W2, W3` with `W1@fx` in segment 0; two tags of one base keep id order; a tag whose base is missing stays last; a tag listed in `order.md` keeps its written place.

**How we will know it worked**
- The new tests fail without the change and pass with it, and the full `scripts/test_all.py` stays green (the screen's move keys use `tree_of(items)`, which needs segments that never go down).
Hypothesis: "Tasks on branches" means tasks whose id carries a branch tag, like `W1@fx`, and "the regular order" means beside their base task, as its sibling. Wrong if the author means another kind of branch task (for example tasks worked in `dfs/<task>` worktrees, or children nested in `order.md`), or wants it nested under the base or written into `order.md`. .dfs/artefacts/46ab9850-eee0-4ae2-8e7f-40ea955d00c1.html
Evidence:
- for: In a scratch repo with `order.md` of W1, W2, a break, W3 and a `W1@fx` task, the old `state.items()` returned `W1, W2, W3, W1@fx` with `W1@fx` in segment 1. The new tests for the beside-base, subtree and unplaced-base cases fail without the change and pass with it, so the late placement is what the code did.
- for: `W1@fx` is accepted by `order.ID_LINE` and by `tree.TASK_RE`, and `test_ui.py` and `test_web.py` build such tasks and the list draws their tag apart, so tagged ids are a kind of task the tool lists.
- against: Nothing in the code ties "branch" to the `@tag` ids alone; the Goal could also mean tasks worked in `dfs/<task>` worktrees. A scratch run of `state.items()` in the main checkout lists those in their order.md place already, so that reading shows no fault to fix.
Determination: Confirmed: an unplaced `X@tag` task now sits after the subtree of `X`, in its depth and segment, and `test_order.py` passes (101 tests); `test_all.py` fails the same 55 tests with and without the change.

### W148.2 · Place the tagged task as a child of its base
Parent: W148
Status: parked
Approach: In `items()`, give an unplaced `X@tag` depth `X`+1 right after `X`. Parked: `walk()` and `next_items` hold a child until its parent is done and a raise on the parent blocks it, but a task begun on a branch is not work under its base.

### W148.3 · Write the tagged id into order.md when the task is created
Parent: W148
Status: parked
Approach: Add the id to `order.md` after its base at each place a tagged task is created, so the order file holds the answer. Parked: it needs a write at every creation site and edits a file the author owns, while a derived placement needs none and the author can still move the task, which writes it.

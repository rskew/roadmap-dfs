# W88 · The pre-commit check judges a first-time commit of old files as new damage

## Summary

The pre-commit guard now judges a task file git already holds only on what a commit changes: a rule violation, an unstaged artefact name or a coordinate the file already had at HEAD no longer refuses later commits. A roadmap written before the guard is adopted by committing its task files once with `DFS_ADOPT=1` in the environment: its findings, including oversized files and artefact pages it does not stage, are then printed as notes and none refuses it, and the README and `init.py` explain this. Two things differ from the Goal's wording: adoption is declared rather than detected, because git holding no task file is also a new roadmap's state and nothing in the commit separates a first node worked in place from an old file (`.dfs/artefacts/a7747c47-7cd1-49f6-81c3-8b78aea466c9.html` shows the options), and a task file added after git already holds others is judged in full, so adopting a roadmap a few files at a time is not covered. A file adopted over the size budget is still refused when a later commit adds to it, until it is shelved; the README says so.

## Goal

The pre-commit check judges only what a commit changes, and treats files with no history as grandfathered, so adopting an existing roadmap directory does not mean rewriting old tasks or bypassing the hook.

When previously untracked task files are staged, the check treats every existing violation as introduced by that commit. The size check reports "GREW it (~0 before)" for files with no earlier version to compare with. Rules added after a task was written fail it retroactively; in one project that was 92 findings across about 40 tasks: a Hypothesis with no artefact page named (29), a Parent that is a task id rather than a node (about 40), artefact pages referenced but not staged or not found (6), and two files over the token budget. The check also requires every referenced artefact to be staged, which pulls in a project's whole artefact directory (about 200 files, 17 MB in that project). The only ways through are rewriting old tasks to satisfy newer rules or bypassing the hook, and bypassing disables the guard for that commit.

Done looks like:
- A commit is judged only on what it changes; files with no history are grandfathered (no "GREW it (~0 before)", no retroactive rule findings).
- Referenced artefacts are not all required to be staged with a first-time commit.
- There is a documented way to adopt an existing roadmap directory, or a stated way to baseline known findings.

Worth doing: the guard is only worth having if people can leave it on; today the first commit of an existing roadmap pushes them to bypass it.

## Tree

### W88.1 · Judge a tracked task file only on what the commit changes
Status: confirmed
Approach: In `scripts/check.py` `main`, for a task file HEAD holds, refuse only what this commit introduced: a `check_shape` finding is refused when HEAD's copy (with HEAD's archive) does not already produce it, `check_attachments` judges only the artefact names the commit adds to the text and archive, and the coordinate warning skips a file the commit leaves unchanged. Tests in `scripts/test_tree.py`: an old shape fault (a Parent naming the task id) and an old unstaged artefact name at HEAD no longer refuse an unrelated commit; the same fault or name added by the commit still does.
Determination: Confirmed: `check.py` now refuses only the shape faults and unstaged artefact names a commit adds to a file HEAD holds; the two new tests fail on the old guard and pass on the new, and `test_tree`, `test_ignored` and `test_walk` pass (`test_init`'s outside-git case fails only because the test temp dir had to sit inside this repo, /tmp being noexec).

### W88.2 · Grandfather the commit that first brings a roadmap's task files into git
Parent: W88.1
Status: confirmed
Approach: In `scripts/check.py`, when `.dfs` is committed (not gitignored) and HEAD holds no task file under `.dfs/items`, the commit is the roadmap's adoption: every file is judged with no history, so each finding (shape, Hypothesis artefact, Ask, writer, unstaged artefact, size) is printed as a grandfathered note and none refuses; the size check never reports "GREW it (~0 before)". A task file new to an already-tracked roadmap is still judged in full. Tests in `scripts/test_tree.py` for both.
Hypothesis: "Files with no history are grandfathered" means the files of a roadmap git has never held, so the adoption commit is told apart by HEAD holding no task file, and a task file new to a roadmap git already holds (a task written from the screen, a branch's part) is new work, judged in full. Wrong if the author wants task files added to an already-tracked roadmap grandfathered too, for adopting one piece at a time. .dfs/artefacts/ba5e1eae-d498-46ab-af48-190d669ee191.html
Evidence:
- for: `branch.py` `carry_uncommitted` says a task written from the screen is left uncommitted for "the branch's first session" to commit, so a new task's first node lands in a file with no history; `test_tree` `test_a_plain_commit_adding_the_same_hypothesis_is_still_refused` refuses a Hypothesis in a new branch part, and still passes.
- for: `test_the_commit_that_adopts_a_roadmap_grandfathers_what_its_files_hold` (a Parent naming the task, a Hypothesis with no page, an unstaged artefact, over the budget) fails on the guard before this node and passes after; `test_a_task_file_new_to_a_tracked_roadmap_is_judged_in_full` refuses the same file once HEAD holds another task.
Determination: Confirmed: the commit that first brings a roadmap's task files into git has its findings printed as grandfathered and passes, while a task file new to a tracked roadmap is judged in full and a new file over the budget reads "ADDS it" rather than "GREW it (~0 before)"; `test_tree`, `test_ignored` and `test_walk` pass.

### W88.6 · Fix: a new roadmap's first task commits are taken for an adoption and pass unjudged
Parent: W88.2
Status: confirmed
Approach: `scripts/check.py` `main` sets `adopting` whenever `.dfs` is committed and HEAD holds no file under `.dfs/items`, and then grandfathers every finding. That is also the state of every NEW roadmap: `init.py` makes `.dfs/items/` empty, the author writes a task from the screen (left uncommitted), `branch.py` branches `dfs/<task>` from a main that holds no task file and `carry_uncommitted` moves the task in, so the first session's commit of its first node is judged as an adoption: a Hypothesis naming no artefact page, an Ask, a Parent naming the task, the writer check and the size budget are all printed as "grandfathered" and none refuses. It holds for every task branched before any task file reaches main, which is exactly the exemption W88.3 was parked for. Checked: in a `test_tree.Check` repo with `code.txt` and `.dfs/ROADMAP.md` committed and no task file, staging a `W1.md` whose W1.1 has `Parent: W1` and `Hypothesis: It holds. Determination: Confirmed: `check.py` adopts a roadmap only off an item branch `dfs/<task>`, so a new roadmap's first node there is judged in full; the new test fails on the old guard and passes now, the adoption test still passes, and `test_tree`, `test_ignored`, `test_walk` and `test_templates` pass (`test_init`'s outside-git case still fails only because the test temp dir sits inside this repo).

### W88.8 · Fix: a session's first node worked in place, off main or in a repo with no commit, is still taken for an adoption
Parent: W88.6
Status: confirmed
Approach: `scripts/check.py` `main` sets `adopting` when the commit is staged, `.dfs` is committed, HEAD holds no file under `.dfs/items` and the branch is not an item branch `dfs/<task>`. Excluding item branches covers only the case where `branch.py` `enter` cuts a worktree. `enter` returns None, so the session works and commits in place, in two cases: the checkout is off `main`/`master` (README "Where an item is worked"), or the repo has no commit yet. In both, a new roadmap's first node is still grandfathered. Checked in a `test_tree.Check` repo with `code.txt` committed and no task file. On a branch `feature`, staging `W1.md` whose W1.1 has `Parent: W1` and `Hypothesis: It holds. Wrong if not.` gives `check.py --staged` exit 0 with "this commit adopts the roadmap", and three findings are listed as grandfathered: the Parent, the Hypothesis with no page, and the writer check's "adds W1.1 to the part of the default branch". In a repo with no commit (unborn `master`), the same staging gives exit 0 with two findings grandfathered. The same test also passes a fresh roadmap's first task merge into main as an adoption, so a fault that a conflict resolution introduces there is grandfathered. Fix: tell an adoption apart by something other than the branch name. For example, adopt only files that already carry history from before the guard (a determined node, or a log entry older than the commit), or require an explicit opt-in for the adoption commit. Then make the README "Adopting an existing roadmap" section, `init.py`'s docstring and next steps, and `check.py`'s docstring and the comment above `adopting` ("An adoption is made on main, or on any branch that is not one") match. Settled by `scripts/test_tree.py` tests in which the first-node commit of a fresh roadmap's first task is refused for a Hypothesis with no page both on a non-default, non-item branch and in a repo with no commit, while `test_the_commit_that_adopts_a_roadmap_grandfathers_what_its_files_hold` still passes.
Hypothesis: Nothing in a commit tells an adoption from a session's first node, since both arrive with HEAD holding no task file and a fresh first node is already confirmed and its task already carries a session log line, so the adoption commit must be declared: `DFS_ADOPT=1` in the commit's environment, one step the author takes once per roadmap. Wrong if the author wants an adoption recognised with no step (the branch-name rule, which lets a first node worked in place pass unjudged), or if a mark of old history does separate the two. .dfs/artefacts/a7747c47-7cd1-49f6-81c3-8b78aea466c9.html
Evidence:
- for: with `code.txt` committed and no task file, staging a first node whose W1.1 has `Parent: W1` and a Hypothesis with no page: the branch-name guard exited 0 on `feature` and in a repo with no commit (two new tests fail on it), and the new guard exits 1 on both and on `dfs/W1`.
- for: a fresh task's first-node commit holds a confirmed node and a task whose log has its session line, so "a determined node" or "a log entry" marks old history in neither direction.
- against: the author must know the variable; the refusal prints it, and the README, `init.py`'s docstring and its next steps name it.
Determination: Confirmed, and the Goal is met: `check.py` grandfathers a commit only when it is made with `DFS_ADOPT=1` and HEAD holds no task file, so a first node worked in place off main, in a repo with no commit, or merged into main is judged in full, and a refusal there names the variable; the adoption test passes with it and is refused without, the two new tests fail on the old guard, and `test_tree`, `test_ignored`, `test_walk`, `test_templates` and `test_init` pass.

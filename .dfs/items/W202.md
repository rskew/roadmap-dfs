# W202 · Reduce idle CPU usage

## Summary

An idle terminal screen now uses about half the CPU it did: 0.30 CPU-seconds in 20 s instead of 0.59, measured with its `git` children on this repository. The saving comes from its once-a-second change check, which no longer starts two `git` processes each tick and lists the temp directory once instead of three times; the web page's change watcher shares the cheaper listing. The Goal named no process, so this reads it as the screen and the web server that run while nobody works; an idle web server was already near zero and is unchanged within noise, the browser page's timers only run while a run's log or the chat list is showing, and the per-second check of task files was left as it is.

## Goal

Reduce idle CPU usage

## Tree

### W202.1 · Measure where an idle roadmap spends CPU
Status: confirmed
Approach: **The question**
- Which of the processes that run while nobody is working spends CPU, and how much each?

**Why it matters**
- The Goal names no process. A web server fix was made once already (idle `web.py`: 6.56 s of CPU in 20 s down to 0.03 s). The terminal screen (`tui.py`, wakes every `POLL_MS`) and the web page's timers are not measured.

**What this node does**
- Run the web server (`scripts/web.py`) and the terminal screen (`scripts/tui.py`) idle in a scratch copy of this repo, and read each process's CPU time over 20 s from `/proc/<pid>/stat`. Read the page's `setInterval` timers in `scripts/web/index.html`.

**How we will know it worked**
- A table of CPU seconds per idle second for each process, so the next node targets the biggest one.
Determination: Idle, the terminal screen (`tui.py`, which also runs the web watcher) takes about 0.63 CPU-s in 20 s with its git children and `web.py` alone about 0.13 s, and the screen's once-a-second `watch_signature` (two `git` processes, then globs over the temp directory and the task folders) is nearly all of it; confirmed.

### W202.2 · Make the screen's once-a-second watch cheaper
Parent: W202.1
Status: confirmed
Approach: **The question**
- How much of the screen's idle CPU goes if `watch_signature` (`scripts/tui.py`) stops spawning `git` every tick and stops listing the whole temp directory?

**Why it matters**
- Per tick it runs `dfs_paths.ignore_files()` (two `git` processes, about 2 ms each) and globs `dfs_run_*` in every run root, one of which is `/tmp` (3,265 entries here, 6,000 in the earlier W110 case). It then globs `dfs_run_*/*.json` and `console.log` again. The web watcher in the same process lists the same roots a second time.

**What this node does**
- Keep `ignore_files()`'s answer for a few seconds (the ignore files' own mtimes are still in the signature, so a change shows), list each run root once per tick and share the run directories between the two globs.

**How we will know it worked**
- Idle `tui.py` CPU over 20 s (parent plus children) before and after, a test that two ticks inside the ttl run no `git`, and `test_tui`-side suites that touch `watch_signature` (`test_screen`, `test_ui`, `test_runs`) pass.
Determination: `tui.watch_signature` now takes 4.1 ms instead of 11 ms (`web.roadmap_signature` 2.6 ms instead of 4.0 ms) by asking git for the ignore files once per 10 s and listing each run root once with `runs.run_paths`, and an idle `tui.py` with its git children uses 0.30 CPU-s in 20 s instead of 0.59 (an idle `web.py`, 0.13 to 0.20 s, is within noise); the new tests, one red on the old code, and `test_screen`, `test_runs`, `test_webscreen`, `test_ignored`, `test_live` passed, and `test_web` fails the same four tests as before; confirmed, and the Goal is met.

Hypothesis: "Reduce idle CPU usage" means the terminal screen and the web server, the two roadmap processes that run while nobody works. Wrong if another idle process or a page timer costs more CPU than the screen's watch does now. .dfs/artefacts/9d90aed3-2b16-4a7e-9699-2b774aa7bc38.html

### W202.6 · Cut the screen's once-a-second cost when there are hundreds of run folders
Parent: W202.3
Status: open
Approach: **The question**
- In the real checkout (431 run folders, `/tmp` and `.dfs/runs` as run roots), `tui.watch_signature` takes 42.6 ms a tick, `runs.run_dirs` 45.9 ms and `web.roadmap_signature` 10.5 ms. A profile of `watch_signature` shows about 3,100 `stat` calls a tick and a `sorted` over `Path` objects that costs a third of the time. Which of that work can be skipped or made cheaper without hiding a change?

**Why it matters**
- The scratch-copy measurement that called the Goal met had few run folders. The screen on the real checkout still uses about 10 percent of a CPU while idle, and a long-lived repo only gets more run folders.

**What this node does**
- Profile one tick of the screen (`watch_signature`, then what `poll` and `draw` call, including `run_dirs`) on the real checkout. Cut the biggest parts first: sort strings, not `Path` objects; stat only the files a change can show in (run folders that are not finished); keep a finished run folder's answer between ticks.

**How we will know it worked**
- The same three timings on the real checkout before and after, and the idle CPU of a `tui.py` started there over 20 s, with the existing tests (`test_screen`, `test_runs`, `test_webscreen`, `test_live`) still passing.

### W202.4 · Hypothesis: a ten-second-late ignore-file location is acceptable to the screen
Parent: W202.2
Status: open
Approach: W202.2 made `tui.ignore_files_cached` (`scripts/tui.py`) ask git where the ignore files are once per `IGNORE_FILES_TTL` (10 s) instead of every tick. This assumes that a change in where git looks for ignore rules (a new `core.excludesFile` or `.git/info/exclude`, or a different checkout) may show up to 10 s late, and that no other part of the screen needs it sooner. The docstring says so, but the node has no `Hypothesis:`. State it as a Hypothesis on W202.2 with its page: the 10 s figure, who sees a stale header ("git hides .dfs") and for how long, and what would show it wrong (a test or a user step that changes the config and expects the screen to follow in under 10 s).

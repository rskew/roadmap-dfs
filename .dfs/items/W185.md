# W185 · Models should be selectable per task, rather than per work run. The dfs instance sets the defaults.

## Summary

Each task can now have its own plan and implement model. A task's choice is kept under `tasks` in the run root's models file, its chain starts on it, and a task with no choice runs on the instance's defaults as before. You choose it on the task's page (two drop-downs, with the instance default as the empty option) or on the screen with `:model <task> plan|implement <name|none>`. The choice lives in the run root, not in the task file, so it is per instance and does not show in a task's git history; the other design is kept as a parked alternative. No screenshot was saved: the browser here draws no text.

## Goal

Models should be selectable per task, rather than per work run. The dfs instance sets the defaults.

## Tree

### W185.1 · Keep each task's models in the run root's models file and read them when its chain starts
Status: confirmed
Approach: **The question**
- Where is a task's own plan and implement model kept, and how does its chain pick it up?

**What this node does**
- In `scripts/work.py`, the models file (`.dfs/runs/models`, `models_file()`) gets a `tasks` key: `{"tasks": {"W185": {"plan": "haiku", "kiro": {...}}}}`. Each task's record has the same shape as the file's top level (claude's choice at its top, kiro's under `kiro`).
- `read_models(path, agent, item=None)` gives, per role, the task's choice if it has one, else the instance default from the top level, else "". Without `item` it reads as today.
- `set_model(role, name, item=None)` writes the task's record; an empty name removes the task's choice, so the instance default applies again. Same name checks as today.
- `start_chain(item, cap)` passes `item` to `read_models`, so `PLAN_MODEL` and `IMPLEMENT_MODEL` are set per task.
- A new `task_models(item)` returns the task's own choices alone, for the screens.

**How we will know it worked**
- New tests in `scripts/test_worker.py`: a task with a choice starts its chain on it while another task starts on the instance default; clearing the choice returns it to the default; claude's and kiro's task choices stay apart; the old file shape still reads the same.
Hypothesis: A task's model choice belongs in the run root's models file, not in the task file. Wrong if the author wants the choice in the task's own git history, since the run root is gitignored and per instance. .dfs/artefacts/b2963af7-54f7-41ee-9fe5-89255c924dfb.html
Evidence:
- for: `run.sh` already gets its models only from `PLAN_MODEL` and `IMPLEMENT_MODEL` set in `start_chain`, which already knows the item, so no runner change is needed.
- for: A task in flight has its current file only on its branch; a choice made in the author's checkout would not reach it.
- for: The six new tests in `test_worker.py` pass with the file kept in the run root: a task's own choice reaches only its chain, and clearing it returns the instance default.
Determination: A task's models are kept under `tasks` in the run root's models file and `start_chain` reads them per task, so the instance still sets the defaults; passed.

### W185.6 · Fix: a task's typed ("Other") model name goes to the instance default, and is not shown on the task
Parent: W185.3
Status: confirmed
Approach: Two faults in `scripts/web/index.html` and `scripts/work.py`, both met when a task is given a model that the drop-down does not list.
- In the global `change` handler, the "Other" text box branch calls `setModel(e.target.dataset.role, v)` with no item. The task's box carries `data-item`, but it is dropped, so a name typed on task W7 is written as the instance default and changes every task. Fix: pass `e.target.dataset.item` as the third argument. Add a flow to `ui_flows.mjs` (`taskmodels`) that types a name in a task's Other box and checks `S.work.models` is unchanged and `S.work.task_models.W1` has it.
- `WorkMixin.model_choices` in `scripts/work.py` adds only the instance's kept names (`self.models()`) to the list. A name a task chose that is not listed is missing, so the task's drop-down shows the empty "Instance default" option while the chain really runs on the task's name. Fix: also add every name in `all_task_models()` to the list. Add a test in `test_worker.py` or `test_web.py` that a task's own unlisted name is in `model_choices()` and in the snapshot.
Determination: A name typed in a task's Other box now goes to that task (the instance default is untouched), a task's own unlisted name is in the model choices so its drop-down shows it, and the task's models section stays open while its Other box is shown; passed.

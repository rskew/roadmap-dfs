# W147 · A node with a raise shouldn't also show refute/confirm

## Summary

A node with an open raise no longer offers Refute/confirm. In the web page the node card, the right-click menu and the `c` shortcut leave it out, and in the terminal tree the footer drops "f correct" and `f` points to `a` to answer instead. Once the raise is answered the node offers it again, and the key help in both places says so. The Goal is met. Two readings were assumed and put to the author on a page: that "a raise" means an unanswered one, and that the action is hidden rather than shown disabled. The server still accepts a correction if one is sent directly.

## Goal

A node with a raise shouldn't also show refute/confirm

## Tree

### W147.1 · Web: hide Refute/confirm on a node that has an open raise
Status: confirmed
Approach: **The question**
- The web page shows an Answer button on a node's raise card and also a Refute/confirm button, so the author is offered two ways to settle one node. Which actions should a node with an open raise show?

**What this node does**
- In `scripts/web/index.html`, leave out the Refute/confirm button from the node sheet (`drawSheet`) and from the right-click menu when the node has an open raise (`r.raises.length`), and ignore the `c` shortcut there. The Answer button stays; a node whose raise is answered shows Refute/confirm again.

**How we will know it worked**
- A browser flow in `scripts/ui_flows.mjs` opens a node with a raise and finds no `[data-act=correct]` in the sheet or the menu, then opens one without a raise and finds it. Run the web tests.
Determination: The sheet button, the right-click menu entry and the `c` shortcut are gone on a node with an open raise; the new browser flow failed without the change and passes with it.

### W147.2 · TUI: no correct action on a node that has an open raise
Parent: W147.1

### W147.3 · Hypothesis: a raise on a node means an open raise, and hiding Refute/confirm (not disabling it) is what the author wants
Parent: W147.1
Status: confirmed
Approach: **The question**
- The changes under W147.1 and W147.2 read "a node with a raise" as an unanswered raise, and remove Refute/confirm instead of disabling it. Neither node stated that as an assumption. Is it what the author meant?

**What this node does**
- States both readings as a Hypothesis with an answer page, and leaves the code as it is. The page lets the author switch node state and behaviour and see what the card offers.
Hypothesis: "A node with a raise" means a raise nobody has answered or settled, and the author wants Refute/confirm hidden (web) or refused with a message (terminal) while it is open, not shown disabled. It is a UI rule only: the server still accepts a correction sent directly. Wrong if the author answers raises only to correct nodes, wants the button visible with a reason, or wants it hidden after the raise is answered too. .dfs/artefacts/de600010-59fb-46ca-a55d-c3db8437b222.html
Evidence:
- for: `open_raises` in scripts/tree.py drops a raise once an `answer` or `settled` entry names it, and the web `r.raises` and TUI `row["raises"]` both come from it, so the built rule is "open raise" in both places.
- for: the web already shows a node with an open raise as needing the author (`wantsYou`, the "raise" tag), so a second action beside Answer is the duplicate the Goal names.
- against: `settled` entries are written by scripts/github.py when a pull request lands, not by the author, so a node can lose its raise without anyone answering; the hidden button comes back then.
- against: `/api/correct` in scripts/web.py and `record_correction` do not check for a raise, so the rule is only in the interface.
- The page's own check (`artefact_check.sh`) reports a blank render in this sandbox for this page and for an existing artefact alike (no fonts configured: boxes draw, text does not), so its layout was not read here.
Determination: Both readings are now stated with a page; nothing in the code contradicts them, and the author's ruling on the page decides whether to keep them.

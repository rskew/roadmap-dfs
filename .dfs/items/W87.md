# W87 · A walk's worktree is built from git, so it fails when the project doesn't track its roadmap files

## Summary

A walk's worktree now shares every planning file the project's ignore rules hide, even when git tracks some of them (for example a blanket `.*` rule over files force-added once): the task files and the current `order.md` are linked to the main checkout's copies, the merge puts the tracked ones back around its rebase, and entering a task whose force-tracked file has uncommitted edits keeps those edits. A worktree begun before this change that committed such a file keeps the branch's version, and one that both sides changed is left unshared with a message. If a worktree still lacks the task file, the chain stops before any session and records why, the walk turns off with that reason (so does a failure to enter the worktree at all), and the status line and tree pane say the task file is missing rather than showing an empty tree. The Goal is fully met; one thing differs from before: a force-tracked task file is now edited in the main checkout through the link, so it is left modified and uncommitted there after the merge rather than committed by the branch; the author may prefer the merge to commit it. The merge also leaves the author's own uncommitted edits to a file the branch changed for git to refuse, and no longer writes them over the branch's change; when a merge fails, the raise or node it writes into the task file is kept alongside the edits it set aside, and an interrupted merge (Stop chain) puts those edits back instead of losing them. The author has since committed their own edits to `scripts/branch.py` and `scripts/test_chain.py` on main, which had been refusing the merge, and the branch merges into current main with no conflict.

## Goal

A walk's worktree always has the task file and the current order.md, even when the project's ignore rules hide the roadmap directory (for example a blanket .* rule), so the first session can be briefed.

Starting a walk creates a worktree on a new branch from HEAD and symlinks the untracked state (runs, artefacts, theme) into it, but items/ and order.md come only from what git tracks. When the ignore rules hide the roadmap directory, only force-added files are tracked, so newer task files and the current order.md never reach the worktree. The first session then fails with "dfs_state: no task file for <id>" and "dfs_run: state.py --brief <id> failed; a session cannot be briefed", the run exits rc=2, and the walk switches itself off with "the chain ended without recording why"; the real cause is only in that run's console log. The status view meanwhile lists the task as open with "no nodes yet — plan the task", which looks like corruption although the file is intact in the main checkout. The same project walked fine on the previous version, before worktrees.

Done looks like:
- The worktree gets items/ and order.md from the main checkout, or they are symlinked like the other state.
- Preflight checks that the task file exists in the worktree and names the cause if it does not.
- "Ended without recording why" records the briefing failure as the reason.
- The status view shows a missing task file differently from an empty tree.

Worth doing: a project with ignored roadmap files cannot walk at all, and the failure points at the wrong cause.

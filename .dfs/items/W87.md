# W87 · A walk's worktree is built from git, so it fails when the project doesn't track its roadmap files

## Summary

A walk's worktree now shares every planning file the project's ignore rules hide, even when git tracks some of them (for example a blanket `.*` rule over files force-added once): the task files and the current `order.md` are linked to the main checkout's copies, and the merge puts the tracked ones back around its rebase so a commit the author makes to them meanwhile does not stop it. If a worktree still lacks the task file, the chain stops before any session and records why (the missing file and the ignore rule behind it), the walk turns off with that reason instead of "ended without recording why", and the status line and tree pane say the task file is missing rather than showing an empty tree. The Goal is fully met; the one path not covered by an automated test is a briefing that fails for some other reason after the task file check, which was checked by hand.

## Goal

A walk's worktree always has the task file and the current order.md, even when the project's ignore rules hide the roadmap directory (for example a blanket .* rule), so the first session can be briefed.

Starting a walk creates a worktree on a new branch from HEAD and symlinks the untracked state (runs, artefacts, theme) into it, but items/ and order.md come only from what git tracks. When the ignore rules hide the roadmap directory, only force-added files are tracked, so newer task files and the current order.md never reach the worktree. The first session then fails with "dfs_state: no task file for <id>" and "dfs_run: state.py --brief <id> failed; a session cannot be briefed", the run exits rc=2, and the walk switches itself off with "the chain ended without recording why"; the real cause is only in that run's console log. The status view meanwhile lists the task as open with "no nodes yet — plan the task", which looks like corruption although the file is intact in the main checkout. The same project walked fine on the previous version, before worktrees.

Done looks like:
- The worktree gets items/ and order.md from the main checkout, or they are symlinked like the other state.
- Preflight checks that the task file exists in the worktree and names the cause if it does not.
- "Ended without recording why" records the briefing failure as the reason.
- The status view shows a missing task file differently from an empty tree.

Worth doing: a project with ignored roadmap files cannot walk at all, and the failure points at the wrong cause.

## Tree

### W87.1 · Link the ignored `.dfs` entries git also tracks (items/, order.md) into the worktree
Status: confirmed
Approach: In `branch.share_ignored_state`, link every top-level `.dfs` entry the ignore rules match (`git check-ignore --no-index`, so a force-tracked `items/` or `order.md` counts) even when the worktree already holds it because git tracks part of it: mark its tracked paths `git update-index --skip-worktree`, move any untracked or edited file into the main checkout (`_move_into`), and put the link in its place, so a project with a blanket `.*` rule gets the main checkout's newer task files and current `order.md`. Skip-worktree paths make `git rebase` refuse when main changed them (seen: "Your local changes ... would be overwritten by checkout"), so `merge` restores them from HEAD before `_rebase` and shares them again after. Test in `test_chain.py`: a `.*` rule with `items/W1.md` and `order.md` force-tracked, a new untracked `W2.md` and an edited `order.md`; `branch.py enter W2` gives a worktree with both, `git status` clean, and a merge after the author commits a change to `W1.md` goes through.
Determination: `branch.py enter` on a project whose `.*` rule hides `.dfs` with `items/W1.md` and `order.md` force-tracked now gives the worktree the untracked `W2.md` and the edited `order.md` with `git status` clean, and the merge goes through after the author commits a change to `W1.md` (the new `test_chain` case, red without the put-back around the rebase); all 74 `test_chain` tests pass.

### W87.2 · Preflight checks the task file in the worktree and names the cause
Status: confirmed
Approach: In `run.sh`, after `branch.py enter` moves the chain into the worktree, check `dfs_tree.exists(<task>)` there as the preflight does in the main checkout; when it is missing, say that the worktree lacks the task file the main checkout has, and why it can (the project's ignore rules hide `.dfs` and only force-added files reach the branch), record the stop, and exit 2. A test in `test_chain.py` breaks the worktree's copy and reads the message.
Determination: `run.sh` now checks the task file in the worktree after entering it and, when it is missing there, stops before any session with `stop=brief` and a `cause` naming the worktree, the missing file and the ignore rule that hides it, and the main checkout's preflight no longer fails first on a reused worktree; the new `test_chain` case passes with the other 74.

### W87.3 · A chain that cannot brief a session records why it stopped
Status: confirmed
Approach: `run.sh` records `stop=brief` with `cause=<what failed>` in `meta.json` when the preflight of W87.2 or `build_prompt` fails; `runs.py` carries `cause`; `walk.py` maps `brief` in `WALK_STOP` to "a session could not be briefed: <cause>" instead of "the chain ended without recording why". Tests in `test_walk.py`/`test_chain.py`.
Determination: a briefing failure (the worktree preflight, or `state.py --brief` failing in `build_prompt`) is now recorded as `stop=brief` with its `cause`, and the walk turns itself off with "a session could not be briefed: <cause>" instead of "the chain ended without recording why"; `test_walk` covers the reason, and the `build_prompt` path was exercised by hand with a failing `state.py` (meta recorded the cause), since no chain test reaches it before `--foreign-dirt` fails first.

### W87.4 · The status view tells a missing task file from an empty tree
Status: confirmed

### W87.5 · Fix: entering a task whose force-tracked file has uncommitted edits crashes on the link
Parent: W87.1
Status: confirmed
Approach: In `branch.enter`, `share_ignored_state` now links `.dfs/items` into a fresh worktree even when git tracks part of it, and only then runs `carry_uncommitted`, which copies each of the task's dirty paths from the main checkout to the worktree. With `items` linked, source and destination are the same file: `shutil.copy2` raises `SameFileError`, `branch.py enter` exits 1 with a traceback, and `carry_named_attachments` never runs. Had the copy gone through, the next step (`git checkout HEAD -- <path>` in the main checkout) would have reverted the author's edit, which is the only copy. Reproduced by hand: a repo with a `.*` rule, `.dfs/items/W1.md` force-added and committed, a line appended to it (an answered raise, a task edited from the screen), then `branch.py enter W1` → `SameFileError: '.../.dfs/items/W1.md' and '.../.dfs/worktrees/W1/.dfs/items/W1.md' are the same file`. `run.sh` runs `ITEM_TREE="$(branch.py enter)" || exit 2` before the trap and `meta_set`, so no stop is recorded and the walk says "the chain ended without recording why", which is the symptom the Goal sets out to end. Fix: `carry_uncommitted` skips (leaves as they are) the paths it would reach through a link, since the worktree already shares them. Optionally, an `enter` failure records a stop and its cause too. Settle with a `test_chain` case: the blanket-`.*` fixture with the task's own force-tracked file edited and uncommitted in the main checkout. `branch.py enter` exits 0, the worktree reads the edit, and the main checkout still has it.
Determination: `carry_uncommitted` now leaves a path alone when the worktree reaches it through a link (same resolved parent directory), so `branch.py enter` on a blanket-`.*` project with the task's force-tracked file edited and uncommitted exits 0, the worktree reads the edit and the main checkout keeps it (new `test_chain` case, red without the guard); all 77 `test_chain` tests pass. The optional recording of an `enter` failure as a stop was left out.

### W87.6 · Fix: a reused worktree whose branch committed a force-tracked planning file reads the main checkout's stale copy
Parent: W87.1
Status: open
Approach: `share_ignored_state` runs on every `enter`, including the reuse of an existing worktree. For a `.dfs` entry that git tracks in part, `_hide_tracked` marks the worktree's tracked paths `--skip-worktree` and deletes every one that `git diff` shows unedited, then links the main checkout's copy in its place. A copy the branch has COMMITTED is unedited, so the branch's newer version is replaced by the main checkout's older one. Before W87.1, a project with a force-tracked task file worked it in a real tracked copy, and `_commit_task_files` committed the tree onto the branch. Every worktree already in progress when this version lands is in that state. Reproduced by hand: the old `branch.py enter W1` (at 62b8ec6) on a `.*` project with `items/W1.md` force-tracked, a commit on `dfs/W1` that confirms W1.1, then the new `branch.py enter W1`. The worktree now reads `Status: open` for W1.1, while `git show HEAD:.dfs/items/W1.md` has it confirmed. The next session sees the node open again and redoes it. Its edits go to the main checkout's working copy, where the merge of a branch that changed the same file meets them. An edited (uncommitted) worktree copy is no better off: it is moved aside as `W1.md.from-worktree`, and the stale copy is read. Fix: before linking, where the worktree's tracked copy differs from the main checkout's file, carry the branch's version into the main checkout (as `carry_uncommitted` does the other way) or say so and leave that entry unlinked. Settle with a `test_chain` case that builds the pre-W87.1 state (a real tracked `items/W1.md` in the worktree with a branch commit changing it), runs `branch.py enter W1`, and checks that the worktree reads the branch's tree.

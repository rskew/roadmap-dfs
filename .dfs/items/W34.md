# W34 · Task name field text doesn't follow cursor when scrolling on mobile

## Summary

The task name field (and the project name and node title fields, which had the same fault) is now a text box that wraps, so a long name stays on screen with the caret and never scrolls sideways. Enter still saves, and a pasted line break becomes a space. This was built from the cause a phone browser's one-line input most likely has; the fault could not be reproduced in the sandbox's emulated phone, so the Goal is met in design and in emulation but not yet seen on a real phone.

## Goal

Task name field text doesn't follow cursor when scrolling on mobile

## Tree

### W34.1 · Reproduce the field in an emulated phone
Status: confirmed
Approach: Open Edit task on W3 in Playwright's iPhone 13 emulation (Chromium, DejaVu fonts, since the sandbox has none), set a 92-character name, and press End, Home, then ArrowRight 60 times, reading `#en`'s `scrollLeft`, `scrollWidth`, `clientWidth` and `selectionStart` after each.
Determination: Blink follows the caret in the single-line name field (End scrolled to 517 of 823, Home to 0, 60 ArrowRights to 233, typed text stayed in view), so the fault is not reproducible here and belongs to a real phone browser's handling of a horizontally scrolling `<input>`, which this sandbox cannot drive.

### W34.2 · Wrap the one-line name fields
Parent: W34.1
Status: confirmed
Approach: In `scripts/web/index.html` the task name (new and edit), project name and node title fields become `textarea.line` from a `line()` helper: one row that grows to its text, Enter submits, line breaks in a paste become spaces on submit. `design.css` sets letter-spacing normal on dialog fields. `ui_flows.mjs` `namefield` and `test_ui.py` cover wrap, no sideways scroll, Enter saving to W3.md.
Hypothesis: A phone's one-line input scrolling sideways is what loses the caret in the task name field, so a field that wraps removes the fault. Wrong if a wrapped field loses the caret on the author's phone too, or the one-line field keeps it, which would put the fault in the dialog's scrolling under the keyboard; try both in .dfs/artefacts/4834a266-5af1-43e5-abb5-8858a6ec8e91.html.
Evidence:
- for: emulated iPhone 13 shows the wrapped field with no sideways scroll (scrollWidth equals clientWidth for a 92-character name) and Enter saving "Stop cache stampedes"; ![the wrapped name field in an emulated phone](.dfs/artefacts/7b2402e2-c398-4315-bad9-47cce4d58d4f.png)
- against: the one-line field followed the caret correctly in the same emulation, so nothing here showed the fault in the old field.
Determination: Confirmed as built and tested in emulation (namefield passes, and the other flows fail only where they failed before it, apart from one timeout that passes alone), with the fix on a real phone left to the author to try.
Ask: Does the name field now keep your caret on your phone, and if not, was the fault in the one-line field or in how the dialog scrolls under the keyboard? I chose the wrapped field from the one-line input's sideways scrolling.

# W68 · Reordering items: show edited order with some kind of pending indicator rather then flashing back to the old order before the server update brings the edited order back

## Summary

Dragging a row by its grip, or nudging it with the arrow keys, now draws it in its new place at once, with a dashed outline and a "saving…" tag until the server's reply lands, so the list no longer snaps back to the old order first. A refused move puts the order back and shows the reason, and if the list cannot be read back it draws the order from before the move and says it may be out of date. When several moves are in flight the last one sent decides the list, and a row keeps its saving mark until its last move is answered. The out, in and break buttons have no preview, since they change the parent or a fence, but they show the same saving mark on the row.

## Goal

Reordering items: show edited order with some kind of pending indicator rather then flashing back to the old order before the server update brings the edited order back

### W68.2 · Fix: the local preview of a root-level move across a break is drawn where the server will not put it
Parent: W68.1
Status: confirmed
Approach: `guessMove` in scripts/web/index.html builds the preview from the items alone, but the server treats a break as a sibling at the root (order.py header: "A BREAK IS A SIBLING AT THE ROOT"; `moved`/`placed` count it among `siblings_of` and move the item across the fence, the fence staying at its slot in the node list). With nodes W1, ---, W2: `order.moved(n,'W2',-1)` gives W1, W2, --- and `order.moved(n,'W1',1)` gives ---, W1, W2; `order.placed(n,'W2','W1',True)` gives W1, W2, ---; the client's guess for the same moves keeps the break between the two (W2 | W1, or W2 | W1 for down), which is a different order. So a root-level up/down/place that crosses or lands beside a break is drawn in one place marked saving, then jumps to another when the reply replaces it, the very flash the Goal removes. Fix: make `guessMove` follow order.py for root items: treat a break as a sibling for up/down (a step onto the fence moves the item across it, the segments being dealt by position after), and for `place` put the item before/after the target's span in the break-inclusive list. Easiest is to build the node list with the fences (as `order.tree_of` does) in the client, move in it, and deal segments back from the breaks' positions. Check: add a break-crossing case to the `reorderpending` flow (or a unit check of the guess) that drops/nudges a root row across a break with `/api/order` held, and asserts the held page already shows the order, break included, that the reply then leaves unchanged.
Determination: Confirmed: `guessMove` now moves within the break-inclusive node list as order.py does, counting segments by the fences that survive a re-read; the new reorderbreak flow (nudge up across a break and back down, reply held) was red on the old guess and passes now, and reorder, reorderpending and the other reorder flows still pass.

### W68.3 · Minor findings from the review
Parent: W68.1
Status: confirmed
Approach: Fix in one pass, beside W68.2:
- `moveTask` (index.html): when a move is refused and the `/api/state` refetch also fails, the `catch` leaves the guessed (refused) order on screen with nothing marking it; restore from a saved copy of `S.state` taken before the guess, or say the list may be out of date.
- `moveTask`: with two moves in flight, the last reply to land sets `S.state`; if replies arrive out of order the older one wins. Take the state from the reply of the latest-sent request, or always refetch `/api/state` once `inflight` reaches 0.
- No test covers the `S.stale` path (a list render landing while a move is in flight) or the out/in/break pending mark; add one each to `reorderpending`.
- The pending tag is spliced in with `inner.replace("</span></span>\n", …)`, which depends on the exact whitespace of the template above it; build the tag into `inner` instead so a reformat cannot silently drop it.
Determination: Confirmed: a refused move whose list cannot be read back restores the pre-move list and toasts that it may be out of date, the last move sent decides the final list whichever reply lands last, the saving tag is built into the row, and `reorderpending` now covers the mid-write list read, the out/in/break mark and the failed read-back, which the old code failed.

### W68.4 · Fix: two moves of one row in flight lose the saving mark early, and a throwing redraw would leave every list render dropped
Parent: W68.1
Status: confirmed
Approach: In `moveTask` (scripts/web/index.html) make `S.pending` a Map of id to the number of moves of that row in flight, so the "saving…" mark stays until the last reply for the row lands (a held ArrowUp sends several moves of one row; the Set dropped the mark at the first reply while the second was unwritten). Also move the `redraw()` that follows `S.inflight++` inside the `try`, with the pending count released in a `finally` and the in-flight count after it, so a throw in `drawTasks` cannot leave `S.inflight` above 0 and every later list render dropped as stale. Check: `reorderpending` sends ArrowDown then ArrowUp on one row with both replies held, releases only the first, and asserts the row is still marked saving until the second lands; it is red on the Set.
Determination: Confirmed: `S.pending` is now a per-row count and `redraw()` sits inside the `try`; the new two-moves-in-flight check in `reorderpending` was red on the Set and passes now, with reorder and reorderbreak still passing.

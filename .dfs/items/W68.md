# W68 · Reordering items: show edited order with some kind of pending indicator rather then flashing back to the old order before the server update brings the edited order back

## Summary

Dragging a row by its grip, or nudging it with the arrow keys, now draws it in its new place at once, with a dashed outline and a "saving…" tag until the server's reply lands, so the list no longer snaps back to the old order first. A refused move puts the order back and shows the reason, and if the list cannot be read back it draws the order from before the move and says it may be out of date. When several moves are in flight they are written one at a time in the order they were made (two requests sent a millisecond apart were seen reaching the server reversed, so this is needed), the last one sent decides the list, and a row keeps its saving mark until its last move is answered, and a move made while a refused one is being read back is not drawn over by the read-back. The out, in and break buttons have no preview, since they change the parent or a fence, but they show the same saving mark on the row.

## Goal

Reordering items: show edited order with some kind of pending indicator rather then flashing back to the old order before the server update brings the edited order back

### W68.2 · Fix: the local preview of a root-level move across a break is drawn where the server will not put it
Parent: W68.1
Status: confirmed
Approach: `guessMove` in scripts/web/index.html builds the preview from the items alone, but the server treats a break as a sibling at the root (order.py header: "A BREAK IS A SIBLING AT THE ROOT"; `moved`/`placed` count it among `siblings_of` and move the item across the fence, the fence staying at its slot in the node list). With nodes W1, ---, W2: `order.moved(n,'W2',-1)` gives W1, W2, --- and `order.moved(n,'W1',1)` gives ---, W1, W2; `order.placed(n,'W2','W1',True)` gives W1, W2, ---; the client's guess for the same moves keeps the break between the two (W2 | W1, or W2 | W1 for down), which is a different order. So a root-level up/down/place that crosses or lands beside a break is drawn in one place marked saving, then jumps to another when the reply replaces it, the very flash the Goal removes. Fix: make `guessMove` follow order.py for root items: treat a break as a sibling for up/down (a step onto the fence moves the item across it, the segments being dealt by position after), and for `place` put the item before/after the target's span in the break-inclusive list. Easiest is to build the node list with the fences (as `order.tree_of` does) in the client, move in it, and deal segments back from the breaks' positions. Check: add a break-crossing case to the `reorderpending` flow (or a unit check of the guess) that drops/nudges a root row across a break with `/api/order` held, and asserts the held page already shows the order, break included, that the reply then leaves unchanged.
Determination: Confirmed: `guessMove` now moves within the break-inclusive node list as order.py does, counting segments by the fences that survive a re-read; the new reorderbreak flow (nudge up across a break and back down, reply held) was red on the old guess and passes now, and reorder, reorderpending and the other reorder flows still pass.

### W68.8 · Fix: the read-back step added to `reorderpending` fails on about a third of runs
Parent: W68.7
Status: confirmed
Approach: The step "a move made while a refused one is being read back" in `reorderpending` (scripts/ui_flows.mjs, from `let readBack, readDone` to `sendLast()`) is flaky. In the review it failed in 2 of 7 plain runs of `python3 scripts/test_ui.py -k dropped_row` (under `nix shell nixpkgs#playwright-test` with FONTCONFIG_FILE set), with "the refused move's list is being read back: 2 != 1" and with "the move made during the read-back is drawn at once: W2,W3,W1 != W1,W3,W2"; with logging added it failed in 3 of 8. Cause seen: the route on `**/api/state` counts and holds every list read, and the page makes stray ones: the SSE push (`/api/events`, 120 ms after order.md changes, index.html line ~1518) calls `render(false)`, which reads `/api/state` for the previous steps' writes and for this step's own writes (logged: 3 to 4 reads per run, with `S.stale` true on the later ones). So `reads` is not "the refused move's read-back", `waitForTimeout`/`reads` gates race the first keypress, and the held stray reads reach `readGate`. Make the step deterministic: let the page settle first (no pending, `S.inflight === 0`, no read in flight), hold only the read-back that follows the refusal (e.g. mark the refusal with a flag set in the `/api/order` route and have the `/api/state` route hold only reads made after that flag, letting every other read through), and wait on `S.inflight === 1` plus that flag instead of a `reads` count. Check: run `-k dropped_row` at least 15 times in a row with 0 failures, and confirm the step is still red when the `current()` / read-back guard in `moveTask` is removed (so it still discriminates).
Determination: Confirmed: the step now waits for the page to settle, holds only the first list read made after the refusal and waits on `S.inflight === 1` instead of counting reads, and `-k dropped_row` passed 15 runs in a row (it failed 2 of 7 before); with the `S.inflight === 1` read-back guard in `moveTask` loosened it is red in 3 of 3 runs, so it still discriminates.

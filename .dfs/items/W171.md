# W171 · in chat, stopping and sending a new message loses the previous message in the log

## Summary

In the chat, a message whose turn was stopped (or failed) before the agent wrote it down now stays in the conversation when the next message is sent. It is kept in the place it was sent and is forgotten only by "New chat". The Goal is met, reading "the log" as the conversation the page shows. The kept message lives in memory, as the shown-but-not-yet-recorded messages already did, so a server restart forgets it. A message the agent did record under changed text is not shown twice, and the note on a lost first turn now says the agent has no record of the message.

## Goal

## Tree

### W171.1 · keep a message whose turn was stopped when the next one is sent
Status: confirmed
Approach: **The question**
- In the chat page, why does the earlier message vanish from the conversation after Stop and a new message? Test `test_a_message_stopped_before_it_was_recorded_stays_shown_when_the_next_is_sent` (in `scripts/test_chat.py`) is red without the fix: the list holds only `second`.

**Why it matters**
- `Chats.state` shows a sent message from `self.pending` until the agent's transcript records it. A stopped turn never records it, so the entry waits for a transcript message that will not come. When the next message is recorded, the old entry counts as recorded and is dropped. The author loses what they wrote.

**What this node does**
- In `Chats.turn`, when a turn ended stopped or failed, move its pending messages that the transcript does not hold into `self.kept[scope]` as `(text, at)`, where `at` is how many transcript messages came before it.
- `Chats.state` inserts them at `at`, like steering messages, so they stay in place after later turns. `Chats.clear` forgets them.

**How we will know it worked**
- The new test passes, and `scripts/test_chat.py` and `scripts/test_web.py` still pass.
Determination: Confirmed: the stopped message now stays in place after the next message, and the new test (red before) plus the 91 chat tests pass.

### W171.2 · Hypothesis: what "the log" means, and that a kept message need only last until restart
Parent: W171.1
Status: confirmed
Approach: **The question**
- W171.1 made two choices the Goal does not settle. Which "log" did the author mean? Must a stopped message outlive a server restart?

**What this node does**
- States both as a Hypothesis with an answer page, and records the evidence. It changes no code.
Hypothesis: "The log" is the conversation the chat page shows (`Chats.state` messages, the `#chat-log` element), not the debug file `<run root>/chat/<scope>.log`; and `Chats.kept`, held in memory like `Chats.pending`, is enough, so a restart may forget a stopped message the agent never recorded. Wrong if the author meant the debug file, or expects a stopped message to survive a restart (then it must be saved in the scope's record file). .dfs/artefacts/dec88b74-e8a3-43af-8617-a628f6d3128d.html
Evidence:
- for: `scripts/web/index.html` names the element that shows the conversation `#chat-log` (`role="log"`), so the page itself calls it the log.
- for: grep of `chatlog.log(` calls in `scripts/chat.py` shows they write lengths and events ("message of %d characters"), so a lost message's text was never in the debug file to lose.
- against: one call (`scripts/chat.py`, steering messages dropped on a stop) writes message text to the debug file as detail. The text is also shown to the author as a note, so it is not lost, but the debug file is not wholly text-free.
- for: `pending` and `kept` are plain dicts set in `Chats.__init__`; the scope's record file holds only `sid`, `ended` and `backend`. A restart already forgot a message shown before the agent recorded it, so `kept` adds no new loss.
Determination: Confirmed: the page calls the conversation the log, and the debug file holds no sent-message text but the dropped steering ones, so the reading stands; the in-memory limit is stated and left for the author to overrule.

### W171.3 · Minor findings from the review
Parent: W171.1
Status: confirmed
Approach: One line per finding.
- `Chats.keep_unrecorded` moves every pending entry that `recorded_apart` finds unmatched by text. `Chats.state` also requires `held < e[1]` (the author-message count) before it shows one as unrecorded. A stopped or failed turn whose agent recorded the message under changed text would now show it twice (once from the transcript, once from `kept`). Apply the same count test in `keep_unrecorded`, and add a test for it.
- The note "the message was not kept" (the `lost` case in `Chats.turn`) now sits beside the same message still shown in the conversation. It means the agent has no record of it, but a reader may take it as contradicting the list. Consider wording it as "the agent did not receive it".
- The new test only covers a stopped claude turn. A failed turn (`CHAT_STUB_FAIL`) and the codex/opencode/kiro first-turn `lost` case reach `keep_unrecorded` too, and are untested.
- Several tests in `scripts/test_chat.py` fail when `TMPDIR` is on a noexec mount (the stubs cannot run). This is the environment, not the change.
Determination: Confirmed: `keep_unrecorded` now uses the same count test as `state`, the note reads "the agent has no record of the message", and new tests for a failed turn and for changed text pass (the changed-text test red without the fix), with all 93 chat tests passing.

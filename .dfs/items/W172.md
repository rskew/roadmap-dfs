## Tree

### W172.1 · Offer Steer while a background chat answers
Status: confirmed
Approach:
- **The question**: a chat on the page that runs as a background agent on the screen can answer for a long time. Why can the author not send it a message then?
- **Why it matters**: a headless turn already takes a steering message while it answers. A background chat does not: its state says `busy` but `steer` is false, so the page hides Send.
- **What this node does**: in `Chats.state` (`scripts/chat.py`) set `steer` true when the chat is live and answering (`talking`), for the agents in `STEERED`. `Chats.send` already types into a live screen chat, and `ptyrelay` types at once after the first message, so no other change is planned.
- **How we will know it worked**: a `test_chat.py` test shows `steer` true for a talking screen chat and that a send is typed into it; the page test in `test_web.py` shows the button reads Steer; both are red without the change.
Hypothesis: each agent (claude, codex, opencode, kiro) accepts text typed while it answers and acts on it as a steering or queued message. Wrong if one drops it, runs it as a separate command or breaks its screen. .dfs/artefacts/b18b7438-5b0f-4f7d-9a5d-85b7f952d584.html
Evidence:
- for: `ptyrelay._ready` returns true at once after the first typed message, so a later message is typed while the agent answers (read in `scripts/ptyrelay.py`).
- for: the new test `test_a_message_can_steer_the_screens_chat_while_it_answers` fails without the change and passes with it; the 57 other `test_chat` failures are the same with and without it (missing agent stubs).
- against: the agents are not installed here except kiro-cli, so none was run with a message typed mid-answer.
Determination: Confirmed on the evidence so far: a background chat that is answering now reports `steer`, so the page shows Steer and the message is typed into it; how each real agent treats text typed mid-answer is not yet seen.

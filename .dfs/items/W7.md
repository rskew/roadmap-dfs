# W7 · Can't install pwa on Chrome Android

## Summary

The web page's manifest, icons and worker already met Chrome's install criteria; what was missing was a secure origin, since Chrome on Android offers Install only over https or localhost. A server bound to loopback behind a TLS proxy such as `tailscale serve` now answers the proxy's hostname when it is named with `--allow-host` or DFS_WEB_ALLOW_HOST (the latter is how the terminal screen's page takes it), the page tells an Android user on plain http why Install is missing, and the README writes out the https routes. Install itself was not tried on a device or against a real proxy, so the Goal is met by reasoning and tests rather than by watching it install. Generating a self-signed certificate was left out because Chrome will not install from a certificate the phone does not trust.

## Goal

Can't install pwa on Chrome Android

## Tree

### W7.1 · Audit what Chrome Android requires against what the page serves
Status: confirmed
Approach: Check `/manifest.json`, the icons, `/sw.js` and `index.html` against Chrome's install criteria (secure context, manifest with name, 192 and 512 icons, start_url, display standalone, a registered worker), by requesting them from a running server and reading `test_web.py`'s installability test.
Hypothesis: The page is served over plain http on a LAN address (`--host 0.0.0.0` or DFS_WEB_HOST, the environment's setting), where Chrome Android offers no Install, and nothing else is missing. Wrong if the user reaches it over https or localhost and Install is still absent.
Evidence:
- for: Served with `DFS_WEB_HOST=0.0.0.0` the manifest, `sw.js` and all icons return 200 with the right types; the icons measure 192, 512, 512 and 180 pixels; the manifest has name, start_url, scope, display standalone and a maskable icon. Nothing in the files fails the criteria.
- for: `web.py` serves http unless `--cert`/`--key` are given, and its docstring already says Android's Install needs https; the startup note says so only once, in a terminal line.
Determination: Confirmed: the manifest, icons and worker are sound, so the cause is the missing secure context, and the work is making an https route easy and the page say why Install is missing.

### W7.2 · Let a loopback-bound server answer a TLS proxy's hostname
Parent: W7.1
Status: confirmed
Approach: The documented https route is `tailscale serve`, which forwards to a server bound to 127.0.0.1. `host_ok` in `scripts/web.py` refuses any non-loopback `Host` there (421, for every path), so the proxy route is dead. Add `--allow-host NAME` (repeatable, also DFS_WEB_ALLOW_HOST, comma-separated) whose names `host_ok` accepts in addition to loopback, and `same_origin` already compares Origin to Host. Test in `test_web.py`: a loopback server answers 421 for an unlisted name and 200 for a listed one; the rebinding refusal is unchanged.
Hypothesis: A TLS proxy in front of a loopback server forwards the public hostname in `Host` unchanged. Wrong if the proxy rewrites `Host` to the upstream address, in which case the refusal never fires and this node changes nothing.
Evidence:
- for: A server started with `--host 127.0.0.1` answered 200 to `Host: 127.0.0.1:port` and 421 to `Host: phone.tail1234.ts.net` on `/` and `/manifest.json`, so a proxy that forwards its public name is refused for every path today.
- against: No proxy is installed in this environment (no `tailscale`), so whether one forwards its name in `Host` was not observed.
Determination: Confirmed: `--allow-host` / DFS_WEB_ALLOW_HOST admit a named proxy host on a loopback server (new test in `test_web.py` passes; the rebinding and cross-origin refusals are unchanged); the proxy's `Host` forwarding is untested here.
Ask: Does `tailscale serve` (or your proxy) forward its public hostname in `Host`? I assumed it does and added `--allow-host` for it.

### W7.4 · Serve https itself with a generated self-signed certificate
Parent: W7.1
Status: parked
Approach: `web.py --https` generates a self-signed cert and serves with it.
Determination: Parked: Chrome Android treats a certificate it does not trust as an error and withholds Install and worker registration, so the user would still need to install a root on the phone; `--cert`/`--key` with a trusted cert (mkcert, tailscale) already covers it.

### W7.5 · Fix: the page the TUI serves ignores DFS_WEB_ALLOW_HOST
Parent: W7.2
Status: confirmed
Approach: `DFS_WEB_ALLOW_HOST` is read only in `web.py:main()` (`names = args.allow_host + os.environ.get(...)`). The TUI's own server, `tui.py:start_web()` -> `dfs_web.serve(dfs_web.default_host(), ...)`, passes no `allow_hosts`, and `serve()` does `ALLOW_HOSTS.clear()` then fills from its argument, so a TUI-served page bound to the default 127.0.0.1 still answers 421 to a TLS proxy's hostname whatever the env says. The TUI is how the page is normally served (DFS_WEB_HOST is its setting, and it has no `--cert`/`--key` either), so for that user the README's `tailscale serve` route is dead; only a separate `python3 scripts/web.py` works. Fix: have `serve()` (or `start_web`) fall back to `DFS_WEB_ALLOW_HOST` (comma-separated) when `allow_hosts` is not given, keep `--allow-host` additive in `main`, and say in the README that the env var is how the TUI's page takes it. Settle with a test in `test_web.py`/`test_webscreen.py`: with DFS_WEB_ALLOW_HOST set, `serve("127.0.0.1", 0, ...)` answers 200 for the named Host and 421 for another, and with it unset nothing is added.
Determination: Confirmed: `serve()` in `web.py` now adds DFS_WEB_ALLOW_HOST to its `allow_hosts` argument, so the TUI's page admits a proxy's name (new `test_serve_takes_allowed_hosts_from_the_environment` passes: env and flag names 200, others 421, unset adds nothing) and the README says the TUI takes it only as the env var.

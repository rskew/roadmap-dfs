# W47 · Tell from the web page whether a node is complete, started or open

## Goal

On the web page's task tree, every node shows its state in a mark and not only in the colour of its left rule: a tick for a complete (confirmed) node, an empty `o` for an open node not yet started, and a filled-in `o` for an open node whose implementation has started. "Started" is a status the node itself carries: a session marks the node started when it begins to change code for it, and the node's closing commit replaces it with its ruling. From the task page alone, without relying on colour, the author can see which nodes are finished, which are underway and which are not begun.

## Tree

### W47.1 · `started` is a node status that everything treats as open
Status: confirmed
Approach: In `scripts/tree.py` add `started` to `STATUSES` and the Status line's grammar, and make every place that tests for `open` (the current node, the tree being complete, editable nodes, dormant and pruned, the state and the checks in `scripts/state.py` and `scripts/check.py`) treat a started node as an open one. Tests in `scripts/test_tree.py` that go red first.
Determination: Confirmed: `started` is a valid status that `effective` reads as open, so the frontier, completion, dormancy, outline and edit all treat it as open while `nd["status"]` still says started; the new tests went red first and the tree, walk, screen and web suites pass apart from one chat test that fails the same without the change.

### W47.2 · A session marks its node started, uncommitted
Parent: W47.1
Status: confirmed
Approach: Add `tree.py start <node>`, which sets `Status: started` in the working copy without committing, and tell the work briefing to run it before a session changes code for the node. The node's commit then rules it confirmed or refuted as before, so a started node is seen only while a session is on it or after one was cut off mid-node. Check the hook that enforces node commits does not refuse the uncommitted change.
Determination: Confirmed: `tree.py start <task> <node>` rewrites only that node's Status line in the working copy, the work briefing tells a session to run it, and the checker passes both the staged edit of a started node and its ruling (the hook only runs on a commit, so the uncommitted mark is never judged).

### W47.3 · Serve each node's progress from web.py
Parent: W47.2
Status: open
Approach: In `scripts/web.py`, add a `progress` field to each node row: `done` for confirmed, `started` for started, `open` for open, and nothing for refuted, parked, dormant and pruned, which keep their chips.

### W47.4 · Draw the mark on each row
Parent: W47.3
Status: open
Approach: In `scripts/web/index.html`, put a ✓, an empty `o` or a filled `o` before each node's id, with an aria-label saying the state, so the rule's colour is no longer the only signal. The terminal screen's tree gets the same marks if it already shows a status glyph.

### W47.5 · Check it in a browser and document it
Parent: W47.4
Status: open
Approach: A flow in `scripts/ui_flows.mjs` and `scripts/test_ui.py` that opens a task with one confirmed, one started and one open node and sees the three marks; a test in `scripts/test_web.py` for `progress`; a README line saying what the marks and the `start` command mean.

# W131 · Optimise the UX

## Summary

The work measured where the author's time goes from the logs as they stood on 2026-11-05: 50 raises, 21 written by the runner (since stopped) and 29 by sessions. Session raises are long (median 326 words) yet usually answered in a few words, and the 6 that name an answer page were answered faster (median 2.2 hours against 3.4), a hint only. Of 165 artefact pages, 127 can post a ruling and none is empty, but 36 of the 73 Hypothesis pages written since W100 never say what would show their assumption wrong. Changes built, none of which changes what any rule refuses: the raise template in `SKILL.md` opens with a "What I need from you" line (the logs cannot show it helps: the four raises that opened with the ask were answered in 1.8 hours against 3.2, but they ask different things); `scripts/check.py` prints a note when a new or changed Hypothesis's page never says what would show it wrong; in the terminal screen the tree pane's rule now carries the task, status and sessions so an opened node cannot scroll them away, and a closed node's "wrong if" wraps whole instead of ending in an ellipsis; the closed web row shows the "Wrong if" under its one-line verdict. Each was checked by drawing the real screen code into a recording window and the web page's DOM, and the tests that touch them pass (the failures left in `test_web`, `test_chat` and two in `test_tree` fail the same without the change); colour, the real footer, the side panel and how the web row looks stayed unseen because this sandbox cannot draw text. A one-page decision view per task and a link to the code explainer were left unbuilt because the existing views carry the same content.

## Goal

Following from our optimisation of the dfs flow, do some broad research and experimentation into how we can improve the UX around task management. The goals are to enhance user understanding of assumptions and raises, and reducing the time required of the user. In other words, let the user spend less time guiding the process, but enable them to get a deeper understanding of the system in that shorter time.
In focus are things like integration and quality of artefacts, presentation of tasks and nodes, appropriateness and informativeness of raises, and possibly integration if interactive system exploration and design tools, maybe others too (be creative)

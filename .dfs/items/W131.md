# W131 · Optimise the UX

## Summary

The work measured where the author's time goes from the logs as they stood on 2026-11-05: 50 raises, 21 written by the runner (since stopped) and 29 by sessions. Session raises are long (median 326 words) yet usually answered in a few words. The 6 that name an answer page were answered a little faster (median 2.2 hours against 4.9 for the 18 others since the first page raise; a shuffle gives a gap that large 1 time in 10, few raises of one kind can be compared, and the answers are no longer), so it is a lean and not a finding; the raise template now asks for a page on a raise that offers options. Of 165 artefact pages, 127 can post a ruling and none is empty, but 38 of the 73 Hypothesis pages written since W100 never say what would show their assumption wrong. It built, without changing what any rule refuses: a "What I need from you" opening line in the raise template (the logs cannot show it helps); a `check.py` note when a new Hypothesis page never says what would show it wrong; in the terminal screen and web page, a tree-pane rule that keeps the task, status and sessions on screen when an opened node scrolls the title away ("12 sessions since you spoke", shortened and then clipped so it never meets the scroll tag); a closed node's "wrong if" that wraps whole and ends at the test without the answer-page path (also in the assumptions list and accept prompts), and the same "Wrong if" under the closed web row; and a `Code files` line on an opened node listing the code files (not the `.dfs/` planning files) its commits changed, cached by commit and saying how many commits past the first 8 it did not read. One older node's figure, 36 of 73 pages that never say what would show the assumption wrong, stands as written there; the count of 38 is the shipped check's. Each was checked by drawing the real screen code into a recording window and the web page's DOM, and the tests that touch them pass (the failures left in `test_web`, `test_chat` and two in `test_tree` fail the same without the change); colour, the real footer, the side panel and how the web row looks stayed unseen because this sandbox cannot draw text, and an opened node's own "Wrong if" block still shows the page path. A one-page decision view per task was left unbuilt because the task page and the Accept dialog already carry the Summary, each assumption's "Wrong if" and the reviewers' notes, and a link to the code explainer was left unbuilt because notes exist for three files and 8% of node commits touch one; both rest on a small sample (one fixture task, four nodes) and are open to your ruling on their pages.

## Goal

Following from our optimisation of the dfs flow, do some broad research and experimentation into how we can improve the UX around task management. The goals are to enhance user understanding of assumptions and raises, and reducing the time required of the user. In other words, let the user spend less time guiding the process, but enable them to get a deeper understanding of the system in that shorter time.
In focus are things like integration and quality of artefacts, presentation of tasks and nodes, appropriateness and informativeness of raises, and possibly integration if interactive system exploration and design tools, maybe others too (be creative)

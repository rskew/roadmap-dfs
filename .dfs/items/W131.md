# W131 · Optimise the UX

## Summary

The work measured where the author's time goes from the logs as they stood on 2026-11-05: 50 raises, 21 written by the runner (since stopped) and 29 by sessions. Session raises are long (median 326 words) yet usually answered in a few words, and the 6 that name an answer page were answered a little faster (median 2.2 hours against 4.9 for the 18 others since the first page raise; a shuffle gives a gap that large 1 time in 10, few raises of one kind can be compared, and the answers are no longer, so it is a lean and not a finding), and of 165 artefact pages, 127 can post a ruling and none is empty, but 36 of the 73 Hypothesis pages written since W100 never say what would show their assumption wrong. It built, without changing what any rule refuses: a "What I need from you" opening line in the raise template (the logs cannot show it helps) and a line asking for an answer page on a raise that offers options; a `check.py` note when a new Hypothesis page never says what would show it wrong; and, in the terminal screen and web page, a tree-pane rule that keeps the task, status and sessions on screen when an opened node scrolls the title away (it shortens, then clips, so it never meets the scroll tag), a closed node's "wrong if" that wraps whole and ends at the test without the answer-page path (also in the assumptions list and accept prompts), and the same "Wrong if" under the closed web row. Each was checked by drawing the real screen code into a recording window and the web page's DOM, and the tests that touch them pass (the failures left in `test_web`, `test_chat` and two in `test_tree` fail the same without the change); colour, the real footer, the side panel and how the web row looks stayed unseen because this sandbox cannot draw text, and an opened node's own "Wrong if" block still shows the page path. A one-page decision view per task and a link to the code explainer were left unbuilt because the existing views carry the same content.

## Goal

Following from our optimisation of the dfs flow, do some broad research and experimentation into how we can improve the UX around task management. The goals are to enhance user understanding of assumptions and raises, and reducing the time required of the user. In other words, let the user spend less time guiding the process, but enable them to get a deeper understanding of the system in that shorter time.
In focus are things like integration and quality of artefacts, presentation of tasks and nodes, appropriateness and informativeness of raises, and possibly integration if interactive system exploration and design tools, maybe others too (be creative)

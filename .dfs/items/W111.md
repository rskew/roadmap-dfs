Status: confirmed
Approach: Drive the web page (`scripts/web/index.html`) in headless chromium at 1280x800 against the example project: press Esc, arrow keys, j/k, Enter, `/` and `?` from the task list, a task and a node, and a form dialog, recording the hash and the focused element after each key. Each gap becomes a fix node below.
Hypothesis: "Desktop UX" in the Goal means the web page in a desktop-wide browser, not the terminal screen. Wrong if the author meant the terminal screen (`tui.py`), or both. .dfs/artefacts/2397e5d1-b7e1-42c8-9f46-6551eb296221.html
Evidence:
- for: The terminal screen's key table already lists esc as back one level, up/down and j/k, `/` search as you type and `?` for keys (`KEY_TABLE` in `tui.py`), and was reviewed in `docs/tui-ux-review.md`; the Goal's three examples are what the web page lacks.
- for: The headless run found Esc on a task does nothing, j/k on the list do nothing, `/` and `?` do nothing, and the page has no search field.

Determination: Esc from a node to its task works, but Esc on a task does not go to the list, j/k and left/right do nothing on the list, and `/` and `?` do nothing; so the audit finds work on the web page and the node is confirmed.

### W111.3 · Esc on a task goes back to the task list
Parent: W111.1
Status: confirmed
Approach: In the page's keydown handler (`index.html`, the `addEventListener("keydown"` near `j`/`k`), make Escape on a task with no node open call `up()` so it leaves to the list, as it already does from a node to its task. Keep it inert inside dialogs, inputs and the context menu. Check with a flow in `ui_flows.mjs` and `test_ui.py`: Esc from a node lands on the task, Esc again lands on the list, Esc in a form closes only the form.
Determination: Esc now goes node to task to list and closes only a form, shown by the new `escape` flow, which fails with the handler change removed and passes with it; the suite's other failures are the same with and without it (five chat tests fail on the baseline, and `bar_buttons_work_from_chats` fails on two of four baseline runs).

### W111.4 · j/k and the arrow keys step through the list and the tree the same way
Parent: W111.1

### W111.5 · `/` searches the task list and a task's nodes
Parent: W111.1
Status: confirmed
Approach: Add a search field to the task list and to a task, focused by `/` and cleared by Esc, filtering rows by id, title and goal text as you type. Check with a flow that types into it and counts the rows left.
Determination: `/` now focuses a search field heading the list (hides tasks not holding every word of id or goal) and a task (keeps nodes whose id or title hold them, folded ones included); Esc clears and leaves it, Enter moves to the first row left; the new `find` flow passes and fails on the old page, `keys` and `escape` still pass, and the full suite fails the same 23 environmental tests as before. Adding the field made the page scroll on arrow steps, which exposed the middle-control scroll selection stealing focus from the `keys` flow; arrow steps now clear it. This chromium drops all but the last typed character in a field, so the flow sets the text with `fill` rather than typing it, and the screenshot ![the list filtered to one task](.dfs/artefacts/6f0c1d7e-2b3a-4c55-9a10-5d1e7a9b4c21.png) shows the layout only, as this browser draws no text.

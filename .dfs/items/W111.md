# W111 · Audit the desktop UX, things like esc to back out of node then task, arrow keys, searching, etc

## Summary

The web page now has the desktop keys the Goal named. Esc backs out from a node to its task to the list (closing only a form or the search when one is open), j/k and the arrows step through the list and the tree, Left/Right fold nodes, `/` searches the task list and a task's nodes, and `?` lists the keys from the same table the handler reads. The Goal was met for the web page; the terminal screen already had these keys and was left alone, on the reading that "desktop UX" meant the browser. The search flow sets the field's text with `fill` because this test browser drops typed characters, so real typing was not exercised.

## Goal

Audit the desktop UX, things like esc to back out of node then task, arrow keys, searching, etc

### W111.7 · Fix: the list's arrow and j/k handler takes keys from the walk box's selects
Parent: W111.4
Status: confirmed
Approach: In `scripts/web/index.html`, the page-level `addEventListener("keydown"` handler (near `KEYS`) skips only `dialog, input, textarea, [data-grip]` targets. On the task list (`v === "tasks"`) it then calls `e.preventDefault()` and `stepList()` for every j/k/ArrowUp/ArrowDown. The list's walk box (`#walkbox`, `#nextsel` and `#agentsel`, drawn at ~line 808) holds `<select>` elements, so a keyboard user focused on "Next" or "Agent" can no longer change the option with the arrow keys (the default is cancelled and focus jumps to a task), and j/k type-ahead is taken too. Fix: also ignore targets inside `select` (and any other control that uses these keys natively), then add a step to the `keys` flow in `scripts/ui_flows.mjs` that focuses `#nextsel` on the list (walk enabled, with more than one option), presses ArrowDown and checks the select's value changed and focus stayed. Check the flow fails without the guard.
Determination: The page-level key handler now ignores keys pressed in a `select`, so ArrowDown on the walk box's Next select changes its option and j does not move focus to a task; the new step in the `keys` flow fails without that guard ("ArrowDown on the Next select changes its option") and passes with it. The step also showed that changing a walk select redrew the list and dropped focus to the first task, so `drawTasks` now puts focus back on the walk-box control it replaced; `walk` and `walkpin` fail the same way with and without the change (typed digits and list height in this chromium).

### W111.9 · Fix: Esc does nothing on the run log and artefact views, which have a Back button
Parent: W111.3
Status: confirmed
Approach: In `scripts/web/index.html` the page-level keydown handler (near `KEYS`, `addEventListener("keydown"`) returns at `if (!S.task || v !== "task") return;`, so Esc is bound only on the list and a task. The run log (`#/r/...`) and artefact (`#/a/...`) views show the bar's Back button (`chrome()` hides `#back` only on `tasks` and `chats`), and `up()` already handles both (`leaveRun`, `history.back()` / `go(t/<task>)`), but Esc on them does nothing, so "Esc backs out" (the Goal's first example, and the `back` entry in `KEYS`) holds only for node, task and form. W111.1's audit only drove the list, a task, a node and a form, so these views were never checked. Fix: let Esc call `up()` on the `run` and `artefact` views as well (still inert inside dialogs, inputs, selects and the context menu), keep the `back` text in `KEYS` true, and add steps to the `escape` flow in `scripts/ui_flows.mjs`: open an artefact from a task and press Esc to land on the task, and open a run log and press Esc to land where its Back button does. Check the new steps fail without the handler change. Also decide, and write as a Hypothesis, whether `?` should list that Esc applies there.
Determination: Esc now calls `up()` on the run log and artefact views too, landing on the task each was opened from, shown by new steps in the `escape` flow that fail without the handler line ("waitForSelector" times out on the artefact) and pass with it; the `?` entry for Esc now names them, which is a wording the table draws, so it is not a Hypothesis. The `escape` test now runs through `with_runs` so the fixture has a run to open; the full suite fails 10 tests, nine the same without the change and `a_drag_lands_either_side_of_a_break`, which passed on a baseline run and passes twice more with the change.

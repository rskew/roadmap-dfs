# W97 · Workshop how we might optimize our dfs system using existing dfs projects. For example, staticly analysing past behavior, as well as experimenting with changes by re-running old tasks from their initial state. Quality of the design and implementation will be hard to judge but it's the most important factor

## Summary

The work mines what four past dfs projects recorded, replays an old task from its starting point to score a changed system against the original, and ends in `docs/dfs-optimization.md` with five ranked candidate changes and a replay loop to test them. The main finding is that review loops are the cost: 11% of tasks (those with three or more issues rounds) hold 34% of spend, and 41% of spend follows a review that found issues. One candidate (a reviewer that finds more at round one) was tested against the task logs and not shown (3 of 43 later findings were already in the code unchanged). Three replays of one task under the current tool passed the first review twice and failed once, so one replay cannot judge a change, and they were not sealed from the box (the live run logs were readable and three of the four W55 replays were shown the original's conclusions), so that pass rate is an upper bound, and the loop's keep rule needs four more passes of twelve (chance alone keeps a null change 6 to 7% of the time). The path that runs a changed system is tested and ran once, on a harmless one-line change to the skill that every work session read, so the harness can run an arm; no candidate has been through the replay loop, which is real spend ($47 to $83 for a first candidate), and only roadmap-dfs can be replayed from this box. Whether that is enough for the Goal's "experimenting with changes" is the author's call.

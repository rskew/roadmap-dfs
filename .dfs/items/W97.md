# W97 · Workshop how we might optimize our dfs system using existing dfs projects. For example, staticly analysing past behavior, as well as experimenting with changes by re-running old tasks from their initial state. Quality of the design and implementation will be hard to judge but it's the most important factor

## Summary

The work mines what four past dfs projects recorded, replays an old task from its starting point to score a changed system against the original, and ends in `docs/dfs-optimization.md` with five ranked candidate changes and a replay loop to test them. The main finding is that review loops are the cost: 12% of tasks hold 42% of spend, and the bugs found are mostly ones the work did not test for. The Goal was met as a workshop: no candidate has been run through the loop yet, since that is real spend and one replay was too noisy to judge by, and only roadmap-dfs can be replayed from this box.

## Tree

### W97.1 · Inventory what past dfs projects recorded and what each record can answer
Status: confirmed
Approach: Survey the four dfs projects whose history is on this box (roadmap-dfs, chirpstack-docker, house, shop-app): Claude Code transcripts under `$HOME/.claude/projects`, each repo's git history of `.dfs/items` and `.dfs/archive`, and the runner's `dfs_run_*` directories. Write the inventory (source, size, what question it answers, what it cannot) as the first section of `docs/dfs-optimization.md`.
Determination: Transcripts (~2,000 sessions over four projects), runner directories with per-session cost (roadmap-dfs only), task files, git history and 39 old tool versions are on this box, so all four projects can be mined but only roadmap-dfs can be replayed; the table is in `docs/dfs-optimization.md`.

### W97.2 · Mine past sessions into one dataset and report where the work goes
Parent: W97.1
Status: confirmed
Approach: A read-only script, `scripts/history.py`, that joins each session's transcript (tokens, turns, tool calls, guard refusals) to the node it committed and the task it served, across every project in the inventory, and prints the distributions an optimization would move: sessions and tokens per finished task, per node kind, per review round, and the share spent on failure (refused commits, refuted nodes, critic backtracks, re-reads). Findings go in `docs/dfs-optimization.md`.
Hypothesis: What dfs should be optimized for is quality first: how often a task's finished work is found wanting (review rounds with issues, critic backtracks, author corrections, a later task fixing it), with sessions and dollars per task as the cost traded against it. Wrong if the author wants cost, or their own attention (raises, time spent reviewing), as the objective, with quality held as a floor. .dfs/artefacts/21860a14-6904-48d5-8a3c-a10e6df343d6.html
Evidence:
- for: `history.py` over 1,919 sessions: 41.5% of all dfs spend falls on a task after one of its reviews said issues, so the quality failure is also the largest cost.
- for: of 81 review findings in roadmap-dfs's task logs, 32 are bugs the work did not test for and 19 unmarked assumptions; the Goal itself calls quality "the most important factor".
- against: cost and attention are measurable today (runner `total_cost_usd`, 83 raises over 250 tasks) while quality is only measurable through reviews, which are themselves sessions that can miss.
Determination: `scripts/history.py` mines all four projects' transcripts into session and task records with dollar costs matching the runner's to 0.1% at the median, and shows that trees declared finished too early (41.5% of spend after a review found issues) outweigh every other cost, with the tree's branching almost never used.

### W97.3 · Replay an old task from its initial state under a changed system
Parent: W97.2
Status: confirmed
Approach: A harness that rebuilds a finished task's starting point (the repo at the commit before its first node, its task file holding only the Goal), runs a chain on a scratch clone with a chosen roadmap-dfs version, and scores the replay with `history.py`'s `session()` on the same measures as the original. Prove it on one small finished roadmap-dfs task whose first review found issues, since what a change should move is whether the first finished tree passes review.
Determination: `scripts/replay.py` rebuilds W55's starting point, runs the real chain on a scratch clone and scores it beside the original: the replay's first review also found issues (6 sessions and $3.48 against 5 and $1.30), so the harness reproduces the failure it is meant to move, and one replay is too noisy to judge a change by; the table and limits are in `docs/dfs-optimization.md`.

### W97.4 · Rank the optimization candidates and write the experiment loop
Parent: W97.3
Status: confirmed
Approach: From the W97.2 findings and the W97.3 replay, list candidate changes to the skill, law and tooling, each with the evidence for it and the replay that would test it, and write the loop (mine, change, replay, compare) in `docs/dfs-optimization.md`. The loop replays each arm several times, since one replay of W55 cost 2.7 times its original, and bounds a replay's single Bash call, since one sat 53 minutes in `grep -r /`.
Determination: `docs/dfs-optimization.md` section 4 ranks five candidate changes by the spend behind each and writes the loop (mine, choose, change, replay each arm three times, compare per task, keep or drop), and `replay.py` now bounds one Bash call to 15 minutes by default (`--bash-minutes`); the Goal is met as a workshop, and the loop has not yet been run on a candidate.

# W97 · Workshop how we might optimize our dfs system using existing dfs projects. For example, staticly analysing past behavior, as well as experimenting with changes by re-running old tasks from their initial state. Quality of the design and implementation will be hard to judge but it's the most important factor

## Summary

The work mines what four past dfs projects recorded, replays an old task from its starting point to score a changed system against the original, and ends in `docs/dfs-optimization.md` with five ranked candidate changes and a replay loop to test them. The main finding is that review loops are the cost: 12% of tasks hold 42% of spend, and the bugs found are mostly ones the work did not test for. The Goal was met as a workshop: no candidate has been run through the loop yet, since that is real spend and one replay was too noisy to judge by, and only roadmap-dfs can be replayed from this box.

### W97.2 · Mine past sessions into one dataset and report where the work goes
Parent: W97.1
Status: confirmed
Approach: A read-only script, `scripts/history.py`, that joins each session's transcript (tokens, turns, tool calls, guard refusals) to the node it committed and the task it served, across every project in the inventory, and prints the distributions an optimization would move: sessions and tokens per finished task, per node kind, per review round, and the share spent on failure (refused commits, refuted nodes, critic backtracks, re-reads). Findings go in `docs/dfs-optimization.md`.
Hypothesis: What dfs should be optimized for is quality first: how often a task's finished work is found wanting (review rounds with issues, critic backtracks, author corrections, a later task fixing it), with sessions and dollars per task as the cost traded against it. Wrong if the author wants cost, or their own attention (raises, time spent reviewing), as the objective, with quality held as a floor. .dfs/artefacts/21860a14-6904-48d5-8a3c-a10e6df343d6.html
Evidence:
- for: `history.py` over 1,919 sessions: 41.5% of all dfs spend falls on a task after one of its reviews said issues, so the quality failure is also the largest cost.
- for: of 81 review findings in roadmap-dfs's task logs, 32 are bugs the work did not test for and 19 unmarked assumptions; the Goal itself calls quality "the most important factor".
- against: cost and attention are measurable today (runner `total_cost_usd`, 83 raises over 250 tasks) while quality is only measurable through reviews, which are themselves sessions that can miss.
Determination: `scripts/history.py` mines all four projects' transcripts into session and task records with dollar costs matching the runner's to 0.1% at the median, and shows that trees declared finished too early (41.5% of spend after a review found issues) outweigh every other cost, with the tree's branching almost never used.

### W97.3 · Replay an old task from its initial state under a changed system
Parent: W97.2
Status: confirmed
Approach: A harness that rebuilds a finished task's starting point (the repo at the commit before its first node, its task file holding only the Goal), runs a chain on a scratch clone with a chosen roadmap-dfs version, and scores the replay with `history.py`'s `session()` on the same measures as the original. Prove it on one small finished roadmap-dfs task whose first review found issues, since what a change should move is whether the first finished tree passes review.
Determination: `scripts/replay.py` rebuilds W55's starting point, runs the real chain on a scratch clone and scores it beside the original: the replay's first review also found issues (6 sessions and $3.48 against 5 and $1.30), so the harness reproduces the failure it is meant to move, and one replay is too noisy to judge a change by; the table and limits are in `docs/dfs-optimization.md`.

### W97.5 · Fix: a replay runs without the dfs guard, without a git identity, and with the original's answer in its clone
Parent: W97.3
Status: confirmed
Approach: `replay.py prepare` clones into DEST and relies on the clone's `.git/hooks`, but the documented DEST (`/tmp/dfs-replay-W55-a`) is on a noexec mount, so git skipped `pre-commit` and `pre-merge-commit` ("hook was ignored because it's not set as executable" in three of the W55 replay's work sessions): the replay ran with no dfs_check, so it tested a different system from the original, and its `refused commits` is 0 by construction, which voids candidate 4's test. The clone also has no `user.name`/`user.email` ("Author identity unknown" in three sessions, each spending turns to work around it), and `origin` is the live repo, whose `origin/main` holds the original W55 nodes and every later commit, so a session could read the answer (none did in W55's replay, by a search of its tool calls). Fix in `prepare`: refuse a DEST where `.git/hooks/pre-commit` cannot run (or install the hooks so they run), give the clone the original checkout's identity, and remove `origin` and the remote refs after the checkout. `test_replay`'s prepare test checks only that the hook exists, so make it commit something the guard refuses and see the commit fail.
Determination: `replay.py prepare` now refuses a DEST where a script cannot run, gives the clone the checkout's git identity, and seals it (no `origin`, tags, reflog or unreachable objects), with tests that the guard refuses a bad commit and that the later work is absent; the 15 tests pass here, but the W55 replay could not be rerun (no `claude` and no exec-capable mount in this session), so the doc's W55 section is marked void until it is.

### W97.6 · Fix: a replay's score counts failed commits as nodes and can merge other replays' transcripts
Parent: W97.3
Status: confirmed
Approach: `history.session()` treats a commit as made unless its tool result has `is_error`: a refused commit keeps `ok` None and counts, and a command whose commit failed but whose last step succeeded counts too. The W55 replay scored "7 node commits" while its `main` holds 5 (W55.2 and W55.5 were counted twice after "Author identity unknown" failures with `is_error` false), so the doc's "4 against 7" row is wrong. Decide `ok` from the output (git's `[branch sha] subject` line, or the subject in a following `git log`), count a refused commit as not made, and add a `test_history` case for each. Separately, `replay.transcripts()` globs `<encoded dest>*`, so scoring `dfs-replay-W55-1` also takes in `dfs-replay-W55-10`, `-11`, `-12`, the names a 24-replay loop is likely to use; match the exact directory and its `--dfs-worktrees-<task>` worktrees only, and test two replays whose names share a prefix.
Determination: `history.session()` now counts a commit as made only if its result is no error, not a dfs_check refusal and carries none of git's failure lines (unless a `[branch sha]` line shows a retry worked), its subject pattern now reads a quoted `|` before `commit`, and `replay.transcripts()` globs the exact directory plus its `--dfs-worktrees-*` ones, so `-1` no longer takes in `-10`; three new tests fail on the old code and the W55 replay's transcripts now score 5 nodes, as its `main` holds.

### W97.9 · Fix: the findings behind the top candidates are counted by hand, by string, or in-sample
Parent: W97.2
Status: open
Approach: Three figures in `docs/dfs-optimization.md` carry the ranking of candidates 1 and 2 and the hypothesis that the tree does not branch, and none is checkable as stated. (1) "32 bugs the work did not test for, 19 unmarked assumptions, 25 lesser wording" out of 81 review findings: `scripts/history.py` has no code that finds or classifies findings (grep for finding/untested/assumption finds nothing), so the split is a session's own reading, offered as a measurement. Put the 81 findings (task, review line) and each one's class in a file or `history.py` output so a reader can disagree with a row, and say who classified; then recount. (2) "35 `Status: refuted` against 2,350 `Status: confirmed`" counts strings across transcripts, which include every re-read of a task file, the skill's own text and tool output, so it is not a count of node events; and "none of 497 nodes refuted" reads the `Status:` field only, while `tree.py` (`corrections()`) records a critic backtrack or author correction as a refutation in the task's Log (the items directory holds 6 backtracks and 20 corrections, more in the archive). Recount from the task files with their effective statuses, backtracks and corrections included, and restate "the tree does not branch" only to the extent that count supports. (3) "dollars match the runner's to 0.1% at the median" is true by construction: `history.calibrate()` takes the median of `cost/units` per model, and the check then compares the same sessions, so the median error is zero; the honest figures are the 40% at the 90th percentile and the share of spend that is estimated (about 1,350 of 1,919 sessions had no runner price). Re-check with a split (fit on half the priced sessions, error on the other half, and per project), report the estimated share of the 41.5% and of each session kind, and say whether the headline shares move when computed in raw weighted token units instead of dollars. The redo must leave `docs/dfs-optimization.md` sections 1 to 2 stating only what these recounts show.

### W97.10 · Fix: the keep rule and the noise claim rest on one void replay, and the free test goes unrun
Parent: W97.4
Status: open
Approach: Section 4 of `docs/dfs-optimization.md` sets "kept if at least two more first-review passes of twelve, no task worse by more than one of three" and justifies it by "one task replayed to 1.3 and 3.5 dollars". That pair is the original against a replay under a different system (no dfs guard, no git identity, per W97.5), so it measures the difference between two systems, not the spread between two replays of one system; the 2.7x cost and the "harness reproduces the failure" in W97.3's determination rest on the same void run. The threshold has no hypothesis saying what it assumes or what would show it wrong, and with 12 binary outcomes, a 30% base fail rate and a pass/fail judged by another LLM session, two extra passes is within what chance gives. Do not change the threshold on reasoning: after W97.8's guarded W55 replay, run at least two further replays of the same task under the same tool, compare first-review outcome and cost across all three, and write the rule as a Hypothesis (assumed per-replay pass probability, how often two arms of three replays would differ by two of twelve by chance, computed from that) with the observation that would refute it. Also run what section 4's "Next" says goes first and costs nothing: for the tasks with two or more issues rounds, check in the task logs whether round 1's review could have found the later rounds' findings (candidate 3), and record the result and the tasks, so that at least one candidate has been tested against the history before the Goal's "experimenting with changes" is called met by a plan alone.

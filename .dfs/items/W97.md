# W97 · Workshop how we might optimize our dfs system using existing dfs projects. For example, staticly analysing past behavior, as well as experimenting with changes by re-running old tasks from their initial state. Quality of the design and implementation will be hard to judge but it's the most important factor

## Summary

The work mines what four past dfs projects recorded, replays an old task from its starting point to score a changed system against the original, and ends in `docs/dfs-optimization.md` with five ranked candidate changes and a replay loop to test them. The main finding is that review loops are the cost: 11% of tasks (those with three or more issues rounds) hold 34% of spend, and 41% of spend follows a review that found issues; the one candidate tested against the task logs (a reviewer that finds more at round one) was not shown, since 3 of 43 later findings were in the code unchanged. Replays run inside a proot sandbox that hides the live checkout, its run logs, the tool's tables of every task's review findings and the author's agent homes, under the agent the screen is set to, and `replay.py score` reads claude's transcripts and kiro's run logs (credits, not dollars): a claude replay of W55 passed its first review at $2.36 against the original's $1.30, a kiro replay passed it at 5.7 credits, and neither showed the original's conclusions. The loop keeps a change on a lead of four of twelve first-review passes over the control (chance alone keeps a null change 7.4% of the time if a first review passes half the time, 5.8% if it passes 70%); no candidate has been through it yet, which costs $47 to $83 for a first one, only roadmap-dfs can be replayed from this box, codex and opencode replays cannot be scored yet, and proot hides paths without being a security boundary, so whether this is enough for the Goal's "experimenting with changes" is the author's call.

Status: confirmed

The per-agent live tests (test_{claude,codex,kiro,opencode}_chat.py) and test_agent_interrupt.py discover their binary by a version-pinned /nix/store glob, so the stale pins skip the agents that changed. Run each live test against the installed binary via TEST_*, under TMPDIR inside the repo (/tmp is noexec), and record which pass and the exact failure of each that does not. Capture the raw `opencode run --format json` stream and opencode.db schema for 2.1.1 to see how opencode_result/opencode_turns break. This node reads the Goal "chat should work with kiro and codex and opencode and claude" as: the existing chat feature runs a turn and reads the transcript under each agent's current pinned version, measured by the per-agent chat tests.
Determination: codex 0.163.0, claude 2.1.311 and kiro-cli 2.31.1 pass their live chat tests as they are (and test_agent_interrupt passes); only opencode 2.1.1 fails, three of three tests, from three faults: opencode_turns, opencode_exists and the updated-time query in chat.py read the dropped `session`/`message`/`part` tables (2.1.1 keeps `session_v2` and `session_message`, whose `data` holds the text as `content: [{type: text, text}]` and a `type` of user/assistant/idle); `opencode run --format json` ends without a `step_finish` event in 4 of 5 runs, so opencode_result calls a finished answer an error; and `opencode run` now starts a managed `serve --service` on fixed port 49374 that outlives the turn, so a second run under another HOME exits 1 with "port already in use" and the tests' scratch HOMEs collide. The version pins in the tests' binary globs (codex-0.162, opencode-1.18) are stale but only skip, never fail.

### W124.3 · find why opencode's turn sometimes reports the model's socket closed
Parent: W124.2
Status: confirmed
Approach: In about 3 of 8 runs of test_opencode_chat.py a page turn (`run --standalone --format json --session`) ends in an `error` event, "Transport: The socket connection was closed unexpectedly", right after the fake model (test_agent_models.FakeOpenAIModel, an HTTP/1.0 server that streams SSE and closes) was asked. Decide whether the fake server's way of ending the stream (no length, no chunking, close right after `[DONE]`) is what Bun's fetch rejects, by running the same `opencode run --standalone` turn against the model 30 times with and without HTTP/1.1 chunked replies and counting errors; fix whichever side it is (the fake model, or a retry in chat.py if a real endpoint can do it too), then rerun test_opencode_chat.py 8 times.
Determination: The "socket closed" / "Unable to connect" errors were opencode 2.1.1's own private server (`serve --stdio`, started by `run --standalone`) crashing in Bun 1.4.2 with a Bus error 0.3s after start (seen in `--print-logs` stderr of a failing run, never in 30 plain runs against the same fake model), so the HTTP/1.0 fake model was not the cause; run.sh's new opencode_turn runs a turn again, twice at most, only when the stream holds a `Transport:` error and no step_start, and test_chat.py covers it with a stub (59 tests pass). Live test_opencode_chat.py still failed 4 of 8 runs after that, with no crash and no retry in those runs, from a different fault.

### W124.4 · stop opencode's screen and page turns from racing on one store
Parent: W124.3
Status: confirmed
Approach: Find which faults in the live test_opencode_chat.py failures come from the screen's opencode and the page's `opencode run --standalone` turns sharing one opencode.db, by running the file repeatedly with `--print-logs`, a `ps` before each turn and a dump of the stored `session_message` rows on failure. Fix what the evidence names in run.sh (the screen's `opencode` TUI), chat.py (`opencode_turns`) and the retry in `opencode_turn`, with a stub test in test_chat.py for each.
Determination: Two faults, not a race on one store. (2) A user message stored twice (rows 3 ms apart, the page then showing it twice, once with the run's `--print-logs` showing a Bun "Bus error" in `serve --stdio` 1s after start with no other opencode process running) was the W124.3 retry re-sending a message the crashed attempt had already stored: chat.py's `opencode_turns` reads a user message repeated with no row between once, and `opencode_turn` does not run again when the session's store gained an answer (`chat.py --opencode-answers`); test_chat.py covers both (61 pass; the guard test fails without the guard). test_opencode_chat.py then passed 22 of 22 and 6 of 6 full runs, but 4 of 8 in one window with host load 6 to 17, each failing in the screen test with the TUI never storing an answer, so reliability under that load is not shown.

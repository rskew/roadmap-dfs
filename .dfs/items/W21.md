# W21 · Require assumptions to create an interactive artifact to explain and decide an assumption

## Summary

A node that states a Hypothesis now has to name an interactive page for it, `.dfs/artefacts/<uuid>.html`, which explains the assumption and lets the author operate it to decide. SKILL.md and docs/artefacts.md say so, templates/_TEMPLATE_ASSUMPTION.html is the starting page, and check.py refuses a commit that adds, changes or reopens a Hypothesis without a page that exists and has a control with a handler on it. The Goal is met; what the check cannot do is judge whether the page says anything, so a page whose handler changes nothing would pass, and that stays with the author reading it. The check judges only new or changed Hypotheses, so older nodes, including ones whose Hypothesis has since moved to the archive, keep the wording they were committed with.

## Goal

Require assumptions to create an interactive artifact to explain and decide an assumption

### W21.2 · check.py refuses a new Hypothesis that names no interactive artefact
Parent: W21.1
Status: confirmed
Approach: In scripts/check.py add a check run beside check_history: a node that is new in this commit, or whose Hypothesis changed since HEAD, and that states a Hypothesis and is not refuted or parked, must name in that Hypothesis a `.dfs/artefacts/<name>.html` that exists in the index (or working tree without --staged) and is interactive (a control and a handler on it). Nodes already at HEAD with an unchanged Hypothesis are exempt, so the existing W1 to W20 history still commits. Cover it in scripts/test_tree.py: no artefact, a missing file, a static page, an interactive page, an unchanged old Hypothesis, and a parked node.
Hypothesis: A page counts as interactive when it has a control (`<input`, `<button`, `<select`, `<textarea` or `<details`, or one created by `createElement`) and a handler that answers it (`addEventListener(` or an `onclick`-style attribute). Wrong if real interactive pages that authors reasonably write are refused by it, so sessions fight the check instead of drawing the page; that it can be passed by a page that changes nothing is accepted, since only a reader can judge that. The page to operate is .dfs/artefacts/04afa94e-b439-49cd-b5f5-bf194d724c26.html.
Evidence:
- for: check.py's own pages pass it: templates/_TEMPLATE_ASSUMPTION.html and the page above both have a control and a handler, so a session that starts from the template is not refused.
- for: scripts/test_tree.py refuses a missing page, a static page, a button nothing listens to and a listener with no control, and accepts addEventListener, onclick and a createElement control; the parked and unchanged-old-Hypothesis cases are left alone. All 75 tests pass; test_chat and test_web fail the same way without this change (the sandbox has no claude stub).
- against: the page above, clicked headless, shows a handler that changes nothing still passes and CSS-only tabs are refused, so the rule is a floor and cannot tell a good page from a pointless one.
Determination: Confirmed: check.py now refuses a commit that adds, changes or reopens a Hypothesis unless it names an existing `.dfs/artefacts/<name>.html` with a control and a handler, and judges nothing already at HEAD.
Ask: Is a control and a handler the right floor for interactive, or should check.py ask for more (a handler that writes to the page) or less (any script)? I chose control and handler as the cheapest test that refuses a static picture.

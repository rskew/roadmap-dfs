# W75 · Items should be completed in git branches, passing review merges the branch into main/master

## Summary

Each item is now worked on its own branch, `dfs/<task>`, in its own git worktree under `.dfs/worktrees/<task>`, cut from the default branch on the first run, so a walk never switches the checkout the author has open. Every work, critic and review session runs in that worktree, and the screen and web page read the task, list a task never yet committed, and open its pages and the author's attachments through it. A passing review, or the author's accept, rebases the branch onto `main` or `master` and merges it in with `--no-ff` (local, never pushed) and removes the worktree and branch; a rebase or merge that conflicts, a dirty worktree and a hook's refusal reopen the item with a node naming the cause, and the author's overlapping uncommitted edits, or an accept from a checkout off the default branch, are a raise, so no unmerged item ends the chain done. The Goal was met in full; the one gap is that the screen's uncommitted and not-on-origin marks read only the main checkout while a task is in its worktree.

## Goal

Items should be completed in got branches, passing review merges the branch into main/master

### W75.11 · Fix: a passing review whose merge fails for any reason but a conflict or the author's edits is reported done and never merged
Parent: W75.6
Status: confirmed
Approach: In `run.sh`, `merge_item` treats every `branch.py merge` exit other than 3 and 4 as success, so exit 1 (`"dirty"`: the worktree holds uncommitted non-task changes; or a `BranchError`, such as the main checkout no longer on `main`/`master`, or a failed commit) ends the chain `stop: done` with `dfs/<task>` and its worktree left in place, and every later run prints `DONE before run 1` and fails the same way, so the branch is never merged. Checked with test_chain's stub, recipe `work,confirm,rmeddle` (a review that edits `app.txt` and gives `ok`, which the runner notes as "the next session commits it"): the chain stopped `done`, printed "not merged: its worktree holds uncommitted work that is not the task's", had no merge commit and kept the worktree, and a second run did the same. `tree.append_log`'s accept also ignores what `merge()` returns. And when a pre-merge-commit hook refuses the merge, git leaves MERGE_HEAD with no conflicted files (checked: `Not committing merge`, rc 1, MERGE_HEAD present, `--diff-filter=U` empty), which `_unmerged` takes for a conflict: it reopens the item with a "Rebase … and resolve the conflicts: files conflict" node that a rebase cannot settle, and drops the hook's message. Fix: make a merge that did not go through never stop the chain `done`. Reopen with a node that names the actual cause (commit or drop the stray changes, or the guard's message), or raise when only the author can settle it, and tell a hook refusal apart from a conflict (unmerged paths present or not). Add test_chain tests for a dirty worktree after a review `ok` and for a refusing pre-merge-commit hook.
Determination: Confirmed: `branch.py merge` now exits 3 for a dirty worktree (an open node asks for the stray changes to be committed or dropped), a hook's refusal of a clean merge (an open node carries its message; `_unmerged` tells it from a conflict by the unmerged paths) and a refused commit of the task's files, and 4 with a raise when the checkout is off the default branch; `run.sh` treats any other non-zero exit as blocked, so no unmerged item ends the chain `done`; three new test_chain tests (dirty worktree, refusing hook, off-branch raise) pass beside the rewritten review-changes-code test, with test_chain (50), test_tree, test_live, test_init and test_walk green.

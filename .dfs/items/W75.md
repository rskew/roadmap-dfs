# W75 · Items should be completed in git branches, passing review merges the branch into main/master

## Goal

Items should be completed in got branches, passing review merges the branch into main/master

## Tree

### W75.1 · Work each item's branch in its own git worktree, leaving the author's checkout on main
Status: confirmed
Approach: Spike in a scratch repo with the dfs hooks installed: `git worktree add <dir> -b dfs/W1` from main, `tree.py start` and a node commit inside the worktree, then `git merge --no-ff dfs/W1` from the main checkout. Then the same merge against a conflicting change, and against the author's uncommitted edits on main.
Hypothesis: The author keeps the screen and web page open on the main checkout while a walk runs, so an item's branch `dfs/<task>` is worked in a worktree per item (`.dfs/worktrees/<task>`, gitignored), and the walk never switches the author's checkout. Wrong if the author is fine with a walk switching their own checkout between item branches; then switching in place (W75.2) is simpler. .dfs/artefacts/761192a3-2add-4f56-9c0f-4f3b8c1f7f82.html
Evidence:
- for: inside the scratch worktree, `tree.py start W1 W1.1` edited the worktree's task file and left main's untouched, since `work_root()` is the cwd; a session run in the worktree needs no change to write the right file.
- for: `git merge --no-ff -m … dfs/W1` from the main checkout merged (rc 0) with the pre-merge-commit guard clean, while an unrelated file on main had uncommitted edits.
- for: this checkout held 49 uncommitted `.dfs` paths at the session's start (tasks made and edited from the screen); a checkout switched to an item branch carries them onto it, where that item's first session commits them.
- against: main's checkout reads main's copy of the task file, so the screen shows none of the branch's progress until the merge unless reads of that task go to the worktree.
- against: in the worktree the pre-commit guard printed `clean (0 task files)` and committed a task file whose heading named W9; `check.py --staged` run by hand there refused it. Git exports GIT_DIR to a worktree's hooks, and check.py's `git ls-files` from `.dfs/` then takes `.dfs/` for the top of the tree.
Determination: Confirmed: git and the session tools work an item's branch in a worktree as they are, and the merge back runs from the main checkout; the costs are routing that task's reads to the worktree and making the guard see task files inside one.

### W75.2 · Switch the author's checkout to the item branch for each chain
Status: parked
Approach: `run.sh` switches the work root to `dfs/<task>` (cut from main) for the chain and back to main when it stops; the merge runs on `done`. No routing of reads and no second tree.
Determination: Parked: simpler, but the walk would switch the checkout the screen and the author's own uncommitted edits live in, and tasks committed on one item's branch vanish from it while another item runs; taken if the author refutes W75.1's hypothesis.

### W75.3 · Make the pre-commit and pre-merge-commit guard judge task files inside a worktree
Parent: W75.1
Status: open
Approach: In `scripts/hook.sh`, after cd-ing to the toplevel, export `GIT_WORK_TREE` (or unset `GIT_DIR`) so `check.py`'s git calls from `.dfs/` see the worktree's index. Test (in test_tree.py or test_init.py): in a scratch repo with the hooks installed, a commit in a `git worktree` of a task file whose heading names another task is refused, and a clean one passes.

### W75.4 · Item branches write untagged, and the main checkout reads a worked task from its worktree
Parent: W75.3
Status: open
Approach: In `paths.py`, an item branch is `dfs/<task>` and its worktree `.dfs/worktrees/<task>` (gitignored by `init.py`'s `.dfs/.gitignore` and this repo's); `branch_tag()` returns "" on an item branch, so its nodes are plain `W75.n` and merge into main's task file as written, and check.py's writer rule follows. In `tree.py`, `part_path`, `archive_part` and the artefact lookup (`web.py`, `tui.py`) for a task whose worktree exists resolve inside it when read from the main checkout, so the screen, the web page, `--review` answers and the author's accept read and write the branch's copy. Tests in test_tree.py / test_web.py.

### W75.5 · A work chain runs its sessions in the task's worktree, cutting the branch on its first run
Parent: W75.4
Status: open
Approach: In `run.sh`, a chain started from the main checkout on a task with no worktree runs `git worktree add .dfs/worktrees/<task> -b dfs/<task> <default branch>` (reusing an existing `dfs/<task>`), moves the task file's uncommitted state there, and launches every session with cwd = the worktree; the run directory, `meta.json` and the runner's log entries stay where the screen reads them. Test in test_chain.py with the stub agent: a chain's node commits land on `dfs/<task>`, main does not move.

### W75.6 · A passing review merges the item branch into the default branch
Parent: W75.5
Status: open
Approach: A `merge` command (in `tree.py` or a new `branch.py`) merges `dfs/<task>` into the default branch (`main`/`master`, local only, no push) with `git merge --no-ff`, keeping the node commits' subjects in history, then removes the worktree and deletes the branch. `run.sh` calls it when a chain stops `done` after a review `ok`; decide whether the author's accept (screen and web) merges too. Test in test_chain.py.

### W75.7 · A merge that cannot go through reopens the item rather than leaving main half-merged
Parent: W75.6
Status: open
Approach: On a conflict, `git merge --abort` and add an open node to the task: merge the default branch into `dfs/<task>` in the worktree and resolve, which completes the tree again and earns another review. A merge git refuses before starting because the author's uncommitted edits on main overlap it is a raise naming the paths. Tests for both.

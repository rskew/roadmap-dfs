# W136 · code explainer

## Summary

A code explainer now exists: `scripts/explain.py` reads a Python file and draws its call tree, then six lenses (data flow, state, resources, failure, queue, errors handled) with one set of shapes, arrows and a legend on every page. A call is drawn in the tree only when the code fixes its target, so a call on a dict, queue or thread is left out rather than guessed, and a function the notes mark that no drawn call reaches is listed after the entries so it still has its dots. The lens facts a person has to judge are hand-written notes in `docs/explain/`, and the generator fails if a note names a function the code no longer has. Pages exist for the inbox hook, the chat relay and the walk's limit decision (`.dfs/artefacts/cca5687a-1302-4679-b607-918a5d2ba1c1.html`, `.dfs/artefacts/0463d25c-be27-4134-a0da-d148c82a343f.html`, `.dfs/artefacts/f698cb4e-5b23-4cd7-b5b3-2d04ccb889f5.html`). The Goal's "is it useful" is only partly shown: the author of the notes answered 18 questions from the pages (14 fully, 3 partly, 1 missed, gaps since fixed), but no other reader has tried them, and the lenses were not inferred from code because queue and failure facts need judgement.

## Goal

let's prototype a code explainer feature, by doing it for a few selected previous tasks and seeing if it's useful. the goal is to show the code from a few different key perspectives, to enable the user to quickly get a solid understanding of:
- data flow
- state
- resource usage
- failure propagation
- queue behaviour
- errors handled

there should be a top-level presentation of the code, maybe as call trees, to get an overview. then the different lenses, which consistent graphical semantics so the user can learn to read them quickly and accurately.

### W136.2 · Generate each page from the code's call tree plus hand-written lens notes
Parent: W136.1
Status: confirmed
Approach: **The question**
- How is an explainer page made so that it stays true to the code and reads the same for every piece of code?

**What this node does**
- `scripts/explain.py` reads a Python file with `ast` and draws the call tree (who calls whom, inside the named files) as the top-level view.
- A notes file per subject, `docs/explain/<subject>.json`, holds the lens facts a person has to judge: each fact names the function it belongs to, the lens, and one plain sentence.
- The generator writes one self-contained mobile-first HTML page: the call tree first, then one tab per lens, all drawn with one set of shapes, colours and arrows, with the legend on every page.
- `docs/explain.md` defines that grammar: one shape per kind of thing (function, queue, state, resource, error path) and one arrow style per kind of edge (call, data, failure).
- The generator refuses notes that name a function the code no longer has, so a page cannot drift silently.

**How we will know it worked**
- The inbox piece renders (`docs/explain/inbox.json`, the other two pieces follow in their own nodes), and a note naming a missing function makes the generator fail.
- `scripts/test_explain.py` passes.
Determination: `scripts/explain.py` renders the inbox page from its call tree and notes, refuses a note naming a function the code lacks, and `scripts/test_explain.py` passes; the browser check could not read the text in this sandbox, so the page's wording is not yet seen.

### W136.9 · Fix: the call tree resolves calls to the wrong function and is called "true by construction"
Parent: W136.2
Status: confirmed
Approach: `scripts/explain.py` `_resolve` turns any attribute call `x.name(...)` into the one analysed function called `name` when only one has that name and `x` is not in the hand-kept list `os, sys, json, subprocess, shlex`. So calls on dicts, queues, threads and other objects are drawn as calls to the analysed method. Checked by running `read_code` on the shipped notes' files: in `scripts/ptyrelay.py`, `self.relays.get(scope)`, `INTERRUPT.get(...)` and `self.outbox.get(...)` (a `queue.Queue`) all show up as calls to `ChatHost.get`, so the page draws `Relay.interrupt -> ChatHost.get`, `Relay._typist -> ChatHost.get` and `ChatHost.failure -> ChatHost.get`, none of which exist. Each `threading.Thread(...).start()` shows up as a call to `Relay.start`, and in `scripts/walk.py` `self.walk_pr_thread.start()` in `walk_poll_prs` shows up as `HeadlessWalk.start`, which draws a false chain `walk_poll_prs -> HeadlessWalk.start -> WalkMixin.walk_start -> walk_begin`, a cycle that is not in the code. W136.7 put the walk tree's clutter down to `self.event` resolving to `HeadlessWalk.event` (that one is a legitimate subclass call), so these wrong edges went unseen. `docs/explain.md` ("true by construction") and the `explain.py` docstring ("the part a machine can do truthfully") promise a tree the code does not keep, and the tree is the top-level view the Goal asks for. What to do: resolve an attribute call only when the owner is `self`/`cls` (a method of the class, or of a subclass or base in the files read), or a name that is a class or module-level function in the files read; leave every other `x.name()` out rather than guess by the bare name. Add tests to `scripts/test_explain.py` with a dict `.get` and a `Thread(...).start()` next to a same-named analysed method, that fail on the current code; regenerate the three pages in `.dfs/artefacts/` and say in the determination what each tree now shows; fix the two sentences in `docs/explain.md` and the docstring if any guess remains.
Determination: `_resolve` now draws only `f()`, `self.f()` (own class, bases, or the one subclass that defines it), `Class.f()` and `Class(...).f()`, so the relay tree lost its seven false edges (`ChatHost.get` from `Relay.interrupt`, `Relay._answer_first_launch`, `Relay._typist`, `ChatHost.ensure` and `ChatHost.failure`, and `Relay.start` from `Relay.close` and `ChatHost.close_all`) but keeps `ChatHost.ensure -> Relay.start`, the walk tree lost `walk_poll_prs -> HeadlessWalk.start` (and so the false cycle) and `start_chain -> HeadlessWalk.items` but keeps the `self.event` calls into `HeadlessWalk`, the inbox tree is unchanged, and the new `WrongOwners` test fails on the old code and `test_explain.py` passes; the pages are now `.dfs/artefacts/12f89a4c-a1b1-432d-8bea-ec1e4bc3939b.html` (inbox), `.dfs/artefacts/a8e0fa3f-311e-48ac-b75f-aaf482e73c2c.html` (relay) and `.dfs/artefacts/c6b9fbf3-25fc-4c59-9948-0d8d9971efbe.html` (walk), all clean at desktop and 360px, and I read the trees from the code's call lists, not from the pictures.

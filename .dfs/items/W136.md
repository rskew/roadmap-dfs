# W136 · code explainer

## Summary

A code explainer now exists: `scripts/explain.py` reads a Python file and draws its call tree, then six lenses (data flow, state, resources, failure, queue, errors handled) with one set of shapes, arrows and a legend on every page. Lens buttons sit above the tree: a tap lights the functions with a note in that lens, fades the rest, says how many are lit, and shows only that lens's section (picture: ![the inbox page with the Failure lens picked](.dfs/artefacts/ac4b63d8-2e90-4856-bfb7-4d6e49e9f785.png)). A call is drawn only when the code fixes its target; the lens facts a person has to judge are hand-written notes in `docs/explain/`, and the generator fails if a note names a function the code no longer has. Pages exist for the inbox hook, the chat relay and the walk's limit decision (`.dfs/artefacts/6592a532-c7d9-4cc7-8916-f2fe18813d61.html`, `.dfs/artefacts/bc5caeae-c842-400a-be61-d2359755b7a1.html`, `.dfs/artefacts/c94f8e86-4608-44e5-aedc-3bfaa5b1a4d8.html`).

The Goal's "is it useful" is only partly shown. A reader given just a page answered 9 of 18 questions from it, 4 partly and 5 not at all (none confidently wrong), while a reader with only the code answered all 18; the 8 gaps found are fixed. The readers were sub-agents, not people, and no time was measured, so whether the pages are quick to read is not shown. Every lens sentence was also marked against the code by readers other than its writer (193 claims: 173 true, 20 loose, none false, the loose ones reworded).

The explanation is now part of the work: the session that completes a tree updates the notes and renders the page (`SKILL.md`), and the review brief has the reviewer mark each sentence true, loose or false and log the counts. This reads a "round" as the work that ends with the tree complete; if each work session was meant, that is a one-line change. Of the four ways to explore a page, only the lens lights were built, as chosen; the function card, scenario steps and round diff were not.

## Goal

let's prototype a code explainer feature, by doing it for a few selected previous tasks and seeing if it's useful. the goal is to show the code from a few different key perspectives, to enable the user to quickly get a solid understanding of:
- data flow
- state
- resource usage
- failure propagation
- queue behaviour
- errors handled

there should be a top-level presentation of the code, maybe as call trees, to get an overview. then the different lenses, which consistent graphical semantics so the user can learn to read them quickly and accurately.

# W136 · code explainer

## Summary

A code explainer now exists: `scripts/explain.py` reads a Python file and draws its call tree, then six lenses (data flow, state, resources, failure, queue, errors handled) with one set of shapes, arrows and a legend on every page. A call is drawn in the tree only when the code fixes its target, so a call on a dict, queue or thread is left out rather than guessed, and a function the notes mark that no drawn call reaches is listed after the entries so it still has its dots. The lens facts a person has to judge are hand-written notes in `docs/explain/`, and the generator fails if a note names a function the code no longer has. Pages exist for the inbox hook, the chat relay and the walk's limit decision (`.dfs/artefacts/ca2a6ad9-92b8-4d9e-8109-0f864f1841c4.html`, `.dfs/artefacts/9a728687-7eee-4f70-aac7-e1ef0157d02d.html`, `.dfs/artefacts/644aec44-b5c3-4a28-90bd-d811a623d5ed.html`). The Goal's "is it useful" is partly shown: three readers who had not seen the notes wrote 18 questions from the code, a reader with only a page answered 9 from the page, 4 partly and 5 not at all (none confidently wrong), and a reader with only the code answered all 18; so the pages are an honest first look at queue, state and failure, not a replacement for the code, and whether they are quick to read is not shown (no time or step count exists for the page-only reader, and no person has read one), the 8 gaps found are fixed, and the readers were sub-agents, not people, and only the code-only reader's steps were counted, no time. Every lens sentence was also marked against the code by readers other than its writer (193 claims: 173 true, 20 loose, none false, the loose ones reworded). The lenses were not inferred from code because queue and failure facts need judgement.

## Goal

let's prototype a code explainer feature, by doing it for a few selected previous tasks and seeing if it's useful. the goal is to show the code from a few different key perspectives, to enable the user to quickly get a solid understanding of:
- data flow
- state
- resource usage
- failure propagation
- queue behaviour
- errors handled

there should be a top-level presentation of the code, maybe as call trees, to get an overview. then the different lenses, which consistent graphical semantics so the user can learn to read them quickly and accurately.

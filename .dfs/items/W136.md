# W136 · code explainer

## Summary

A code explainer now exists: `scripts/explain.py` reads a Python file and draws its call tree, then six lenses (data flow, state, resources, failure, queue, errors handled) with one set of shapes, arrows and a legend on every page. Lens buttons sit above the tree: a tap lights the functions with a note in that lens, fades the rest, says how many are lit, and shows only that lens's section (picture: ![the inbox page with the Failure lens picked](.dfs/artefacts/ac4b63d8-2e90-4856-bfb7-4d6e49e9f785.png)). A call is drawn only when the code fixes its target; the lens facts a person has to judge are hand-written notes in `docs/explain/`, and the generator fails if a note names a function the code no longer has. Pages exist for the inbox hook, the chat relay and the walk's limit decision (`.dfs/artefacts/e1f24a07-5c6d-4b8e-9a31-7d2c40b6a9f5.html`, `.dfs/artefacts/bc5caeae-c842-400a-be61-d2359755b7a1.html`, `.dfs/artefacts/c94f8e86-4608-44e5-aedc-3bfaa5b1a4d8.html`).

The Goal's "is it useful" is only partly shown. A reader given just a page answered 9 of 18 questions from it, 4 partly and 5 not at all (none confidently wrong), while a reader with only the code answered all 18; the 8 gaps found are fixed. The readers were sub-agents, not people, and no time was measured, so whether the pages are quick to read is not shown. Every lens sentence was also marked against the code by readers other than its writer (193 claims: 173 true, 20 loose, none false, the loose ones reworded).

The explanation is now part of the work: the session that completes a tree updates the notes and renders the page (`SKILL.md`), and the review brief has the reviewer mark each sentence true, loose or false and log the counts. A checksum of each noted function is kept beside the notes (`docs/explain/*.sums`), so `explain.py --drift` lists the functions whose code changed since the notes were last read; the inbox notes had gone stale that way (a new agent-file removal), were corrected by my own reading and not re-marked by another reader. This reads a "round" as the work that ends with the tree complete; if each work session was meant, that is a one-line change. Of the four ways to explore a page, only the lens lights were built, as chosen; the function card, scenario steps and round diff were not.

## Goal

let's prototype a code explainer feature, by doing it for a few selected previous tasks and seeing if it's useful. the goal is to show the code from a few different key perspectives, to enable the user to quickly get a solid understanding of:
- data flow
- state
- resource usage
- failure propagation
- queue behaviour
- errors handled

there should be a top-level presentation of the code, maybe as call trees, to get an overview. then the different lenses, which consistent graphical semantics so the user can learn to read them quickly and accurately.

### W136.26 · Fix: the `.sums` checksums depend on the Python version, so another interpreter flags every noted function as changed
Parent: W136.25
Status: confirmed
Approach: `scripts/explain.py` `_info` stores `hashlib.sha1(ast.dump(node).encode())` as the function's checksum, and `docs/explain/*.sums` commits those values. `ast.dump` output is not stable across Python versions. Checked: with the Python 3.13.5 and 3.14.7 envs `explain.py docs/explain/inbox.json --drift` prints nothing and `test_explain.py` passes; with the Python 3.12.8 env (`/nix/store/0xw7ac8fwklpnnvhb3ckb3b3q5irpryw-python3-3.12.8-env/bin/python3`) `--drift` lists every noted function of inbox as "changed" and `test_the_shipped_notes_are_confirmed_against_the_code` FAILS, with the code untouched. `flake.nix` uses an unpinned `pkgs.python3`, so a nixpkgs bump (or any 3.12 user) gets a failing test and a drift list that is all noise, and the only way out is a blanket `--confirm` with nothing read, which is the rubber-stamp the check exists to prevent. Fix: make the checksum independent of the interpreter, e.g. hash the function's source text with comments, blank lines and indentation normalised (`ast.get_source_segment` then `tokenize` without COMMENT/NL tokens), or hash a version-stable canonical walk of the tree (node class names and field values written out by `_info` itself, not `ast.dump`); regenerate the three `.sums` files; add a test that the checksum of a fixed snippet equals a literal value (so a different Python that changed it would fail in the test, not in the shipped notes), and keep the existing comment/spacing-do-not-count test. Verify by running `test_explain.py` and `--drift` for all three notes files under the 3.12, 3.13 and 3.14 envs above.
Determination: The checksum is now made by `explain.py`'s own walk of the syntax tree (class and field names, empty fields left out), not `ast.dump`, so it is the same on Python 3.12.8, 3.13.5 and 3.14.7: a new test pins a fixed function to a literal checksum, I regenerated the three `.sums` files from sources unchanged since the last `--confirm`, `--drift` is empty for all three notes under each of the three interpreters, and `test_explain.py` (24) passed under each.

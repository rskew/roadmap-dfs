# W136 · code explainer

## Goal

let's prototype a code explainer feature, by doing it for a few selected previous tasks and seeing if it's useful. the goal is to show the code from a few different key perspectives, to enable the user to quickly get a solid understanding of:
- data flow
- state
- resource usage
- failure propagation
- queue behaviour
- errors handled

there should be a top-level presentation of the code, maybe as call trees, to get an overview. then the different lenses, which consistent graphical semantics so the user can learn to read them quickly and accurately.

## Tree

### W136.1 · Pick three finished pieces of code to explain
Status: confirmed
Approach: **The question**
- Which few earlier tasks give the explainer something to show on every one of the six lenses?

**What this node does**
- Read the function lists of the code the earlier tasks touched and choose three pieces that between them cover data flow, state, resource usage, failure propagation, queue behaviour and errors handled.
- `scripts/inbox.py` (task W104, a message sent to a running agent): the queue (waiting, claimed, delivered), the page-to-hook data flow, and the hook errors.
- `Relay` and `ChatHost` in `scripts/ptyrelay.py` (tasks W17 and W90, chat sessions): a pty, a child process and threads per chat, the idle reaper, and a child that dies.
- `walk_decide` and the walk bookkeeping in `scripts/walk.py` (task W132, stop at a usage limit): how a run's stop cause becomes hold, stop or go on, and the walk's state.

**How we will know it worked**
- Each lens has at least one real thing to show in at least two of the three pieces.
Determination: The three pieces are `scripts/inbox.py`, `Relay` and `ChatHost` in `scripts/ptyrelay.py`, and `walk_decide` with the walk state in `scripts/walk.py`; their function lists show every lens at least twice.

### W136.2 · Generate each page from the code's call tree plus hand-written lens notes
Parent: W136.1
Status: started
Approach: **The question**
- How is an explainer page made so that it stays true to the code and reads the same for every piece of code?

**What this node does**
- `scripts/explain.py` reads a Python file with `ast` and draws the call tree (who calls whom, inside the named files) as the top-level view.
- A notes file per subject, `docs/explain/<subject>.json`, holds the lens facts a person has to judge: each fact names the function it belongs to, the lens, and one plain sentence.
- The generator writes one self-contained mobile-first HTML page: the call tree first, then one tab per lens, all drawn with one set of shapes, colours and arrows, with the legend on every page.
- `docs/explain.md` defines that grammar: one shape per kind of thing (function, queue, state, resource, error path) and one arrow style per kind of edge (call, data, failure).
- The generator refuses notes that name a function the code no longer has, so a page cannot drift silently.

**How we will know it worked**
- The inbox piece renders (`docs/explain/inbox.json`, the other two pieces follow in their own nodes), and a note naming a missing function makes the generator fail.
- `scripts/test_explain.py` passes.
Determination: `scripts/explain.py` renders the inbox page from its call tree and notes, refuses a note naming a function the code lacks, and `scripts/test_explain.py` passes; the browser check could not read the text in this sandbox, so the page's wording is not yet seen.

### W136.8 · Judge whether the pages help
Parent: W136.7
Status: open
Approach: **The question**
- Does reading a page get someone to a right answer about the code faster than reading the code?

**What this node does**
- Once all three pages exist, write six questions per piece, one per lens, whose answers are known from the code and from the earlier tasks' review findings (for example, W104.15: a hook inside a subagent must not claim a message).
- Answer each from the page alone, then check the answer against the code; list what the page left out or got wrong.

**How we will know it worked**
- A table of question, answer from the page, true answer, and whether the lens showed it. Pages that miss a lens fact are fixed or the grammar is changed.

# W59 · Option to run sandbox in docker daemon mode to start automatically on reboot

## Summary

`sandbox daemon [command args]` now runs the sandbox detached with the container engine's `--restart unless-stopped`, so it starts again when the host reboots (default command: the repo's app command), and `sandbox stop` removes it. The nix sidecar is restarted the same way, and its socket now lives in `.container-state/nix-proxy` and is mounted as a directory so a restarted sidecar is picked up in either start order. The Goal is met in the script and README; it was checked against a stub engine, not a real reboot, since no docker daemon was available. It relies on the engine being enabled at boot and on the tool's store paths surviving garbage collection; a systemd-unit alternative was left aside.

## Goal

Option to run sandbox in docker daemon mode to start automatically on reboot

## Tree

### W59.1 · `sandbox daemon`: detached containers with a restart policy
Status: confirmed
Approach: Add a `daemon` mode to scripts/sandbox.sh: `sandbox daemon [command args...]` runs the command (default: CONTAINER_APP_CMD, as the container's main process) in a detached container started with `--restart unless-stopped` and without `--rm`, so the engine brings it back on reboot until `sandbox stop` removes it. The nix proxy sidecar gets the same policy and stays up after the script exits (no EXIT trap); its socket directory moves from a mktemp dir under XDG_RUNTIME_DIR (wiped on reboot) to `.container-state/nix-proxy`, and the main container mounts that directory rather than the socket file, so a restarted sidecar's new socket is seen and start order does not matter. Add `sandbox stop` (removes both containers) and document both in the header and README. Check with a stub `docker` on PATH in scripts/test_sandbox.py asserting the arguments, plus `bash -n`.
Determination: Confirmed against a stub engine only: scripts/test_sandbox.py (9 tests, passing) shows daemon mode passes `-d --restart unless-stopped` and no `--rm` to both containers, keeps the sidecar after the script exits, replaces an earlier daemon, cleans up a failed start, and `stop` removes both, while the ordinary modes stay `--rm`; no docker daemon runs in this environment, so a real reboot was not tried.

### W59.2 · Generate a systemd unit instead of using the engine restart policy
Status: parked
Approach: `sandbox daemon` would write a user systemd unit that runs the foreground sandbox, enabled with `systemctl --user enable`, so boot start does not depend on the engine's restart policy.
Determination: Parked: it adds a second supervisor and a systemd dependency, while docker's `--restart unless-stopped` already does this wherever the docker service is enabled at boot; take it up if the restart policy proves unreliable (e.g. rootless podman without podman-restart.service).

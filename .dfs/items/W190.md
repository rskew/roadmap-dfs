# W190 · The in app chat seems to go out of sync when things like limits are hit, it just hangs and does nothing with a new message

## Summary

A page chat that runs as a background claude on the terminal screen now notices when claude stops at its usage-limit menu. The chat state reports the limit and its reset time, so the page shows its limit line, and the next message gets an Esc first so claude submits it and answers that the limit is hit, instead of the message being lost in the menu. The limit is dropped again once claude answers a message with no sign of it, so a reset time in a zone the code cannot read, or a limit lifted early, no longer leaves the line up. The Goal was met for claude's background chat, the one a real chat log showed hanging; this was checked with a stub that draws the menu text, not with a real claude at its limit. It assumes claude writes the menu's words as one run of bytes, and answers a message at its limit within 10 seconds in words the limit check knows ("hit your ... limit"); every real answer found fits, but a different wording or a slower answer would drop the limit line too early. A limit menu in codex, opencode or kiro background chats is not read, since none was seen, and headless page turns already reported a limit before this.

## Goal

Determination: The real log `.dfs/runs/chat/W68.log` shows claude answering "You've hit your session limit · resets 5:20pm (UTC)" and then sitting at its `/rate-limit-options` menu; `Relay` types the page's next message into that menu, claude records nothing, so `Chats.state` keeps the message as sent and unanswered with no `backend` limit, which is the hang.

Add a stub test in `scripts/test_ptyrelay.py`: a stub that shows the menu with a non-UTC "resets" text, then answers a message normally after Esc, must end with `relay.limit` None. ### W190.6 · Minor findings from the review

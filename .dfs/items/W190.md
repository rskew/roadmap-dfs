# W190 · The in app chat seems to go out of sync when things like limits are hit, it just hangs and does nothing with a new message

## Summary

A page chat that runs as a background claude on the terminal screen now notices when claude stops at its usage-limit menu. The chat state reports the limit and its reset time, so the page shows its limit line, and the next message gets an Esc first so claude submits it and answers that the limit is hit, instead of the message being lost in the menu. The Goal was met for claude's background chat, the one a real chat log showed hanging; this was checked with a stub that draws the real menu text, and not with a real claude at its limit. A limit menu in codex, opencode or kiro background chats is not read, since none was seen, and headless page turns already reported a limit before this.

## Goal

The in app chat seems to go out of sync when things like limits are hit, it just hangs and does nothing with a new message

## Tree

### W190.1 · Find which chat path hangs when the agent hits a usage limit
Status: confirmed
Approach:
- **The question**: when an agent hits a usage limit, which chat path stops answering new messages?
- **Why it matters**: a page turn (`Chats.turn`, one headless run per message) already reports a limit as an error and a `backend` state. The page's other path is the background chat (`ptyrelay.Relay`, an interactive agent on a pty), which the web page uses whenever the terminal screen serves it.
- **What this node does**: read the chat logs under `.dfs/runs/chat/` for a limit, and read `chat.py` and `ptyrelay.py` for what the page does with a chat that is stuck.
- **How we will know it worked**: the stuck state is seen in a real log, and the code path from it to a hung page is named.
Determination: The real log `.dfs/runs/chat/W68.log` shows claude answering "You've hit your session limit · resets 5:20pm (UTC)" and then sitting at its `/rate-limit-options` menu; `Relay` types the page's next message into that menu, claude records nothing, so `Chats.state` keeps the message as sent and unanswered with no `backend` limit, which is the hang.

### W190.2 · Make a background chat see the limit menu, show the limit, and get past the menu
Parent: W190.1
Status: confirmed
Approach:
- **The question**: can `Relay` tell that claude is at its limit menu, report it as the chat's `backend` limit, and press Esc before typing a message so the message is submitted and recorded?
- **Why it matters**: the page then shows the limit as soon as it is hit, and a message sent anyway is recorded by claude with its "hit your limit" reply, so the page and the agent agree and nothing hangs.
- **What this node does**: in `scripts/ptyrelay.py`, `Relay` notes when the screen shows "What do you want to do?" with "Stop and wait for limit to reset" and keeps the `resets ...` text from it; `_typist` writes Esc and waits for the redraw when that menu is up. `ChatHost`, `work.py` and `tui.py` get a `chat_limit(scope)` that returns it, and `Chats.state` in `scripts/chat.py` returns it as `backend` for a live chat. Tests in `scripts/test_ptyrelay.py` (a stub agent that draws the menu from the real log) and `scripts/test_chat.py`.
- **How we will know it worked**: the stub test is red without the change (the message is typed into the menu) and green with it (Esc first, then the message), and `state()["backend"]` carries the limit and its reset time.
Hypothesis: The hang the Goal describes is claude's limit menu in a page chat, and Esc leaves that menu at its prompt so a message typed after it is submitted. Wrong if Esc does not leave the menu in a real claude, or if the hang the author sees is on another path. .dfs/artefacts/87ec73ff-9dd2-44c6-a1b7-df60e3d63839.html
Evidence:
- for: `.dfs/runs/chat/W68.log` shows the menu drawn on the agent's screen after the limit answer, with "Esc to cancel" printed on it.
- for: the stub test of a message sent while the menu is up is red without the change (nothing typed after 15s) and green with it; a message typed with the menu up reaches the prompt only after Esc.
- against: no real claude at its limit was available here, and the stub is built from the real log's text, so Esc leaving the menu in a real claude is read from the menu's own "Esc to cancel" and not run.
Determination: A background claude chat at its limit menu now shows as `backend` with the reset time and gets Esc before the next message is typed, so the message reaches the prompt; the new stub tests pass (red without the change), and no other relay or chat test changed result, but a real claude at its limit was not run.

### W190.3 · Fix: a chat's limit set from the menu is never cleared by the chat working again
Parent: W190.2
Status: confirmed
Approach: `Relay.limit` in `scripts/ptyrelay.py` returns the limit from the moment `_follow_limit` sees the menu until `limit_reset_at` passes, and nothing else clears `limit_at`. `Esc` only clears `limit_menu`. The headless path is different: `Chats.backend` and `Chats.turn` drop the limit once a later turn goes by without hitting one. Two cases keep the page's "has hit its usage limit" line up while the agent answers fine. (1) `limit_reset_at` is None, because `limit.reset_at` only reads "(UTC)" times (checked: `reset_at('resets 5:20pm (Europe/Berlin)', now)` is None). Then `Relay.limit` holds for the whole life of the relay. (2) The limit lifts before the printed reset time (for example the user resets it with claude's own option). Then the line stays until the clock passes the old time. Fix it so that the limit is dropped once claude is seen working past it: for example, clear `limit_at` when the agent draws its prompt or any new output after Esc and a typed message with no menu drawn again, and keep it when the menu is drawn again. Add a stub test in `scripts/test_ptyrelay.py`: a stub that shows the menu with a non-UTC "resets" text, then answers a message normally after Esc, must end with `relay.limit` None. Another stub that shows the menu again after the message must keep it. Also state as a Hypothesis, with its page, that claude's raw output holds "Stop and wait for limit to reset" as one run of bytes (the real log `.dfs/runs/chat/W68.log` shows it that way after the escapes are stripped, but no raw capture was read; the stub test draws it plain, so it cannot fail on this).
Hypothesis: Claude's raw terminal output holds "Stop and wait for limit to reset" as one run of bytes, which is what `_follow_limit` matches. Wrong if a real claude draws those words with cursor escapes between them: then the menu is never seen, and the match must run on the screen text instead. .dfs/artefacts/001236e5-1dfe-41f5-801b-3d2682aa1ff8.html
Evidence:
- for: the real log `.dfs/runs/chat/W68.log` shows the words whole after its escapes were stripped, which is also how `chatlog.screen_text` would show a split drawing, so it does not decide the matter.
- against: no raw capture of a real claude was read, and the stub test draws the words plain, so it cannot fail on this.
- for (the fix): with the reset text `resets 5:20pm (Europe/Berlin)` the old relay kept `limit` for good after a message was answered (a script run showed it still set 8s later); with `_probe_limit` the new test sees it None. The test where the stub draws the menu again keeps the limit.
Determination: A chat at a limit now drops it when claude answers a message without saying it is still at its limit (`_probe_limit`), and keeps it when the menu or a "hit your limit" answer comes back; the two new stub tests pass and the other relay and chat tests are unchanged, but a real claude's raw bytes for the menu were not read.
Explained on `.dfs/artefacts/70d710f8-20fc-4f8a-9ebe-b0f513ae400f.html`.

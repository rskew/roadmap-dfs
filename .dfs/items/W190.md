# W190 · The in app chat seems to go out of sync when things like limits are hit, it just hangs and does nothing with a new message

## Goal

The in app chat seems to go out of sync when things like limits are hit, it just hangs and does nothing with a new message

## Tree

### W190.1 · Find which chat path hangs when the agent hits a usage limit
Status: confirmed
Approach:
- **The question**: when an agent hits a usage limit, which chat path stops answering new messages?
- **Why it matters**: a page turn (`Chats.turn`, one headless run per message) already reports a limit as an error and a `backend` state. The page's other path is the background chat (`ptyrelay.Relay`, an interactive agent on a pty), which the web page uses whenever the terminal screen serves it.
- **What this node does**: read the chat logs under `.dfs/runs/chat/` for a limit, and read `chat.py` and `ptyrelay.py` for what the page does with a chat that is stuck.
- **How we will know it worked**: the stuck state is seen in a real log, and the code path from it to a hung page is named.
Determination: The real log `.dfs/runs/chat/W68.log` shows claude answering "You've hit your session limit · resets 5:20pm (UTC)" and then sitting at its `/rate-limit-options` menu; `Relay` types the page's next message into that menu, claude records nothing, so `Chats.state` keeps the message as sent and unanswered with no `backend` limit, which is the hang.

### W190.2 · Make a background chat see the limit menu, show the limit, and get past the menu
Parent: W190.1
Status: started
Approach:
- **The question**: can `Relay` tell that claude is at its limit menu, report it as the chat's `backend` limit, and press Esc before typing a message so the message is submitted and recorded?
- **Why it matters**: the page then shows the limit as soon as it is hit, and a message sent anyway is recorded by claude with its "hit your limit" reply, so the page and the agent agree and nothing hangs.
- **What this node does**: in `scripts/ptyrelay.py`, `Relay` notes when the screen shows "What do you want to do?" with "Stop and wait for limit to reset" and keeps the `resets ...` text from it; `_typist` writes Esc and waits for the redraw when that menu is up. `ChatHost`, `work.py` and `tui.py` get a `chat_limit(scope)` that returns it, and `Chats.state` in `scripts/chat.py` returns it as `backend` for a live chat. Tests in `scripts/test_ptyrelay.py` (a stub agent that draws the menu from the real log) and `scripts/test_chat.py`.
- **How we will know it worked**: the stub test is red without the change (the message is typed into the menu) and green with it (Esc first, then the message), and `state()["backend"]` carries the limit and its reset time.
Hypothesis: The hang the Goal describes is claude's limit menu in a page chat, and Esc leaves that menu at its prompt so a message typed after it is submitted. Wrong if Esc does not leave the menu in a real claude, or if the hang the author sees is on another path. .dfs/artefacts/87ec73ff-9dd2-44c6-a1b7-df60e3d63839.html
Evidence:
- for: `.dfs/runs/chat/W68.log` shows the menu drawn on the agent's screen after the limit answer, with "Esc to cancel" printed on it.
- against: no real claude at its limit was available here, so Esc leaving the menu is read from the menu's own text and not run.

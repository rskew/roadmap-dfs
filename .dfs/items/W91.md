# W91 · Parallel workers

## Summary

A walk now takes a second number beside its budget, the chains to run at once (default 1). Each free slot takes a task of its own, a task left on its cap or a limit first and then the order, with a task under another waiting until its parent is done and its chain has merged, the walk's continuation included, all sharing the one budget; merges and worktree cuts take turns under a lock. The `w` prompt and `:walk` read `20 3`, the header names every live chain, and the web page's Start form has a "Chains at once" field with the chains listed. Where no worktree is cut (the checkout is off main or master, or has no commit) at most one chain without a worktree runs at a time, since chains would otherwise share the one checkout, and a task that already has a worktree takes a slot beside it; each chain's unfinished work is briefed as its own in its worktree or the one checkout, whatever the others do. The Goal was met in full, with four choices of mine for the author to read: a new chain's cap is an even share of the budget not already reserved by live chains, at most 16 chains run at once, a task left on its cap goes before the order, and stopping one chain by hand is a walk stop that turns the walk off and ends every chain after its run. The screen's curses tests could not run here, so the prompt and badge are covered by unit tests rather than a live terminal.

## Goal

Enable multiple tasks to be worked on at once. Now safe due to tasks being actioned in worktrees. Add a second option to a walk, the number of parallel sessions

### W91.3 · The walk runs up to `parallel` chains at once
Parent: W91.2
Status: confirmed
Approach: In `walk.py`'s `WalkMixin`, `walk_begin(budget, parallel=1)` sets `walk_parallel`, and one record per chain the walk started (run dir, start time, that task's own `dfs_state.content` entries, whether it was pinned) replaces `walk_dir`, `walk_started`, `walk_content` and `walk_chain_pin`. `walk_tick` judges each ended chain with `walk_decide` (moved = that task's content grew), then fills `walk_parallel - len(live work chains)` slots from `dfs_state.next_items(items, free, busy=tasks with a live chain, first=pin or data["next_item"])`; a chain started by hand fills a slot and its task is busy. A new chain's cap is `(budget - spent - sum of live walk chains' caps) // free slots`, at least 1 and none when nothing is left, so the budget stays a hard bound; a task whose chain ended `cap` or `limit` and is still open goes first next time, so a share-capped chain is carried on rather than left. A `limit` holds new starts while live chains run on; a `stop`, `walk_end_chain` and `walk_off` lower every live walk chain to its current run (`lower_cap`); a pin takes the next free slot, and with none free lowers the most recently started walk chain. `parallel=1` behaves as today. Tests in `test_walk.py` (two slots fill with two tasks, the caps sum to the budget, one chain ending refills its slot, a stop ends both).
Determination: `WalkMixin` keeps one record per chain and fills `walk_parallel` slots through `next_items`, with caps that sum to at most the remaining budget, each chain judged by its own task's content (`state.full()` now gives `contents` per task), and a stop, hand-stop or pin lowering the live chains; 14 new `test_walk.py` tests and one in `test_walker.py` pass with the rest of the walk, screen, order and chain suites (the chat-stub and hook tests that run from `/tmp` fail the same on main).

### W91.6 · Fix: a child task starts while its done parent's chain is still merging
Parent: W91.2
Status: confirmed
Approach: `state.next_items`'s `held(it)` holds a task only under an ancestor whose status is `open` (and not a draft). But a task's status turns `done` at its review `ok`, before its chain merges it: `run.sh` reads `done` and only then calls `merge_item` (`branch.py merge`, which can still fail and reopen the task with a conflict node, exit 3). Throughout that gap the parent's chain is live and the parent is in `busy`, but `held` never looks at `busy`. Checked: with A done and in `busy`, and B a child of A, `next_items(walk([A done depth 0, B open depth 1, C open depth 0]), 2, busy={"A"})` returns `["B", "C"]`. A headless walk reloads every 2 s, so when a slot is free the child is taken as soon as the parent's review lands. Its `branch.py enter` can take `dfs-branch.lock` before the parent's merge does, so the child's worktree is cut from a default branch without the parent's work, and if the merge then reopens the parent, the child runs beside an open parent. Fix: an ancestor that is in `busy` holds its subtree as well (or any ancestor still on an item branch, i.e. with a worktree). Add a `test_order.py` case for a done-but-busy parent, and a `test_walk.py` tick in which a parent's chain is live with the parent `done`, and check that the child is not started.
Determination: `state.next_items` now holds a task under any ancestor in `busy`, done or not, so a child waits for its parent's chain to finish merging; the two new tests (`test_order.py`, and a `test_walk.py` tick with a live chain on a done parent) fail without the change and pass with it, with the other 170 order, walk and walker tests.

### W91.7 · Fix: a parallel walk where no worktree is cut runs its chains in one checkout
Parent: W91.3
Status: confirmed

A task that already has a worktree may keep its slot. Add a `test_walk.py` test, and update README's Parallel walks paragraph to say what happens there.
Determination: `paths.gets_worktree` (now also what `branch.enter` asks) says whether a task is worked in a worktree, and `walk_tick` starts at most one chain without one at a time while chains with one run beside it, `walk_begin` says so for a parallel walk where none is cut, and README says it; the two new `test_walk.py` tests pass with the walk, walker, order and chain suites (74 chain tests, 4 minutes).

### W91.8 · Fix: the walk's carry list restarts a task that was made a draft, or that the order now holds
Parent: W91.3
Status: confirmed
Approach: `walk_judge` puts any task whose chain ended `cap` into `walk_carry`. `walk_lead` filters the carry only by `status == "open"`, and `next_items` puts lead tasks first with no `reachable`, draft or `held` check. `walk_draft_marked` ends a chain by lowering its cap, so that chain ends `cap` and its task, now a draft, is carried and started again at once. Checked with `test_walk.Ticks`: with W7's chain live, `walk_draft_marked("W7")` lowers it to run 3. Then, with W7 marked `draft=1` and the chain ended `stop="cap"`, the next `walk_tick` starts `("W7", "17")`, a fresh chain on the draft. On main, `continue_last` refused a draft, so this is a regression even at `parallel` 1. The same unchecked carry restarts a task that an ancestor's raise or a fence now holds. Fix: carry only a task that is still workable (open, reachable, not a draft unless the author pinned that chain, as `test_a_pinned_draft_whose_chain_hits_a_limit_is_resumed_after_the_hold` requires). Add the probe above as a test.
Determination: `walk_lead` now carries a task only while it is open, reachable, not held by an open or busy ancestor, and not a draft unless the author pinned it (`walk_carry_pinned`), so a task made a draft mid-chain is no longer restarted; three new `test_walk.py` tests (two fail without the filter, the third keeps a pinned draft carried through two caps) pass with the other 169 walk, order and walker tests.

### W91.9 · Fix: with a gitignored roadmap, a parallel chain's own unfinished work is briefed as another task's
Parent: W91.3
Status: confirmed
Approach: `state.foreign_dirt(task)` (used by `brief` and by `run.sh --foreign-dirt` at chain start) attributes the uncommitted paths outside `.dfs/` to the task with the latest session over every task (`latest_session`), on the premise in its docstring and in run.sh's "SERIAL, SO THE DIRT HAS AN OWNER" that agents work serially. With a gitignored `.dfs/`, every item worktree links the main checkout's `items` (`branch.share_ignored_state`), so a session in A's worktree sees B's session entries from a parallel chain. When A's last session ended mid-node (on a cap, or cut off), A's next brief, which `run.sh` builds before logging A's own `session` entry, names that dirt "NOT this task's: the last session was B's" and has it committed or stashed as foreign. Fix: inside an item worktree, the dirt is that task's own (or nobody's) whatever other tasks did, so `foreign_dirt` should ask only that task's sessions there, or the owner should be looked up per checkout. Correct the "serially" comments to match. Add a test with an ignored roadmap, two tasks, and B's session logged after A's.
Determination: `state.foreign_dirt` now asks only the task's own sessions when the checkout is that task's item branch, so another task's later session no longer makes a worktree's dirt foreign, and its docstring and `run.sh`'s comment no longer say agents work serially; the new `test_chain.py` test fails without the change and passes with it, the old foreign-dirt test now runs in place (where tasks do take turns), and the chain, walk, walker and order suites pass.

### W91.12 · Fix: the walk's continuation starts a child while its done parent's chain is still merging

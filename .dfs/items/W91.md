# W91 · Parallel workers

## Summary

A walk now takes a second number beside its budget, the chains to run at once (default 1). Each free slot takes a task of its own, the walk's continuation first and then the order, with a task under another waiting for its parent, all sharing the one budget, and merges and worktree cuts take turns under a lock. The `w` prompt reads `20 3`, the header names every live chain, and the web page's Start form has a "Chains at once" field with the chains listed. The Goal was met in full; the cap on chains at once is 16, a limit the author did not ask for, and the screen's curses tests could not run here, so the prompt and badge are covered by unit tests rather than a live terminal.

## Goal

Enable multiple tasks to be worked on at once. Now safe due to tasks being actioned in worktrees. Add a second option to a walk, the number of parallel sessions

### W91.1 · Serialise the chains' git steps on the main checkout
Status: confirmed
Approach: `branch.py merge` (rebase in the worktree, `merge --no-ff` in the main checkout, worktree removal) and `branch.py enter` (`worktree prune`, `worktree add -b`) each run under an exclusive `fcntl.flock` on a file in the git common dir, so two chains finishing at once merge one after the other instead of one failing on `index.lock` and being raised as "your uncommitted edits stop the merge". Check: a test in `test_chain.py` or `test_tree.py` that runs two merges of two finished tasks concurrently and sees both merged.
Determination: `branch.py`'s `enter`, `merge` and `release` now run one at a time under `dfs-branch.lock` in the git common dir; the new `test_chain.py` test sees a merge wait while the lock is held (and fail that assertion with the lock removed) and then merge, and the other 74 chain tests pass.

### W91.2 · Choose the items that fill the walk's free slots
Parent: W91.1
Status: confirmed
Approach: `state.py` gains `next_items(walked, n, busy)`: up to `n` workable tasks, `continue_last`'s answer first, then preorder, skipping tasks with a live chain (`busy`) and tasks under an ancestor that is not yet done. `full()` keeps `next_item` as the first of them. Tests in `test_order.py` or `test_walk.py`.
Hypothesis: A task nested under another in `order.md` waits for that parent (any open, non-draft ancestor) to be done before a parallel walk takes it, as one chain at a time already does; separate branches run together. Wrong if nesting only groups tasks for raises and the author wants a child worked while its parent is. .dfs/artefacts/efef401a-025c-4ba4-85e8-ed00d94204fd.html
Evidence:
- for: `state.py` `walk`'s docstring says "a child is work that only makes sense under its parent", and `continue_last` keeps one chain on a task until it is done or blocked, so with one chain a child already starts only after its parent.
- for: `order.md`'s prose gives a break as "the one thing nesting cannot say", so nesting alone does not order separate branches: they are the ones `next_items` runs together.
Determination: `state.next_items` picks up to `n` tasks (the walk's continuation first, then the order, skipping busy tasks and tasks under an open non-draft ancestor), and three new `test_order.py` tests pass with the other 81.

### W91.3 · The walk runs up to `parallel` chains at once
Parent: W91.2
Status: confirmed
Approach: In `walk.py`'s `WalkMixin`, `walk_begin(budget, parallel=1)` sets `walk_parallel`, and one record per chain the walk started (run dir, start time, that task's own `dfs_state.content` entries, whether it was pinned) replaces `walk_dir`, `walk_started`, `walk_content` and `walk_chain_pin`. `walk_tick` judges each ended chain with `walk_decide` (moved = that task's content grew), then fills `walk_parallel - len(live work chains)` slots from `dfs_state.next_items(items, free, busy=tasks with a live chain, first=pin or data["next_item"])`; a chain started by hand fills a slot and its task is busy. A new chain's cap is `(budget - spent - sum of live walk chains' caps) // free slots`, at least 1 and none when nothing is left, so the budget stays a hard bound; a task whose chain ended `cap` or `limit` and is still open goes first next time, so a share-capped chain is carried on rather than left. A `limit` holds new starts while live chains run on; a `stop`, `walk_end_chain` and `walk_off` lower every live walk chain to its current run (`lower_cap`); a pin takes the next free slot, and with none free lowers the most recently started walk chain. `parallel=1` behaves as today. Tests in `test_walk.py` (two slots fill with two tasks, the caps sum to the budget, one chain ending refills its slot, a stop ends both).
Determination: `WalkMixin` keeps one record per chain and fills `walk_parallel` slots through `next_items`, with caps that sum to at most the remaining budget, each chain judged by its own task's content (`state.full()` now gives `contents` per task), and a stop, hand-stop or pin lowering the live chains; 14 new `test_walk.py` tests and one in `test_walker.py` pass with the rest of the walk, screen, order and chain suites (the chat-stub and hook tests that run from `/tmp` fail the same on main).

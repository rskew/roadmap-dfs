# W93 · Make the tests faster

## Goal

Prune low value tests, make tests more targeted, and parallelise where possible

## Tree

### W93.1 · Run the suite in parallel with one command
Status: confirmed
Approach: Add `scripts/test_all.py` (stdlib only, like the rest of the suite; its `test_` name keeps it out of the nix package): it discovers every `test_*.py` beside it, splits the tests into shards, runs the shards in a pool of `python3 -m unittest` subprocesses (one per core by default, `-j N` to change), and prints each failing shard's output, the slowest tests and one summary line. Make `test_screen.py` pass under the loader as well as as a script (its curses `color_pair` patch only runs under `__main__` now, so `-m unittest test_screen` errors 12 times). The check: the whole suite passes under `test_all.py`, and its wall time against the serial baseline (about 870s summed over modules, `test_chain` alone 262s).
Determination: `python3 scripts/test_all.py` runs all 893 tests on 8 cores in 178s against about 870s module by module (211s on a cold run with no remembered times), `test_screen` and `test_init` (whose outside-git case now sets `GIT_CEILING_DIRECTORIES`, so an in-repo TMPDIR no longer fails it) pass under it, and the only failures left are opencode real-agent tests that fail under its load (one per run in two runs: `test_opencode_chat`'s page-continues case, then `test_agent_interrupt.test_opencode_needs_a_second_escape`), so confirmed.

### W93.2 · Shorten the long-pole real-agent chat tests
Status: refuted
Approach: Once the suite runs in parallel, its wall time is bounded by the slowest single tests, which are the real-CLI chat tests: `test_kiro_chat` (1 test, 68s; its fake model holds the opening turn 12s), `test_opencode_chat` (3 tests, 88s), `test_agent_interrupt` (4, 58s), `test_codex_chat` (3, 32s), `test_agent_start` (3, 27s), `test_claude_chat` (2, 20s) and `test_artefact_check` (4, 34s). Profile each, cut fixed holds, sleeps and polling intervals to what the assertion needs, and check each still fails when the behaviour it pins is broken. The opencode ones also fail now and then under `test_all.py`'s load (their fixed `settle=8` start-up sleep and 10s waits), so replace fixed sleeps with waits on what the agent shows, and run the suite under `test_all.py` three times without a failure.
Determination: Refuted: the parallel run is bound by throughput, not by its slowest test: with 16 jobs it took 165s against 178s with 8 while the summed test time nearly doubled (2171s against 1182s), and the slowest test (`test_kiro_chat`, 79s) is well under the wall time, so shortening the sleeps in the real-agent tests would not shorten the run; letting at most two real-agent tests run at once was tried as well and made the run slower (206s) without ending its failures.

### W93.3 · Prune low-value tests
Status: confirmed
Approach: Look for tests that pin the same behaviour as another at a higher cost (duplicate real-agent tests across agents, one scenario set up once per assertion), and remove or narrow them, writing down each removal and the test that still covers it. `test_chain`'s overlap with the `state.py` unit tests is left to the last node, which measures it.
Determination: Four cuts, about 105s of the 1325s summed test time: `test_live.WhichSessionIsThis` ran the same two-run codex chain in `setUp` for each of its four assertions and is now one test with four subtests; `test_chat`'s real-kiro "answers the page and is resumed" test is gone (the stub-kiro test with the same assertions covers the flow, the `fixtures/kiro` files recorded from a real kiro-cli 2.27.1 cover its stream and session format, and `test_kiro_chat` and `test_kiro` still run a real kiro); its real-kiro "cannot reach its model" test is a stub-kiro test (`CHAT_STUB_NO_MODEL` replays the fixture's `runError`, and it fails with the session id removed) at 0.3s against 19s; and `test_agent_interrupt`'s one-escape opencode test became the first half of the two-escape test (a raw ESC must not stop it, then `interrupt()` must), the two-ESC table itself staying pinned by `test_ptyrelay`; the suite ran 888 tests in 165s (1136s of tests) against 893 in 225s (1325s), with only load flakes in untouched `test_ptyrelay` tests (which pass run alone), so confirmed. The refuted W93.2 commit changed only the task file, so there was no code to revert.

### W93.4 · Make two assertions that fail under load wait for their outcome
Status: confirmed
Approach: `test_ptyrelay.Looking.test_attached_the_screen_goes_on_polling_while_keys_keep_coming` counted the polls in a fixed second of keys, which a loaded machine falls short of; it now sends keys until five polls or 5s have passed. `test_opencode_chat.OpencodeCrossing.test_a_conversation_the_screen_began_is_read_and_continued_by_the_page` read the page's messages once, right after the page's turn ended, and opencode can write the message to its database later; it now waits up to 10s for it. Each failed once under `test_all.py`; the check is two full parallel runs, and the ptyrelay test run against an `attach` that polls only when no key came.
Determination: Neither failed in two full runs under `test_all.py`, and the ptyrelay test still fails ("the poll ran 0 times in 5s of keys") against an `attach` that starves its poll, so confirmed.

### W93.5 · Find why opencode's double-Escape stop fails under load
Status: confirmed
Approach: `test_agent_interrupt.Interrupt.test_opencode_needs_a_second_escape` failed in 3 of 4 full runs under `test_all.py` ("opencode hung up on the answer it was given" not seen in 10s after `relay.interrupt()`) and passes run alone. Find whether the page's Stop itself (ptyrelay's two Escapes, `INTERRUPT_GAP` 0.3s apart) misses on a loaded machine, which is a product bug, or only the test's timing (its `settle=8` start-up sleep, its 1.5s "part-way through" sleep); fix whichever it is, then get three full parallel runs with no failure.
Determination: It is the test's timing, not the page's Stop: opencode sends a second request to title the conversation, which carries the user's message and comes first on a loaded machine, so the test took it for the answer's request, slept 1.5s and sent its two Escapes before the answer was under way; `stop_a_slow_answer` now waits for a request that is not the title one. With 24 busy loops on 8 cores the old test failed 2 of 3 times and the new one passed 12 of 13 (the one failure was under an extra probe script, cause not seen), and it passed in all 3 full `test_all.py` runs, so confirmed; those runs still failed one or two other real-agent start-up tests each (kiro and opencode not drawing within 90s/60s), which are the next node.

### W93.6 · Stop the tests reading and writing `scripts/.dfs`
Status: confirmed
Approach: `scripts/.dfs/runs/chat/project.json` is tracked (it came in with the first web page), `test_webscreen.Reopening.test_a_reload_that_reopens_a_task_tells_the_page` errors with FileNotFoundError on `scripts/.dfs` when it is gone, and a run of the suite leaves `scripts/.dfs/runs/chat/W1.log` behind. Every shard of `test_all.py` runs in `scripts/`, so that directory is state the shards share. Find the tests that fall back to the working directory as the work root, point them at their own temp root, and delete the stray file.
Determination: The one test that needed `scripts/.dfs` was `test_webscreen.Reopening`, whose screen ran `git status` in `tui.STATE` (fixed at import from the working directory) while the test moved only `tui.ROOT`; it now moves both, the stray `project.json` is deleted, and a full run under `test_all.py` with no `scripts/.dfs` passed but for the opencode stop and left nothing there (the `W1.log` an earlier run left did not come back), so confirmed.

### W93.7 · Cut test_chain's cost
Status: confirmed
Approach: `test_chain` is about a quarter of the summed test time (73 tests, 262s run alone, about 10s each under `test_all.py`'s load) and, as the run is throughput-bound, its CPU is what the wall time follows. A traced test spends its time in about twenty `python3` and many `git` processes per session that `run.sh` starts, with no sleeps. Measure which rules each chain test pins that `test_tree`/`state.py` unit tests already pin and drop or merge those runs, or share the per-test git set-up; measure summed and wall time before and after.
Determination: The chain rules (the ten-session raise, the critic every fifth session, the refused ok) live in `run.sh`, which no `test_tree` unit test reaches, so only two runs were redundant: `test_the_authors_word_starts_the_review_rounds_over` ran nine stub sessions to reach a state `review_rounds_unsettled` reads from the log, and now writes that log and asserts it (and fails with the `accept` reset removed from the function), and `test_an_answer_resets_the_session_count` repeated the ten-session run of the test before it, so the two are one; eight more tests that waited five work sessions for the critic to be due now set `DFS_CRITIC_EVERY=1` (the count of five stays pinned by `test_the_critic_runs_after_every_fifth_work_session`); the eleven tests took 147s before and the ten 47s after, run one after the other under the same load, and a full `test_all.py` passed all of `test_chain`, so confirmed.

### W93.8 · Make the real-agent start-up waits survive load
Status: confirmed
Approach: In three full runs under `test_all.py`, a different start-up test failed each time: `test_agent_start`'s kiro trust-all case and its opencode prompt-drawn case ("the model was asked with the message" not seen in 90s) and `test_opencode_chat`'s page-continues case ("the screen's opencode drew itself" not seen in 60s). Find whether the agent is slow to draw under load or the test sends before the agent can take input, and make each wait for what the agent shows rather than a fixed time; then get three full parallel runs with none of them failing.
Determination: Three causes found and fixed: `ptyrelay` typed a message after 25s even to a kiro still on "Launching..." (under load that comes before its trust-all question is drawn, and the message is lost), so an agent with a known prompt screen (kiro, opencode) is now waited for up to 90s; a message typed to a codex that draws its trust question seconds after its splash sat behind the unanswered question, so the typist now answers it once it appears; and `test_opencode_chat` read opencode's database after fixed 10s to 30s windows that load overruns, now 30s to 60s; with 24 busy loops on 8 cores the kiro and codex start-up tests passed in 3 of 3 runs where kiro failed 3 of 3 before, and six full `test_all.py` runs gave two clean passes and four failures from other causes (an opencode that hangs at start-up on about a quarter of starts under 20 busy loops and was seen to fail `test_opencode_needs_a_second_escape` and the opening-turn test in one run, and `test_ptyrelay` load flakes), so the three causes are confirmed and the hang is the next node.

### W93.9 · Survive opencode hanging at start-up under load
Status: open
Approach: Under load a real opencode TUI sometimes never reaches its prompt: it draws its terminal queries (colours, size, capabilities), enters the alternate screen and then sleeps in `epoll_wait` with 4s of CPU spent for 100s or more (5 of 20 starts under 20 busy loops, 0 of 8 unloaded, where it draws its prompt in 4.5s), and replies to its queries (OSC 4, window size, OSC 11, DA1, XTVERSION, CPR) did not wake it. Find whether the hang is opencode's (a race at start) or something the relay or tests set up, and then make the tests that start an opencode (`test_agent_start`, `test_agent_interrupt`, `test_opencode_chat`) start it again when it has drawn no prompt within a limit, if that is all that can be done; then get three full parallel runs with none of them failing.

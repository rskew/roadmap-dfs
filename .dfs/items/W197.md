# W197 · Allow starting multiple chats on a node

## Summary

A task can now have more than one chat. The first keeps the task's own key, so every chat that exists still opens, and each further one is `W13_2`, `W13_3` and so on, with its own conversation, title, log and steering messages; each reads the whole task as the first does. On the web page, "Chat +" (task header) and "Another chat" (task view) start one, and the Chats list shows each under its task with a "chat N" tag. On the terminal screen, `O` starts one. The Goal is met, reading "a node" as a roadmap task (the thing a chat is attached to today), not as a tree node such as W13.4; the page and screen changes were tested in code but not seen running, because there was no node or browser flow here. The `_` (not `-`) joins the task and the number because a task whose tag ends in a dash and a digit, such as `W1@fix-2`, is a real task id. Empty records of a chat that was started and never used are not cleaned up.

## Goal

Allow starting multiple chats on a node

## Tree

### W197.1 · A chat key can name a second chat on the same task
Status: confirmed
Approach: **The question**
- Chats are kept one per scope, where a scope is a task id (`W13`) or `project`. How can a task have more than one chat without breaking the chats that exist?

**What this node does**
- `scripts/chat.py`: a scope is now `<task>` (the first chat, unchanged, so old records still open) or `<task>-<n>` for n of 2 or more. `SCOPE` accepts it, `task_of(scope)` gives the task part, and `check` and `list` test the task part with `dfs_tree.exists`. `Chats.new_scope(task)` returns the first `<task>-<n>` with no record. The project chat stays single.
- Tests in `scripts/test_chat.py`: `task_of`, `check` for `W1-2` (good), `W1-1`, `W1-0`, `project-2` and `W9-2` for an unknown task (refused), `new_scope`, and that `list` shows two chats of one task.

**How we will know it worked**
- The new tests are red without the change and green with it; the other tests in `test_chat.py` give the same result as before.
Hypothesis: "A node" in the Goal means a task (a roadmap item), the thing a chat is attached to now, and not a tree node such as W13.4. Wrong if the author meant chats pinned to a tree node. .dfs/artefacts/2736a311-75bf-4798-a7ea-2ff401ed2a17.html
Evidence:
- for: `chat.py` `Chats.check` and `list` accept only a task id or `project`, and the web page's Chat buttons (`data-scope`) are on the task page and in the Chats list, so a task is the only thing a chat is attached to today.
- against: nothing seen; the Goal says "node", and a task's own file calls its steps nodes.
Determination: A task can now have chats `W1`, `W1-2`, `W1-3` with their own records, titles and conversations; the new test is red without the change and green with it, and the 57 other failures in `test_chat.py` are the same with and without it.

### W197.6 · Fix: a task whose tag ends in `-<n>` (such as `W1@fix-2`) is read as a second chat of another task
Parent: W197.1
Status: confirmed
Approach: **The question**
- A task id may be `W1@fix-2`. The chat key `<task>-<n>` cut that end off and read it as chat 2 of `W1@fix`. How do we split a chat key exactly?

**What this node does**
- Join the task and the number with `_`, which no task id holds: `W13_2`. `MORE` and `task_of` in `scripts/chat.py`, the `case` in `scripts/run.sh` (digits only, 2 or more, no leading zero) and `chatTask`/`chatNo` in `scripts/web/index.html` all use it. `new_scope` hands out `<task>_<n>`.
- Test in `test_chat.py`: tasks `W1@fix` and `W1@fix-2` each keep their own chat, `new_scope` gives `W1@fix_2`, and `run.sh` reads `W1@fix-2` as its own task. The other chat, web and screen tests use `_`.
Hypothesis: A key of the form `<task>_<n>` cannot clash with a task id or an existing record, since a task id holds no `_` and no chat was keyed `W13-2` outside this branch. Wrong if a chat record named `<task>-<n>` already exists in a project that has run an earlier build of this branch. .dfs/artefacts/2736a311-75bf-4798-a7ea-2ff401ed2a17.html
Evidence:
- for: `TAG_RE` in `scripts/paths.py` is lower-case letters, digits and dashes, and `TASK_RE` in `scripts/tree.py` adds only `@`, so no task id holds `_`.
- for: W197.1 to W197.5 are not merged, so no record of `W13-2` exists in main.
Determination: A chat key is now `<task>_<n>`, and `W1@fix-2` is its own task with its own chat; the new test is red without the change, and `test_chat` (101), `test_screen` (129) and the new web test pass.

# W83 · Adding a node to a closed task should re enable the "walk here next" button

## Goal

Adding a node to a closed task should re enable the "walk here next" button

## Tree

### W83.1 · Find why a reopened task gets no "Walk here next" button
Status: confirmed
Approach: Reproduce in a scratch roadmap with a done W1 (one confirmed node, review ok) and an open W2: add a node to W1, then read the walk's candidates (`walk_snapshot`, which `index.html` `drawTask` shows the button from). Once with `walk.HeadlessWalk` (`web.py` on its own), once with `tui.UI(None)` serving the page through `UiWalker` while a thread calls `ui.poll()` each second, reading `/api/add`, `/api/walk` and the `HUB` pushes over HTTP.
Determination: The task does reopen (status open, current node W1.2), but on the page the terminal screen serves, `/api/walk` reads the screen's items, which lag the file until the screen's next poll reloads them, and nothing tells the page to read again after that; the page's redraw check in `render` (`sig`) also leaves out the walk's candidates, so a later read that has W1 among them would not redraw either.

### W83.2 · The page learns when the screen's walk changes, and redraws when the task's candidacy does
Parent: W83.1
Status: started
Approach: `tui.py` `UI.reload`: when this screen serves the page (`self.web`) and the reload changed what the walk would show (the open items and `next_item`), call the new `web.Handle.notify` (`HUB.notify`), so the page reads `/api/walk` again. `index.html`: put the button's condition in one helper used by `drawTask` and the task view's `sig`, so whether the button shows is part of what decides a redraw. Check: a test in `test_webscreen.py` that a real `UI` serving the page pushes after a reload that reopens a task and not after one that changes nothing; the scratch reproduction run again shows the push following the reload.

### W83.3 · Snapshot candidates read from the files rather than the screen's items
Parent: W83.1
Status: parked
Approach: `tui.py` `UiWalker.snapshot` lists the candidates from `dfs_state.full()` (or has the screen reload via `call_soon` when `watch_signature()` differs from `ui.sig`) instead of the screen's cached items.
Determination: Parked: `full()` re-parses every task on each `/api/walk`, which `walk_marks` also calls for every `/api/state` (the page notes a full read takes most of a second on a big roadmap), and `call_soon` waits behind an open prompt; a push after the screen's own reload costs neither.

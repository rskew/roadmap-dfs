# W109 · Bug

## Summary

A task file written in the main checkout and never committed now reaches the task's worktree whichever way the walk enters it: on a fresh branch, as before, and now also when the branch or the worktree was left by an earlier attempt, which is where the reported stop came from. The file, and any untracked attachment it names, is moved across uncommitted and the first session commits it on the task's branch (an attachment the main checkout already tracks stays where it is); edits made in the main checkout to a file the worktree already holds stay there, as they did, and the author may rule on that choice. The Goal is met by moving the file rather than by either fix the report suggests: the walk still never commits on the author's default branch, and the up-front refusal was not added because the file no longer needs a manual commit. Two separate tooling issues noticed on the way (task-file writes that are not atomic, and a run record left open when its process dies) are outside this Goal; the author chose to give them a task of their own, so nothing for them was done here.

## Goal

Bug report for the dfs tool

> A new task file that isn't committed stops the walk when it reaches that task
>
> *What happened:* The walk reached W117, which had been created in the main checkout but never committed. It created the worktree .dfs/worktrees/W117 from main, then stopped with "walk off — W117: a session could not be briefed: the worktree … has no .dfs/items/W117.md, which the main checkout has: the branch carries only what git tracks" (runs/activity.log, 1792668065). The same applies to W118, W120, W121 and W122, which were untracked at that point.
>
> *Expected:* A task file that exists in the main checkout is briefed without a manual commit, or the problem is caught earlier.
>
> *Suggested fix, either of:*
> 1. The walk commits new or changed .dfs/items/*.md and order.md on the main branch before it cuts a worktree.
> 2. The step that creates a task file (run.sh --open, the TUI's new-task action, a chat session) commits it. Failing that, the walk should refuse before starting and say which files are untracked, not spend a chain launch to find out.
>
> *Repro:* Create .dfs/items/Wn.md without committing it, list it in order.md, and let the walk reach it.

### W109.9 · Fix: carry only untracked attachments into a worktree that already exists, never one the main checkout tracks
Parent: W109.7
Status: confirmed
Approach: W109.7 made `branch.enter`'s existing-worktree path call `carry_named_attachments(task, wt)`, which runs on every chain that enters a task's existing worktree. It reads the worktree's task file and calls `tree.carry_attachments`, which `os.replace`s every `.dfs/artefacts/<name>` the text names that is a file in the main checkout and missing from the worktree, and never checks whether the main checkout tracks it. So a page committed on the default branch after the task's branch was cut (another task's merged page, cited in this task's Goal or a node), and missing from a worktree whose branch has commits of its own (`catch_up` cannot fast-forward), is moved out of the author's checkout. Checked with a scratch `test_chain.Chain` test: `git worktree add -b dfs/W1`, commit `own.txt` on `dfs/W1`, commit `.dfs/artefacts/<uuid>.html` on master, make the worktree's W1.md name it, then `branch.py enter W1`: the main checkout's `git status --porcelain` shows `D .dfs/artefacts/<uuid>.html`. After a full chain (`work,confirm,rok`) to done and the merge, it still shows ` D`: the author's checkout is left with a tracked file deleted, which a later `git commit -a` commits. Before W109.7 this path did not move attachments; the reused-branch path has had the same move since W75.19. Fix: move only names not in the main checkout's index (as `tree.untracked_artefacts` filters them), in `carry_named_attachments` or `tree.carry_attachments`, so it covers the existing-worktree path, the reused-branch path, and words written later. Add a `test_chain` test of that scenario: the page stays in the main checkout, `git status` is clean after `enter` and after the merge, and the existing untracked-attachment tests still pass.
Determination: `tree.carry_attachments` now skips a name the main checkout tracks (`git ls-files` there), which covers the existing-worktree and reused-branch paths: the new `test_chain` test, a page committed on master after `dfs/W1` was cut with commits of its own, fails without the change (the page is gone from the main checkout) and passes with it, and `test_chain` (111 tests), `test_ignored`, `test_walk`, `test_tree`, `test_walker` and `test_web` pass.

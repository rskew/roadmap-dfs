# W50 · Allow setting a custom background image for dfs for a project

## Goal

Allow setting a custom background image for dfs for a project

## Tree

### W50.1 · Keep a per-project background image in `.dfs/background-image`
Status: confirmed
Approach: In `scripts/paths.py` add `background_image_file()`, `read_background_image()` (returns `(bytes, content_type)` or None, the type sniffed from the file's magic bytes: png, jpeg, webp, gif; anything else counts as no image), `background_image_version()` (the file's mtime in ns, "" when absent, so the page can bust its cache) and `write_background_image(data)` (refuses non-images and more than 8 MB with ValueError; empty or None clears). The file has no extension, so a hand-placed file works whatever it was called. `.dfs/background` (colours) is untouched. Check with new cases in `scripts/test_theme.py`: round trip for each type, a text file refused, an oversize refused, clearing, a stray file in the place ignored, the colour files unchanged.
Determination: The picture is kept in `.dfs/background-image` and read, versioned, written and cleared by `paths.py`, with png, jpeg, webp and gif accepted by their first bytes and text, svg, other RIFF files and anything over 8 MB refused; the three new `test_theme.py` cases and the older ones pass (11 tests), and the colour files are unchanged by it.

### W50.2 · Set, clear and serve the image from the web server
Parent: W50.1
Status: confirmed
Approach: In `scripts/web.py` add `POST /api/background-image` (JSON `{"image": "<base64>"}` sets it, `{"image": ""}` clears it; this route alone takes a body up to the image cap plus base64 overhead, every other write keeps `MAX_BODY`) and `GET /background-image` (the bytes, sniffed `Content-Type`, `Cache-Control: no-cache`, `X-Content-Type-Options: nosniff`, 404 when none). Put `background_image` (the version token, "" for none) into `state_json` and `index_html`, and call `HUB.notify()` on a change so open pages repaint. Check with `scripts/test_web.py` cases: set then GET returns the same bytes and type, state carries the token and it changes on a new image, clear returns 404, a text body and an oversize body are refused, the Host and same-origin guards still apply to the new route.
Determination: `POST /api/background-image` sets or clears the picture (base64 in JSON, up to the cap, other writes keep their 64 KB limit) and `GET /background-image` serves it with its own type, `no-cache` and `nosniff`; `/api/state` and the page carry a version token that changes with a new picture, and the Host, origin and JSON guards apply. The new `test_web.py` case passes; the only failure in the file, the chat test, fails the same without the change.

### W50.3 · Paint the page on the image and offer the control

Add a file input with a preview and a "Remove image" box to the project dialog (`renameForm`), reading the file in the browser and posting it to `/api/background-image`; `syncColour` repaints when the state's token changes. Check with a flow in `scripts/ui_flows.mjs` that sets an image and sees the page paint it and the veil hold, and a screenshot of light, dark and no image (`artefact_check.sh`; say so if no browser starts); the browser tests need the fonts setup from memory.

Parent: W50.3

### W50.6 · Name the image by path or URL in `.dfs/background`
Status: parked
Approach: Add an `image <path-or-url>` line to `.dfs/background` instead of storing the bytes.
Determination: Parked; a path is only good on the machine that holds it and a URL makes the page fetch from a third party, while a stored file travels with the repo like `.dfs/title` and `.dfs/theme` and can be set from a phone.

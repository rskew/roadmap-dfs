# W191 · Load the whole node tree for a task so that expanding a node is instant

## Summary

On the web page, opening a node, stepping to the next or previous one and closing it now draw at once from the task the page already holds. Before, each of these read the task, the work and the state from the server again. A task is still read again when you first open it, when a change to it is pushed, and after any write. I read the Goal as the web page's node sheet; the terminal screen already keeps the loaded tree, so I left it alone. A task changed while the live connection is down is not read again until the next push or a reload.

## Goal

Load the whole node tree for a task so that expanding a node is instant

## Tree

### W191.1 · Find what happens when a node is opened on the web page
Status: confirmed
Approach:
- **The question**: when a node is opened on the web page, is the node's text drawn from what the page already holds, or does the page ask the server again?
- **Why it matters**: if it asks again, every open, Prev, Next and close waits for the network, and that is what the Goal calls not instant.
- **What this node does**: read `scripts/web/index.html` (`renderDraw`, the `hashchange` handler) and `scripts/web.py` (`task_json`), time `task_json` on the biggest tasks here, and count the page's requests in a real browser while a node is opened, stepped and closed. The terminal screen is read too: `Tui.tree_of` in `scripts/tui.py`.
- **How we will know it worked**: the requests are listed and the cause is named in the code.
Determination: Every route change, including opening, stepping and closing a node, runs `render(true)`, which reads `/api/task/<id>`, `/api/work` and `/api/state` again (nine requests for open, Next and close in a browser; `task_json` takes about 0.1 s on W173 and W139 on top of the network), although `/api/task` already carries every node's card; the terminal screen keeps a loaded tree keyed on file times, so it is not slow.

### W191.2 · Draw a node from the task the page already holds
Parent: W191.1
Status: confirmed
Approach:
- **The question**: can opening, stepping and closing a node use the task the page holds, and read nothing?
- **Why it matters**: the whole tree, with each node's card, is already in `S.task` after the first read. Reading it again on every route change is the delay.
- **What this node does**: in `renderDraw` (`scripts/web/index.html`), a `hashchange` inside the task already open, with no push waiting (`stale` is empty for it), draws from `S.task` and skips the task, work and state reads. A first visit, a push for this task and every write still read it. A new flow `node_open_reads` in `scripts/ui_flows.mjs` and its test in `scripts/test_ui.py` count the requests.
- **How we will know it worked**: the flow is red today (three task reads for open, Next and close) and green after, and the other flows in `scripts/test_ui.py` that open nodes keep passing.
Hypothesis: Opening a node's card is the "expanding" the Goal means, and the task the page holds is current enough to draw it, since a change to a task is pushed on the event stream and marks it `stale`. Wrong if the author means another screen, or a change can reach a task with no push. .dfs/artefacts/2cc7f3e9-ec8c-44ff-914a-16495c259342.html
Evidence:
- for: the flow `node_open_reads` is red on the old code with nine reads (three each of `/api/task/W1`, `/api/work`, `/api/state`) and green on the new code with none.
- for: `push_scope` (a change to the open task is read again) passes in the whole `test_ui.py` run on the new code.
- against: a task changed while the event stream is down (the "live" notice shows) is not read again when a node is opened; only the next push or reload brings it in.
- against: two older flows leaned on the slow read: one pressed Escape after closing a sheet (it now leaves the task, as Escape on a task does) and one unfolded rows after following a node link, which dropped the draw's focus. Both were changed; a real fault the second showed, two keys pressed before the first draw redrawing the rows and losing focus, is fixed in the page.
Determination: Opening, stepping to and closing a node now draw at once from the task the page holds, with no read of the task, work or state; the whole `test_ui.py` run has the same 28 failures as the old code (none new), and the new flow passes.

### W191.3 · Keep a task's JSON on the server between changes
Parent: W191.1
Status: parked
Approach: Cache `task_json` in `scripts/web.py`, keyed on the file times as `Tui.tree_of` does, so a repeat read costs no parsing. It cuts the 0.1 s of server work but leaves a round trip for every open, so the node still waits for the network. Taken only if the page cannot hold the task.
Determination: Parked: the round trip stays, so it is not instant on a phone link; the page holding the task is first.

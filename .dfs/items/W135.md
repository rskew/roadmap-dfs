# W135 · Improve the chat ux

## Summary

The web chat dialog now sends on Enter with a desktop keyboard (Shift+Enter adds a line; a touch screen keeps Enter as a new line), keeps an unsent draft when the dialog is closed and reopened, shows a Newest button when the reader has scrolled away from the end, and no longer shifts its input row when a turn runs. The terminal chat was left alone because it is the agent's own screen, and adding steering messages is a separate task. Checked in headless chromium at 360px and 1200px against a stubbed chat; the repository's own chat tests fail the same four ways with and without these changes, so they could not confirm them.

### W135.7 · Fix: Enter submits while a turn is running, past the disabled Send
Parent: W135.3
Status: confirmed
Approach: In `scripts/web/index.html` the `#chat-input` keydown handler (W135.3) calls `$("#chat-form").requestSubmit()` on a bare Enter at a fine pointer, and the `#chat-form` submit handler never looks at the chat's busy state: it only checks for an empty message and a scope. `requestSubmit()` does not honour the disabled Send button, so the UI's own guard ("while it answers, Send waits", asserted in `scripts/ui_flows.mjs` around line 1282) is bypassed by Enter. A desktop user who types the next message while the agent is answering and presses Enter gets, for a background turn, the server's refusal ("it is still answering the last message" in `scripts/chat.py` `send`) as an error toast, and the `catch` re-enables `#chat-send`. For a chat running on the terminal screen, `chat.py` `send` hands the message to the screen's chat (`w.chat_send`) while it is talking, which the page never allowed from the Send button. Before W135.3 only Ctrl/cmd+Enter could do this; now plain Enter makes it routine. Fix: have the submit handler (or the Enter branch) return without sending while `#chat-send` is disabled (busy, or `elsewhere`), keeping the draft, and add a flow in `scripts/ui_flows.mjs` that presses Enter while a turn is busy and sees no `/api/chat/send` call and no toast. Settled when that flow fails without the guard and passes with it.
Determination: The submit handler now returns while Send is disabled, so Enter no longer sends during a running turn or on a chat open in another terminal; the new flow `chat_enter_busy` fails without the guard and passes with it.

### W135.8 · Hypothesis: a fine pointer stands for "has a keyboard" in the Enter-sends rule
Parent: W135.3
Status: open
Approach: W135.3 decided that Enter sends only where `matchMedia("(pointer: fine)")` matches and stays a new line otherwise, but it carries no Hypothesis. That rests on an assumption the session could not settle: that the primary pointer tells whether a physical keyboard is in use. It is wrong for a tablet or a touch laptop with a hardware keyboard whose primary pointer reports coarse (Enter there still adds a line, and only Ctrl/cmd+Enter sends), and for a desktop with a touch-first primary pointer. The placeholder in `scripts/web/index.html` is also set once at load from the same test, so it does not follow a pointer that changes. State it as a Hypothesis on W135.3's page (what is assumed, and what would show it wrong: a hardware-keyboard device where Enter does not send, or an author who would rather have a setting or Enter-always-sends), with its page, rather than editing the determined node.

# W135 · Improve the chat ux

## Summary

The web chat dialog now sends on Enter with a desktop keyboard (Shift+Enter adds a line; a touch screen keeps Enter as a new line), ignores Enter while a turn is running and says why, leaves an input method's Enter (Safari's confirm of a Japanese, Chinese or Korean candidate) alone, keeps an unsent draft when the dialog is closed and reopened, shows a Newest button when the reader has scrolled away from the end, keeps its input row steady when a turn runs, and says "Working on it" while the agent works. The terminal chat was left alone because it is the agent's own screen, and adding steering messages is a separate task. Whether a fine pointer is a fair stand-in for "has a keyboard" is stated as an assumption for the author to rule on, since tablets with a keyboard case keep Enter as a new line. New browser flows cover each behaviour, but after the last rebase and the later fixes they could not be run in the sandbox (no node or playwright), so they should be run where chromium exists before the task is accepted.

### W135.7 · Fix: Enter submits while a turn is running, past the disabled Send
Parent: W135.3
Status: confirmed
Approach: In `scripts/web/index.html` the `#chat-input` keydown handler (W135.3) calls `$("#chat-form").requestSubmit()` on a bare Enter at a fine pointer, and the `#chat-form` submit handler never looks at the chat's busy state: it only checks for an empty message and a scope. `requestSubmit()` does not honour the disabled Send button, so the UI's own guard ("while it answers, Send waits", asserted in `scripts/ui_flows.mjs` around line 1282) is bypassed by Enter. A desktop user who types the next message while the agent is answering and presses Enter gets, for a background turn, the server's refusal ("it is still answering the last message" in `scripts/chat.py` `send`) as an error toast, and the `catch` re-enables `#chat-send`. For a chat running on the terminal screen, `chat.py` `send` hands the message to the screen's chat (`w.chat_send`) while it is talking, which the page never allowed from the Send button. Before W135.3 only Ctrl/cmd+Enter could do this; now plain Enter makes it routine. Fix: have the submit handler (or the Enter branch) return without sending while `#chat-send` is disabled (busy, or `elsewhere`), keeping the draft, and add a flow in `scripts/ui_flows.mjs` that presses Enter while a turn is busy and sees no `/api/chat/send` call and no toast. Settled when that flow fails without the guard and passes with it.
Determination: The submit handler now returns while Send is disabled, so Enter no longer sends during a running turn or on a chat open in another terminal; the new flow `chat_enter_busy` fails without the guard and passes with it.

### W135.8 · Hypothesis: a fine pointer stands for "has a keyboard" in the Enter-sends rule
Parent: W135.3
Status: confirmed
Approach: W135.3 decided that Enter sends only where `matchMedia("(pointer: fine)")` matches and stays a new line otherwise, but it carries no Hypothesis. That rests on an assumption the session could not settle: that the primary pointer tells whether a physical keyboard is in use. It is wrong for a tablet or a touch laptop with a hardware keyboard whose primary pointer reports coarse (Enter there still adds a line, and only Ctrl/cmd+Enter sends), and for a desktop with a touch-first primary pointer. The placeholder in `scripts/web/index.html` is also set once at load from the same test, so it does not follow a pointer that changes. State it as a Hypothesis on W135.3's page (what is assumed, and what would show it wrong: a hardware-keyboard device where Enter does not send, or an author who would rather have a setting or Enter-always-sends), with its page, rather than editing the determined node.
Hypothesis: The primary pointer (`matchMedia("(pointer: fine)")`) tells whether a physical keyboard is in use, so Enter sends only there. Wrong if a hardware-keyboard device reports a coarse primary pointer, so Enter adds a line where the user expects it to send, or if the author would rather have a setting or Enter that always sends. .dfs/artefacts/41e05ca6-8cd2-4d7c-a0b4-8b9819d2748a.html
Evidence:
- for: headless chromium with the desktop profile reports `pointer: fine` true and `hover: hover` true, so a mouse-and-keyboard desktop gets Enter-sends.
- for: the iPhone 13 profile reports `pointer: coarse` and `any-pointer: fine` false, so a phone keeps Enter as a new line, which is wanted.
- against: the iPad Pro 11 profile also reports `pointer: coarse` and `any-pointer: fine` false, so a tablet with a keyboard case is expected to lose Enter-sends; these are device profiles, and no real hardware-keyboard tablet was tried.
Determination: The assumption is now stated with its page; a fine primary pointer is a fair stand-in for a keyboard on desktops and phones but unproven for tablets with a keyboard, and the author rules on it.

### W135.11 · Fix: Enter confirming an input-method candidate sends the half-typed message on Safari
Parent: W135.3
Status: confirmed
Approach: The `#chat-input` keydown handler in `scripts/web/index.html` (just above the "The colour can change under an open page" comment) skips only `ev.isComposing`, then on a bare Enter at a fine pointer calls `$("#chat-form").requestSubmit()`. On Safari (desktop, where `pointer: fine` is true) the keydown of the Enter that confirms an IME candidate (Japanese, Chinese, Korean) arrives after `compositionend`, with `isComposing` false and `keyCode` 229. Before W135.3 only Ctrl/cmd+Enter sent, so this could not happen; now a CJK user on Safari who confirms a candidate sends an unfinished message that cannot be taken back. Fix: also return when `ev.keyCode === 229` (and, for a robust version, when a `compositionend` fired within the last few ms: keep a timestamp in a `compositionend` listener on `#chat-input` and ignore an Enter within about 50ms of it). The same `ev.isComposing`-only test sits at the form fields (`el.addEventListener("keydown"` near line 1534) and the account code field (near line 1878); fix all three through one small helper, so the page has one rule for "this Enter is the input method's". Settled by a flow in `scripts/ui_flows.mjs` that dispatches a `KeyboardEvent("keydown", { key: "Enter", keyCode: 229, isComposing: false, cancelable: true })` on `#chat-input` and sees it not cancelled and no `/api/chat/send` call, while a plain Enter still sends; the flow must fail without the check.
Determination: One helper, `imeEnter`, now decides whether an Enter belongs to the input method (isComposing, keyCode 229, or within 50ms of compositionend) and the chat box, the form fields and the account code field all use it; the new flow `chat_ime` was written but not run here (no node or playwright), so it is unproven in a browser.

# W142 · Chat often shows failed to fetch when switching back from another app

## Summary

The chat no longer breaks when the phone's browser comes back from another app. A request that gets no answer now leaves the conversation in place under a "could not reach the server" notice, the page keeps asking until the server answers, and an open chat is read at once when the page becomes visible again (the live-update stream is also reopened if the browser gave up on it). A message whose answer was lost is not sent twice; it stays in the box with a note that it may have gone. The cause was found and the fix checked in headless chromium with the network made to fail, not on a phone, and the new browser test for it passes. Two things rest on assumptions put to the author: that the phone rejects the request rather than leaving it hanging (a hung request has no timeout), and that only the chat, not the other views, needed to recover.

## Goal

Chat often shows failed to fetch when switching back from another app

Status: confirmed

**What this node does**

### W142.2 · Keep the chat through a failed request and refresh it on return
Parent: W142.1
Status: confirmed
Approach: **What this node does**
- In `scripts/web/index.html`, `chatLoad` must not replace the conversation with "Not available" when the request failed at the network (a `TypeError`, not an answer from the server). It keeps the log, tries again after a short wait, and keeps polling while the chat is open.
- `api` marks a network failure so callers can tell it from the server's own error, and a read (GET) is tried once more after a short wait before it fails.
- When the page becomes visible again (`visibilitychange`), is restored from the page cache (`pageshow`) or the network returns (`online`), an open chat is loaded at once and its poll restarted.
- A send is never repeated by the page (it could post the message twice); its failure toast says the message may not have gone and the chat is reloaded so the reader sees whether it did.

**How we will know it worked**
- The run from the first node, repeated, shows the log kept, polling continuing and the chat current after a simulated return.
Determination: With the same simulated failure the chat keeps its conversation, shows a "could not reach the server" notice, keeps polling and clears the notice once the server answers, and a visibilitychange fetches at once; a failed send keeps the typed message and is not repeated (![the notice under the log; headless chromium here has no fonts, so text is not drawn](.dfs/artefacts/2ffd01c2-78bd-435d-ba12-b3d28e8ce56c.png)).

### W142.4 · Hypothesis: a rejected fetch is what the phone raises on return

Determination: The assumption is stated with its page; the report's wording fits it, a hanging request is the one case left uncovered, and only a run on the phone can settle it.

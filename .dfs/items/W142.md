# W142 · Chat often shows failed to fetch when switching back from another app

## Summary

The chat no longer breaks when the phone's browser comes back from another app. A request that gets no answer now leaves the conversation in place under a "could not reach the server" notice, the page keeps asking until the server answers, and an open chat is read at once when the page becomes visible again (the live-update stream is also reopened if the browser gave up on it). A message whose answer was lost is not sent twice; it stays in the box with a note that it may have gone. The cause was found and the fix checked in headless chromium against the real page and server with the network made to fail, not on a phone. The new browser test `chat_lost` could not be run here (no playwright), and the machine's test suites already had failures that are unrelated to this change.

## Goal

Chat often shows failed to fetch when switching back from another app

## Tree

### W142.1 · Reproduce the failure in a real browser
Status: confirmed
Approach: **The question**
- When the page's request to the server fails the way a phone's does after the browser was in the background, what does the open chat show, and does it recover on its own?

**What this node does**
- Serve the real `scripts/web/index.html` from the real server (`scripts/web.py`) and drive it with headless chromium over its debugging pipe. Open a chat, then make one `fetch` reject with `TypeError: Failed to fetch` (what a browser raises when the network was cut), and read the page.
- Read `chatLoad` and `api` in `scripts/web/index.html` beside the result.

**How we will know it worked**
- The run shows what the log says after the failure and whether polling carries on (a later fetch is made or not).
Determination: Reproduced in headless chromium on the real page and server: one rejected poll replaces the whole conversation with "Not available · Failed to fetch" and no request is made afterwards, because `chatLoad` renders the error and never schedules the next poll.

### W142.2 · Keep the chat through a failed request and refresh it on return
Parent: W142.1
Status: confirmed
Approach: **What this node does**
- In `scripts/web/index.html`, `chatLoad` must not replace the conversation with "Not available" when the request failed at the network (a `TypeError`, not an answer from the server). It keeps the log, tries again after a short wait, and keeps polling while the chat is open.
- `api` marks a network failure so callers can tell it from the server's own error, and a read (GET) is tried once more after a short wait before it fails.
- When the page becomes visible again (`visibilitychange`), is restored from the page cache (`pageshow`) or the network returns (`online`), an open chat is loaded at once and its poll restarted.
- A send is never repeated by the page (it could post the message twice); its failure toast says the message may not have gone and the chat is reloaded so the reader sees whether it did.

**How we will know it worked**
- The run from the first node, repeated, shows the log kept, polling continuing and the chat current after a simulated return.
Determination: With the same simulated failure the chat keeps its conversation, shows a "could not reach the server" notice, keeps polling and clears the notice once the server answers, and a visibilitychange fetches at once; a failed send keeps the typed message and is not repeated (![the notice under the log; headless chromium here has no fonts, so text is not drawn](.dfs/artefacts/2ffd01c2-78bd-435d-ba12-b3d28e8ce56c.png)).

# W36 · Chat should have an interrupt button

## Goal

Chat should have an interrupt button

## Tree

### W36.1 · Interrupt a headless chat turn
Status: confirmed
Approach: In scripts/chat.py `run_turn` takes an `on_start(process)` callback and starts the turn in its own process group; `Chats` keeps the running turn's process per scope and gains `interrupt(scope)`, which ends the group as a timeout does (SIGTERM, SIGKILL after TURN_GRACE) and makes the turn finish with a `note` message ("Stopped before it answered.") instead of an error. A new chat's session id is chosen before the turn (CHAT_SID without CHAT_RESUME starts it under that id), so the conversation survives an interrupt of its first turn. Check: a test with a stub claude that sleeps.
Determination: Confirmed: test_chat's new stop test passes (the sleeping stub's turn ends within seconds with roles you, note, the session is kept and the next message is answered); the only other test_chat failure, "will not send while the screens chat is open", fails the same without my change, and every test needs TMPDIR on an exec-capable mount since /tmp here is noexec.

### W36.2 · Interrupt a chat the screen runs in the background
Status: confirmed
Approach: `ptyrelay.Relay.interrupt()` drops the messages still queued to be typed (and one the typist has taken but not yet typed) and writes ESC to the pty; `UiWalker.chat_interrupt` in scripts/tui.py and `HeadlessWalk` (returns False) expose it, and `Chats.interrupt` presses it in the screen's chat when no headless turn is running. Check: test_ptyrelay with a bash agent that reports the bytes it reads, and test_chat with a fake screen.
Hypothesis: A lone ESC byte typed into the interactive claude on its pty interrupts the answer it is giving and leaves the process and session running, as Esc does at the keyboard (see .dfs/artefacts/7c2e5a41-3b0f-4d6a-9e18-5f2a6d0b9c13.html, which compares Esc, Ctrl-C and SIGTERM). Wrong if, on a real claude answering in the background, Stop leaves it still answering or the claude exits.
Evidence:
- for: test_ptyrelay: a bash agent reading raw bytes on the pty receives exactly one ESC from `interrupt()`, stays live and still hears the next message, so the byte reaches the process and the relay survives it.
- against: no claude binary exists in this sandbox, so claude's own reaction to the byte is unobserved; it rests on Esc being claude's documented interrupt key.
Determination: Confirmed as far as it can be here: the relay's side works under test_ptyrelay and test_chat, and claude's reaction to Esc is the one thing only the author can see on a real chat (artefact text does not draw here, the sandbox has no fonts).
Ask: Does Stop on a chat the screen runs actually interrupt claude on your real setup? I chose Esc over Ctrl-C because Ctrl-C at an idle prompt quits claude.

# W36 · Chat should have an interrupt button

## Summary

The chat dialog on the page now has a Stop button, shown while the agent is answering. For a chat the page runs itself it ends the turn's process group and the log says "Stopped" rather than showing a failure; for a chat the screen runs in the background it types Esc into that claude and drops anything still queued to be typed, so the conversation and the process stay. The Goal is met and tested (a stub claude, a bash pty agent and a Chromium flow), except that no real claude was available here, so that Esc stops a real background chat is the assumption left for the author to try. Ctrl-C was not used because at an idle prompt it quits claude.

## Goal

Chat should have an interrupt button

## Tree

### W36.1 · Interrupt a headless chat turn
Status: confirmed
Approach: In scripts/chat.py `run_turn` takes an `on_start(process)` callback and starts the turn in its own process group; `Chats` keeps the running turn's process per scope and gains `interrupt(scope)`, which ends the group as a timeout does (SIGTERM, SIGKILL after TURN_GRACE) and makes the turn finish with a `note` message ("Stopped before it answered.") instead of an error. A new chat's session id is chosen before the turn (CHAT_SID without CHAT_RESUME starts it under that id), so the conversation survives an interrupt of its first turn. Check: a test with a stub claude that sleeps.
Determination: Confirmed: test_chat's new stop test passes (the sleeping stub's turn ends within seconds with roles you, note, the session is kept and the next message is answered); the only other test_chat failure, "will not send while the screens chat is open", fails the same without my change, and every test needs TMPDIR on an exec-capable mount since /tmp here is noexec.

### W36.2 · Interrupt a chat the screen runs in the background
Status: confirmed
Approach: `ptyrelay.Relay.interrupt()` drops the messages still queued to be typed (and one the typist has taken but not yet typed) and writes ESC to the pty; `UiWalker.chat_interrupt` in scripts/tui.py and `HeadlessWalk` (returns False) expose it, and `Chats.interrupt` presses it in the screen's chat when no headless turn is running. Check: test_ptyrelay with a bash agent that reports the bytes it reads, and test_chat with a fake screen.
Hypothesis: A lone ESC byte typed into the interactive claude on its pty interrupts the answer it is giving and leaves the process and session running, as Esc does at the keyboard (see .dfs/artefacts/7c2e5a41-3b0f-4d6a-9e18-5f2a6d0b9c13.html, which compares Esc, Ctrl-C and SIGTERM). Wrong if, on a real claude answering in the background, Stop leaves it still answering or the claude exits.
Evidence:
- for: test_ptyrelay: a bash agent reading raw bytes on the pty receives exactly one ESC from `interrupt()`, stays live and still hears the next message, so the byte reaches the process and the relay survives it.
- against: no claude binary exists in this sandbox, so claude's own reaction to the byte is unobserved; it rests on Esc being claude's documented interrupt key.
Determination: Confirmed as far as it can be here: the relay's side works under test_ptyrelay and test_chat, and claude's reaction to Esc is the one thing only the author can see on a real chat (artefact text does not draw here, the sandbox has no fonts).
Ask: Does Stop on a chat the screen runs actually interrupt claude on your real setup? I chose Esc over Ctrl-C because Ctrl-C at an idle prompt quits claude.

### W36.5 · Fix: Stop on a screen-run chat leaves a message that was never typed shown as sent
Parent: W36.2
Status: confirmed
Approach: `Chats.send` (scripts/chat.py) hands a message to the screen's chat and records it in `self.pending[scope]`; `state()` keeps showing a pending message as a "you" line until the transcript contains it. `Relay.interrupt` (scripts/ptyrelay.py) drops messages still in the outbox, and the typist drops one it has taken but not typed, so a message sent and then stopped within the wait-to-type window (up to READY_TIMEOUT, or while claude is still drawing) never reaches claude. `Chats.interrupt` does not touch `pending` on that path, so the page shows "You: <message>" forever with no answer, no note and Send enabled, until a new chat or the next send overwrites it. Fix: when the screen's interrupt drops a message, clear `pending[scope]` (have `Relay.interrupt` return/report whether it dropped one, or clear `pending` in `Chats.interrupt` when the transcript does not hold it) and say in the log that it was stopped (the `note` role) so the author sees the message was not sent. Check: a test_chat case with a fake screen whose relay holds a queued message, press Stop, and assert the state no longer lists it as an unanswered "you" line (or lists it with the stopped note).
Determination: Confirmed: `Relay.interrupt` now returns how many messages it dropped untyped (None if not running; a counter `unsent` covers queued and typist-held ones), `Chats.interrupt` clears `pending` and shows the stopped note when it is above zero, and the new test_chat case and the updated test_ptyrelay cases pass (test_chat's one other failure is the known one that fails without the change).

### W36.6 · Minor findings from the review
Parent: W36.5
Status: open
Approach: One line each:
- chat.py `run_turn` now starts the turn with `start_new_session=True`, so a Ctrl-C or kill of the server no longer reaches a running turn and it is left to finish alone (up to claude's own end); consider ending running turns on server shutdown, or note it.
- chat.py `turn`: if Stop is pressed after the agent has already answered (process exited, `end_turn` returns early) the turn still sets `stops[scope]`, so "Stopped before it answered." is appended after a real answer; only mark stopped if the process was actually signalled.
- chat.py: a failed first turn now also saves the pre-chosen session id (no transcript), where before nothing was saved; harmless (the next send reuses it without --resume) but undocumented and untested.
- web/index.html `who` maps role `note` to "Stopped" in the Chats list, so any future note would read as Stopped; and no test checks that Stop in a screen-run chat leaves the page without a note.

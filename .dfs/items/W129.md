# W129 · I see "the terminal screen is busy" red toast when starting a walk, but if I cancel the walk has actually started

## Summary

The page's walk Start no longer shows the red "terminal screen is busy" toast when the screen has already begun the command. The screen's call is now called off only while it is still queued; once the screen has taken it, the page waits for the result, up to a further 60 seconds, and a command that exits the screen still frees the waiting request. The Goal is met by that fix in the code and its tests; the slow start itself was not reproduced here, since a reload takes 0.14 s on this machine.

## Goal

I see "the terminal screen is busy" red toast when starting a walk, but if I cancel the walk has actually started

## Tree

### W129.1 · call_soon stops timing out once the screen has begun the command
Status: confirmed
Approach: In scripts/tui.py, `UI.call_soon` waits 5 s for `done` and then marks the `_Call` cancelled and raises "the terminal screen is busy", but `drain_commands` may already be inside `call.fn()` (the walk's Start runs `walk_begin`, whose `start_chain` spawns the runner and calls `reload()`, taking seconds on a large roadmap). The caller gets the 409 toast while the walk starts anyway. Give `_Call` a lock and a `started` flag: `drain_commands` sets `started` (unless already cancelled) under the lock before running `fn`; on timeout `call_soon` takes the lock and cancels only if not started, and otherwise keeps waiting for `done` so the page gets the real result. Test in scripts/test_webscreen.py: a command that starts then outlasts the timeout must return its result with no "busy" error (red on the old code), and the existing never-drained and late-command tests must still pass.
Determination: Confirmed: the new test (a command begun at 0.05 s and finished at 0.45 s against a 0.2 s timeout) raised "busy" on the old call_soon and returns the result on the new one, and all 17 tests in test_webscreen.py pass; the 5 s case on the real screen was not reproduced here, where a reload takes 0.14 s.

### W129.2 · a begun command can no longer hang the request thread
Parent: W129.1
Status: confirmed
Approach: In scripts/tui.py, bound the wait W129.1 added and make `done` always set. `drain_commands` runs `call.fn()` in try/except Exception/finally so `call.done.set()` runs even on a BaseException (SystemExit, KeyboardInterrupt), which is stored as the error then re-raised after `done` is set. `call_soon` gets a `running_timeout=60.0` for the second wait after the screen has begun the command; if that also elapses it raises "the terminal screen is still running the command" rather than hanging. Rewrite the docstring: it gives up after `timeout` only on a command still queued, and then waits up to `running_timeout` for one the screen has begun. Tests in scripts/test_webscreen.py: a command raising SystemExit releases the waiting caller with an error; a begun command that never finishes returns the "still running" error after `running_timeout` (small values); the W129.1 tests still pass.
Determination: Confirmed: a SystemExit inside a command now frees the waiting caller with an error, a begun command that never finishes returns "still running" after the second timeout, the docstring says what the timeouts do, and all 19 tests in test_webscreen.py pass.

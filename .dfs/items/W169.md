# W169 · Chat should show accurate state of backend, such as usage limit

## Summary

When a page chat turn stops on a usage limit, the chat now reports it as a fact of its own: the state carries a `backend` entry with the limit, when it resets and which agent hit it, and the page shows a line above the message box. The entry survives a restart and goes when the reset time passes, when a later turn goes by without the limit, or when the chat runs under another agent. Claude's limit is read from its 429 status; codex, opencode and kiro are read from the wording of their error, so a limit worded differently (opencode's "Too many requests (429)") is missed. Left out: background chats and the work's own hold do not show the limit, the Chats list carries the data but does not draw it, and the page flow for the new line was written but not run, since this box has no browser test tooling.

## Goal

Chat should show accurate state of backend, such as usage limit

## Tree

### W169.1 · Find where the chat misstates the backend when the agent hits a usage limit
Status: confirmed
Approach:
- **The question**: when the agent behind a chat hits a usage limit, what does the chat show, and where is that wrong?
- **Why it matters**: the Goal is open ("accurate state of the backend, such as the usage limit"). The fixes depend on which chat paths misreport. They are a page turn (`Chats.turn`, one headless run per message), and a background chat (`Relay`, an interactive agent on a pty, shown as `busy` while it has printed in the last 2s). Today a turn's failure is the agent's raw last words in `notes`, and `limit.classify` (which reads a limit and its reset time) is not used by the chat at all.
- **What this node does**: run one claude page turn against a stub that ends in a 429 (`is_error`, `api_error_status` 429, "You've hit your session limit · resets 3pm (UTC)") and print `Chats.state` and `Chats.list`. The codex, opencode and kiro paths and the background chat are read in `chat.py` and `ptyrelay.py`, not run.
- **How we will know it worked**: what the chat shows for the limit is written down, and each missing state is named. The next node is planned from it.
Determination: A claude page turn that ends in a 429 shows only the agent's raw words as a generic error, and nothing in the chat state says "usage limit", when it resets, or that the work is holding for the same limit, so the chat does not report the backend's state.

### W169.2 · Give the chat a `backend` state that says a usage limit, and show it on the page
Parent: W169.1
Status: confirmed
Approach:
- **The question**: can `Chats.state` carry the backend's limit as a fact (limit hit, reset text, reset time) that the page shows as its own line, apart from the message list?
- **Why it matters**: W169.1 found the limit is only the text of the last error note. Reading `chat.py`, that note is kept in memory, is dropped by the next send, and nothing marks when the limit lifts. The chat also does not see the work's hold (`work.snapshot()["hold"]`).
- **What this node does**: in `Chats.turn`, run `limit.classify` on the turn's raw stdout and stderr and keep `{limit, resets, reset_at}` per scope (saved in the scope's record so a restart keeps it). `state()` returns it as `backend`, and drops it once `reset_at` has passed or a later turn answers. The page draws it as a line above the box. Do the claude page turn first; codex, opencode and kiro use the same classify call with their agent name.
- **How we will know it worked**: tests in `scripts/test_chat.py` with a stub that ends in a 429 show `backend.limit` true with the reset text, then false after an answered turn. Run with `TMPDIR` set to a directory that is not `noexec` (this box's `/tmp` is, so run.sh cannot start the stubs there). A page flow checks the line is drawn.
Determination: A page turn that ends on a usage limit now sets `backend` ({limit, resets, reset_at, agent}) in the chat state, kept in the scope's record, cleared by an answered turn, a different failure or the reset time, and the page draws it as a line above the box; the unit tests pass, but the page flow could not run because this box has no playwright.

### W169.3 · Fix: a limit kept for one agent is shown after the chat has moved to another agent
Parent: W169.2
Status: confirmed
Approach: In `scripts/chat.py`, `Chats.backend(scope)` returns the saved `backend` without checking which agent the chat now runs under. A chat with no session id takes its agent from the screen's choice (`Chats.agent` calls `read_agent` when the record has no `sid`). A first turn by codex, opencode or kiro that hits a limit saves no sid, so the record holds only `backend`. If the author then switches the agent (the screen's `x`) to claude, `state()` still returns `backend` with `agent: "codex"`, and the page says the codex has hit its limit and that a message "may not be answered". That is false: claude will run it. Fix: `backend()` (or `state()`) returns None when `backend["agent"]` is not the chat's current agent, and the saved entry is dropped when a turn runs under another agent. Add a test in `scripts/test_chat.py`: set a codex limit with no sid, change the agent file to claude, and check `state()["backend"]` is None. Also check a claude limit is still shown while the agent is claude.
Determination: `Chats.backend()` now returns None when the saved limit belongs to a different agent than the chat's current one, and a stopped turn under another agent drops the old entry; the new test went red without the fix, and all 87 chat tests pass.

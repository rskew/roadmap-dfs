# W159 · replay.py run leaves the killed run's runner alive when a wrapper timeout ends the command

## Goal

When `replay.py run` is wrapped in the shell `timeout` and that timeout fires, the wrapper ends but the chain's runner started by `replay.py` keeps running in the background, so a later `replay.py run` on the same DEST finds a runner still working the same worktree. Found while working W153 (filed there as a draft, not fixed there; seen by earlier sessions of that task, not re-run when filing).

Goal: a `replay.py run` that is killed or timed out ends its runner and the agent below it, or the next `run` on that DEST says a runner is still alive and does not start a second. Show the case first: run with a short `timeout`, then list the processes.

Not re-run (W153.51): it needs a replay under a short `timeout` and a process listing, and a replay costs credits this note does not justify. Left unverified.

## Tree

### W159.1 · Show the case with a stand-in runner
Status: confirmed
Approach: **The question**
- When `replay.py run` is ended by `timeout`, does the runner it started stay alive?

**What this node does**
- `proot` is not installed here and a real replay costs credits, so `scripts/replay.py`'s `launch` is swapped for a shell that starts a long `sleep` and waits on it (a stand-in for proot, run.sh and the agent). `replay.run` is driven under `timeout 2` and under `timeout --foreground 2`, and `ps` lists what is left.

**How we will know it worked**
- The case is shown when a `sleep 300` is still listed after `run` was ended.
Determination: Under `timeout --foreground 2` (which signals only `replay.py`) the stand-in `sh` and its `sleep 300` were still listed after `run` died, reparented to pid 1; plain `timeout 2` signals the whole group and left nothing, so the real proot chain is shown only for the first form and not run for real (no proot here).

### W159.2 · Run the runner in its own group, end it with `run`, refuse a second
Parent: W159.1
Status: open
Approach: **What this node does**
- In `replay.run`, start the runner with `start_new_session=True` so it is one process group. Handle SIGTERM, SIGHUP and SIGINT by sending the same signal to that group, then SIGKILL after a short grace, and always end the group when `run` returns or raises.
- Write the group id to `DEST/.git/replay.pid` and remove it when the group is gone. At the start of `run`, if that file names a group that is still alive (`os.killpg(pgid, 0)`), exit saying a runner is alive on DEST and not start a second. This covers a `kill -9` of `replay.py`, which no handler can catch.
- Tests in `scripts/test_replay.py` drive the stand-in under both `timeout` forms and a SIGKILL of `run`, and check the sleep is gone or the second `run` is refused.

**How we will know it worked**
- The new tests fail on the old `run` and pass on the new one; `test_replay.py` passes.

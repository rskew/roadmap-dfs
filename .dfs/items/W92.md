# W92 · Starting a walk should work if the tui is in a chat

## Summary

The web page's Start now starts the walk while the terminal screen is showing a chat. Before, it waited five seconds and answered that the screen was busy. While a chat is open, the screen goes on doing its once-a-second work: it runs what the page asks, and an already-running walk keeps starting its chains, without drawing over the chat. The Goal is fully met for chats. Screens blocked by a prompt or an editor still answer "busy", as before, since the Goal named only chats.

## Goal

Starting a walk should work if the tui is in a chat

## Tree

### W92.1 · The screen keeps polling while a chat is attached
Status: confirmed
Approach: `UI.open_chat` hands the terminal to `ptyrelay.Relay.attach`, whose select loop blocks the screen's thread, so `poll` stops running: the page's walk Start (queued by `UiWalker.start` through `UI.call_soon`) is never drained and comes back 409 "the terminal screen is busy", and a walk already on stops ticking until ctrl-]. Give `attach` an `idle` callback it calls at most every 0.3 s whatever is typed, and have `open_chat` pass `self.poll`, which draws nothing. Check: a test in `test_webscreen.py` attaches a real relay with `open_chat`'s callback and POSTs `/api/walk/start`, red before the change and green after, plus a `test_ptyrelay.py` test that `idle` runs while keys keep arriving.
Determination: Confirmed: with the real screen in a chat in a pty, the page's Start returned 200 in 0.37 s and the walk started its chain while the chat still echoed typing, where the unchanged code returned 409 "busy" after 5 s and started nothing; the new tests go red on the old code and green on the new.

### W92.2 · Run the page's walk commands on the server thread while a chat is attached
Status: parked
Approach: When `Relay.attached` is set, `UI.call_soon` runs `fn` on the web server's thread under a lock instead of queueing it for `poll`.
Determination: Parked: it breaks the rule that the walk's state belongs to the screen's thread, and a walk already on would still not tick until the chat is detached, which the polling in `attach` fixes as well.

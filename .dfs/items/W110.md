# W110 · The page is slow

## Goal

The page is slow

## Tree

### W110.1 · Find where the web page's time goes
Status: confirmed
Approach: Time `web.py`'s handlers in-process on this repo (111 tasks): `state_json` (`/api/state`), `walk_json` (`/api/walk`), `task_json` (`/api/task/<id>`) and `state.full()`, then profile `state_json` with cProfile.
Hypothesis: "The page" is the web page `scripts/web.py` serves, and it is slow because its server takes seconds to answer each read, not because the browser draws slowly. Wrong if the author meant the terminal screen (`tui.py`), drawing or scrolling in the browser, or one task's page whose own data is slow. .dfs/artefacts/0516321c-0047-47fd-bf0f-4d949168b90d.html
Evidence:
- for: `state.full()` takes 0.81 s; `/api/state` takes 1.75 s because it runs `full()` twice (once for the rows, once more through `walk_marks` -> `HeadlessWalk.snapshot` -> `reload`); `/api/walk` takes 0.84 s; `task_json` takes 0.03 s for W81, 0.09 s at worst over all 111 tasks.
- for: the cProfile of `state_json` shows 666 git processes from `tree.default_ref`, 3 per task, called by `state.state_for` for each row; memoizing `default_ref` cut `full()` from 0.81 s to 0.31 s.
- for: with the walk on (the default), `HeadlessWalk.loop` calls `full()` every `TICK` (2 s) whether or not anyone is looking, about 40% of a core that every request shares.
- for: the page asks `/api/state` and `/api/walk` together when the list opens and `/api/task` and `/api/walk` when a task opens (`index.html` lines 594 and 622), so every view waits on at least one `full()`.
Determination: The web page's server spends nearly all its time in `state.full()`, built up to three times per view and every 2 s by the idle walk thread, and 60% of each build is `default_ref` spawning 3 git processes per task; confirmed.

### W110.2 · Cache `tree.default_ref`
Parent: W110.1
Status: confirmed
Approach: In `scripts/tree.py`, keep `default_ref(cwd)`'s answer per `cwd` for a few seconds, the way `unpushed` and `uncommitted` already keep theirs (`ttl=5.0`), so `state.state_for` stops running 3 git processes per task. Check: `state.full()` time before and after, a test in `scripts/test_tree.py` that a second call within the ttl runs no git, and `test_tree`, `test_web`, `test_unpushed` pass.
Determination: `default_ref(cwd, ttl)` now keeps its answer per `cwd` when given a ttl and `state.state_for` passes 5 s, which took `state.full()` from 0.81 s to 0.31 s, `/api/state` from 1.75 s to 0.64 s and `/api/walk` from 0.84 s to 0.32 s, with the new test and `test_unpushed`, `test_tree`, `test_web`, `test_walk`, `test_walker` and `test_screen` passing (8 errors seen only when `test_walk`/`test_walker`/`test_screen` run after `test_tree` in one process, which the base code shows the same); confirmed.

### W110.3 · Build `state.full()` once per `/api/state` request
Parent: W110.2
Status: open
Approach: `web.state_json` runs `dfs_state.full()` and then `walk_marks`, whose `HeadlessWalk.snapshot` reloads it again. Make `snapshot(data)` (`scripts/walk.py`) take the data it is given instead of reloading, and pass `state_json`'s. Check: `state_json` time halves, and `test_web` and `test_walk` pass.

### W110.4 · Stop the idle walk thread rebuilding the state every 2 s
Parent: W110.3
Status: open
Approach: `HeadlessWalk.loop` (`scripts/walk.py`) calls `reload()` (`state.full()`) every `TICK` even while the walk is off. Skip the reload when the walk is off, if `walk_tick` does nothing then, or else reuse the last build until `web.roadmap_signature` changes. Check: an idle server's CPU over 20 s before and after, and `test_walk` and `test_web` pass.

### W110.5 · Memoize `state.full()` by the files it reads
Parent: W110.1
Status: parked
Approach: Keep `state.full()`'s result keyed by `web.roadmap_signature()` (the task files', archives', order file's and chains' mtimes) plus HEAD, so every request and the walk thread share one build until something changes.
Determination: Parked, since the state also depends on git facts no file mtime shows (a push moving `origin/main`, a worktree commit), so a stale list is its risk; taken if caching `default_ref` and removing the repeated builds leave the page slow.

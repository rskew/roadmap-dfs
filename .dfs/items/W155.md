# W155 · Error 502 when selecting opus as the implement model for walk

## Summary

The 502 is fixed. The terminal screen that hosts the page had no action for choosing a model, so every model choice (opus or any other name) made the server drop the connection without a reply, and the proxy in front showed 502. The screen now takes the choice like it takes the agent, and any other unexpected server error is answered as a JSON 500 instead of a dropped connection. Also, a kiro walk now refuses claude-only names such as `opus` (kiro-cli rejects them when the chain starts) and lists kiro's models. The Goal is met; the page itself was not driven in a browser, but a real server over the screen's walk is tested over HTTP and the live server's dropped reply was seen with curl.

**What this node does**
- Add `UiWalker.set_model(role, name)` that runs `ui.set_model` on the screen's thread through `call_soon`, as `set_agent` does.
- In `Handler.handle_any`, answer any other exception with a JSON 500, so no request is ever closed without a reply.
- Test in `scripts/test_webscreen.py` (a real server over a screen's `UiWalker`): POST `/api/walk/model` with `opus` answers 200 and the screen keeps it, a bad role answers 409, and a walker that raises an unexpected error gets a JSON 500.

**How we will know it worked**
- The test is red before the change (`RemoteDisconnected: Remote end closed connection without response`) and passes after.
Determination: The 502 was a dropped connection: the terminal-hosted server had no model action, so every model choice raised `AttributeError` and closed the socket with no reply, which the proxy showed as 502; `UiWalker.set_model` now runs the choice on the screen and any other exception is answered as a JSON 500 (red before, passed after; the same four test_web failures as before this task remain, test_webscreen and test_walker pass).

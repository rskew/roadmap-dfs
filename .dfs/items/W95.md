# W95 · The start walk form should have the fields in it rather than some fields on the form and some fields on the modal

## Summary

The web page's walk box now holds every field a walk starts with: Next, Agent, Budget and Chains, one place to fill in; what was typed is kept when the list redraws, and a server push leaves the box alone while a number is being typed in it, so the digits stay in the order typed. Start walk still opens a short "Start the walk?" dialog, but it holds no field: it says what starting does, with the box's numbers, and starts on a second tap. The Goal is met; the confirming step was kept on purpose, since the project's own rule for the terminal is that starting a walk is a deliberate second step, not one tap. The terminal screen's walk prompt is unchanged.

### W95.4 · Fix: a push while typing in the walk box's Budget or Chains scrambles the number
Parent: W95.2
Status: confirmed
Approach: In `scripts/web/index.html`, Budget (`#bud`) and Chains (`#par`) now sit in the walk box, which every server push redraws. The flow is `/api/events` "change", then `render(false)`, then `drawTasks()`, then `walkHtml()`. `S.walkDraft` keeps the value, and `render()` puts focus back on `#bud` by id, but the new input's caret lands at the start. So digits typed after the push go in front of the ones typed before it. Before W95 the fields were in the modal, which a push does not redraw (`S.dirty`). A probe showed it at 1280×800 and on an iPhone 13 viewport: open the walk box, click `#bud`, select all and type "1", call `render(false)` as a push does, then type "2". The field reads "21", not "12", and Enter opens a dialog saying "21 sessions in all". Fix it so a push cannot alter what is being typed in the box. Options: hold the box's redraw while focus is in `#bud` or `#par` and draw it once focus leaves, as `S.dirty` does for an open dialog; or redraw the rest of the list without replacing a focused field. Add a step to the `walk` flow in `scripts/ui_flows.mjs` that types one digit, calls `render(false)`, types a second and checks the value is both digits in order; it must fail on the current code. Also fix the Summary's claim that what was typed is "kept across the list's redraws", which is only half true now.
Determination: Confirmed: `drawTasks(true)`, which a push's render calls, keeps the existing `#walkbox` while focus is in `#bud` or `#par` and the walk is off, and a `focusout` catch-up redraws just the box once focus leaves (not mid-tap on its buttons); the new `walk` step types "1", calls `render(false)`, types "2" and reads "12", where the old code read "21". `test_the_walk_controls` and `..._stay_under_the_bar_as_the_list_scrolls` pass, and the full `test_web test_webscreen test_ui` run fails only flows that fail on main (pad, walktags, layout, markdown, bar-from-chats; the reorder flow failed once under load and passed three times alone). The first version redrew the whole list on focus leaving, which broke the walkpin drag step, so the catch-up replaces the box alone.

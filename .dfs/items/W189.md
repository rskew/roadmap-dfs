# W189 · Chat messages should have a copy to clipboard button

## Summary

Every message in the web chat dialog (yours, the agent's, prompts and error lines) now has a Copy button in its head that puts that message's text on the clipboard. An agent's reply is copied as the markdown it wrote. On a page served over plain http, where the browser has no clipboard API, it copies through a hidden selected box instead, and a toast says if copying failed. The terminal chat is unchanged, since it has no buttons and the terminal copies by selection.

## Goal

Chat messages should have a copy to clipboard button

## Tree

### W189.1 · Add a Copy button to each chat message in the web page
Status: confirmed
Approach: **The question**
- Can every message in the web chat dialog carry a button that puts that message's text on the clipboard?

**What this node does**
- In `scripts/web/index.html`, `chatDraw` draws a `Copy` button in the head of each message (you, agent, prompt, error; not the "Working on it" line). It carries the message's index, and the click handler (`chatcopy`) copies that message's raw text from the last chat state (the agent's markdown source, not the drawn HTML).
- It uses `navigator.clipboard.writeText`, and falls back to a hidden textarea with `execCommand("copy")`, because the page is often served over plain http on a LAN, where `navigator.clipboard` does not exist. It then shows a toast ("Copied." or an error).
- The button is at least `--hit` high, keeps its place when the log redraws, and does not change the log's scroll. Only the web page has buttons; the terminal chat is left as it is, since the terminal copies by selection.

**How we will know it worked**
- A new flow in `scripts/ui_flows.mjs` (run through `scripts/test_ui.py`) opens a chat with a you, an agent and an error message, grants clipboard permission, clicks Copy on each and reads the clipboard back. It also checks the fallback path with `navigator.clipboard` removed. A screenshot shows the button.
Determination: Each chat message now has a Copy button that copies its own text, with a fallback for pages without `navigator.clipboard`, and the Goal is met: the new flow passed, with the button shown in ![the chat with Copy buttons](.dfs/artefacts/c4964e64-eaf7-41f8-bb75-3645629a22f7.png)

### W189.2 · Fix: Copy buttons are torn out and rebuilt on every poll while the agent is busy
Parent: W189.1
Status: confirmed
Approach: In `scripts/web/index.html`, `chatDraw` sets `log.innerHTML` whole whenever its state signature changes. While a turn is busy (or `live`), `chatLoad` polls every 1.5 s and `busy_for` changes each time, so the whole log, with every Copy button, is replaced about every 1.5 s, which is when a reader waits and most wants to copy an earlier message. Two things follow. A button that has keyboard focus loses it on each redraw, so a keyboard or screen-reader user cannot rest on Copy and press Enter. A tap whose press lands on the old button and whose release lands on the new one gives no click, so some taps do nothing. The node's own text says the button "keeps its place when the log redraws", but `chat_copy` serves one fixed state, so the signature never changes and no redraw happens in that test. Nothing checks this claim. Fix it in the way this page already does elsewhere (give focus back to the same control after a draw, as `focusKey` and the grip redraw do; or update only the changed messages and the "Working on it" line instead of replacing the log). Then extend `chat_copy` in `scripts/ui_flows.mjs`: serve a busy state whose `busy_for` rises between polls, focus a Copy button, wait for a redraw, and check that focus is still on the same message's Copy button and that pressing Enter copies that message. Note that `node` is not on this session's PATH, so run the flow where `test_ui.py` does not skip.
Determination: A busy-turn poll now changes only the seconds in the "Working on it" line, a real redraw gives focus back to the same message's Copy button, and the extended `chat_copy` flow passed with the fix and failed without it.

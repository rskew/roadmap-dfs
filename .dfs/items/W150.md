# W150 · Bug

## Summary

After the runner commits a task's files, the worktree's index now matches HEAD, even when the repo's `pre-commit` hook stages a file such as `version.txt`. Before, that file stayed one count behind HEAD as a staged rollback, and the next merge refused over it. The fix is in `scripts/branch.py` (option A of the raise), so it holds for any repo with a staging hook. A test with such a hook fails without the fix and passes with it; the whole `test_chain.py` suite passes.

## Tree

### W150.1 · Re-sync the index after the runner's `--only` commit
Status: confirmed
Approach: **The question**
- When a repo's `pre-commit` hook runs `git add <file>`, does the runner's `git commit --only` (in `_commit_task_files`, `scripts/branch.py`) leave the real index behind HEAD for that file?

**Why it matters**
- The staged rollback makes the next merge see uncommitted changes, so every merge attempt costs a session.

**What this node does**
- Reproduce in a scratch repo with such a hook (done: HEAD and the work tree hold the bumped value, the index the old one, `git status` shows `MM`).
- In `_commit_task_files`, after a successful `--only` commit, run `git reset -q HEAD -- <paths changed by HEAD>` (from `git diff-tree --root --no-commit-id --name-only -r HEAD`) so the index matches HEAD for the files the hook added. Work tree files are untouched.
- Add a test in `scripts/test_chain.py` beside the other hook tests: a `pre-commit` that bumps and stages a file; after `branch.py merge`, `git diff --cached HEAD` in the worktree is empty. Show it red without the change.

**How we will know it worked**
- The new test fails without the reset and passes with it; the other `test_chain.py` tests pass.
Determination: The index disagreed with HEAD after a `--only` commit with a staging hook, and a `reset` of the files HEAD changed fixes it, so the node is confirmed and the Goal is met.

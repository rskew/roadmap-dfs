# W11 · Can't edit items

## Summary

The web page can now edit what it shows: "Edit task" changes a task's name and Goal, and "Edit" on an open or parked node changes its title and Approach. Confirmed and refuted nodes cannot be edited, because a determined node is history; add a node instead. A Goal with a line like `## Why` is refused, since it would split the task file. The Goal's wording was only "Can't edit items", so I took it to mean the web page, since the terminal already opens an item's file in `$EDITOR`. The dialogs' JavaScript was not run in a browser here (no node for the UI test); the server side is tested.

### W11.4 · Fix: a Goal with a `## ` line splits the task file when edited from the web page
Parent: W11.1
Status: confirmed
Approach: `tree.edit_task` (scripts/tree.py) writes the goal text verbatim as `t["sections"]["Goal"]`, and `render` emits it between `## Goal` and `## Tree`, so any goal line starting `## ` (a markdown heading a phone user may well type, e.g. `## Why`) becomes a new section on the next parse. Checked in a scratch repo: `edit_task("W1","Thing","Why\n\n## Why not\nbecause")` leaves `load()["goal"] == "Why"`, `order == ["Goal","Why not","Tree","Log"]`; the page then shows the goal truncated, and saving the dialog again drops "because" for good. A goal containing `## Log` produces a second Log section and the first edit_node afterwards duplicates the Log. Fix: make `edit_task` refuse (ValueError, so 409 in web.py `act`) a goal with a line matching the section-heading pattern `^##? ` that `split_sections` splits on (or otherwise keep it from being read as a heading), and add a test in test_tree.py (goal with `## Log` is refused and the file is byte-identical) and test_web.py (409). Check by running the probe above and `check.py --staged`.
Determination: Confirmed: `edit_task` now refuses (ValueError, 409 on the page) a goal with any line `split_sections` reads as a section heading, via the shared `SECTION_HEAD` pattern, leaving the file byte-identical; the new `test_tree` and `test_web` cases pass, and the only failure in those suites is the chat test, which cannot run the sandbox's agent stub.

### W11.5 · Minor findings from the review
Parent: W11.4
Status: confirmed
Approach: One line each:
- `edit_node` flattens a multi-line Approach into one line (`" ".join(approach.split())`) while the dialog's Approach is a textarea; either say so in the label/docstring or keep the line breaks as wrapped lines.
- `edit_node` and `task_json` detect an archived Approach by comparing the field to the literal `"archived."`; a real Approach that reads exactly that is made uneditable, so use the archive module's own marker/helper if there is one.
- `test_tree`/`test_web` do not cover a goal or approach containing heading-like lines, nor `edit_task` when the Goal section is missing from the file (the `order.insert(0, "Goal")` branch).
- The dialogs' JavaScript (`editTaskForm`, `editNodeForm`, the `edittask`/`editnode` handlers) was never run in a browser; run `test_ui.py` where node and a browser exist, and add a flow to `ui_flows.mjs` for each dialog.
Determination: Confirmed for the first three findings (the Approach label and docstring say line breaks become spaces, `SHELF_STUB` replaces the literal, tests cover heading-like lines and a missing Goal section); the dialogs' JavaScript still has not run in a browser, since this sandbox has chromium but no node for `test_ui.py`.
Ask: Can `test_ui.py` be run where node and a browser exist, and a flow added to `ui_flows.mjs` for each edit dialog? I left it, since a flow I cannot run would be a guess.

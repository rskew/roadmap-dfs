# W116 · Github mode

## Summary

With `.dfs/github` written, a finished task is held on its branch instead of merged. The author's Open PR mark (screen `P`, the web button, or `github.py pr`) rebases, pushes and opens its pull request with `gh`. The walk then polls the pull request: each comment or review becomes an open node worked and raised on as usual, reviewed fixes are pushed to the branch, a pull request merged on GitHub is landed locally and its worktree and branch removed, and one closed unmerged is a raise. The Goal is fully met; nothing is posted back to GitHub, and the mode was tested against a fake `gh` and a bare remote because `gh` is not logged in here. The README's "GitHub mode" section describes it.

## Goal

Tasks aren't merged when complete but instead created as pull requests once marked as ready by the user. Watch PRs for comment and review, creating review items as nodes and actioning and raising as normal.

### W116.10 · Fix: landing a merged pull request commits on local main, so the next landing cannot fast-forward
Parent: W116.8
Status: open
Approach: `github.land` fast-forwards the default branch to `<remote>/<default>` and then commits the task's log there (`_commit_task_files(task, work_root, "the pull request is merged")`), never pushing it, so after every landing local main is one commit ahead of the remote (test_chain's end-to-end test shows `git log hub/master..master` = "W1: the pull request is merged"). The next pull request merged on GitHub that does not carry that commit (one opened before the landing, or any squash/rebase merge) cannot be fast-forwarded: `land` raises asking the author to run `git pull --ff-only <remote> <default>`, which fails too ("Diverging branches can't be fast-forwarded"), and the task stays unlanded with its worktree. Reproduced by committing a local-only `.dfs/items/W0.md` on main before `merge_on_github` + `watch`: the raise is logged and the advised pull exits 128. Choose how the landing log reaches the remote or is reconciled (push it, rebase local-only roadmap commits onto the fetched default branch, or keep the log off main until the author pushes) so that two pull requests landed in a row both land, and add a test_chain test that lands two merged pull requests in turn, one squash-merged.

### W116.11 · Fix: line comments past the first page are never turned into nodes
Parent: W116.4
Status: open
Approach: `github._pull` reads line comments with `gh api repos/<o>/<r>/pulls/<n>/comments` without `--paginate`, and the REST endpoint returns 30 per page oldest first, so on a pull request with more than 30 line comments every later one (including each new one) is never seen and never becomes a node, silently. Add `--paginate` (it concatenates JSON arrays, so check the output is still parsed as one list: `gh api --paginate` emits `[...][...]` for several pages unless `--slurp` or a `--jq '.[]'` per-line form is used), and extend test_github's Watch test with a fake `gh` serving two pages.

### W116.12 · Fix: a task held for its pull request lets the tasks under it start without its code
Parent: W116.2
Status: open
Approach: In GitHub mode a held task reads `done` (`tree.status_of`), so `state.next_items`/`held_by_parent` no longer hold its children in `.dfs/order.md`: the walk cuts a child's worktree from the default branch, which lacks the parent's work until its pull request is merged on GitHub (and a later PR comment can reopen the parent under a child already built). `next_items`' own docstring names this hazard for a parent still merging ("a child cut before that merge lands starts from a default branch without the parent's work"). Choose and test the behaviour: hold a child while an ancestor is held unmerged or its pull request is open (as a busy parent is held), or cut the child from the parent's branch; a test in test_state/test_walker should show a child under a held parent is not picked (or starts with its code).

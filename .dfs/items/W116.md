# W116 · Github mode

## Goal

Tasks aren't merged when complete but instead created as pull requests once marked as ready by the user. Watch PRs for comment and review, creating review items as nodes and actioning and raising as normal.

## Tree

### W116.1 · GitHub mode's lifecycle, and its switch `.dfs/github`
Status: confirmed
Approach: Add the per-roadmap switch: `.dfs/github` holds the git remote to push to (`origin` when written empty), its absence is today's local merge. `scripts/paths.py` gains `github_file`, `read_github` and `write_github` beside the theme's, and `roadmap_parts` lists the file; a test in `scripts/test_theme.py`'s style covers on, off and a bad remote name. The nodes below build the lifecycle the Hypothesis names.
Hypothesis: In GitHub mode a finished task (review passed, or accepted) is not merged but held with its branch and worktree; the author's own "Open PR" mark, a log entry of its own and not the draft/ready mark, pushes `dfs/<task>` and runs `gh pr create`; the walk polls the PR with `gh`, each new comment or review becomes an open node (text and link in its Approach) worked and raised on as normal, the branch is pushed after each work session, and the PR merged on GitHub removes the worktree and branch and leaves the task done (closed unmerged is a raise). Wrong if "ready" meant the existing draft/ready mark or the accept, if the PR should open at once as a GitHub draft PR, or if comments should also be answered on GitHub. .dfs/artefacts/0552cf42-be26-4f41-a90b-c4a234172e40.html
Evidence:
- for: the Goal says a task is "created as pull requests once marked as ready by the user", which names a step of the user's after completion, not completion itself; `branch.merge` is today the one place a finished task leaves its branch (called from `run.sh`'s `merge_item` and `tree.py`'s accept), so the hold and the mark replace a single call.
- against: the roadmap already has a `ready` log kind (the end of a draft), so "marked as ready" may mean that mark; the reading above keeps the two apart.
- for: `gh auth status` here says not logged in, so the PR steps are testable only against a fake `gh`, which the nodes below plan for.
Determination: `.dfs/github` turns GitHub mode on with its remote and is part of the roadmap; `test_github.py`'s four tests and `test_ignored`/`test_init` pass, so the switch holds and the lifecycle is planned beneath it.

### W116.2 · Hold a finished task unmerged in GitHub mode
Parent: W116.1
Status: open
Approach: When `.dfs/github` is on, `branch.merge` (called by `run.sh`'s `merge_item` after a passing review and by `tree.py`'s accept) commits the task's left-over files onto `dfs/<task>` and returns "held" instead of rebasing and merging; `run.sh` ends the chain done; `status_of` says the task is done and waiting for the Open PR mark. Tests in `test_chain.py` and `test_tree.py`.

### W116.3 · The author's Open PR mark pushes the branch and opens the PR
Parent: W116.2
Status: open
Approach: A new log kind `pr` (`tree.py pr <task>`): rebase `dfs/<task>` onto the default branch, `git push -u <remote> dfs/<task>`, `gh pr create --base <default> --head dfs/<task>` with the task's title and Summary (`branch._task_details`) as body, and log the PR's url. A push or `gh` failure is printed and logs nothing. Tested with a fake `gh` on PATH and a bare repo as the remote.

### W116.4 · Watch an open PR: comments and reviews become nodes, a merge closes the task
Parent: W116.3
Status: open
Approach: A new `scripts/github.py watch [<task>]`: for each task whose last `pr` entry names an open PR, read its comments, reviews and review comments through `gh api`, add one open node per new one (author, text, url in the Approach; ids already turned into nodes kept in a `github` log entry so none is added twice, and the PR's own author's bot comments skipped); a PR merged on GitHub removes the worktree and local branch and logs it merged; one closed unmerged is a raise. Tests with a fake `gh`.

### W116.5 · Push the branch after each work session on a task with an open PR

# W117 · Pull-down refresh should work from the top bar when in item list

## Summary

Pull-down refresh on the task list is now the browser's own: the installed page gets the native pull-to-refresh, and the page no longer has a gesture of its own that cancelled the browser's drag on the top bar. The bar and the list set no touch or overscroll limits, and a flow checks that a drag down from the bar cancels no touch. The Goal is met as far as the page can see: native pull-to-refresh does not run in the headless browser used here, so the pull itself was not seen on a real phone, and no other cause of it being disabled on the list was found in the page.

## Goal

Pull-down refresh should work from the top bar when in item list

## Tree

### W117.1 · A pull gesture of the page's own on the top bar of the task list
Status: confirmed
Approach: In `scripts/web/index.html`, touch listeners on `#bar` that act only on the task list (`route().view === "tasks"`, no dialog open): a finger that lands on the bar and drags down shows a `#pull` strip under the bar that grows with the drag ("pull to refresh", then "release to refresh" from 72px), and let go past that reloads the page (`location.reload()`, which brings the list back at its scroll through `sessionStorage`); a non-passive `touchmove` cancels the browser's pan while pulling, and `chrome()` gives the bar the class `pulls` on the list, whose `touch-action: pan-x pan-down` keeps a downward drag there from scrolling the list up first. A `pullrefresh` flow in `scripts/ui_flows.mjs` (360x260 touch, list scrolled to 120) drives CDP touch events on the bar; the README's phone section names the gesture.
Hypothesis: The author pulls in the installed page (standalone, from the manifest), where neither Chrome nor Safari offers its own pull-to-refresh, so the page must make the gesture itself; a refresh is a full reload, as the browser's own pull-to-refresh is, and a pull on the bar works wherever the list is scrolled, since the bar is pinned. Wrong if the author meant the browser's own pull-to-refresh in a browser tab, blocked by something on the page, or a refresh that re-reads the list without reloading the page. .dfs/artefacts/a5f9d408-642f-4963-ae19-3f1d6486a423.html
Evidence:
- for: `scripts/web.py` builds the manifest with `display="standalone"`, and nothing in `index.html` or `sw.js` made a pull gesture before this node (grep for touch, pull and refresh found none), so the installed page had no refresh by pulling at all.
- for: the `pullrefresh` flow passes: a 40px drag from the bar shows "pull to refresh" and reloads nothing, a 120px one shows "release to refresh" with the list held at 120 and reloads the page on letting go, the list comes back at 120, and a pull on W9's screen does nothing; against main's `index.html` the same flow fails (`#pull` is null). ![The task list on a phone mid-pull: "release to refresh" under the bar](.dfs/artefacts/cdc657ce-1fc7-4d80-bc53-a8d3d90a38ce.png)
Determination: Confirmed: on the task list a drag down from the top bar reloads the page wherever the list is scrolled, shown by the `pullrefresh` flow; `test_ui`, `test_web` and `test_webscreen` (177 tests) fail only layout, barfromchats, markdown and walktags, which fail the same against main's page.

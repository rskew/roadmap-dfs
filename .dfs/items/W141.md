# W141 · Allow adding steering messages to a chat

## Summary

A message the author sends from the web page while an agent is answering a chat turn no longer waits for the turn to end. It is left in that chat's inbox and the agent reads it at its next step, through hooks for claude and codex, a plugin for opencode and an agent of its own for kiro. The page keeps Send on (labelled Steer) and marks each such message waiting, then read. A message the turn never got to is sent as one new turn on the same session; if the turn was stopped or failed it is not sent, but its text stays in a note in the chat so it can be sent again, and a message left waiting by a server that restarted is treated the same way when the next turn starts. The Goal is met for all four agents on the server side; the page script and its new browser check were not run in a browser, because this sandbox has no browser that renders text.

## Goal

Allow adding steering messages to a chat

## Tree

### W141.1 · A message sent to a busy claude chat turn reaches it through an inbox
Status: confirmed
Approach: **The question**
- Today `Chats.send` in `scripts/chat.py` refuses a message while the page's headless turn is answering ("it is still answering the last message"), and the page disables Send. How can a message sent in that time steer the turn instead?

**What this node does**
- Give each scope a chat inbox, `<run root>/chat/<scope>/inbox` (with `delivered/` beside it), written with `runs.post_message`. `Chats.send` on a busy scope posts there instead of raising, and logs it in the chat log. `Chats.turn` gives the box to `run.sh --chat-turn` as `CHAT_INBOX`.
- `run.sh --chat-turn` under claude adds `--settings` with the `inbox.py` hooks over that box, as a chain session gets. The other agents come in the nodes after.

**How we will know it worked**
- `test_chat.py` and `test_claude_chat.py`: a message sent during a stand-in claude turn is in its next request and is shown as delivered; a send with no turn running still starts one.
Hypothesis: "Steering" means a message sent while the agent answers reaches that same turn at its next step, as the chain inbox does, and not one held until the turn ends. Wrong if the author wants a message held until the answer is done, or if claude's hooks do not fire in a headless `-p` chat turn. .dfs/artefacts/34f70ca4-240d-4906-b9c6-004fb1a7c103.html
Evidence:
- for: `python3 -m unittest test_inbox.RealClaude` (claude 2.1.317 `-p` with the inbox hooks, a stand-in model) passed 3 of 3: the mid-tool-call and the about-to-stop messages both reach the next request. A chat turn is the same `-p` call.
- for: `test_inbox.RealClaudeChat` drives `Chats.send` twice around a real claude via `run.sh --chat-turn`: the second request holds the steering message, the first does not, and the page state shows it `delivered`.
- against: the same test with `chat.STEERED` emptied (the old behaviour) fails with "it is still answering the last message", so the old code refused it; no evidence yet that codex, opencode or kiro turns read the box, which the later nodes test.
- against: the browser check of the page above rendered no text in this sandbox (the stock template fails the same way), so the page was checked for structure only.
Determination: Confirmed for claude: a message sent during a chat turn is left in the scope's inbox, is in the turn's next request, and shows as waiting then delivered; codex, opencode and kiro still refuse it until their nodes.

### W141.2 · A steering message the turn never read becomes the next turn
Parent: W141.1
Status: confirmed
Approach: **The question**
- A message that arrives after the agent's last step (or for kiro after its last tool call) stays in the box. What happens to it?

**What this node does**
- When `Chats.turn` ends and the box still holds messages, `Chats` sends them as one new turn on the same session (so the author never has to resend). If the turn was stopped, the leftovers are dropped and said so, as a stopped turn's pending message is today.

**How we will know it worked**
- A test sends during a turn whose stand-in never reads its inbox: the message is answered by a second turn, once, and the state shows it as sent and answered.
Determination: Confirmed: `Chats.unread` sends a steering message the turn never read as one new turn on the same session (shown as a sent message, once), and drops it with a note in the chat log when the turn was stopped or failed; test_chat (all of it) and test_inbox.RealClaude(Chat) pass.

### W141.7 · An unread steering message is sent as the next turn, or shown in a note when the turn was stopped or failed
Parent: W141.2
Status: confirmed
Approach: **The question**
- A steering message that arrives after the agent's last step is still in the box when the turn ends. `Chats.unread` in `scripts/chat.py` decides what then happens. W141.2 chose without saying it was a choice. Is that choice sound, and was the text of a dropped message lost?

**What this node does**
- States the choice as a Hypothesis with its page, and settles the lost text: when the turn was stopped or failed, `Chats.unread` still removes the messages from the box and `steers.json` (they are not sent), but now puts their text in the chat's error note ("N message(s) sent during the turn were never read and are not sent: ...") and in the chat log, so the author can send them again.
- `test_chat.py`'s stopped-turn test checks the text is in a note and not sent as a message.
Hypothesis: A steering message the turn never read is sent on its own as one new turn when the turn was answered, and is not sent when the turn was stopped or failed, because the author stopped or the agent broke and the message may no longer fit. Wrong if the author wants an unread message kept in the box for their own next send, or sent after a stopped or failed turn too. .dfs/artefacts/21890d10-ddb1-4465-8475-4fd3881141a9.html
Evidence:
- for: `test_a_steering_message_the_turn_never_read_is_sent_as_the_next_turn_once` (stand-in claude that reads no inbox): the message is answered by one second turn on the same session and shows as a sent message, so an answered turn needs nothing from the author.
- against: before this node a stopped turn's unread message left no trace in the page (`test_a_steering_message_a_stopped_turn_never_read_is_dropped` found its text nowhere), so the author had to retype it from memory; the note now carries it, and the test fails without the change.
- against: the page .dfs/artefacts/21890d10-ddb1-4465-8475-4fd3881141a9.html was checked with `artefact_check.sh`, which reports a blank page because this sandbox renders no text (the stock template fails the same way), so the page was not looked at.
Determination: Confirmed: sending an answered turn's unread message as the next turn stays, a stopped or failed turn's is still not sent but its text now stays in a note and the chat log, and the author's answer on the page can overturn either; test_chat and test_inbox.RealClaudeChat pass (with `TMPDIR` off the sandbox's noexec `/tmp`).

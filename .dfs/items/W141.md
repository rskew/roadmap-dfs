# W141 · Allow adding steering messages to a chat

## Goal

Allow adding steering messages to a chat

## Tree

### W141.1 · A message sent to a busy claude chat turn reaches it through an inbox
Status: confirmed
Approach: **The question**
- Today `Chats.send` in `scripts/chat.py` refuses a message while the page's headless turn is answering ("it is still answering the last message"), and the page disables Send. How can a message sent in that time steer the turn instead?

**What this node does**
- Give each scope a chat inbox, `<run root>/chat/<scope>/inbox` (with `delivered/` beside it), written with `runs.post_message`. `Chats.send` on a busy scope posts there instead of raising, and logs it in the chat log. `Chats.turn` gives the box to `run.sh --chat-turn` as `CHAT_INBOX`.
- `run.sh --chat-turn` under claude adds `--settings` with the `inbox.py` hooks over that box, as a chain session gets. The other agents come in the nodes after.

**How we will know it worked**
- `test_chat.py` and `test_claude_chat.py`: a message sent during a stand-in claude turn is in its next request and is shown as delivered; a send with no turn running still starts one.
Hypothesis: "Steering" means a message sent while the agent answers reaches that same turn at its next step, as the chain inbox does, and not one held until the turn ends. Wrong if the author wants a message held until the answer is done, or if claude's hooks do not fire in a headless `-p` chat turn. .dfs/artefacts/34f70ca4-240d-4906-b9c6-004fb1a7c103.html
Evidence:
- for: `python3 -m unittest test_inbox.RealClaude` (claude 2.1.317 `-p` with the inbox hooks, a stand-in model) passed 3 of 3: the mid-tool-call and the about-to-stop messages both reach the next request. A chat turn is the same `-p` call.
- for: `test_inbox.RealClaudeChat` drives `Chats.send` twice around a real claude via `run.sh --chat-turn`: the second request holds the steering message, the first does not, and the page state shows it `delivered`.
- against: the same test with `chat.STEERED` emptied (the old behaviour) fails with "it is still answering the last message", so the old code refused it; no evidence yet that codex, opencode or kiro turns read the box, which the later nodes test.
- against: the browser check of the page above rendered no text in this sandbox (the stock template fails the same way), so the page was checked for structure only.
Determination: Confirmed for claude: a message sent during a chat turn is left in the scope's inbox, is in the turn's next request, and shows as waiting then delivered; codex, opencode and kiro still refuse it until their nodes.

### W141.2 · A steering message the turn never read becomes the next turn
Parent: W141.1
Status: confirmed
Approach: **The question**
- A message that arrives after the agent's last step (or for kiro after its last tool call) stays in the box. What happens to it?

**What this node does**
- When `Chats.turn` ends and the box still holds messages, `Chats` sends them as one new turn on the same session (so the author never has to resend). If the turn was stopped, the leftovers are dropped and said so, as a stopped turn's pending message is today.

**How we will know it worked**
- A test sends during a turn whose stand-in never reads its inbox: the message is answered by a second turn, once, and the state shows it as sent and answered.
Determination: Confirmed: `Chats.unread` sends a steering message the turn never read as one new turn on the same session (shown as a sent message, once), and drops it with a note in the chat log when the turn was stopped or failed; test_chat (all of it) and test_inbox.RealClaude(Chat) pass.

### W141.3 · The web page lets the author send while the agent answers
Parent: W141.1
Status: confirmed
Approach: **What this node does**
- `scripts/web/index.html` keeps Send enabled while `st.busy` for a headless turn, labels it as steering, and shows a steering message as waiting until it is read, then as delivered (`runs.messages` gives the state). Stop stays. `chat.py` `state` returns the steering messages with their state.
- README's chat section and `chat.py`'s docstring say what steering is and when a message waits.

**How we will know it worked**
- `test_web.py` / `ui_flows.mjs`: the Send button is enabled during a busy turn and a message sent then shows as waiting, then delivered.
Determination: Confirmed for the server side only: `Chats.state` returns `steer` and each steering message with its waiting or delivered state, and `index.html` keeps Send enabled (labelled Steer) during a steerable turn and tags those messages, but the page script was not run in a browser here, because this sandbox renders no text; test_chat passes, test_web has the same 2 failures as before.

### W141.4 · Queue the message as the next turn, with no hooks
Status: parked
Approach: In `Chats.send`, a message to a busy scope waits in memory and goes as the next turn when the current one ends; no change to `run.sh` or the agents.
Determination: Parked: it is not steering, since the message reaches the agent only after the answer it meant to change; take it if the inbox hooks cannot be made to fire in a headless chat turn for most agents (W141.2 already needs this path for what the hooks miss).

### W141.6 · Kiro chat turns read the inbox through their own agent
Parent: W141.1
Status: open
Approach: Kiro finds its hook only in the agent file `.kiro/agents/dfs-inbox.json` in the working directory, which names one box. Chats run in the shared work root, so two chats, or a chat and a work session there, would overwrite each other's box. Name the agent by the box (`inbox.py` `install_kiro_agent`/`kiro_agent` take a name; `self_as_subagent` refuses any `dfs-inbox*` name), install it in `run.sh --chat-turn`, and check with `test_kiro_chat.py`.

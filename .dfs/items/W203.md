### W203.1 · Pin the two-file format and settle the open questions
Status: confirmed
Approach: **The question** - What exactly is the status file, the history file and the link syntax, and what do we choose for the six open questions in the goal's document? **Why it matters** - Every later node (parser, migration, checks, briefing) builds on these choices. A wrong one found late costs a rewrite. **What this node does** - Writes `docs/history-format.md`: the status file's sections (Goal and summary, Decisions in force, Live tree, Not taken, Raises), the history file's per-node sections and log, `Supersedes:` and `Tags:` fields, a `superseded` status, file names and how branch parts map. - Answers each open question as a stated choice with its reason. Adds one Hypothesis, with an answer page, for the choices the author may want the other way. - Adds a fixture task in the new format for the tests that follow. **How we will know it worked** - The doc covers every item in the goal's document, and a small hand-written fixture task is accepted by the later parser.
Hypothesis: Three choices stand: superseded is derived from the `Supersedes:` links of confirmed nodes and never stored; each branch part has its own history file; the log stays in its own file. Wrong if the author wants a stored superseded status, one history per task with tagged ids, or the log inside the history file. .dfs/artefacts/d4f7bca0-c9fe-41e7-8eb2-d147a8829147.html
Determination: Confirmed: `docs/history-format.md` pins both files, the fields, the links and the six answers, and `scripts/fixtures/history/` holds a hand-written task (W9) in that format.

### W203.2 · History module: parse, append and render the per-node history file
Parent: W203.1
Status: confirmed
Approach: **The question** - Can one module read and write the history file so that a node's full text, every Evidence line and the log survive a round trip? **What this node does** - Adds a module (not `history.py`, which is taken by session metrics) that parses the history file into the same node dict shape `dfs_tree` uses, renders it back byte for byte, and appends a line to a node's section without touching other lines. **How we will know it worked** - New tests: parse then render gives the same text; an append changes only the end of one section; Evidence comes back for every node.
Determination: Confirmed: `scripts/taskhistory.py` parses the fixture history into `tree.parse_nodes`-shaped nodes (last line wins, Evidence for every node), renders it byte for byte and appends inside one section only; its 7 new tests pass.

### W203.3 · Migration: old task file, archive and log into a history file, losslessly
Parent: W203.2
Status: confirmed
Approach: **The question** - Can an old-format task (task file, `**<id> Field**:` archive lines, log file, archived `**Log**:`) become a history file with nothing lost? **What this node does** - Adds `tree.py migrate <task>`: merges each node's file fields with its archive lines, Evidence included, in written order; merges the logs by time; then checks every line of the old files appears in the history. - Runs it over every task in `.dfs/items` and `.dfs/archive/items` in a test. **How we will know it worked** - The lossless check passes for every existing task, and fails on a fixture with a line deleted.
Determination: Confirmed: `tree.py migrate` writes a history file and a merged log for an old task, refuses when any old line would be lost, and all 203 tasks in the repo migrate losslessly and read back the same; a fixture with a line deleted is found.

### W203.5 · Show, Supersedes, superseded status and tags

### W203.8 · check.py rules for the new format
Parent: W203.6
Status: open
Approach: **The question** - Can the checker hold the hand-kept parts to the history, so the status file cannot go stale? **What this node does** - Adds to `check.py`, for new-format tasks only: (1) each decision line cites a node or answer that exists; (2) a cited node is confirmed and not superseded; (3) a commit confirming a node with `Supersedes:` also removes or rewrites decision lines citing what it supersedes; (4) every open, started or parked node is in the live tree and no other; (5) the history file only grows, except a merge keeping both sides' lines; (6) the status file is under budget, the only size rule left, and it does not block adding a node. The critic's brief asks it to sample decision lines against the evidence. **How we will know it worked** - One red-then-green test per rule, each refused without the fix.

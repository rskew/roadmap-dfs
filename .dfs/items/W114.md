# W114 · Bug reports

## Summary

The tool now rewrites task files, their archives and `order.md` by writing a temp file beside them and renaming it over, so a process killed mid-write leaves the old text instead of an empty file, and a temp file a kill leaves behind is swept by the next write. If a task file is empty anyway while the branch has it, `run.sh` refuses to start and says how to restore it, instead of briefing a finished tree as a task to plan. When either screen starts, the terminal one or the standalone web page, it closes each run record left open by a process that is gone, marks it lost and logs a died line; it only closes records from its own pid namespace, which `run.sh` now records, so a screen on the host cannot close a containerised walk's live chain. It still does not restart the walk on its own. The third report, a new task's first walk refusing to start, needed no new code: the installed version predated the change that moves a never-committed task file into the worktree, which the tests show now covers a fresh branch, a reused one and a leftover worktree, so creating a task still does not commit it on the author's branch.

## Goal

roadmap-dfs f9d0b9b: two stops of the walk, three defects

1. A killed walk leaves the task file empty (W118, Oct 23)
run.sh W118 14 started run 5, the implementation review, at 11:52:37 UTC. Within the same second, .dfs/worktrees/W118/.dfs/items/W118.md was truncated to 0 bytes and run-5.json stayed empty.
No died or hold line was written. meta.json still says open for a pid that is gone, and the TUI restarted in a new container on Oct 24.
With the empty file, state.py reported "no nodes yet — plan the task". A restart would have planned W118 from scratch over a finished 96-line tree.
Cause: tree.py rewrites task files with p.write_text(render(t)) in compact, shelve, append_log, edit_task, delete_node, edit_node, start_node and add_node. That call truncates and then writes, so a kill in between leaves an empty file. A full disk is unlikely, since 289 GB was free. I don't know which of those functions was running, or what killed the process.
Fix suggested: write through a temp file in the same directory and os.replace it, as runs.py and agent.py already do. This applies to the archive and order.md too.
Work-around used: git checkout -- .dfs/items/W118.md in the worktree restored the file from the branch HEAD. Anything the review had written but not committed was lost.

2. A walk killed with its supervisor leaves no record
died and hold lines come from the supervisor, so when it dies too, nothing records the end and nothing restarts the walk.
Fix suggested: on start, the TUI closes any meta.json that is open while its pid is dead, with a died line saying the supervisor was lost.
Fix suggested: on start, run.sh refuses a task file that is empty while the branch HEAD has a non-empty version.

3. A new task's first walk refuses to start (W127, Oct 25)
run.sh W127 12 stopped at 15:21:47 UTC with "a session could not be briefed: the worktree … has no .dfs/items/W127.md … the branch carries only what git tracks".
A task created from the TUI or chat is written to .dfs/items/<task>.md but not committed. Its worktree is cut from git, so the file is missing. W117 and W118 hit the same problem and were fixed by hand in 2b5b4d6.
Fix suggested: creating a task commits its file and its place in order.md. Failing that, branch.py enter copies untracked task files into the new worktree, or commits them, instead of stopping the walk.
Work-around used: I committed the file on main as 03fe0bc and removed the empty dfs/W127 worktree and branch so the walk recuts them.

### W114.1 · Write task files, their archive and order.md through a temp file and os.replace
Status: confirmed

A `test_tree` test makes `os.replace` raise during each rewrite and checks the task file keeps its old text and no temp file is left; `test_tree`, `test_order` and `test_tui` pass.
Determination: Every rewrite of a task file, its archive, `order.md` and an author's edit put back after a merge now goes through `paths.write_atomically`: the new `AtomicWrites` test, with `os.replace` failing, finds all eight `tree.py` rewrites leave every `.dfs` file as it was (it fails on all eight with the old code) and a rewritten file keeps its mode, and `test_tree`, `test_order`, `test_web`, `test_screen`, `test_chain`, `test_ignored` and `test_walk` pass with TMPDIR inside the repo (two tests fail under the noexec /tmp before and after).

### W114.5 · Fix: close lost runs when the standalone web screen starts too, and only runs of the screen's own pid namespace
Parent: W114.3
Status: confirmed
Approach: `runs.close_lost` is called only from `tui.UI.__init__` (`scripts/tui.py`, after `discover_runs()`), so `web.py` run on its own (`web.main` → `serve` → `walk.HeadlessWalk`, its own walk) never closes a record its dead chains left open. That is the screen the README sets up to come back after a reboot (`sandbox daemon dfs-web`), and a reboot or container restart is exactly how a chain dies with its supervisor: the restarted page shows the run as died, but `meta.json` stays open and no died line is written. Call `close_lost` once as `HeadlessWalk` (or `web.main` when it makes its own walker) starts, writing the same died line through its `event` (the same `activity.log`), and add a test beside `test_runs.CloseLost` that starts the headless walk over a dead record. A second problem is in `close_lost` itself. It decides "dead" with `pid_is_chain`, which reads `/proc/<pid>/cmdline` in the screen's own pid namespace, but `meta.json`'s pid is `run.sh`'s `$$` in the chain's namespace. Each `sandbox` container has its own namespace (`docker run`, no `--pid`), so a screen started on the host or in another container while a containerised walk runs reads that walk's live chains as gone. It then writes `finished`/`stop: lost` into their `meta.json`. After that the owning screen's `run_dirs` reads them as not live, its `walk_tick` judges them `lost` and turns the walk off, and `walk_foreign` no longer counts them as busy, so a second chain can be started on the same task. Before W114 a cross-namespace screen only displayed these runs wrongly; now it rewrites them. Settle it by recording the chain's namespace in `meta.json` (e.g. `readlink /proc/$$/ns/pid` beside `pid` in `run.sh`'s `meta_set`) and closing only records from the screen's own namespace (records without it treated as before). Otherwise, if the author says one screen per repo across namespaces is not supported, write that down as the node's Hypothesis.
Determination: The standalone page now closes lost runs as it starts (`web.main` calls the new `WalkMixin.close_lost_runs`, which the terminal screen uses too) and `close_lost` closes only records from its own pid namespace, which `run.sh` now records as `pidns` (records without one are judged as before): the new `test_runs` tests for the headless walk and for a record from another namespace, and the `test_chain` check of `pidns` in `meta.json` (it fails with the old `run.sh`), pass with `test_runs`, `test_webscreen`, `test_web`, `test_screen`, `test_walk`, `test_walker`, `test_live` and `test_chain`.

### W114.6 · Minor findings from the review
Parent: W114.1
Status: confirmed
Approach: Tidy these alongside W114.5:
- `tree.compact` and `tree.shelve` write the archive before the task file, so a kill between the two leaves the moved entries in both, and the next compact archives them again (duplicated, not lost). Say so in a comment, or make the second write tolerate it.
- `paths.write_atomically` leaves a `.W1.md.XXXXXX` temp file in `.dfs/items` when SIGKILL lands between `mkstemp` and `os.replace` (the `except` never runs). It shows as untracked dirt and nothing removes it.
- `paths.write_atomically` is followed by three blank lines instead of two.
- `run.sh`'s empty-task-file check runs `git show HEAD:<rel>` with `rel` relative to the work root (the CWD). For a `.dfs` below the git toplevel, that path is wrong and the check passes silently; `HEAD:./<rel>` is relative to the CWD.
- `runs.close_lost` writes `finished` with `time.strftime("%Y-%m-%dT%H:%M:%S%z")` (`+0000`), while `run.sh` writes `date -Is` (`+00:00`). The page shows both.
- `walk.WALK_STOP["lost"]` is reached only when another screen closes one of this walk's own chains. A walk judges only chains it started, and `close_lost` runs at startup, before there are any. W114.3's "the walk reads `lost` as a stop" describes a path ordinary use never takes. Say that in a comment beside the entry.
Determination: All six minor findings are dealt with: comments on the archive-first write order and on the `lost` stop, a sweep of stale `.name.XXXXXXXX` temp files by `write_atomically`, the stray blank line, `HEAD:./<rel>` in `run.sh`, and a `date -Is`-style `finished` in `close_lost`: the new stale-temp and timestamp tests pass, `git show HEAD:./f` was confirmed in a subdirectory where `HEAD:f` fails, and `test_tree`, `test_runs`, `test_order`, `test_webscreen`, `test_web`, `test_screen`, `test_walk`, `test_walker`, `test_live`, `test_ignored` and `test_chain` pass.

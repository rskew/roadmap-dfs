# W48 · Chat in the tui has weird line wrapping since we added the background chat sessions

## Summary

A chat that runs in the background now starts at the size of the screen's terminal, instead of a fixed 40 rows by 120 columns, and is resized whenever the terminal's size changes, including a change made while a prompt or dialog is open, so what it wraps while nobody looks matches the width it is later looked at in. This is the cause found by reading the code, and it is tested with a stand-in agent; the real claude is not installed here, so the wrapping in a real chat was not seen. Attaching still resizes the chat to the terminal as before, and a chat attached at the time is left to that.

## Goal

Chat in the tui has weird line wrapping since we added the background chat sessions

## Tree

### W48.1 · Start a background chat at the width of the terminal it will be looked at in
Status: confirmed
Approach: `Relay.start` (scripts/ptyrelay.py) gives every chat a fixed 40x120 pty when no size is passed, and the web page starts chats while the screen is on curses, so a claude draws and wraps its first screens at 120 columns and `attach` then resizes it under a terminal that never saw them. Default the pty to the size of the process's own terminal (fixed 40x120 only when there is none), and make the host resize every running chat when the screen is resized (`ChatHost.resize`, called on KEY_RESIZE in scripts/tui.py). Check with test_ptyrelay.py: an agent that prints `stty size` starts at the terminal's size, and a resize reaches it.
Determination: A background chat now starts at the size of the screen's terminal and follows the screen's resizes; test_ptyrelay.py passes (24 tests), but with no claude here the wrapping itself was not seen.

### W48.2 · Resize the background chats from the poll tick, so a resize made inside a prompt or dialog reaches them
Parent: W48.1
Status: confirmed
Approach: Only the main loop's KEY_RESIZE (scripts/tui.py `loop`) calls `ChatHost.resize`; the prompt input's getch loop and the dialogs swallow KEY_RESIZE, so a resize made while one is open leaves the chats at the old width, which is the wrapping W48 is about. Add `UI.follow_terminal_size`, which compares `ptyrelay._terminal_size()` with the size last given to the chats and calls `chat_host.resize` when it changed; call it from `poll()` and from the KEY_RESIZE branch. Also test in test_ptyrelay.py that `Relay.resize` leaves an attached chat alone. Check: test_ptyrelay.py passes, and a UI with a stand-in chat host gets one resize per size change.
Determination: The screen now compares the terminal size on every poll tick and on KEY_RESIZE and tells the background chats once per change, so a resize made inside a prompt or dialog reaches them; test_ptyrelay.py passes (26 tests), and no real claude was run here.

### W48.3 · Test that the poll tick follows the terminal size
Parent: W48.2
Status: confirmed
Approach: The reviews found nothing tested that `UI.poll` (scripts/tui.py) calls `follow_terminal_size`, the call that carries a resize made inside a prompt or dialog to the chats, so deleting it would pass. Add `test_the_poll_tick_follows_the_terminal_size_before_anything_else` to Sizing in scripts/test_ptyrelay.py: a UI whose `follow_terminal_size` is recorded and whose next step in `poll` raises, so `poll` is seen to call it first. The other review notes are left: `Looking.test_ctrl_bracket_detaches_and_it_keeps_running` flakes about 1 run in 10 and did before W48; `Relay.start` sets its size after the fork and a resize's redraw counts as activity, both predating the need of this task and harmless to the wrapping.
Determination: The poll tick is now tested to call `follow_terminal_size`; test_ptyrelay.py passes (27 tests) apart from the known ctrl-] flake, which failed 2 of 6 runs here, and no real claude was run.

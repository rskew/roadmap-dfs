# W60 · Big screen experience

## Summary

Eight ways to use a big screen were written up (mirror the phone, a fluid wide layout, a game controller, a TV mode, the phone as a remote, a wall board, the terminal UI, a review mode), and the two the author chose were built: from 1500 px wide the page uses the whole screen with type scaled up to 1.75 times, a rail of tasks beside the tree and node, hover tints, a right-click node menu on hover devices and the keys Enter, c and f; and a game controller layer that shows a button hint bar and a larger focus ring only while a pad is connected, moves focus with the d-pad or left stick, presses with A, backs out with B, adds with X, shows flagged nodes with Y, steps nodes with the bumpers and lists the buttons on Start. The other six proposals stay written up and unbuilt, since the author picked these two, and `.dfs/artefacts/146e80d9-d0b4-40dd-ae13-96184e509418.html` still shows which would come first for another setup. Both builds are tested with a faked pad and a resized browser, not on a real dock, TV or controller, and they assume the browser reports 1500 CSS px or more when docked and exposes the Gamepad API (an iPhone that only mirrors gets neither).

## Goal

Propose a few different ways we could enable a good experience with a big screen. This might be via plugging the mobile into a dock, or either way maybe interacted with via a game controller. Go broad!

## Tree

### W60.1 · Survey what the page and the terminal do on a big screen today
Status: confirmed
Approach: Read `scripts/web/index.html` and `design.css` for the wide-screen layout (breakpoints, `--page`, `--col`, type and hit sizes) and for every keyboard and pointer input, and read the TUI's `KEYS` table; serve `scripts/web.py` on a spare port and screenshot the task page at 1920x1080 and at a 10-foot TV size (1920x1080 at 2x zoom, i.e. 960x540 CSS px). Record what is wasted, what is unreachable without a mouse and what already helps, as the ground the proposals start from.
Determination: Nothing on a big screen is built: at 1920 and 3840 px wide the page is capped at 1180 px (`--page`, a two-pane list and sheet from 900 px), body type stays 17 px and buttons stay 44 px at any size, the only keys are `j` `k` `n` Esc plus arrow keys on a reorder grip, the TUI has its own `KEYS` table, and nothing reads the Gamepad API. ![The task page on a 3840x2160 screen: content in the middle 30%](.dfs/artefacts/2c29d392-ad43-40b2-af1c-944523ff2c9a.png)

### W60.2 · Mirror the phone and change nothing
Status: parked
Approach: The phone's screen is mirrored or cast to the big screen (iPhone USB-C adapter, Chromecast, Miracast) and the page is used as it is, rotated to landscape so the 360 px single column fills more of it; the only work is a README note on how to do it.
Determination: Parked: it costs nothing but leaves the page a letterboxed phone screen with 17 px type, which is the problem the Goal names; it is the baseline every other proposal is judged against.

### W60.3 · Fluid wide layout for a docked phone
Status: parked
Approach: `scripts/web/index.html` and `design.css`: replace the fixed `--page: 1180px` and the two-pane list and sheet with a layout that uses the screen, three panes (task list, tree, node sheet) from about 1500 px up to 1800 px, with `clamp()` type steps scaled by viewport width; add pointer affordances (hover, right-click menu) and keyboard keys beyond `j` `k` `n` Esc (Enter opens, `c` corrects, `f` flags); extend `test_ui.py` to audit 1920 and 2560 px. For an Android phone in desktop mode or Samsung DeX, where the browser gets a desktop-width window.
Determination: Parked only because the recommendation node names it as the first build and the author has not yet chosen to build it; unpark it to start.

### W60.4 · Game controller on the web page
Status: parked
Approach: `index.html` gains a Gamepad API loop (`gamepadconnected`, polled each animation frame): the d-pad and left stick move focus to the nearest focusable control in that direction (spatial navigation, scoped to an open dialog when there is one), A presses it, B is Back or closes a dialog, Y toggles flagged nodes, X adds a node, bumpers go to the previous and next node, triggers switch the bottom tabs, Start opens a button legend. A button glyph hint bar shows only while a pad is connected, and the focus ring grows to 4 px. Works in Chrome on Android and desktop, Steam Deck, and anything whose browser exposes the Gamepad API.
Determination: Parked only because the recommendation node names it, with the fluid layout, as the first build and the author has not yet chosen to build it; unpark it to start.

### W60.5 · Ten-foot TV mode
Status: parked
Approach: A mode, chosen by `?tv`, remembered per browser, or offered when the viewport is 1920 px wide with no hover, for a TV, console or Steam Deck browser seen from a sofa: type at 24 to 28 px, one pane at a time (list, then tree, then node, with a breadcrumb), a large focus tile instead of a thin ring, 5% overscan margins, dark by default, no control smaller than 64 px, no hover-only reveal. Built on the controller layer's focus movement.
Determination: Parked: it is the right next step once the controller layer exists, since a TV at sofa distance needs both, but it adds a second layout to keep tested, so it waits for the first two to settle.

### W60.6 · Phone as the remote for the big screen
Status: parked
Approach: The big screen shows the page (any browser, Chromecast or a TV's own). The phone opens `/remote`: a touchpad, a d-pad, big Confirm, Refute and Next buttons, and a text box for corrections. `web.py` takes its posts and pushes them as events to the display over the `/api/events` stream it already has, and the display moves focus as if from a keyboard. Needs a pairing step (a short code shown on the display) because the server has no login and a remote that anyone on the network can reach would drive the roadmap.
Determination: Parked: it suits a screen nobody can plug a controller into, but it adds a network input path and a pairing and security design the server does not have, and the author's two examples (dock, game controller) do not need it.

### W60.7 · Wall board of what needs you and what is running
Status: parked
Approach: A read-only `/board` page for a monitor left on, glanceable from across a room: large cards for open raises and assumptions, the live runs and their log tails (from `/api/events`), counts per task, cycling through tasks unattended, dark, no controls. Anything is done on the phone, which stays the input device.
Determination: Parked: it gives the big screen a use but not an interactive one, which is the experience the Goal asks about; cheap enough to add later beside any other proposal.

### W60.8 · The terminal UI on the big screen
Status: parked
Approach: No web change: the docked phone or a PC runs `scripts/tui.py` in a big-font terminal (Termux, the Android Linux terminal, or ssh), and a controller is mapped to its keys by the OS (Steam Input, an Android key mapper) with a documented preset (d-pad to `j` `k` `h` `l`, A to Enter, B to Esc, Y to `?`); the TUI gets a `pad` section in its `KEYS` help so the preset is visible on screen.
Determination: Parked: it reuses the most input handling, but a terminal at sofa distance is still terminal-shaped, with no artefacts or screenshots, and it depends on a per-OS key mapper outside this repo.

### W60.9 · Review mode: one node per screen with its artefact at full size
Status: parked
Approach: A presentation view of a task for reviewing with someone beside the author: each node fills the screen with its Approach, Determination and Evidence, and its artefact page or screenshot in an iframe at full size; left and right step through the tree, and on a node with a Hypothesis A confirms and B refutes (each after a confirm prompt), X opens a correction. Uses the controller layer for input and the TV mode for scale.
Determination: Parked: it is the use that most needs a big screen (artefacts are authored for one) but it stacks on both earlier proposals, so it cannot be first.

### W60.10 · Recommendation: build the wide layout and the controller layer first, keep the rest parked
Status: confirmed
Approach: Compare the proposals in W60.2 to W60.9 on what screen they assume, what drives it and what they add, and choose the first build: the fluid wide layout (W60.3) and the controller layer (W60.4) together, since a docked or TV screen needs both and the TV mode, review mode and TUI preset all stand on them. The author unparks any other proposal to build it; the comparison page lets them see what would come first for another setup.

Wrong if the screen only mirrors the phone (an iPhone, a cast) or a second device or nothing drives it, since then the phone-as-remote or the wall board comes first. .dfs/artefacts/146e80d9-d0b4-40dd-ae13-96184e509418.html
Evidence:

- for: a web search found Android 16 desktop mode (Pixel 8 and newer, recent Samsung phones) gives a docked phone floating Chrome windows on the monitor, so the browser there gets a desktop-width page.

Determination: Confirmed as the first build because it fits the two setups the Goal names and nothing built contradicts it, but it rests on an Android docked phone and is weakest if the author's phone is an iPhone, where W60.6 or W60.2 would come first.

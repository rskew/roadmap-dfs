# W60 · Big screen experience

## Summary

Eight ways to use a big screen were written up (mirror the phone, a fluid wide layout, a game controller, a TV mode, the phone as a remote, a wall board, the terminal UI, a review mode), and the two the author chose were built: from 1500 px wide the page uses the whole screen with type scaled up to 1.75 times, a rail of tasks beside the tree and node, hover tints, a right-click node menu on hover devices and the keys Enter, c and f; and a game controller layer (reaching every control on the page, scrolled clear of the fixed bars, and only for a standard-mapped pad) that shows a button hint bar and a larger focus ring only while a pad is connected, moves focus with the d-pad or left stick, presses with A, backs out with B, adds with X, shows flagged nodes with Y, steps nodes with the bumpers and lists the buttons on Start. The other six proposals stay written up and unbuilt, since the author picked these two, and `.dfs/artefacts/146e80d9-d0b4-40dd-ae13-96184e509418.html` still shows which would come first for another setup. Both builds are tested with a faked pad and a resized browser, not on a real dock, TV or controller, and they assume the browser reports 1500 CSS px or more when docked and exposes the Gamepad API (an iPhone that only mirrors gets neither).

## Goal

Propose a few different ways we could enable a good experience with a big screen. This might be via plugging the mobile into a dock, or either way maybe interacted with via a game controller. Go broad!

### W60.6 · Phone as the remote for the big screen
Status: parked
Approach: The big screen shows the page (any browser, Chromecast or a TV's own). The phone opens `/remote`: a touchpad, a d-pad, big Confirm, Refute and Next buttons, and a text box for corrections. `web.py` takes its posts and pushes them as events to the display over the `/api/events` stream it already has, and the display moves focus as if from a keyboard. Needs a pairing step (a short code shown on the display) because the server has no login and a remote that anyone on the network can reach would drive the roadmap.
Determination: Parked: it suits a screen nobody can plug a controller into, but it adds a network input path and a pairing and security design the server does not have, and the author's two examples (dock, game controller) do not need it.

### W60.13 · Fix: the d-pad cannot reach controls below the fold, and focus can sit behind the fixed bottom bar
Parent: W60.12
Status: confirmed
Approach: In `scripts/web/index.html`, `padTargets()` keeps only controls with `r.top < innerHeight`, so a control wholly below the viewport is not a candidate for `padMove("down")` and the page never scrolls to it. Checked with a fake pad on a 390x700 phone viewport against the example project (9 tasks): pressing down 40 times visits W1 to W8 and then only the fixed bottom tab buttons (the list is 1078px tall, scroll stopped at 83px), so W9 and everything under it is unreachable by the pad; W7 was also focused with its bottom 23px behind the 52px fixed `#tabs` (no `scroll-padding-bottom`, and `scrollIntoView({block:"nearest"})` does nothing once the control is partly in view). The same stall happens at any width when a row's top lands exactly on the viewport edge (W8's bottom was 700.39 against innerHeight 700). Fix: when no control past the focused one lies in the viewport, fall back to those off-screen (or scroll by a page and retry), pick among all controls in scope, and add `scroll-padding` for the bottom tabs and `#padbar` (and `--bar` at the top) so a focused control is never covered. Settle it with a `pad` flow case at a phone viewport (390x700, touch) and a list taller than the screen: press down until the last task is focused and assert it is reachable and its box is above `#tabs` and `#padbar`.
Determination: Fixed in W60.15: the d-pad reaches every control and the page scrolls it clear of the fixed bars.

### W60.14 · Minor findings from the review
Parent: W60.12
Status: confirmed
Approach: One line each, all small, to be done beside W60.13:
- The `keydown` handler (`scripts/web/index.html`, after the `setInterval` for chats) ignores `metaKey` and `ctrlKey` but not `altKey`, so Alt+F toggles the flagged filter and Alt+C opens the correct form; add `e.altKey` to the guard.
- `padPoll` reads `p.axes[0]` and `p.axes[1]` and button indexes 0-5, 9 and 12-15 for any pad, though only `mapping === "standard"` has that layout; a non-standard pad (a PlayStation or Switch pad on some Android browsers) would press the wrong things. Skip or remap pads whose `mapping` is not `"standard"`.
- `PAD.held` is not cleared when the last pad goes (`padPoll` returns early), so a button held at unplug is "held" on reconnect and its first press is dropped.
- W60.11 and W60.12 carry no `Hypothesis:` though they rest on decisions the author may see differently: that a docked phone reports 1500 CSS px or more (Android desktop mode or DeX may report less), the `--z` steps 1.12/1.3/1.55/1.75 and the 1500px three-pane break, Enter/c/f as the new keys, and a standard-mapped (Xbox-style) pad with A/B/X/Y glyphs. Add them, and ask the author for their screen's CSS width, viewing distance and controller.
Determination: Done in W60.15, except the missing Hypotheses on the two builds, which stay in the Summary's stated assumptions because a determined node is not edited.

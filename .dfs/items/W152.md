# W152 · Fix the walk after a finished item: the worktree is left behind and a second chain starts on the merged item

## Summary

A directory left under `.dfs/worktrees/` whose `.git` points at a gitdir that is gone is no longer taken for a worktree, so a finished item such as W130 loads its real tree and the walk does not start it again. The merge now removes a worktree that git stops half way through (the cause was read-only directories in a replay box holding a copy of the nix store), and when a directory still cannot be removed it says which one is left, what is in it and why. A chain started on a done item with no branch now says it is done and merged instead of failing for a missing task file. The Goal was fully met; the fault with the leftover directory was the cause of both faults, so the walk needed no change of its own.

## Goal

Fix two faults in the roadmap tooling (the branch merge and the walk's supervisor) that left W130's worktree behind and started a chain on an item that was already done. They were found when W130 finished on 2026-11-05.

1. The merge cannot remove the item's worktree. At 2026-11-05T01:36:58Z `dfs_run_ztrfugb7` printed "dfs_branch: W130 merged, but its worktree could not be removed: error: failed to delete '/workspace/roadmap-dfs/.dfs/worktrees/W130': Permission denied", then "dfs_branch: W130: dfs/W130 merged into main". The branch `dfs/W130` was deleted and the worktree was deregistered (`git worktree list` shows only the main checkout and `.git/worktrees/` does not exist), but the directory `.dfs/worktrees/W130/` stayed, holding `flake.nix` and `.dfs/runs/replays/` (four replay boxes from 30 October, some of which the sandbox may have created with permissions the merge could not remove). Its `.git` file still points at the removed `.git/worktrees/W130`. A merge that cannot remove its worktree should say what is left and why, and should not leave a directory a later run takes for a live worktree.
2. The walk starts a chain on an item that has just finished. `dfs_run_ztrfugb7` ended "DONE after run 8 — every live node confirmed, and the implementation reviewed", and 3 seconds later (01:37:00Z) the supervisor ran `run.sh --kiro W130 19` (`dfs_run_7zrg8fcm`). It stopped at once with rc 2: "fatal: not a git repository: (null)", "W130 is worked on branch , in /workspace/roadmap-dfs/.dfs/worktrees/W130" (the branch is empty) and "W130 cannot be briefed: the worktree … has no .dfs/items/W130.md, which the main checkout has: the branch does not track it and it was not moved in from there". The activity log shows it as "died W130's chain ended (rc 2)" and "walk off — W130: a session could not be briefed". A finished and merged item should not be started again, and if the supervisor does start one, the failure should say the item is done and merged, not that its task file is missing.

Neither fault lost work: every W130 commit (the last is f96e772 at 01:36:49Z) is on main, the in-progress `scripts/history.py` edit of 01:27 (stashes aefb0aa and 5013ea2) is the W130.51 change that main holds, and the earlier cut-off chain (`dfs_run_wu3f97z2`, run 2) was finished by the next chain. Reproduce the first fault by finding what owns the leftover directory and which of its files the merge could not delete; reproduce the second from the activity log and the two consoles above (`.dfs/runs/dfs_run_ztrfugb7/console.log`, `.dfs/runs/dfs_run_7zrg8fcm/console.log`). The leftover `.dfs/worktrees/W130/` is evidence, and it made W130 show as an empty tree in the app: `dfs_paths.worktree()` takes any directory holding a `.git` for a live worktree, so `tree.load('W130')` read the empty copy and returned 0 nodes. On 2026-11-05 the dangling `.git` pointer was renamed to `.git.dangling` (nothing else in the directory was touched), after which W130 loads 52 nodes and the app serves it as done; rename it back to restore the first state. The fix to make here is that a directory whose `.git` points at a missing gitdir is not taken for a worktree, and that the merge's failed removal is reported.

## Tree

### W152.1 · A directory whose `.git` points at a missing gitdir is not a worktree
Status: confirmed
Approach: **The question**
- Why did W130 load as an empty tree after its merge, and can the walk then be shown to start it again because of that?

**What this node does**
- In `scripts/paths.py`, `worktree()` and `worktree_states()` take a directory for a worktree only when its `.git` is a directory, or a file whose `gitdir:` target exists. A new helper `is_worktree_dir()` does the test, so both agree.
- Add tests: a leftover directory with a dangling `.git` file is not a worktree, `tree.load` reads the main checkout's file, and the walk does not pick the finished item.

**How we will know it worked**
- The new tests fail without the change and pass with it; `scripts/test_all.py` passes.
Determination: A directory whose `.git` points at a missing gitdir is no longer a worktree, so W130-like leftovers load the main checkout's tree; the new test fails without the change.

### W152.2 · A failed worktree removal is reported with what is left and why, and read-only directories are made writable first
Parent: W152.1
Status: confirmed
Approach: **The question**
- What did the merge fail to delete in W130's worktree, and what should it say and do about it?

**What was found**
- The replay boxes under `.dfs/runs/replays/*/store/nix/store/*` hold nix store copies. Their directories have mode 0555, so unlinking the files inside fails with Permission denied. `git worktree remove --force` then stops half way: it has dropped its registry entry but left the directory.

**What this node does**
- One helper in `scripts/branch.py` removes a worktree: run `git worktree remove --force`; if that fails, give directories under it owner-write permission (no symlink is followed) and remove again, with `shutil.rmtree` when git no longer knows the worktree. If something is still left, say its path, the first entries that cannot be deleted and the error.
- `merge`, `release` and `github.py` use it.
- Add tests that make a read-only directory in a worktree, merge, and check the directory is gone; and one where removal still fails (a locked worktree) that the message names the directory.

**How we will know it worked**
- The tests fail without the change and pass with it.
Determination: A worktree git stops removing (read-only directories) is now cleaned up by `remove_worktree`, and one that still cannot be removed is reported with its path, what is left and why; both new tests fail without the change and pass with it.

### W152.3 · A finished, merged item is not started again, and if it is, the failure says it is done
Parent: W152.2
Status: confirmed
Approach: **The question**
- With W152.1 in place, does the walk still start an item whose tree is done and whose branch is merged? If so, where does it choose it? And what should `run.sh` say when the item has no branch?

**What this node does**
- Reproduce with a done item in a test (`scripts/test_walk.py`), then fix the choice, and make `run.sh`'s briefing check say "W<n> is done and merged" instead of "no task file" when the main checkout's tree is complete and there is no branch.

**How we will know it worked**
- The reproducing test fails before and passes after.
Determination: The walk took W130 because the leftover directory made it load as an empty open tree; with that fixed it reads as done, and `run.sh` now ends a done item with no branch as "done and merged" instead of cutting a worktree. Goal met; the new tests fail without each change and pass with it.

# W40 · Aretfacts don't work well with the installed dfs app, something to do with how they're served, or how back works?

## Summary

An artefact link in the web app no longer opens the bare file in a new window, which an installed app cannot leave. It opens inside the app, under the app's own bar with a Back button, in the same sandbox as before; Back returns to the card or task it was opened from, and to the task after a reload. This was not tried on a real installed phone or desktop app, only in a headless browser, so whether the installed app's own back control would also have worked is unconfirmed; the old behaviour is an assumption read from the code.

## Goal

Aretfacts don't work well with the installed dfs app, something to do with how they're served, or how back works?

## Tree

### W40.1 · Open an artefact inside the web app, under its own bar with Back
Status: confirmed
Approach: In scripts/web/index.html add a route `#/a/<task>/<name>` and a viewer: the app's bar (title, Back; the bottom bar's right cell is Back) above a full-height sandboxed frame on `artefacts/<name>` (an `<img>` for an image). Every artefact link (prose, tiles, screenshots) points at that route and drops `target="_blank"`. Back goes to the previous app screen with history.back() when the reader came by tapping, else to the task. scripts/web.py serving is unchanged. Check: test_web.py pins the route and links; the page is driven in a headless browser.
Hypothesis: In the installed app (manifest scope "/", display standalone) a link to /artefacts/<name> opens the sandboxed file bare, in the app's window with no browser chrome, and the file itself has no way back to the app. Wrong if, in the installed app, tapping an artefact link already opens a window or sheet with its own close or back control. .dfs/artefacts/5df866c7-6fc7-4816-ab3a-329212ce9838.html
Evidence:
- for: web/index.html links artefacts with `target="_blank"` to `artefacts/<name>`, which is inside the manifest's scope and standalone display, and web.py serves that file with a sandbox CSP and no page around it, so no control of the app's is on it.
- for: before the change the browser flow opened an artefact as a bare page in a new window, whose only content was the artefact (the flow's popup held nothing of the app); after it, the page shows the artefact under the app's bar with Back.
- against: not tried on a real phone or desktop install; an install may open an in-scope `_blank` link in a browser window that has its own back.
Determination: Confirmed: an artefact link now opens `#/a/<task>/<name>` in the app under its bar, Back returns to the card or task it came from (and to the task after a reload), and the artefacts flow, rich(), artefactsHtml() and the other test_web tests pass; the other failures in test_ui.py and test_chat/drawTasks in test_web.py fail the same without the change; not tried in a real install. ![the viewer on a phone: the artefact between the bar and Back](.dfs/artefacts/e1c4a7d2-3b58-4f0e-9a61-0d5c2b8f7a13.png)

### W40.2 · Keep the new-tab link and only make the artefact page say how to go back
Status: parked
Approach: Leave target="_blank" and add a "Back to the app" bar to every artefact by wrapping the served page in web.py.
Determination: Parked: wrapping rewrites an agent's page and its CSP; the viewer inside the app does the same job without touching the served file.

### W40.3 · Fix: an artefact link in a chat reply opens the viewer behind the modal chat, so nothing seems to happen
Parent: W40.1
Status: confirmed
Approach: In scripts/web/index.html the chat is a modal `<dialog id="chat">` (chatOpen calls `$("#chat").showModal()`), and agent replies are drawn with `md(m.text)` (chatDraw), so rich() turns an artefact named in a reply into `<a class="art" href="#/a/<task>/<name>">`. Before W40.1 that link was `target="_blank"` and opened a window beside the chat; now it only changes the hash, the render draws the viewer in `#view`, and the open modal dialog stays on top of it (nothing in the click handler or in render() closes `#chat`), so the reader taps the link and sees no change until they press the chat's own Back, and then they land on the viewer rather than the chat they came from. Fix: when an in-app artefact link (`a.art`, `a.shot`) is tapped inside `#chat`, close the dialog first (the `chatlist` act already does `$("#chat").close()` before `go`) so the viewer shows, and make sure Back from the viewer then returns to the task. Check: a ui_flows.mjs flow that opens a task chat whose reply names an artefact (the chat stub in the flows), taps the link, and asserts `#chat` is not open and `iframe.artview` is visible; then Back lands on the task. The same question applies to any other modal dialog that can hold such a link (`#form`: look for rich()/md() output inside forms) and should be answered in the same node.
Determination: Confirmed: the page's click handler now closes every open dialog when an `a.art` or `a.shot` is tapped, so the viewer shows instead of drawing behind the chat; the artefacts flow gained a chat-reply step that goes red without the change (`#chat` stays open) and green with it, and Back from the viewer lands on the task. The only dialog that can hold such a link is the chat (`#form` holds no rich()/md() output), and the close covers any other.

### W40.4 · Minor findings from the review
Parent: W40.1
Status: open
Approach: One line per finding, none a defect the Goal turns on.
- scripts/web/index.html drawArtefact: the "already drawn" guard compares only `view.dataset.art` with the artefact name, not the task, so `#/a/A/x` to `#/a/B/x` (same file name in two tasks) keeps the old frame; key it on task and name.
- drawArtefact: an artefact name the task does not have (a stale or mistyped `#/a/<task>/<name>`) draws a frame of the server's 404 under a bar that names the raw file; say "no such artefact" instead.
- `NAVS` counts every hashchange including `location.replace` ones (sheet close, Back on a task), so it only means "this page has moved at least once"; that is enough today, but the comment above it says it counts "moves" and should say the guard is "nonzero".
- scripts/ui_flows.mjs and test_ui.py skip in this review environment (no browser), so the viewer flow was read, not run; the session's own run of it is the only evidence it passes.
- test_web.py pins the hrefs and the absence of `_blank` in artefactsHtml but nothing pins that rich() output has no `target`, nor the viewer route in route().

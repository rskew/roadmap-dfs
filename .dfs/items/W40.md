# W40 · Aretfacts don't work well with the installed dfs app, something to do with how they're served, or how back works?

## Summary

An artefact link in the web app no longer opens the bare file in a new window, which an installed app cannot leave. It opens inside the app, under the app's own bar with a Back button, in the same sandbox as before; Back returns to the card or task it was opened from, and to the task after a reload. This was not tried on a real installed phone or desktop app, only in a headless browser, so whether the installed app's own back control would also have worked is unconfirmed; the old behaviour is an assumption read from the code.

## Goal

Aretfacts don't work well with the installed dfs app, something to do with how they're served, or how back works?

## Tree

### W40.1 · Open an artefact inside the web app, under its own bar with Back
Status: confirmed
Approach: In scripts/web/index.html add a route `#/a/<task>/<name>` and a viewer: the app's bar (title, Back; the bottom bar's right cell is Back) above a full-height sandboxed frame on `artefacts/<name>` (an `<img>` for an image). Every artefact link (prose, tiles, screenshots) points at that route and drops `target="_blank"`. Back goes to the previous app screen with history.back() when the reader came by tapping, else to the task. scripts/web.py serving is unchanged. Check: test_web.py pins the route and links; the page is driven in a headless browser.
Hypothesis: In the installed app (manifest scope "/", display standalone) a link to /artefacts/<name> opens the sandboxed file bare, in the app's window with no browser chrome, and the file itself has no way back to the app. Wrong if, in the installed app, tapping an artefact link already opens a window or sheet with its own close or back control. .dfs/artefacts/5df866c7-6fc7-4816-ab3a-329212ce9838.html
Evidence:
- for: web/index.html links artefacts with `target="_blank"` to `artefacts/<name>`, which is inside the manifest's scope and standalone display, and web.py serves that file with a sandbox CSP and no page around it, so no control of the app's is on it.
- for: before the change the browser flow opened an artefact as a bare page in a new window, whose only content was the artefact (the flow's popup held nothing of the app); after it, the page shows the artefact under the app's bar with Back.
- against: not tried on a real phone or desktop install; an install may open an in-scope `_blank` link in a browser window that has its own back.
Determination: Confirmed: an artefact link now opens `#/a/<task>/<name>` in the app under its bar, Back returns to the card or task it came from (and to the task after a reload), and the artefacts flow, rich(), artefactsHtml() and the other test_web tests pass; the other failures in test_ui.py and test_chat/drawTasks in test_web.py fail the same without the change; not tried in a real install. ![the viewer on a phone: the artefact between the bar and Back](.dfs/artefacts/e1c4a7d2-3b58-4f0e-9a61-0d5c2b8f7a13.png)

### W40.2 · Keep the new-tab link and only make the artefact page say how to go back

# W43 · The bottom bar is expanding the screen on mobile

## Summary

On a phone the task list no longer grows wider than the screen. A long tag on a task row, such as "+ uncommitted edits, not on main", could not wrap, so it pushed the page wider than the phone; the browser zoomed out, the page panned sideways, and the bottom bar and the add-a-task button, placed from the page's right edge, sat off to the right. The tag now wraps inside its row. I reproduced the fault in a phone-sized browser on this project's own list (411px of layout in a 390px screen) and saw it gone afterwards on the list and a task page. A browser check now fails if a long tag widens the page. I did not see the other screens (node sheet, artefact, chat) with a long tag on them, and the cause was found by measuring, not from the author's description alone.

## Goal

The bottom bar is expanding the screen on mobile

## Tree

### W43.1 · A tag longer than its row no longer widens the page
Status: confirmed
Approach: `.tag` is `white-space: nowrap`, so a task row's long tag ("+ uncommitted edits, not on main", "waiting on …") could not shrink below its text and ran past the row. On a phone the layout became wider than the screen, the browser zoomed out, the page panned sideways, and the fixed bottom bar and the add button, placed from the right edge of the wider layout, sat off to the right. `.item .meta .tag` in `scripts/web/index.html` now has `max-width: 100%; white-space: normal; overflow-wrap: anywhere`, so it wraps inside the row. `ui_flows.mjs`'s list flow adds a long real-text tag to an open row and asserts the tag ends inside the row's body and the page does not scroll sideways (the old check used fixed-width stand-ins, which hid this).
Determination: Confirmed in chromium at iPhone 13 width on this repo's own list: the layout was 411px in a 390px viewport (span.tag 332px wide, tabs and add button at right=411/395), and after the change it is 390px with nothing past the edge on the list and a task page; the new check fails without the change and passes with it, and the other UI flows are unchanged (the same six fail on the base commit). ![the task list at iPhone width, 390px layout, bottom bar and add button inside the screen](.dfs/artefacts/5d0c7a52-3b1e-4c1a-9a57-43a1f0c2b7e1.png)

Reading scripts/web/index.html, the fixed bottom bar (#tabs, 52px plus the safe-area inset) cannot overflow the page's width. Its buttons wrap and shrink to their longest word, and the flows already check 320px and 390px for horizontal overflow. So the fault is not one the code shows by reading, and each plausible reading leads to a different fix:

  1. The page zooms out or pans sideways, so the layout is wider than the phone. I would find what is wider than the viewport and clip or shrink it, and add `min-width: 0`, `overflow: hidden` and ellipsis to the bar's buttons.
  2. The bar grows taller. It may change height between screens (list, task, artefact), or ride up with the on-screen keyboard or Safari's toolbar, so the content jumps. I would pin its height and place it from the layout viewport.
  3. The bar takes too much of a small screen. The 52px tab bar, the 56px node bar (`.sheet-nav`) and the floating add button can stack up and leave little room. I would shrink them or hide them while scrolling.
  4. Something else, such as a particular screen, a tap, or a device.

  My recommendation is to answer with the screen it happens on (list, task, node sheet, artefact or chat), what you do just before it, what grows (the bar, or the whole page sideways or downwards), and the phone and browser. A screenshot would settle it. Without that, I would start at reading 1 and write the fix as a Hypothesis that cannot be verified here. The strongest case against waiting is that reading 1 may be right, and I would then have waited for nothing.

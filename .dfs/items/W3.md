# W3 · Walk failed when started from the page, error fetcing nixpkgs for the agent process, truncated sha?

## Summary

A failed fetch of nixpkgs by the agent launcher now says what failed: the url with the whole revision, the HTTP status and the first line of the response body, on the console and the screen's message line, for a walk started from the page as well as for `--update`, where it used to show only the tail of nix's output (such as `404: Not Found)`) or "exit status 1". The likely reading of "truncated sha" is that cut-off text, since every revision passed or pinned here is 40 characters; the failing run's own log was gone, so that was not confirmed. Making a walk start on a box that cannot reach GitHub, and showing the cause on the page, were left out until the real message shows they are needed.

## Goal

Walk failed when started from the page, error fetcing nixpkgs for the agent process, truncated sha?

## Tree

### W3.1 · agent.py reports the cause of a failed nix fetch, not nix's last line
Status: confirmed
Approach: `scripts/agent.py` `main()` prints only the last line of nix's stderr as `dfs_agent: --rev failed: ...`. For a GitHub fetch failure nix ends with the response body (`404: Not Found)`, or the `{"message":"API rate limit exceeded"...}` JSON), so the console and the screen's message line show a fragment with no URL or sha. Add `reason(stderr)` that returns the last `error:` clause (`error: unable to download '<url>': HTTP error <n>`) plus the first line of the response body, and print that. Check with a fake `nix` on PATH that prints nix 2.24's real 404 shape (captured from `nix flake metadata github:nixos/nixpkgs/<wrong rev>`), in a new `scripts/test_agent.py` that goes red before the change.
Hypothesis: The failure the author saw is `agent.py --rev` (or `--update`) failing on a nix fetch of nixpkgs, and the "truncated sha" is nix's error text cut to its last line, not a short revision being passed. Wrong if the pinned or passed revision is ever shorter than 40 characters (`read_pin` already rejects those, and `AGENT_NIXPKGS_REV` is only read from the environment), or if the failing walk's console shows no `dfs_agent:` line.
Evidence:
- for: `.dfs/runs/agent-nixpkgs.rev` and every `nix run` line in the run consoles carry the full 40-character revision; nothing in scripts/ shortens a revision except `rev[:12]` in the `--update` success message.
- for: a transcript of this project records the sandbox pinning `dfs_agent: --update failed: {"message":…}` on the screen's message line from start-up, i.e. the last line of a GitHub error body.
- against: the failing walk's own console is gone (only the three successful run directories remain), so the exact message the author saw was not read.
- for: `nix flake metadata` of a wrong revision here ends `404: Not Found)`, and the 404 and rate-limit shapes in the new scripts/test_agent.py go red on the old last-line code and green on `reason()`; the full revision and HTTP status now print.
Determination: Confirmed as far as it can be: `agent.py` now prints `error: unable to download '<url with the full revision>': HTTP error <n> — <body line>` instead of the response body's tail, and test_agent.py shows that; the message the author actually saw was not available to compare.
Ask: Could you paste the walk's console line (the `dfs_agent:` text) from the failure, so we can tell a rate limit or no route to GitHub from a bad revision? I assumed a fetch failure and left the fallback node parked.

### W3.4 · Fix: `agent.py --rev` still prints "Command [...] returned non-zero exit status 1", the path a walk started from the page takes
Parent: W3.1
Status: confirmed
Approach: `run.sh` line 135 runs `agent.py --rev` for a walk, and `current()` calls `resolve(..., stream=True)`, which makes `nix()` run with `stderr=None`, so the `CalledProcessError` has `stderr = None`. In `main()`, `detail = getattr(e, "stderr", None) or str(e)` is then `str(e)`, and `reason()` returns "Command '['nix', 'flake', 'metadata', ...]' returned non-zero exit status 1." Checked here: `agent.nix("flake","metadata","--offline","github:nixos/nixpkgs/"+"0"*40, stream=True)` raises with `e.stderr is None`, and `reason(getattr(e,"stderr",None) or str(e))` gives only that "Command ... exit status 1" text. The cause (url, full revision, HTTP status) goes to the terminal as nix streams it, but the `dfs_agent: --rev failed:` line, the one the Goal is about, carries none of it; only `--update` (captured stderr) gets the new text. `scripts/test_agent.py` cannot see this: its fake `nix` raises with `stderr=` set, which the real streamed call never does. Fix: let `current()` capture nix's stderr (and echo it itself if a person should still see nix working), or tee it, so the exception carries it; then make `run_agent` in `test_agent.py` go through the real `nix()` with `stream=True` (a stub on `subprocess.run` that returns a failing process, or a fake `nix` executable on PATH) so the `--rev` 404 test is red on the current code. Re-check the Summary's claim that the console and the screen's message line show the cause for a walk started from the page.
Determination: Confirmed: `nix(stream=True)` now tees nix's stderr (echoed live and kept), so the real streamed call raises with it and `agent.py --rev` prints `dfs_agent: --rev failed: error: unable to download '<url with the full revision>': HTTP error 404 — 404: Not Found`; `test_agent.py` now fails `--rev` through the real `nix()` call (red on the old code, green now), and a real `nix flake metadata` of a zero revision gives that line.

### W3.6 · Fix: a walk started from the page still does not say why it died (the cause stays in console.log)
Parent: W3.1
Status: confirmed
Approach: The Goal is a walk started from the page that fails on fetching nixpkgs. `walk.py` `start_chain` runs `run.sh` with stdout/stderr into `<rundir>/console.log`; `run.sh` line 135 (`AGENT_NIXPKGS_REV="$(python3 agent.py --rev)" || exit 2`) exits before `meta.json` is written, so `walk_tick` (walk.py ~line 276) finds no run after `WALK_START_GRACE` and calls `walk_off("the chain it started is no longer on the box")`. That is all the screen's message line, header badge and `notify` say, and `web.py` does not watch consoles (comment near line 497), so the `dfs_agent: --rev failed: error: unable to download '<url + full revision>': HTTP error <n>` line W3.1/W3.4 now produce is visible only by opening console.log. If you choose not to do this, correct the Summary so it no longer claims the message line shows the cause for a page-started walk, and say why in a Hypothesis.
Determination: Confirmed: `walk_tick` now appends the last `dfs_agent: ... failed:` line from the dead chain's `console.log` to the `walk_off` reason (`chain_cause` in walk.py), so the screen's message line and header badge and the page's walk note carry the url, full revision and HTTP status; `test_walk.py` is red on the old code and green now, and a console with no such line keeps the old reason.

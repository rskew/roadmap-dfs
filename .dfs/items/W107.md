# W107 · Pre commit hook issue

## Summary

When a finished task is merged, the runner now commits only that task's own files, so a file of another task left staged in its worktree is neither committed nor judged by the guard; the item is reopened asking for that stray file to be committed or dropped, which a session can do. When the runner's commit is still refused, the node it opens holds a short one-line gist of the message with line numbers stripped from any file references, so it no longer bloats the task file or carries the warnings that got the next commit refused. The report's guess that other tasks' unchanged files were to blame does not hold for the current guard, which already ignores faults a commit did not add; the failure came from files staged in the worktree. The runner's commits still go through the guard rather than skipping it with --no-verify, since the author has ruled against that bypass before.

- for: with W2.md's fault staged in W1's worktree, the merge returned 3 and W1.md gained `W1.1 · Fix what refuses the commit of W1's files on dfs/W1`, whose Approach holds the guard's whole output: W2's Parent fault, W2's coordinate `a.py:12` and the `--warn` aside. `_commit_task_files` stages the task's paths but runs a bare `git commit`, which commits and judges the whole index.

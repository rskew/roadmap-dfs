# W184 · tree.py log waits forever for input whenever an agent runs it from its shell

## Summary

`tree.py log` and `tree.py add` no longer hang when an agent runs them from a shell whose stdin is an open pipe that nothing writes to. They wait up to one second (or `DFS_BODY_WAIT` seconds) for a body to start, read it to the end if one comes (heredoc, file or pipe), and otherwise carry on with no body. When they stop with stdin still open, they print one line on stderr saying so, so a slow piped body is not lost without a word. The Goal is fully met. Two older tests in `scripts/test_tree.py` (`AppendLog` review `issues` cases) already failed before this change and were left alone, since they are not about this fault.

## Goal

tree.py log waits forever for input whenever an agent runs it from its shell

## Tree

### W184.1 · tree.py log and add read stdin only when a body is actually sent
Status: confirmed
Approach: **The question** - `tree.py log` and `tree.py add` call `sys.stdin.read()` whenever stdin is not a terminal. An agent's shell gives them a pipe that is open and never written, so the read never ends. How do we read a body that is sent, and skip one that is not? **Why it matters** - Every session logs verdicts and raises through `tree.py log`. A hang there stalls the whole session. **What this node does** - Adds `read_body()` in `scripts/tree.py`. It returns "" for a terminal. Otherwise it waits up to one second for the first bytes with `select`, then reads until end of input, and stops at the end or if the writer goes quiet for a second. - `_main` uses it for `log` and `add`. A heredoc, a file redirect and `echo ... |` all deliver within that time. **How we will know it worked** - New tests in `scripts/test_tree.py` run `tree.py log` as a subprocess with an open, silent stdin pipe: it must return, and without the change it must hang (checked red first). Other tests check a heredoc body and a slow writer still arrive whole. `scripts/test_tree.py` passes.
Determination: `read_body()` makes `tree.py log` and `add` return on a silent open stdin, and the new tests failed without it and pass with it, so the Goal is met.

### W184.2 · Hypothesis: a real body starts within one second and never pauses for one second
Parent: W184.1
Status: refuted
Approach: W184.1 made `read_body()` in scripts/tree.py drop any body that starts later than BODY_WAIT (1 second) after the command starts, or that pauses for 1 second mid-way. The body is cut or lost with no message. I checked: `(sleep 2; echo late) | tree.py log W1 session x` logs an entry with no body and exits 0. The node has no Hypothesis for this. Its assumption is that every real writer (heredoc, file, echo, fast pipe) is quick, and that losing a slow piped body is an acceptable price for not hanging. It would be wrong if a slow producer (for example `some_slow_command | tree.py log ...`) is a real use, since the body is then lost silently. State this as a Hypothesis with its page on W184.1's work: name the assumption, what would show it wrong, and what was checked. If it cannot be held, say so in the Evidence and consider a fix, such as printing a warning to stderr when bytes arrive after the wait, or making the wait configurable.
Hypothesis: Every real writer of a body to `tree.py log` or `add` (heredoc, file, echo, fast pipe) starts within one second and never goes quiet for one second, so dropping a slower body is an acceptable price for not hanging. Wrong if a slow producer piped in (such as `some_command | tree.py log ...`) is a real use, since its body is then lost with no message. .dfs/artefacts/c401efa7-13d9-4ae2-9542-4fa5349619de.html
Evidence:
- for: SKILL.md and the repo docs only show a heredoc as the way to give a body, and heredoc, `echo |` and a 0.7s writer all arrived whole through `read_body()`.
- against: `(sleep 2; echo late) | read_body()` returned "" and exit 0, with nothing on stderr.
- against: `(echo first; sleep 2; echo second) | read_body()` returned only "first\n", with nothing on stderr. A pipe from a slow command (a test run, a build) is a natural thing to try.
Determination: The assumption does not hold for a slow piped writer, whose body is lost with no message, so the node is refuted and the fix follows as a sibling.

### W184.3 · tree.py log and add say so when a piped body was cut off, and the wait can be set
Parent: W184.1
Status: confirmed
Approach: **The question** - How do we stop a slow piped body being lost with no message, without bringing back the hang on a silent open stdin? **Why it matters** - `some_slow_command | tree.py log ...` drops its body at the one-second wait and exits 0, so a verdict can be logged without its text and nobody sees it. **What this node does** - In `scripts/tree.py`, `read_body()` notes it was cut off when the read ends with no end of input (the writer still open): it prints one line on stderr saying how many bytes were read, the wait used, and that `DFS_BODY_WAIT` sets a longer wait. The wait is read from `DFS_BODY_WAIT` (seconds) and falls back to 1. Output on stdout and the exit code stay as they are. **How we will know it worked** - Tests in `scripts/test_tree.py` run `tree.py log` as a subprocess: a silent open pipe returns and prints the note; a body that starts at 2s is lost with the note, and with `DFS_BODY_WAIT=4` it arrives whole with no note; a complete body prints no note. The new tests fail before the change and pass after.
Determination: `read_body()` now says on stderr when it stopped with stdin still open and takes its wait from `DFS_BODY_WAIT`, so a slow piped body is no longer lost without a word, and the new tests failed before the change and pass after, so the Goal is met.

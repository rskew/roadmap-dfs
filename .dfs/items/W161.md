# W161 · Raise artefacts should replace the raise/answer UIs. Clicking a raise node should open the artefact fully, and the artefact should have the buttons to submit an answer. Raise nodes with an artefact should be marked so it's not a surprise.

## Summary

A raise whose text names an `Answer with:` page is now marked "answer page" on its node, on the web page and in the terminal screen. Tapping the node on the web page opens that page in full with its own buttons, and `a` on the row in the terminal screen opens it in the browser instead of the editor; sending the answer returns to the task with the raise closed. A raise with no page keeps the text dialog and the editor, and so does a page raise on the terminal screen when its web server is off or the page file is missing, since the page could not send. The docs say so. Two readings of the Goal (pageless raises keep the dialog; a page raise has no separate words dialog) are stated for you to rule on, and the Playwright flows were updated but not run, as no node was available here.

## Goal

Raise artefacts should replace the raise/answer UIs. Clicking a raise node should open the artefact fully, and the artefact should have the buttons to submit an answer. Raise nodes with an artefact should be marked so it's not a surprise.

### W161.5 · Fix: `a` in the terminal screen opens a page that cannot record the answer when the screen's web server is not up
Parent: W161.3
Status: confirmed
Approach: In `scripts/tui.py` `tree_answer`, a raise with an `Answer with:` page now always goes to `open_artefact` and never to the editor. `open_artefact` serves the page from the screen's own web server only when `self.web` is set; otherwise (`DFS_WEB=0`, or `start_web` failing to bind or import, which it does quietly) it gives `http://localhost:3016/<name>` (a plain static server, if up) or a `file://` URI. On either of those the page's POST to `/artefact-state/<name>` goes nowhere, so the author gets a page whose send button fails and the editor is gone: the raise cannot be answered from that screen. Likewise, when the named page file no longer exists, `open_artefact` only sets a message and the raise cannot be answered. Fix: in `tree_answer`, open the page only when `self.web` is set and the file exists; otherwise fall back to the editor flow below it (and say why on the status line, e.g. "web page off, answering in the editor"). Add `test_screen.py` cases: with `ui.web = None` and with the page file missing, `a` on a page raise opens `$EDITOR` and `open_artefact` is not called. Run `python3 -m unittest test_screen`.
Determination: `a` on a page raise now opens the page only when the screen's web server is up and the page file exists, and otherwise opens the editor with a line saying why; two new `test_screen.py` cases are red without the change and the screen tests pass.

Hypothesis: A raise with no `Answer with:` page keeps the text dialog and the editor, and a raise with a page is answered only on its page (whose note box sends words alone), with no separate text dialog beside it. Wrong if the author wants every raise to open a generated answer page, or wants a words-only dialog kept beside a page raise. .dfs/artefacts/f99e2202-8cf9-4ccd-84f9-2c44f111fe5f.html
Evidence:
- for: SKILL.md says a raise reaches for a page only "whenever a picture would let the author decide faster"; it lists a budget, a tooling bug and a choice between wordings as raises with no shape, so pageless raises are expected to exist and need an answer route.
- for: In `_TEMPLATE_ANSWER.html` the send handler takes the note alone when no option is picked (`said()` joins option and note, and only an empty result is refused), so a page raise can be answered in words on the page.
- against: The Goal's "replace the raise/answer UIs" read plainly means no dialog at all; keeping it for pageless raises leaves the old UI in use.
Determination: Both readings are now stated with their page for the author to rule on; they stand until the author says otherwise. The page passes every check but "blank", which the unmodified template also fails in this sandbox (no text is drawn), so its screenshot is not kept.

# W200 · Pulp down to refresh from the top bar

## Goal

Pulp down to refresh from the top bar

## Tree

### W200.1 · Does anything on the page stop the browser's own pull from the bar?
Status: confirmed
Approach: **The question**
- Does the page set anything that would stop the browser's own pull-to-refresh when a drag starts on the top bar of the task list?

**What this node does**
- Read `scripts/web/index.html`, `design.css`, `sw.js` and `web.py` for `touch-action`, `overscroll-behavior`, touch listeners and `preventDefault` on touch; list what is in the bar and its ancestors.
- Run the `native_pull` flow (`scripts/ui_flows.mjs`), which checks the page, body and bar have `auto` overscroll and touch-action and that a drag from the bar cancels no touch.
Determination: Confirmed: nothing blocks it; `touch-action` is set nowhere, `overscroll-behavior: contain` is only on inner scroll boxes (`.work[open]`, `.sheet-body`, `#chat-log`, `#form form`), the page has no touch listeners, and `native_pull` passes. So a pull that fails from the bar is down to the phone's browser, not to the page.

### W200.2 · A pull from the bar that cancels no touch
Parent: W200.1
Status: started
Approach: **The question**
- The page blocks nothing, yet a pull from the bar still does not refresh for the author. Can the page add a pull that refreshes, and still leave the browser's own untouched?

**Why it matters**
- An earlier gesture of the page's own cancelled the browser's drag and was removed on the author's word that the browser's own should be used. The new one must not repeat that.

**What this node does**
- In `scripts/web/index.html`, passive `touchstart`, `touchmove` and `touchend` listeners on `#bar`, active only on the task list (`route().view === "tasks"`, no dialog open). They never call `preventDefault` and the page sets no `touch-action`.
- The pull is counted from the point where the page is at the top (`scrollY <= 0`): the drag past that point. A `#pull` strip under the bar shows "Pull to refresh", then "Release to refresh" from 72px; letting go past that calls `location.reload()`. Text is set only when it changes (it is a live region).
- A `pull_bar` flow in `scripts/ui_flows.mjs` (360x260 touch, CDP touch events) checks: a 120px drag at the top shows the strip and reloads; a 40px one does not; a drag with the list scrolled to 120 reaches the top and reloads only past 72px more; no touchmove is cancelled; the `native_pull` flow still passes. README phone section names the gesture.

**How we will know it worked**
- The new flow passes and fails without the change; `test_ui`, `test_web`, `test_webscreen` fail only what fails on main.
Hypothesis: The browser's own pull is missing or unusable from the bar on the author's phone (for example an installed iPhone page has none), so a page-made pull that cancels nothing is the fix; where a browser pull also exists, both reload once. Wrong if the author's own pull already works from the bar and they meant something else, or they want the list re-read in place or a pull that starts wherever the list is scrolled with no stop at the top. .dfs/artefacts/ea52db5a-a0ae-4d7f-99b5-54d1c692e424.html

### W200.3 · Re-read the list in place instead of reloading
Parent: W200.1
Status: parked

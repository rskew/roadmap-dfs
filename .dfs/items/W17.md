# W17 · How to end chat sessions so we don't leak resources on the sever

## Summary

Ending a chat now ends the agent and everything it started, not just the agent: a helper in its own session or one that ignores hangup no longer survives, and the screen waits for that when it exits. A page turn that times out, or is still running when the screen or `web.py` ends, is ended the same way, a screen or `web.py` sent SIGTERM or SIGHUP ends its chats and turns as quitting does, and a background chat nobody has used for 30 minutes (DFS_CHAT_IDLE, 0 disables) is closed with its conversation kept, so the next message resumes it. The Goal is met for the chats this tool runs; it was checked with stand-in agents, not a real claude, so a process that escapes to init before a close is the one case not covered. A manual "end chat, keep the conversation" button was left out because idle closing makes it unnecessary, and the author may want it anyway.

## Goal

How to end chat sessions so we don't leak resources on the sever

## Tree

### W17.1 · Find how a chat's agent outlives the chat
Status: confirmed
Approach: Reproduce, with scripts/ptyrelay.py's `Relay` and `ChatHost` and a stand-in agent, each way a chat can end (`Relay.close`, `ChatHost.close_all` at screen exit) and look in `pgrep` for what is left. Read scripts/chat.py `turn` (the page's headless turn) for the same.
Determination: Three leaks found: `Relay.close` signals only the agent's pid, so a helper it started in its own session that ignores hangup survives (a `setsid` sleep outlived `close()`); the SIGKILL backstop in `close` is a daemon thread that dies with the screen, so `close_all` at exit leaves an agent that ignores SIGHUP running (`trap '' HUP; sleep` outlived the process); and `Chats.turn` runs `subprocess.run(..., timeout=)`, which on timeout kills only run.sh's pid, not what it started.

### W17.2 · Close a chat by ending everything it started, and wait
Parent: W17.1
Status: confirmed
Approach: In ptyrelay.py, `Relay.close` collects the agent's descendants from /proc (parent links) and its process group, sends SIGTERM to them all, then SIGKILL to what is left after a short grace, `close(wait=True)` blocks until they are gone, and `ChatHost.close_all` uses it so exiting the screen leaves nothing. Tests in test_ptyrelay.py with a stand-in that ignores SIGHUP and one that starts a `setsid` helper.
Hypothesis: Walking /proc parent links finds everything a chat's agent starts. Wrong if a process the agent started has been re-parented to init before close (then it is in no tree walk) and survives.
Evidence:
- for: the two reproductions from W17.1 (a `setsid` helper that ignores HUP and TERM; an agent that ignores HUP, closed at exit) leave no process behind after the change.
- for: the new Leaving tests pass 8 runs in 8 after a race was fixed (SIGKILL is delivered, not instant, so `close(wait=True)` now waits for the processes to be gone).
- against: not tested with a real claude, so what it forks (a tool process that daemonises and is re-parented to init before close) is unobserved; such a process is in no parent-link walk.
Determination: Confirmed: `Relay.close` now ends the agent and everything under it by parent links, and `ChatHost.close_all` waits until they are gone.

### W17.3 · End a page turn's agent on timeout
Parent: W17.2
Status: confirmed
Approach: In chat.py `Chats.turn`, run the turn with `subprocess.Popen(..., start_new_session=True)` and on `TimeoutExpired` kill its whole process group (SIGTERM, then SIGKILL) and reap it, instead of `subprocess.run`'s pid-only kill. Test in test_chat.py with a run.sh stand-in that starts a child and sleeps past a shortened TURN_TIMEOUT.
Determination: Confirmed: `chat.run_turn` starts the turn in its own session and, on timeout, ends it and everything it started with `ptyrelay.stop_tree`; the new TurnTimeout test (a HUP/TERM-ignoring helper in its own session) passes, and the Chat and web tests fail the same 12 and 1 with and without the change because /tmp and /dev/shm here are noexec, so their stub agent cannot run.

### W17.4 · End the screen's chats on SIGTERM and SIGHUP too
Parent: W17.3
Status: confirmed
Approach: In tui.py `main`, make a SIGTERM or SIGHUP to the screen close the chat host as a normal exit does, so a killed screen or a dropped ssh session does not leave background agents. Check with a pty-run screen that is sent SIGTERM and then `pgrep`ed.
Determination: Confirmed: `tui.end_on_signals` turns SIGTERM and SIGHUP into a normal exit so `main`'s `finally` closes the chats; the new test sends each to a screen-like process holding an agent that ignores HUP and TERM and finds the agent gone, and without the handler it goes red (exit -15, agent left).

### W17.5 · Close a chat nobody is using
Parent: W17.4
Status: confirmed
Approach: Background chats now live until the screen exits or "New chat". Add a reaper to the screen's loop that closes a relay that is not `active`, is not attached, and whose transcript has not moved for an idle limit (default 30 minutes, an env override). Its conversation is not lost: `chat.claim` resumes the saved session id when the page or `c` next opens it. Test in test_ptyrelay.py/test_chat.py with a short limit.
Hypothesis: Resuming a closed chat from its transcript is lossless for the author. Wrong if a resumed chat loses something a live one had (an unanswered permission prompt, a half-typed line, an attached screen's scrollback).
Evidence:
- for: the screen's `c` already starts a chat with `--resume` on its saved session id whenever the agent was closed and a transcript exists (`chat.claim`, run.sh `CHAT_RESUME`), so resuming after a close is the path every screen restart takes today.
- against: not run with a real claude here, and a resume cannot bring back an unanswered permission prompt, a half-typed line or an attached terminal's scrollback; the idle test (no output, nothing queued, not attached) makes the first two unlikely, not impossible.
Determination: Confirmed: `ChatHost.reap_idle`, called from the screen's poll, closes a chat after `DFS_CHAT_IDLE` seconds (default 1800, 0 disables) with no output, nothing queued and no terminal attached, and forgets ended ones; the new Idling test covers each exemption, and the Goal is met.
Ask: Is 30 minutes the right idle limit before a background chat is ended (its conversation is kept)? I chose 30 minutes.

### W17.6 · A button to end a chat and keep the conversation
Parent: W17.4
Status: parked
Approach: Add `Chats.end(scope)` and a web endpoint and button that close the background agent but keep the saved session id (unlike `clear`, which also forgets it).
Determination: Parked: it relies on someone remembering to press it, which is how the leak arises, and adds UI the author has not asked for; W17.5 ends idle chats without them. Unpark if the author wants a manual control as well.

### W17.7 · Fix: a page turn running when the server or screen ends is left running
Parent: W17.3
Status: confirmed
Approach: scripts/chat.py `run_turn` now starts each page turn with `start_new_session=True`, and `Chats` keeps no record of the turns in flight. Nothing stops them when the process serving the page ends: `web.py` alone on ^C (`handle.stop()` only stops the HTTP server) or the terminal closing used to reach the turn through the shared process group and session, and no longer does; the screen's exit (`main`'s `finally`, normal, SIGTERM or SIGHUP) only calls `chat_host.close_all()`. The timeout that would end it runs in a daemon thread of the process that is gone, so a `claude -p` turn (and what it started) runs on until it finishes on its own, however long that takes. Fix: have `Chats` remember each running turn's pid (set in `run_turn`, cleared when it returns), add `Chats.close()` that `ptyrelay.stop_tree`s them all, and call it where the chats are closed: in `tui.main`'s `finally` beside `chat_host.close_all()` and in `web.py` main after `handle.stop()`. Test: start a turn whose run.sh stand-in ignores HUP/TERM and starts a helper, call `Chats.close()`, assert the turn's pid and the helper are gone (the existing Chat tests cannot run a stub agent here because /tmp is noexec, so build the test as TurnTimeout does, with `bash -c`).
Determination: Confirmed: `run_turn` records the turn's pid in `Chats.running`, `Chats.close()` ends every one with its helpers, and `web.Handle.stop()` calls it, which covers the screen's exit and `web.py` alike; the new test (a HUP/TERM-ignoring helper in its own session) passes and fails without the change, and test_chat, test_web and test_screen fail the same 23 tests with and without it (noexec /tmp).

### W17.8 · Minor findings from the review
Parent: W17.7
Status: confirmed
Approach: One line each, to be done beside W17.7.
- tui.py `main`'s `finally`: if `ui.web.stop()` raises, `close_all()` is skipped, and a second SIGTERM/SIGHUP during `close_all()` raises SystemExit again and abandons it; run `close_all()` regardless (nested try/finally) and consider ignoring further signals while it runs.
- tui.py `end_on_signals` docstring says the agents "are not hung up on by anyone else when the screen is killed": when the screen dies its pty masters close, so an agent that does not ignore hangup is hung up on by the kernel; reword to say the handler is what makes the ones that ignore hangup (and their helpers) end.
- ptyrelay.py `reap_idle` selects idle chats under the lock but closes them after releasing it: a message the page queues in that window goes to a relay about to be closed and is lost; recheck `outbox.empty()` and `attached` when closing, or close under the lock.
- `DFS_CHAT_IDLE` is documented only in the chat.py docstring; README/docs do not list it beside the other DFS_ variables.
- The signal test (test_screen `KilledWithChatsRunning`) uses a stand-in process, not `tui.main` under a pty, so the handler's install order and interplay with curses are unobserved.
Determination: Confirmed: all five are done (nested finally and signals ignored once exiting, the docstring reworded, `reap_idle` takes the idle relays out of the table under the lock, `DFS_CHAT_IDLE` in the README); the signal test is still a stand-in process, not `tui.main` under a pty, which is left as it was.

### W17.9 · Fix: web.py killed by SIGTERM or SIGHUP leaves the page's turns running
Parent: W17.7
Status: confirmed
Approach: scripts/web.py `main` (lines ~793-798) ends the page's turns (`handle.stop()` -> `Chats.close()`) only when the join loop ends or on KeyboardInterrupt. Since W17.3 each turn runs in its own session (`run_turn`, `start_new_session=True`), so nothing but `Chats.close()` reaches it: a `web.py` sent SIGTERM (`kill`, systemd stop, a container stop) or SIGHUP (the terminal or ssh session closing) dies by the default action, `handle.stop()` never runs, and a `claude -p` turn and its helpers run on, orphaned, for up to TURN_TIMEOUT or however long it takes. Before W17.3 the terminal's SIGHUP reached them through the shared session, so this is a leak W17.3 introduced for the standalone server, which is the process the Goal ("leak resources on the server") is about; W17.4 fixed exactly this for the screen only (`tui.end_on_signals`), and grep shows no `signal` use in web.py. Fix: in `main`, install SIGTERM/SIGHUP handlers (reuse or share `tui.end_on_signals`' shape: raise SystemExit/KeyboardInterrupt in the main thread, ignore further signals once exiting) so the path reaches `handle.stop()`, ideally in a `try/finally` around the join loop. Test in test_web.py (or test_chat.py with `bash -c` as TurnTimeout does, since /tmp is noexec here): run `web.py` as a subprocess with a turn in flight whose helper ignores HUP/TERM, send it SIGTERM and then SIGHUP, and assert the helper is gone; it must fail without the handler.
Determination: Confirmed: `web.main` installs `tui.end_on_signals` and runs `handle.stop()` in a `finally` that starts right after `serve`, so SIGTERM and SIGHUP end a turn in flight with its HUP/TERM-ignoring helper; the new KilledWithTurnRunning test passes 12 runs in 12 and without the handler exits -15 with the helper left (it also caught a signal landing between the startup prints and the `try`, now closed).

### W17.10 · Minor findings from the review
Parent: W17.9
Status: confirmed
Approach: One line each, to be done beside W17.9.
- ptyrelay.py `reap_idle`/`Relay.send`: W17.8 pops idle relays under the lock, but a caller that already holds the relay (from `ensure`/`get`) can pass `send`'s `live` check and `outbox.put` after `close()` has started, so that message is still lost at exactly the idle boundary; make `send` and `close` agree under `Relay.lock` (or have `reap_idle` re-check `outbox.empty()` and `attached` after setting `closing`).
- chat.py `Chats.close()`: a turn thread started by a request still being handled when the server shuts down can call `run_turn` after `close()` ran and so is never ended; a `closed` flag checked in `turn`/`run_turn` would stop that. Also `run_turn` adds the pid to `running` after `Popen`, so a `close()` in that gap misses it; and `close()` snapshots pids and could `stop_tree` a pid recycled after its turn finished.
- test_screen `KilledWithChatsRunning` still uses a stand-in process, not `tui.main` under a pty, so the handler's install order and its interplay with curses are unobserved (already noted in W17.8).
- test_chat/test_web stub-agent tests cannot run in this environment (noexec /tmp), so the Chat tests that exercise `Chats.turn` end to end were never observed passing with W17.7's `running=` argument.
Determination: Confirmed: `Relay.send` and `reap_idle` now agree under the relay's lock (a chat queued to or attached after the table was read is put back), `chat.Running` refuses a turn started after `close()`, records the pid under its lock with `Popen`, and ends only a pid whose start time still matches; the two test_screen/test_chat stub-agent items stay as they were (the stand-in signal test is not `tui.main` under a pty, and noexec /tmp keeps the Chat tests failing the same 12 with and without the change).

# W20 · Chat input should stay above mobile keyboard

## Summary

The chat dialog on the web page is now placed from the visual viewport alone (top and height, no `bottom` taken from `100dvh`), refits shortly after any field gains or loses focus as well as on viewport events, keeps the newest message in view when the keyboard opens, and caps the message box by the visible height rather than the full one. I could not drive a real phone keyboard here: the fit was checked in Firefox with the viewport size set by hand, and the chromium and playwright browser tests cannot run in this sandbox. So the Goal is met as far as the geometry goes, and a check on an iPhone and an Android phone is still the proof.

## Goal

Chat input should stay above mobile keyboard

## Tree

### W20.1 · The existing fit holds the chat above a keyboard, given a correct viewport
Status: confirmed
Approach: The chat dialog is already fitted to `visualViewport` (`--vvh`, `--vvt` in `scripts/web/index.html`). Render the page's own HTML and CSS in headless Firefox, open `#chat`, force `--vvh: 400px` (and `--vvt: 120px`) as a keyboard would leave them, and screenshot where the input, Send and Back land.
Hypothesis: The CSS places the chat correctly whenever `visualViewport` reports the keyboard, so a failure on a phone comes from the values or from when they are set. Wrong if the dialog's box does not sit inside the forced `[vvt, vvt+vvh]`.
Evidence:
- for: with `--vvh: 400px` the dialog filled the top 400 of 800 px, input and Back inside it; with `--vvt: 120px` it sat from 120 to 520, as it should.
- before this node: W19's uncommitted `scripts/run.sh` and `scripts/test_chain.py` were committed on their own as 1694f06 (29 chain tests pass).
- against: a real keyboard could not be raised (no node/playwright, and chromium will not start for a glibc mismatch), so only the CSS half was seen, not the events.
Determination: The CSS half is sound; what a real phone does with the events is unchecked, so the work goes to what the code depends on beside the viewport.

### W20.2 · Fit the chat from the viewport alone and refit on focus
Parent: W20.1
Status: confirmed
Approach: In `scripts/web/index.html`: place `#chat[open]` by `top` and `height` only (centred above 900px) so it no longer depends on `100dvh` agreeing with the viewport the browser fits; refit at 100, 300 and 600 ms after `focusin`/`focusout`, since a phone moves the viewport during the keyboard's slide; keep `#chat-log` at its end across a refit when it was at the end; cap the message box at 30% of `--vvh` instead of `30dvh`. Check in headless Firefox as before, on a phone width and a wide one.
Hypothesis: A `bottom` computed from `100dvh` and a refit only on viewport events are what let the box drift under the keys on a phone. Wrong if a phone still shows the input behind the keyboard after this.
Evidence:
- for: phone width, `--vvh: 400px; --vvt: 120px`: the box sat 120 to 520, unchanged from before; at 1100x1200 with `--vvh: 1000px` it was centred at 50 to 950, as before.
- against: nothing seen; `test_web.py` has one failure (the chat stub cannot run in this sandbox) that fails the same without this change.
Determination: The chat stays inside the visible viewport in every case I could set, and the Goal is met up to a test on a real phone.
Ask: Does the chat now stay above the keyboard on your phone? I could only simulate the viewport here.

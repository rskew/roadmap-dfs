# W78 · Browser back from item to lost is not instant, are we catching the event or something rather than using the regular back stack?

## Summary

Back was never intercepted: it is the browser's own history step. The delay was the list screen waiting for its two reads of the roadmap, each taking most of a second on this roadmap of 84 tasks, before drawing anything. The list now draws at once, at the scroll it was left at, from the state the page already holds, then redraws if the fresh read differs; after the page's own writes (a delete, a draft toggle) it still waits, so a deleted task never flashes back. Making those reads faster on the server, and the similar wait for the walk's read when opening a task, were left out.

## Goal

Browser back from item to lost is not instant, are we catching the event or something rather than using the regular back stack?

## Tree

### W78.1 · Find why Back from a task to the list waits
Status: confirmed
Approach: Read the page's routing in `scripts/web/index.html` (`go`, `leave`, `up`, the `hashchange` listener, `renderDraw`) to see whether Back is the browser's own history step or something the page intercepts, and time `/api/state`, `/api/walk` and `/api/task/W78` against this roadmap with `scripts/web.py` serving it.
Determination: Back is the browser's own history step (the bar's Back calls `history.back()` when the entry beneath is the list, and the page only listens for `hashchange`), but the list screen draws nothing until `/api/state` (0.59–0.84 s here) and `/api/walk` (0.59–0.73 s) answer, each re-running `state.full()` over 84 tasks with about 260 git calls, while `/api/task/W78` takes 0.018 s: the wait is the list's reads, not the back stack.

### W78.2 · Draw the list at once on arriving back at it, from the state already read
Parent: W78.1
Status: confirmed
Approach: In `renderDraw` in `scripts/web/index.html`, when the list screen is arrived at (the view changed) and the page already holds `S.state` and `S.walk` (the task screen keeps both current through `refreshNeeds` and its own `/api/walk` read, and the server's pushes re-render), draw the list and restore its scroll before the `/api/state` and `/api/walk` reads, then redraw only if what they return differs. A new `backinstant` flow in `scripts/ui_flows.mjs` holds both reads and checks that the list and its scroll are there while they are held, by the bar's Back and the browser's.
Determination: Back to the list now draws it, at its old scroll, from the held state before `/api/state` and `/api/walk` answer, except after a write the page itself sent since that state was read (a delete or a draft, whose flows went red when the held list was drawn regardless); `backinstant` fails on the old page and passes on the new one, and the full `test_ui` and `test_web` suites fail only the four flows that already fail on main (chain running, layout, markdown, bar from Chats).

### W78.3 · Make `/api/state` and `/api/walk` fast on the server
Parent: W78.1
Status: parked
Approach: Cache `state_json()` and `walk_json()` in `scripts/web.py` on a cheap fingerprint of the roadmap (the `.dfs/items` mtimes and git HEAD), so each read answers in milliseconds instead of re-running `state.full()` with its git calls per task.
Determination: Parked: it still leaves Back waiting on a round trip, which on a phone over a slow link is not instant, and a cache keyed on a fingerprint risks serving a stale state when the fingerprint misses a change (a branch's worktree, a run's log); drawing what the page already holds makes Back instant whatever the server's speed.

# W89 · Tell the author when the project's ignore rules hide roadmap files

## Goal

The tool tells the author when the project's ignore rules hide roadmap files, and the init step checks that git add works on the roadmap directory.

Nothing currently warns that a rule such as a blanket .* is hiding the roadmap directory. In one project, tasks sat untracked for two weeks until a worktree needed them. The roadmap directory's own ignore file only excludes runs/, which suggests the tool expects everything else in it to be trackable, so a hidden file is a misconfiguration worth reporting early.

Done looks like:
- Init checks that git add works on the roadmap directory and says which ignore rule stops it if not.
- The author is told, outside init too, when roadmap files are ignored or untracked.

Worth doing: it would have caught the untracked tasks two weeks before they broke a walk, and it is the early warning for the walk and pre-commit failures in the two tasks before it.

## Tree

### W89.1 · A probe that names each roadmap file git will not add, and the rule that hides it
Status: confirmed
Approach: Add `hidden()` to `scripts/paths.py`: list the untracked ignored paths under `.dfs` (`git ls-files -o -i --exclude-standard --directory`), find each one's rule with `git check-ignore -v --no-index`, asking only about the roadmap's parts (`roadmap_parts()`: ROADMAP.md, order.md, items/, archive/, artefacts/, title, theme), and return nothing when one rule naming `.dfs` itself hides the whole directory and git tracks none of it. Tests in `scripts/test_ignored.py` for a blanket `.*`, a `*.html` rule, a `.dfs/` rule with files force-added past it, and the clean cases.
Hypothesis: A rule naming the roadmap directory itself (`.dfs`, `/.dfs/`) with nothing under it tracked is the supported choice to keep the roadmap as planning, and every other way a roadmap file is ignored (a broader rule such as `.*` or `*.html`, or files force-added past a `.dfs/` rule) is a misconfiguration to report; a non-roadmap file in `.dfs` (a `__pycache__`) and an untracked file git would add is not reported. Wrong if the author keeps `.dfs` as planning through a broader rule such as `.*` and wants no warning for it, or wants untracked files git would add reported too. .dfs/artefacts/ff4032ac-938c-4c3b-9193-de400ec0feb3.html
Evidence:
- for: `init.py`'s docstring and the README support `.dfs/` "committed with the project or gitignored whole", and the Goal reads `.dfs/.gitignore` excluding only `runs/` as meaning the rest should be trackable: neither names a broader rule as a way to keep it as planning.
- against: the first probe, over all of `.dfs`, reported `.dfs/background-src/__pycache__/` (by `.gitignore:2 __pycache__`) in this repo's main checkout, a cache and not the roadmap; asked only about the roadmap's parts, it reports nothing there or in this worktree.
- for: `test_ignored.py` Hidden: `.*`, `*.html` and files force-added past `.dfs/` are reported with their rule; `.dfs/`, `/.dfs`, `.dfs`, no rule and a `__pycache__` rule are not (11 tests OK).
Determination: `dfs_paths.hidden()` names each roadmap part git will not add with the file, line and pattern of its rule, and is silent for a roadmap ignored whole by a rule naming `.dfs`; confirmed.

# W89 · Tell the author when the project's ignore rules hide roadmap files

## Summary

The tool now notices when a project's ignore rules keep part of the roadmap out of git. `init` asks git which roadmap files it would refuse to add and names the ignore file, line and pattern responsible, making that the next thing to fix; the same report is printed when a work chain starts, and the screen's header shows `git hides .dfs` with the rule spelled out under `h`. A roadmap ignored on purpose by a rule naming `.dfs` (`.dfs/`, `.dfs/*`, `**/.dfs/` and the like), with nothing in it tracked, stays the supported planning-only setup and is not reported; a broader rule such as `.*` or `*.html`, or files force-added past a `.dfs/` rule, is. Untracked files git would add are not reported, since they are commits not yet made, and only the roadmap's own parts are checked, so a cache inside `.dfs` is left alone; `.dfs/artefacts/ff4032ac-938c-4c3b-9193-de400ec0feb3.html` lays out which setups are reported.

## Goal

The tool tells the author when the project's ignore rules hide roadmap files, and the init step checks that git add works on the roadmap directory.

Nothing currently warns that a rule such as a blanket .* is hiding the roadmap directory. In one project, tasks sat untracked for two weeks until a worktree needed them. The roadmap directory's own ignore file only excludes runs/, which suggests the tool expects everything else in it to be trackable, so a hidden file is a misconfiguration worth reporting early.

Done looks like:
- Init checks that git add works on the roadmap directory and says which ignore rule stops it if not.
- The author is told, outside init too, when roadmap files are ignored or untracked.

Worth doing: it would have caught the untracked tasks two weeks before they broke a walk, and it is the early warning for the walk and pre-commit failures in the two tasks before it.

### W89.4 · Fix: `hidden()` reports a roadmap kept as planning by `.dfs/*`, `.dfs/**` or `**/.dfs/`
Parent: W89.1
Status: confirmed
Approach: `dfs_paths.hidden()` in `scripts/paths.py` skips the planning setup only when `check-ignore` returns exactly one path, `.dfs/`, and its pattern stripped of `/`, `/*` and `/**` is `.dfs`. But `.dfs/*` and `.dfs/**` do not ignore the directory itself, so `git ls-files --others --ignored --directory` lists each part (`.dfs/ROADMAP.md`, `.dfs/artefacts/`, `.dfs/items/`), `len(found) == 1` fails, and the `removesuffix("/*")`/`removesuffix("/**")` branch can never match. `**/.dfs/` is not recognised either. In a scratch repo holding a ROADMAP.md, an item and an artefact, with nothing tracked: `.gitignore` = `.dfs/*`, `/.dfs/*`, `.dfs/**` or `**/.dfs/` each gives `ignored()` True, but `hidden()` reports every part. So `init` prints "Settle the ignore rule named above first" in place of ".dfs/ is gitignored here", and every chain start and the TUI header (`git hides .dfs`) warn about a supported planning-only roadmap. Fix: when git tracks nothing under `.dfs`, treat the roadmap as planning if every found entry's rule names the roadmap directory itself (a pattern that matches `.dfs`, `/.dfs`, `**/.dfs`, with an optional trailing `/`, `/*` or `/**`). Settled by `test_ignored.Hidden.test_a_rule_naming_the_roadmap_keeps_it_as_planning` covering those patterns as well as the existing ones, with the force-added case still reported.
Determination: `hidden()` now treats the roadmap as planning when git tracks nothing under `.dfs` and every hidden path's rule names `.dfs` (`.dfs/`, `/.dfs`, `.dfs`, `.dfs/*`, `/.dfs/*`, `.dfs/**`, `**/.dfs/`), and still reports `.*`, `*.html` and force-added files (`test_ignored`, 11 OK; `test_init` 10 OK, `test_chain` 74 OK, `test_screen` 87 OK); confirmed.

### W89.6 · Fix: a `.dfs/` rule cannot silence the warning when a broader rule like `.*` also hides the roadmap
Parent: W89.4
Status: started
Approach: `dfs_paths.hidden()` in `scripts/paths.py` decides "kept as planning" from the one rule `git check-ignore -v` names per path, and git names only the LAST matching rule by precedence. So an author who keeps `.dfs` as planning with a rule naming it, which is the setup `hidden_message` itself recommends, is still warned whenever a broader rule also matches and wins. Checked in scratch repos (ROADMAP.md, order.md, an item and an artefact, nothing tracked): `.gitignore` = `.*` then `.dfs/` is silent, but `.dfs/` then `.*` reports `.dfs/` hidden by `.*`; and `.gitignore` = `.*` with `.dfs/` in `.git/info/exclude` reports `.*` too, because a `.gitignore` outranks `info/exclude`. That last case is the natural one: a project whose shared `.gitignore` has `.*`, and an author who keeps a personal planning roadmap through the local exclude file. Every chain start and the screen's header (`git hides .dfs`) then warn for good, and `init` ends with "Settle the ignore rule named above first", with no way out except editing the project's shared `.gitignore`. Fix: when git tracks nothing under `.dfs` and `.dfs/` itself is hidden, treat the roadmap as planning if any ignore source that applies (the root `.gitignore`, `git rev-parse --git-path info/exclude`, `core.excludesFile`) has a pattern for which `_names_state_dir` is true, not only the rule check-ignore names. To settle it, add `test_ignored.Hidden` cases for `.dfs/` then `.*`, and for `.*` in `.gitignore` with `.dfs/` in `.git/info/exclude`, expecting `[]`, while `.*` alone and files force-added past `.dfs/` are still reported.
Determination: `hidden()` now also reads every ignore file that applies (the root `.gitignore`, `info/exclude`, `core.excludesFile`) and treats the roadmap as planning when any of them has a pattern naming `.dfs` and git tracks nothing under it, so `.dfs/` then `.*`, and `.*` in `.gitignore` over `.dfs/` in `info/exclude`, are silent while `.*` alone and force-added files are still reported (`test_ignored`, 13 OK; `test_init` 10 OK, `test_chain` 74 OK, `test_screen.HiddenFromGit` OK); confirmed.

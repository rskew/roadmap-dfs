# W173 · move the item log into a separate file that isn't loaded by default

## Summary

New log entries now go to `.dfs/items/<task>.log.md` (`<task>/<tag>.log.md` on a branch), so the task file a session reads holds the Goal and the Tree and no longer grows with every runner line. `load` merges the log file with any `## Log` in the task file and the archive, so every count, the web page and the terminal screen show the same as before. The commit guard, the uncommitted-work classifier, carry, delete, archive and the audit, history and replay readers all take the log file, and the terminal screen's tree cache refreshes when the log file changes. `tree.py splitlog <task>` moves an old task's `## Log` across, `tree.py compact` also moves the log file's past to the archive, and the briefing and `SKILL.md` tell a session to open the log file only for an entry's full text. The Goal was met as read: "not loaded by default" means the task file and the briefing leave the log out, while `load` still merges it. No existing task was moved, since the Goal was read as asking for the mechanism and not a one-off bulk move; the author rules on that. The web page and terminal screen were checked through the state they draw from, not by opening a browser.

### W173.7 · Fix: an archived task loses its log, because load_archived does not read the log file
Parent: W173.4
Status: confirmed
Approach: What is wrong: `tree.py load_archived` (tree.py, near line 1164) builds an archived task with `combine(task, [(g, items text, archive text)])`. It never reads the log file. But `_retire` (used by `archive_task`) moves `items/<task>.log.md` into `archive/archived/items/`. Every task made with the new code keeps its whole log there. So once a task is archived, `web.py` `archived_rows` and the task page (web.py near lines 182 and 415) show it with no log: no sessions, no review, no accept, no raises, and a wrong status from `status_of`. What I checked: in a scratch git repo I put `W1.md` and `W1.log.md` (a session and a review entry) under `.dfs/archive/archived/items/`. `load_archived("W1")` returned 0 log entries. `load("W1")` on the same files in `items/` reads both entries. The existing archive test (`test_a_task_is_archived_only_when_done_reviewed_and_pushed...`) uses an in-file log, so it cannot catch this. What to do: make `load_archived` read each part's log file from `archived_dir()/items` (`<task>.log.md`, `<task>/<tag>.log.md`) and pass it as the fourth item of the `combine` tuple. Add a test that archives a task whose log is in its log file and checks that `load_archived` returns the same log, `status_of` and `open_raises` as `load` did before. Check that `retired_ids` and `archived_task_ids` do not count a `.log.md` file as a task.
Determination: Confirmed: `load_archived` now reads each part's log file from the archive, so an archived task keeps its log, status and raises; a new test failed without the change and passes with it, and a `.log.md` file is not counted as a task.

### W173.8 · Fix: the TUI's tree_of cache is keyed on the task file, so a new log entry does not refresh it
Parent: W173.2
Status: confirmed
Approach: What is wrong: `tui.py` `tree_of` (near line 3554) caches the loaded tree, including its log, keyed on the mtimes of the part files and archive files only. New entries now go to `<task>.log.md` and leave the task file untouched. So after `tree.py log <task> raise ...`, an answer, a review or a session entry, `tree_of` keeps returning the old tree. The item pane, the prune check (`actioned_siblings`) and the raises shown for a task stay stale until a node edit moves the task file's mtime. Before this change every log append rewrote the task file, so the key moved. `test_screen.py` replaces `tree_of` with a lambda, so no test sees it. The Summary says the screen was checked through the state it draws from, which does not cover this cache. What to do: add each part's `dfs_tree.log_part(task, g)` to the paths in the `tree_of` key. Look for any other cache keyed on task file mtimes that holds something read from the log (web.py `commits_for` holds git commits only, so it looks fine). Add a test with the real `tree_of`: load a task, append a log entry with `append_log`, call `tree_of` again and see the new entry.
Determination: Confirmed: the TUI's `tree_of` cache key now includes each part's log file (mtime and size), so a new log entry shows at the next read; a test with the real `tree_of` fails without the change and passes with it, and no other cache keyed on part files holds log data.

# W173 · move the item log into a separate file that isn't loaded by default

## Goal

move the item log into a separate file that isn't loaded by default

## Tree

### W173.1 · Map who reads and writes the log, and plan the work
Status: confirmed
Approach: **The question**: what touches a task's `## Log`, so that moving it to its own file breaks nothing?
- **What this node does**: read `tree.py`, `check.py`, `state.py`, `tui.py`, `web.py` and `branch.py` for every reader and writer of the log, and lay the work out as the nodes below.
- **How we will know it worked**: every reader is named, and each is covered by a node below.
Determination: Confirmed: the log is written only by `append_log`, `compact` and `render` in `tree.py` and read through `parse`/`load`, with raw readers in `check.py` (shape, history, coordinates), `tree._edit_kind` and `uncommitted`, and `state.py`'s size note, so the move fits in the nodes below.

### W173.2 · Write new log entries to a sibling log file that `load` merges but a plain read of the task does not show
Parent: W173.1
Status: confirmed
Approach: **The question**: can every log entry live in `.dfs/items/<task>.log.md` (per part: `<task>/<tag>.log.md`), so the task file a session reads has no `## Log`, while code that needs the log still gets it?
- **Why it matters**: the log is what grows the task file past its handoff budget; a session reads it whole at the start, and most of it is runner lines.
- **What this node does**: in `tree.py` add `log_part(task, tag)`, make `append_log` write there, make `load`/`combine` merge it with any `## Log` still in the task file and the archive's `**Log**:` (so old tasks read unchanged), and make `new_part` and `render` stop writing an empty `## Log`. `part_of` must not mistake the log file for a task part.
- **How we will know it worked**: a test in `test_tree.py`: after `append_log`, the task file has no new entry, `load` shows it, and `status_of`, `sessions_since_author` and `open_raises` give the same answers as before on an old fixture with an in-file log.
Hypothesis: "Not loaded by default" means a session's plain read of the task file and the briefing leave the log out, while `load` still merges the log file so every derived answer stays the same. Wrong if the author meant that `load` itself skips the log unless asked. .dfs/artefacts/5ac199d1-db01-47e7-a23a-d17163fcc256.html
Evidence:
- for: with `append_log` and `delete_node` writing to `<task>.log.md`, `python3 scripts/test_tree.py` went from 1 failure and 1 error to 7 failures and 4 errors. Each new one read the entry from the task file's text, or staged only the part file; none showed a wrong derived answer. After the tests were pointed at the log file, only the 2 that already fail without the change remain.
- for: new test shows `append_log` leaves the task file byte for byte as it was, `load` returns the old in-file entries and the new one in order, and `open_raises` still sees the answer.
- for: `test_web`, `test_chain`, `test_critic`, `test_review_tree`, `test_screen`, `test_worker`, `test_work` and `test_order` show no failure that the unchanged code lacks; `test_login`, `test_chat` and some `test_web` cases fail without the change too (no claude or kiro here).
Determination: Confirmed: new entries go to `<task>.log.md` and `load` merges them with any in-file or archived log, so every derived answer is unchanged, and the `check.py` and `state.py` readers already take the file.

### W173.3 · Keep new log entries in the archive's `**Log**:` instead
Parent: W173.1
Status: parked
Approach: Append each new entry to `.dfs/archive/items/<task>.md` under a `**Log**:` line, reusing the archive's existing append-only check and `archived_log` reader.
Determination: Parked: it would put live entries among settled history (shelved fields), every append must start a new `**Log**:` block after any other block, and log-only edits would no longer be told apart from archive edits; it is the fallback if the sibling file's new checks cost more than they are worth.

### W173.4 · Teach the checker and the edit classifier about the log file
Parent: W173.2
Status: open
Approach: **The question**: do the commit guard and the "uncommitted work" classifier still protect the log once it is in its own file?
- **What this node does**: in `check.py` apply the log rules to `<task>.log.md` (well-formed entries, known kinds, answers name a raise, corrections name a node, entries only added, only at the end, only to this branch's part); make the entries that left the task file count as held when the log file holds them whole. In `tree._edit_kind` and `uncommitted`, treat a change to the log file as "log", or "" when only runner lines.
- **How we will know it worked**: `test_check.py` cases (a removed or edited entry in the log file is refused, an appended one passes) and a `test_tree.py` case for `uncommitted`; run `python3 scripts/test_all.py`.

### W173.5 · Move an existing task's log across, and update what sessions are told
Parent: W173.4
Status: open
Approach: **What this node does**: add `tree.py splitlog <task>`, which moves the whole `## Log` of the task file, verbatim, to the log file (the checker accepts it as a move), and make `compact` use the same target. Update `state.py`'s size note and the briefing's "read the task file" lines, the module docstring in `tree.py`, `SKILL.md` and `docs/`, so that a session reads the Tree and the briefing, and opens the log file only when it needs an entry's full text.
- **How we will know it worked**: a test that `splitlog` leaves `load` unchanged; the briefing for a task with a log file names the file and its size without loading it.

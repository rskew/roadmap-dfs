# W194 · Artefacts on a task should link to the node that created them

## Summary

Each artefact tile on a task's web page now has a "from <node>" link under it that opens the card of the node that made it. The node is the first live node whose text, or whose raise, names the file; an artefact only the author attached has no link. The Goal is met for the task page. The full-page artefact view and the screen's `v` pane were left as they are, and the browser flow for the link was added but could not run to the end here.

## Goal

Artefacts on a task should link to the node that created them

## Tree

### W194.1 · The server says which node made each artefact
Status: confirmed
Approach: **The question**
- Which node made each artefact a task page lists?

**Why it matters**
- `artefacts_for` in `scripts/web.py` lists a task's artefacts with no link back, so the author cannot tell which step produced a page or picture.

**What this node does**
- Add a `node` field to each artefact entry from `artefacts_for`. Its value is the id of the first live node, in tree order, whose own text names the file: Approach, Hypothesis, Evidence, Determination, or a raise on it. An artefact only the log names (an attachment the author added) gets an empty `node`.
- Cover it in `scripts/test_web.py`: an artefact named by two nodes gets the earlier one; one named only in an answer gets none.

**How we will know it worked**
- The new test passes, and the existing `test_web.py` tests still pass.
Hypothesis: The node that made an artefact is the first live node, in tree order, whose text names it. Wrong if a node names a page before the node that made it, or if the author means the node of the commit that added the file. .dfs/artefacts/0f6c875f-b530-4077-9bc1-1fe4bd87071e.html
Evidence:
- for: Over the 138 uuid-named pages and pictures that tasks W100 to W193 on main name, the first node to name one is also the node whose commit added the file for 132 of them.
- against: In the other 6 (for example W190.2, W191.2, W109.2), the page was added in the commit before, because it was drawn while the earlier node ended. The link then points at the node the page asks about, not the node whose commit added it.
Determination: Confirmed: each artefact entry now carries the first live node that names it, and the new test passes; the 6 of 138 pages that differ from the commit still link to the node they belong to.

### W194.2 · Each artefact tile links to its node
Parent: W194.1
Status: confirmed
Approach: **What this node does**
- In `scripts/web/index.html`, `artefactsHtml` draws each tile as a link, and a link cannot hold a link. So wrap each tile in a `div.tilebox` and, when the entry has a `node`, put a link under the tile, "from W194.1", to `#/t/<task>/<node>`, which opens that node's card. The tile itself still opens the artefact. The full-page artefact view is left as it is.

**How we will know it worked**
- A check in `scripts/ui_flows.mjs` (the `artefacts` flow) that the link's href is the node's route, and a run in a browser that clicks it and sees the node's card.
Determination: Confirmed: each tile now has a "from <node>" link that opens that node's card; in a headless browser the link's href was `#/t/W1/W1.2` and clicking it opened W1.2, but the `artefacts` UI flow fails on an older click that fails the same way without this change, and no fonts render here, so a screenshot would show no text and none is kept.

### W194.3 · Fix: an artefact named by a raise loses its node link once the raise is answered
Parent: W194.1
Status: confirmed
Approach: `made_by` in `scripts/web.py` builds each node's prose from the row fields `approach`, `card`, `raises` and `page`. The row's `raises` holds only the OPEN raises (`tui.tree_entries` uses `dfs_tree.open_raises`), and the card is built with `raises=[]`. So a page named only by a raise (the usual answer page) gets `node: "W1.3"` while the raise is open, and `node: ""` as soon as it is answered. I checked this with a throwaway test: raise on W1.3 naming `.dfs/artefacts/bb.html`, then an `answer` with the raise's ts as its argument; `GET /api/task/W1` gave `node: 'W1.3'` before and `''` after. The tile then loses its "from W1.3" link. W194.1 says a raise on the node counts, answered or not. Fix: in `made_by` (or `task_json`) also read the raises of every status, that is the `raise` entries of the task log whose first argument is the node id, and add their body to that node's prose. Extend `test_an_artefact_names_the_first_node_that_names_it` in `scripts/test_web.py` so `bb.html`, once its raise is answered, still has `node` W1.3. Keep the rule that the log at large, and an answer's own text, give no node. Then rerun the `test_web.py` artefact tests.
Determination: Confirmed: an artefact named by a raise keeps its node after the raise is answered; the extended test fails without the change (`bb.html` gets no node) and passes with it, and the other artefact tests pass.

### W194.5 · Hypothesis: the node link is wanted on the task page only
Parent: W194.2
Status: confirmed
Approach: W194.2 put the "from <node>" link only on the tiles in `artefactsHtml` in `scripts/web/index.html` (the task page). The full-page artefact view (`#/a/...`) and the screen's `v` pane were left with no node link. The Summary says so, but W194.2 has no Hypothesis, and the Goal ("Artefacts on a task should link to the node that created them") could also mean those views. Review round 1 asked for this to be stated and W194.4 left it as prose. State it as a Hypothesis on W194.2 with its page: the task page is the only place the author needs the link; it is wrong if the author opens an artefact from `#/a/...` or the `v` pane and expects the node link there. Give it a page (an explanation page in `.dfs/artefacts/`) that shows the three views. If the author may want the others, say so in the Hypothesis rather than add the link unasked.
Hypothesis: The "from <node>" link is only needed on the task page's artefact tiles. Wrong if the author opens an artefact from the full-page view (`#/a/...`) or the screen's `v` pane and expects the node link there. If so, the full-page view needs a button in its bar (small, in `index.html`) and the `v` pane needs the node on each row and a key to open it (larger, in `tui.py`). .dfs/artefacts/bc302dab-5440-4db1-b64f-78071c581973.html
Evidence:
- for: In `scripts/web/index.html`, the full-page view's bar (`drawBar`) already shows a "Node X" button when a raise names the page as its answer page (`raiseOnPage`), so the one case where the node matters there is covered; the author gets to every other artefact from the task page, where the link is.
- for: `lines_artefacts` in `scripts/tui.py` groups the `v` pane by the item you are on ("named by <item>"), not by node, so it has no per-node place for a link.
- against: The Goal says only "Artefacts on a task", which does not rule out the other two views; nobody has said the task page is enough.
Determination: Confirmed: the link stays on the task page tiles and the scope is now a stated Hypothesis with its page; the author can refute it there if the other views are wanted.

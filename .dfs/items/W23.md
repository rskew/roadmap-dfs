# W23 · Do we record enough logs from the chat feature to diagnose issues? A project chat session stopped responding

## Summary

No: before this, a chat the page opened in the background wrote nothing when it started, was sent a message, went quiet, exited or was closed for being idle, and a failed page turn's reason was kept only in memory. Every chat now keeps `.dfs/runs/chat/<scope>.log`: its start, each message queued, typed, refused or dropped, each headless turn with its duration and failure reason, the agent's exit code or signal with the last screen it drew, who closed it, and a note when the agent has said nothing for 90 seconds (DFS_CHAT_STALL) after a message. That last screen is what tells a stuck dialog or a hang from a finished answer, so a stalled project chat can be diagnosed from the log; showing the log on the page was left out as a follow-up. The one `test_chat.py` case about another terminal holding the session fails in this sandbox with or without the change.

## Goal

Do we record enough logs from the chat feature to diagnose issues? A project chat session stopped responding

## Tree

### W23.1 · Audit what a stalled chat leaves behind today
Status: confirmed
Approach: Read chat.py, ptyrelay.py and the screen's chat glue (tui.py start_chat, UiWalker, reap_idle) for every point where a chat starts, is typed into, answers, ends or fails, and note what each writes to disk; compare with `.dfs/runs/activity.log` and `.dfs/runs/chat/`.
Determination: No, the logs are not enough: a background chat (the kind the page opens) writes nothing when it starts, is sent a message, goes quiet, exits (its rc is kept in memory and never read), or is closed by the idle reaper, its pty output is discarded unless a terminal is attached, `Relay._typist` drops a queued message silently when the agent has died, a page turn's error lives only in `Chats.notes` (lost on restart), and the web handler's `log_message` is a no-op; `activity.log` holds one chat line in total, and `.dfs/runs/chat/` holds only session ids.

### W23.2 · A per-chat log file: lifecycle, the messages' fate, and the agent's last words
Parent: W23.1
Status: confirmed
Approach: Add `scripts/chatlog.py` with `log(scope, text)` appending `<ts> <text>` lines to `<run root>/chat/<scope>.log`, rotated to `.log.1` at 1 MB, never raising. Give `ptyrelay.Relay` an optional `log` callable (`ChatHost.ensure` binds it to the scope) and have it record: start (pid, argv without prompt text, cwd), a message queued and when it was typed (and whether the agent was ready or the wait timed out, or dropped because the agent had died), the agent's exit (rc or signal, lifetime, seconds since last output), who closed it (idle reaper with the idle time, new chat, screen exit) and a stall line when a message went unanswered with the agent silent for DFS_CHAT_STALL seconds. Keep the last 8 KB of the agent's pty output, ANSI-stripped, and write it into the log at exit, close and stall, so a hung dialog or crash message is visible. Check with test_ptyrelay.py cases using the stand-in agent.
Determination: Done: `chatlog.py` writes `chat/<scope>.log`, and a background chat now records its start, each message queued, typed or dropped, an exit with rc or signal and the agent's last screen, who closed it, and a quiet line after a message (DFS_CHAT_STALL, 90 s); five new test_ptyrelay.py cases pass, and the pty echo means the byte count after a message is never zero, so the last screen is what tells a hang from a finished answer.

### W23.7 · Fix: a timed-out headless turn logs no output from the agent
Parent: W23.3
Status: confirmed
Approach: `chat.py` `run_turn` catches the `TimeoutExpired`, terminates the agent, collects what it had written with `p.communicate(timeout=TURN_GRACE)` (or the `p.communicate()` after `kill`), then re-raises and drops it; `Chats.turn` then logs only `error = "no answer in 10 minutes"`. The page's chat (no screen, so a headless `run.sh --chat-turn`) hanging is the Goal's "a project chat session stopped responding", and its log line shows nothing of what the agent said or was stuck on, unlike the pty path that logs the last screen. Keep the partial stdout/stderr from `run_turn` (e.g. put it on the raised exception or return it), log its last 600 characters beneath the FAILED line, and add a test_chat.py case with a stub runner that times out after writing output, asserting that output is in `chat/<scope>.log`.
Determination: Done: `run_turn` now puts the output it collects after terminating or killing the agent on the `TimeoutExpired`, `Chats.turn` logs its last 600 characters beneath the FAILED line (the page's note stays "no answer in N minutes"), and the new test_chat.py case fails without the change and passes with it.

# W115 · Login to Claude from dfs page

## Summary

The project dialog on the web page now has a "Claude account" control. It shows who claude is signed in as, re-read each time the dialog opens, and Sign in gives claude's own link; you open it, paste the code it shows back into the page, and the page reports the account now signed in or claude's own error. It runs `claude auth login` through the same pinned claude the runs start, so it replaces the one stored login every run, chat and the terminal read, and `--no-walk` turns signing in off like the chat. The Goal is met for one account at a time; keeping several accounts to switch between, or a long-lived token, was left out because the single stored login is what everything already reads. A valid code has never been exchanged here (every check ended at claude's refusal of a made-up one), so your first real sign-in is the success path's first run.

### W115.1 · The web server signs claude in by running `claude auth login` with pipes
Status: confirmed
Approach: A new `run.sh --claude-auth <args>` execs the pinned claude (the same `CLAUDE_CMD` or nixpkgs pin the runs use) as `claude auth <args>`. A new `scripts/login.py` holds one sign-in at a time: it starts `run.sh --claude-auth login` with stdin and stdout as pipes, reads the sign-in URL it prints, writes the code the author pastes to its stdin, and reports `claude auth status --json` (signed in, email, plan) once it ends. web.py serves it at `GET /api/login` and `POST /api/login/{start,code,cancel,check}`. Checked by a test of login.py and test_web against a stub `CLAUDE_CMD` that prints the URL, reads a code and writes a status.

Wrong if the author meant keeping several accounts and switching between them, an API key, or signing in to something other than the agents' CLI. .dfs/artefacts/28c9c785-868a-41c2-b950-97633974bf86.html

### W115.5 · Fix: the dialog's "who is signed in" is read once per server and never again
Parent: W115.3
Status: confirmed
Approach: `Login.state()` in `scripts/login.py` reads `claude auth status` only on the first ask in the server's life (`self.account is None`), and after a sign-in from the page; `scripts/web/index.html`'s `accountForm` only ever calls `GET /api/login`, never `POST /api/login/check`, so nothing on the page re-reads it. A server stays up for days (sandbox.sh starts it `--restart unless-stopped`), so after the author signs in or out in the terminal or another container, or the stored login lapses (the Goal's own case), the dialog still says "Signed in as <old email>, <plan>". If the first read failed (a cold nix cache past `STATUS_TIMEOUT`, 120 s), it says "claude could not say who is signed in" until the server restarts. Checked: a `Login(read=…)` whose reader returns a new account the second time gives the first answer on both `state()` calls, for a good read and for a timed-out one. Fix: re-read the account each time the dialog opens while no sign-in is running (the page calls `/api/login/check` on open, or `state()` takes a flag), keeping the polls cheap; settle it with a test_login case where the stored account changes between two openings and the second shows the new one, and the `account` flow in test_ui still passing.
Determination: Confirmed: `Login.refresh()` re-reads `claude auth status` unless a sign-in is going, `POST /api/login/check` calls it and the dialog calls that on every open; a new test_login case (a failed first read, then a changed account) passes, as do test_web (95) and the `account` flow in test_ui.

### W115.6 · Fix: `--no-walk` leaves the sign-in open, so anyone who can reach the page can replace the machine's claude login
Parent: W115.1
Status: confirmed
Approach: `login_act` in `scripts/web.py` serves `POST /api/login/{start,code,cancel,check}` whatever `WALK["enabled"]` is, while `chat_act` and `walk_act` refuse with 403 under `--no-walk`, whose help says the page "cannot start an agent". The sign-in runs claude and replaces the login every run and chat on the machine uses, so on a `--host 0.0.0.0 --no-walk` server (the mode meant to be safe on a network) anyone on that network can start a sign-in, paste a code from their own account, and the author's agents then run as that account with the author's own login gone. web.py's docstring says it is "like the walk", but the walk can be turned off and this cannot. Fix: refuse the login POSTs under `--no-walk` as the chat does (`GET /api/login` can stay readable), with the page showing the refusal in the dialog; settle it with a test_web case that a `walk_enabled=False` server answers 403 to `/api/login/start` and starts no process. If the session thinks the author would rather keep it open, that is a Hypothesis for the author to read, not a silent choice.
Determination: Confirmed: `login_act` answers 403 to `login/start`, `code` and `cancel` under `--no-walk` (`check`, a read, and `GET /api/login` stay open and now say `enabled`), the dialog shows "Signing in is off" instead of the Sign in button, and the --no-walk help, startup warning and docstring name it; a test_web case shows the 403s and no process started, test_login, test_web (95) and the `account` flow in test_ui pass.

- No session saw a valid code exchanged through the pipe or a run picking up a login made from the page (every real-claude check ended at claude's 400 for a made-up code); the success path rests on the author's first real sign-in, which the Summary should say.

# W139 · thorough performance review, make the page more responsive

## Summary

The web page now loads and updates much faster. On this repo's 141 tasks the list call fell from 697 ms to 265 ms and the task call from 363 ms to 91 ms, text responses are gzipped (the task call goes from 277 KB to 67 KB), and in a headless browser the list draws in about 0.5 s and a task in about 0.25 s, from about 1.9 s and 1.3 s. A page load no longer renders twice, and a change to one task makes an open task page read it again only if it is that task, even when a read is replaced or fails on the way. A page whose event connection drops is told what it missed when it reconnects. The Goal was met for the web page; the terminal screen was not touched, and the cache headers were left as they were, since loosening them for private roadmap data is the author's choice. One narrow gap remains: a change landing between a new page's first read and its event connection is not pushed to it until the next change.

### W139.3 · Make the server calls cheap
Parent: W139.2
Status: confirmed
Approach: **What this node does**: removes the two hot spots the profile found. It parses each task file once per `state_json` call (or caches the parse by file mtime and size), and asks git for the default ref once per `task_json` call instead of once per node card. Output stays byte-identical.
- **How we will know it worked**: the same JSON before and after on every task, `state_json` and `task_json("W130")` timed again and clearly lower, and `scripts/test_web.py` and `scripts/test_tree.py` pass.
Determination: A per-pass `read_scope` in `tree.load` and a 5 s `ttl` on the two remaining `default_ref` calls leave the JSON byte-identical and cut `state_json` from 1158 to 491 ms CPU and `task_json("W130")` from 359 to 116 ms wall.

### W139.4 · Send less over the wire
Parent: W139.1
Status: confirmed
Approach: **The question**: how much of the load is bytes, not compute?
- **What this node does**: measures `/` (169 KB `index.html`), `/api/state` and `/api/task/<id>` as sent. If they go uncompressed and without validators, adds gzip to `Handler.send` in `web.py` for text of 1 KB or more, and tests it in `test_web.py`. It leaves `ETag` and `304` out: every response says `Cache-Control: no-store`, which stops a browser asking again, and loosening that for private roadmap data is a choice for the author.
- **How we will know it worked**: the bytes on the wire fall, a client that does not ask for gzip gets the same bytes as before, and pictures are not compressed.
Determination: gzip at level 1 takes the task call from 277 KB to 67 KB (3 ms) and the 169 KB page to 62 KB, and the cache headers are left as they were.

### W139.6 · Push less, refetch less
Parent: W139.1
Status: confirmed
Approach: **The question**: does every file change make every open page refetch and compare everything?
- **What this node does**: reads `watch` and `roadmap_signature` in `web.py` and the push handler in `index.html`. Known from the browser timing: every page load renders twice, because `/api/events` sends the current version to a new listener and `listen()` turns it into a second `render(false)` 120 ms after the first, which then supersedes the first; and a push on the task view refetches `/api/walk` (a whole-state build) and `/api/state` as well as the task. If a change to one task refetches the open task and the list anyway, sends the changed task ids with the event so the page refetches only what it shows.
- **How we will know it worked**: touching an unrelated task causes no `/api/task` request from an open task page (counted in a test), and a change to the open task still redraws it.
Determination: The event now names the changed tasks and a new page is told nothing, so a page load makes one set of reads and touching an unrelated task makes the open task page skip `/api/task` (the new `push_scope` flow is red without the page change and green with it); `/api/walk` and `/api/state` are still read on each push.

### W139.9 · Fix: a superseded or failed render leaves the open task page stale
Parent: W139.6
Status: confirmed
Approach: In `scripts/web/index.html`, `renderDraw` skips `/api/task/<id>` (`same`) when the push's `changed` set does not name the open task, and reuses `S.task`. But `S.task` is assigned only after the fetch lands and only if `mine === RENDERS`. Race: push 1 names W9 -> `render(false, {W9})` starts and fetches W9; push 2 names only W1 arrives before it lands -> `render(false, {W1})` starts, `same` is true (S.task is still the old W9), and render 1 is then dropped at `if (mine !== RENDERS) return` without storing its fetched task. The page draws the old W9 and shows nothing newer until W9 changes again. The same loss follows a failed `/api/task` fetch (the `catch` toasts, `pushed` was already cleared, the next push reuses the stale `S.task`). Read from the code, not yet run. Fix: carry the unread change forward, e.g. keep a set of task ids known stale (add the push's tasks in the `change` handler; remove an id only when `S.task` for it is stored from a landed fetch), and let `same` hold only when the open task is not in that set. Settle it with a flow in `ui_flows.mjs` next to `push_scope`: touch the open task, then (within the task call's latency, e.g. with the route delayed through playwright) touch another task, and assert the open task's new text is drawn.
Determination: Confirmed: a `stale` map (task id to the push that changed it, cleared only when a read of the task has landed and been kept) now gates the `same` skip, and the new `push_stale` flow (replaced read, then failed read) is red without the page change and green with it.

### W139.10 · Fix: an event stream that has heard nothing reconnects with no catch-up
Parent: W139.6
Status: confirmed
Approach: In `scripts/web.py`, `Hub.subscribe(last)` now queues a catch-up only when the request carries `Last-Event-ID`, and `Handler.events` sends `id:` only with a `change` event. A page that has not yet received any change (an idle page, or a new one) has no id, so when its connection drops (a phone sleeping, a proxy restart, the server restarting) and `EventSource` reconnects, `last` is None and it is told nothing: every change made while it was away is missed until the next one, and the page shows no sign (`#live` is hidden again on `onopen`). Before W139.6 every new listener was told the version, so this was covered. W139.6's Summary names the first-load window only; this reconnect case is wider. Fix: have `events` write an `id: <version>` line (no event) right after `retry: 2000`, so the browser holds an id from the first connection and every reconnect sends it; the server then compares as it already does. Also consider having the page do one `render(false)` when `onopen` follows an `onerror`. Settle it with a `test_web.py` case: connect, read the first lines, drop, `notify`, reconnect with the id the server gave, and expect a `change`; and one where a server restart (new `version`) is caught up.
Determination: Confirmed: `events` now writes `id: <version>` right after `retry`, taken under the hub lock with the subscription, so a page that has heard no change reconnects with an id and is caught up; the new `test_web.py` case is red without the change and green with it (a restarted server's new version is caught up too), and test_web fails the same 4 tests as before.

### W139.11 · Minor findings from the review
Parent: W139.4
Status: confirmed
Approach: One line each:
- `Handler.send` in `scripts/web.py` tests `"gzip" in Accept-Encoding`, so `gzip;q=0` still gets gzip; parse the q-value.
- `Handler.send` adds `Vary: Accept-Encoding` to every response, including ones never compressed; harmless, but the W139.4 test does not check a client without gzip gets identical bytes plus that header on a small body.
- `changed_tasks` in `web.py`: `TASK_FILE` needs digits then `.`, `/` or `\`, so a tagged id file such as `items/W13@tag.md` falls to `None` (rereads everything). Safe, but the comment should say so, or the regex should take `@tag`.
- `full_cached` keys on `roadmap_signature` only, so git-derived fields of the list (ahead, uncommitted, pr) can lag up to `FULL_TTL` = 2 s after a page write that moves only git; say so in the docstring or have writers drop `_FULL`.
- `walk_json` now hands the cached (up to 2 s old) state to `walker().snapshot`, which stores it as `walker.data`; the walker's own actions reload first, but note this in the `snapshot` docstring.
Determination: Confirmed: all five are done (`gzip;q=0` is refused, the small-body `Vary` and a branch's task file are tested, and the two docstrings say what can lag); test_web fails the same 4 tests as before.

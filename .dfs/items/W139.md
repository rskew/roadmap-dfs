# W139 · thorough performance review, make the page more responsive

## Summary

The web page now loads and updates much faster. On this repo's 141 tasks the list call fell from 697 ms to 265 ms and the task call from 363 ms to 91 ms, text is gzipped (the task call goes from 277 KB to 67 KB), and in a headless browser the list draws in about 0.5 s and a task in about 0.25 s, from about 1.9 s and 1.3 s. A page load renders once, a change to one task makes an open task page read it again only if it is that task, and a page that reconnects, or that was still loading when a change was made, is told what it missed. The list and walk share one build for up to 2 s, so a change only git shows (a commit made outside the page) can lag a read by that long; every action made from the page shows at once. The Goal was met for the web page; the terminal screen was not touched, and the cache headers were left as they were, since loosening them for private roadmap data is the author's choice.

### W139.9 · Fix: a superseded or failed render leaves the open task page stale
Parent: W139.6
Status: confirmed
Approach: In `scripts/web/index.html`, `renderDraw` skips `/api/task/<id>` (`same`) when the push's `changed` set does not name the open task, and reuses `S.task`. But `S.task` is assigned only after the fetch lands and only if `mine === RENDERS`. Race: push 1 names W9 -> `render(false, {W9})` starts and fetches W9; push 2 names only W1 arrives before it lands -> `render(false, {W1})` starts, `same` is true (S.task is still the old W9), and render 1 is then dropped at `if (mine !== RENDERS) return` without storing its fetched task. The page draws the old W9 and shows nothing newer until W9 changes again. The same loss follows a failed `/api/task` fetch (the `catch` toasts, `pushed` was already cleared, the next push reuses the stale `S.task`). Read from the code, not yet run. Settle it with a flow in `ui_flows.mjs` next to `push_scope`: touch the open task, then (within the task call's latency, e.g. with the route delayed through playwright) touch another task, and assert the open task's new text is drawn.
Determination: Confirmed: a `stale` map (task id to the push that changed it, cleared only when a read of the task has landed and been kept) now gates the `same` skip, and the new `push_stale` flow (replaced read, then failed read) is red without the page change and green with it.

### W139.10 · Fix: an event stream that has heard nothing reconnects with no catch-up
Parent: W139.6
Status: confirmed
Approach: In `scripts/web.py`, `Hub.subscribe(last)` now queues a catch-up only when the request carries `Last-Event-ID`, and `Handler.events` sends `id:` only with a `change` event. A page that has not yet received any change (an idle page, or a new one) has no id, so when its connection drops (a phone sleeping, a proxy restart, the server restarting) and `EventSource` reconnects, `last` is None and it is told nothing: every change made while it was away is missed until the next one, and the page shows no sign (`#live` is hidden again on `onopen`). Before W139.6 every new listener was told the version, so this was covered. W139.6's Summary names the first-load window only; this reconnect case is wider. Fix: have `events` write an `id: <version>` line (no event) right after `retry: 2000`, so the browser holds an id from the first connection and every reconnect sends it; the server then compares as it already does. Also consider having the page do one `render(false)` when `onopen` follows an `onerror`. Settle it with a `test_web.py` case: connect, read the first lines, drop, `notify`, reconnect with the id the server gave, and expect a `change`; and one where a server restart (new `version`) is caught up.
Determination: Confirmed: `events` now writes `id: <version>` right after `retry`, taken under the hub lock with the subscription, so a page that has heard no change reconnects with an id and is caught up; the new `test_web.py` case is red without the change and green with it (a restarted server's new version is caught up too), and test_web fails the same 4 tests as before.

### W139.13 · Fix: `TASK_FILE` takes the first `items/<letters+digits>/` in a path, so a repo under such a directory names the wrong task
Parent: W139.6
Status: confirmed
Approach: `TASK_FILE` in `scripts/web.py` is `[/\\]items[/\\]([A-Za-z]+\d+)(?:@[^./\\]+)?[./\\]` and `changed_tasks` uses `.search` on the whole absolute path of each changed file, so it matches the leftmost `/items/<name><digits>/` anywhere.

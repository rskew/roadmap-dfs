### W139.1 · Fix the reading of the Goal and take a baseline
Status: confirmed
Approach: **The question**: which "page" does the Goal mean, and what does "responsive" mean?
- **What this node does**: reads the Goal as the web page the roadmap serves (`scripts/web.py` server, `scripts/web/index.html` client) and "responsive" as quick to load and quick to update. Times the server calls the page makes in-process on this repo's 141 tasks, and reads how the client reacts to a push. The numbers are the baseline every later node is compared against.
- **How we will know it worked**: a table of timings in the Evidence, and an answer page the author can use to overrule the reading.
Hypothesis: "The page" is the web page (`scripts/web.py` and `scripts/web/index.html`), and "responsive" means fast to load and to update, not the layout at small widths. Wrong if the author means the terminal screen (`tui.py`) or the phone layout. .dfs/artefacts/add70572-c9d1-4cce-9b36-29e938773ef2.html
Evidence:
- for: `web.py` and its docs call what it serves "the page" and call the terminal view "the screen". The page's viewport tag and 11 `@media` rules already exist, so layout is not obviously the gap.
- for: in-process on this repo, best of 3: `state_json` (the list call) 697 ms / 73 KB, `task_json("W130")` (the task call, run on every change while a task is open) 363 ms / 277 KB.
- for: `index.html` already skips a redraw when the response is unchanged (a signature check in `renderDraw`), so a slow server call is paid on every push even when nothing shows.

Determination: The web page's server calls are the slow part to fix first (list 697 ms, task 363 ms), so the speed reading stands and the work goes under it.

### W139.2 · Profile the two slow server calls
Parent: W139.1
Status: confirmed
Approach: **The question**: where do the 697 ms in `state_json` and the 363 ms in `task_json` go?
- **What this node does**: runs `cProfile` on both against this repo and lists the top callers by cumulative time (file parsing, git calls, repeated state reads).
- **How we will know it worked**: a short list of the real hot spots, with their share of the time, ready to fix in the next node.
Determination: `state_json` reparses each task file about five times (705 `tree.load` calls for 141 tasks, 0.92 of 1.55 s under the profiler), and `task_json` runs git 93 times through 31 `default_ref` calls (0.17 of 0.38 s).

### W139.3 · Make the server calls cheap
Parent: W139.2
Status: confirmed
Approach: **What this node does**: removes the two hot spots the profile found. It parses each task file once per `state_json` call (or caches the parse by file mtime and size), and asks git for the default ref once per `task_json` call instead of once per node card. Output stays byte-identical.
- **How we will know it worked**: the same JSON before and after on every task, `state_json` and `task_json("W130")` timed again and clearly lower, and `scripts/test_web.py` and `scripts/test_tree.py` pass.
Determination: A per-pass `read_scope` in `tree.load` and a 5 s `ttl` on the two remaining `default_ref` calls leave the JSON byte-identical and cut `state_json` from 1158 to 491 ms CPU and `task_json("W130")` from 359 to 116 ms wall.

### W139.4 · Send less over the wire
Parent: W139.1
Status: confirmed
Approach: **The question**: how much of the load is bytes, not compute?
- **What this node does**: measures `/` (169 KB `index.html`), `/api/state` and `/api/task/<id>` as sent. If they go uncompressed and without validators, adds gzip to `Handler.send` in `web.py` for text of 1 KB or more, and tests it in `test_web.py`. It leaves `ETag` and `304` out: every response says `Cache-Control: no-store`, which stops a browser asking again, and loosening that for private roadmap data is a choice for the author.
- **How we will know it worked**: the bytes on the wire fall, a client that does not ask for gzip gets the same bytes as before, and pictures are not compressed.
Determination: gzip at level 1 takes the task call from 277 KB to 67 KB (3 ms) and the 169 KB page to 62 KB, and the cache headers are left as they were.

### W139.5 · Time the client in a headless browser
Parent: W139.1
Status: confirmed
Approach: **The question**: is the browser slow to draw, apart from the server?
- **What this node does**: serves the page from a temporary copy of this repo, loads the list and the W130 task view in headless chromium (playwright, as `artefact_check.mjs` does) and records time to first draw, the draw time of `drawTask`, and long tasks during a push. Fixes the worst hot spot found (for example rebuilding the whole tree with `innerHTML` when one node changed).
- **How we will know it worked**: the same measure before and after, with the draw time down, and `test_web.py`, `test_webscreen.py` and `test_ui.py` pass.
Determination: The browser is not slow to draw (list 17 ms, task 26 ms, no long task over 74 ms); the wait was two whole-state builds per render, one for `/api/state` and one for `/api/walk`, run at once, and sharing one build in `web.full_cached` cut median first draw of the list from about 1.9 s to 0.6 s and of the task from about 1.3 s to 0.8 s, with `test_ui.py` failing the same 24 of 70 tests before and after.

### W139.6 · Push less, refetch less
Parent: W139.1
Status: confirmed
Approach: **The question**: does every file change make every open page refetch and compare everything?
- **What this node does**: reads `watch` and `roadmap_signature` in `web.py` and the push handler in `index.html`. Known from the browser timing: every page load renders twice, because `/api/events` sends the current version to a new listener and `listen()` turns it into a second `render(false)` 120 ms after the first, which then supersedes the first; and a push on the task view refetches `/api/walk` (a whole-state build) and `/api/state` as well as the task. If a change to one task refetches the open task and the list anyway, sends the changed task ids with the event so the page refetches only what it shows.
- **How we will know it worked**: touching an unrelated task causes no `/api/task` request from an open task page (counted in a test), and a change to the open task still redraws it.
Determination: The event now names the changed tasks and a new page is told nothing, so a page load makes one set of reads and touching an unrelated task makes the open task page skip `/api/task` (the new `push_scope` flow is red without the page change and green with it); `/api/walk` and `/api/state` are still read on each push.

# W126 · Draft tasks should stand out more

## Summary

A draft task is now easier to spot in both task lists. In the tui its status word is drawn bold amber, where it was grey, and on the web page an open draft that is not held gets a dashed stripe, an italic goal and a filled "draft" badge in the page's own ink so it follows light and dark mode. The Goal is met for the lists; the task's own page, which already has its Draft button, was left alone. The web change was checked by computed styles only, since playwright, node and a font-bearing browser were not available here, so the browser flow that asserts the stripe survives a hover that repaints the row has not been run. Marking only the two lists, and leaving a held or done draft unmarked, is an assumption the author can rule on.

## Goal

Draft tasks should stand out more

## Tree

### W126.1 · The tui list shows a draft in bold amber
Status: confirmed
Approach: In scripts/tui.py the item list draws a draft's status cell ("draft") in the dim chrome colour, so it recedes beside `open`. Draw that cell bold in the amber look instead (the cursor row keeps its reverse band), and add a test in scripts/test_screen.py that a draft row's status cell is drawn with the bold amber attribute and a plain open row's is not.
Determination: A draft's status cell is now bold amber in the tui list; test_screen goes red without the change and green with it.

### W126.2 · The web task list marks a draft row
Parent: W126.1
Status: confirmed
Approach: In scripts/web/index.html the draft tag in the task list is the same plain `.tag` as any other. Give the row a `draft` class (dashed ink stripe on its left edge, goal in italics) and draw its tag as a filled ink badge (`.tag.draft`: ink background, paper text), so a draft is found at a glance in light and dark mode. Check with scripts/artefact_check.sh or the ui flow `draft` in scripts/ui_flows.mjs (extend it to assert the row has the class), and run test_web.py.
Determination: An open draft's web row now carries a `draft` class (dashed ink stripe, italic goal) and a filled ink badge; Chromium's computed styles confirm it in both modes, but no playwright flow or legible screenshot could run here (no playwright, headless Chromium draws no glyphs), and test_web's chat and login tests fail with or without the change.

### W126.3 · A draft's stripe survives hover and assumptions, and the web marks a draft as the tui does
Parent: W126.2
Status: confirmed
Approach: In scripts/web/index.html draw the draft stripe as an absolutely positioned `.item.draft::before` (pointer-events none) instead of a background-image, so `.item:hover { background }` does not reset it and the `.item.assumes` inset shadow on the same edge does not cover it. Compute one `draft` flag in the list render, `it.draft && it.status === "open" && !it.blocked_by && !it.waiting_on`, as the tui does for its "draft" word, and use it for both the row class and the badge (the badge showed on any draft, done ones included). Extend the ui_flows `draft` flow to assert the stripe pseudo-element exists, and check computed styles in headless Chromium while hovered.
Determination: The draft stripe is now a `::before` that hover and the assumption shadow cannot cover, and the row class and badge share one flag matching the tui (open, not held); Chromium computes the pseudo-element as an absolute 4px dashed stripe, test_screen passes, test_web fails only its two unrelated chat and login tests, and ui_flows could not run (no node or playwright).

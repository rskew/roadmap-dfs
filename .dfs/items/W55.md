# W55 · Codex limits reached until reset time, time not parsed properly? Hold time doesn't match

## Summary

A Codex usage limit says when to try again as "try again at 5:59 PM" (or "try again at Oct 14th, 2026 4:01 AM" for a far reset), with no "resets" and no zone. The limit reader now takes that phrase as the reset and the walk holds until that time on the walk machine's own clock, plus the usual two-minute margin, instead of a flat hour. The Goal is met; one assumption stands: Codex's clock time is on the clock of the machine the walk runs on, which holds on the one box seen, and a Codex run on another clock would be read wrongly. Claude's, Kiro's and Opencode's limits are unchanged.

## Goal

Codex limits reached until reset time, time not parsed properly? Hold time doesn't match

## Tree

### W55.1 · Read codex's "try again at <time>" as the reset instant
Status: confirmed
Approach: Codex ends a usage limit with `You've hit your usage limit. Upgrade to Pro (...) or try again at 5:59 PM.` (or `try again at Oct 14th, 2026 4:01 AM.` for a far reset), with no "resets" and no zone. scripts/limit.py `classify` keeps only text after "resets", so a codex limit records `resets=""` and walk.py holds the flat hour (WALK_HOLD) instead of until the reset. Make `classify` for codex return the "try again at <stamp>" phrase as `resets`, and make `reset_at` parse the bare `H:MM AM/PM` (today, else tomorrow, as for claude's shape) and the `Mon Dth, YYYY H:MM AM/PM` form, adding RESET_MARGIN. Tests in scripts/test_limit.py use lines taken from real codex sessions in ~/.codex/sessions.
Hypothesis: Codex's bare clock time is on the clock of the machine the walk runs on, so `reset_at` reads it in local time. Wrong if a codex run stamps its "try again at" in another zone than the walk's. .dfs/artefacts/06e044d7-e297-44d6-80ee-690f97c9d6ee.html
Evidence:
- for: of 39 limit errors in ~/.codex/sessions on this UTC box, 36 name a clock time 0 to under 5h after the error's UTC timestamp (2026-10-09T01:37Z says 5:38 AM) and 3 name a later date, so the time is on the box's clock.
- against: no log from a codex run in another zone was available, so only one zone is seen.
Determination: Confirmed: limit.py now records a codex limit's "try again at <time>" as its reset and reset_at turns both of its shapes into an instant on the local clock, so the walk holds until then and not the flat hour (real session logs give `try again at 5:59 PM`; test_limit, test_walk, test_chain and test_runs pass), which meets the Goal.

### W55.2 · Fix: a codex limit reads an earlier "resets …" in the stream before its own "try again at"
Parent: W55.1
Status: started
Approach: scripts/limit.py `classify`, codex branch, returns `resets_in(raw) or try_again_in(raw[m.start():])`. `resets_in(raw)` searches the WHOLE stream, so any earlier text containing "resets " (a command's output or a file the session read, e.g. a codex session on this very repo cat-ing scripts/limit.py with its "resets 8pm (UTC)" comment) wins over codex's real "try again at 5:59 PM". Checked: a stream of one `command_execution` item whose output has "# resets 8pm (UTC)" followed by the codex error `You've hit your usage limit. ... or try again at 5:59 PM.` classifies as `(True, 'resets 8pm (UTC)')`, so `reset_at` returns 8pm UTC (or an unparseable string and the flat hour) instead of 5:59 PM, which is the Goal's wrong hold again. Codex's own limit sentence never says "resets", so for codex prefer `try_again_in(raw[m.start():])` and fall back to `resets_in(raw[m.start():])` (or nothing), both read from the limit sentence on. Add a test in scripts/test_limit.py `Codex`: an earlier item containing "resets 8pm (UTC)" before the limit error still gives `(True, "try again at 5:59 PM")`. Run test_limit, test_walk.
Determination: Confirmed: a codex limit is now read from the limit sentence on, "try again at" first and "resets" only after it, so an earlier "resets 8pm (UTC)" in a printed file no longer wins; the new test went red on the old code and green on the fix, and test_limit, test_walk, test_chain and test_runs pass.

### W55.3 · Minor findings from the review
Parent: W55.1
Status: open
Approach:
- scripts/walk.py hold: `reset_at(run["resets"], now)` is evaluated when the walk reads the run end, not at the error's time, so a bare "try again at 5:59 PM" read after 5:59 PM becomes tomorrow's; this is the same as claude's shape, so only note it in the limit.py comment beside TRY_AT_RE if kept.

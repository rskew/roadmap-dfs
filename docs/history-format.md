# The status file and the history file

A task is two files that join by node id. The **status file** is what every session
loads, and it stays small. The **history file** is the task's whole record and is never
trimmed. This page is the format both are built to, as task W203 built it: `scripts/taskhistory.py`
reads and writes it, `tree.py` loads it, `check.py` holds it to the rules below, and an
old-format task is read as before until `tree.py migrate` moves it. W75, the longest task in the
repo, has been moved: its history file holds 69 nodes and 230 log entries, and its status file
is 3,875 characters (968 tokens) against 25,067 characters for its old digest.

The fixture `scripts/fixtures/history/` holds one small task in this format (`W9`): every
rule below can be seen in it, and the parser, the migration and the checks are tested on it.

## Files

For a task `W13` on the default branch:

| File | Is | Written by |
|---|---|---|
| `.dfs/items/W13.md` | the status file | sessions (Goal, Summary, Decisions, Not taken); `tree.py` (Live tree, Raises) |
| `.dfs/items/W13.history.md` | the history file: one section per node | sessions, append only |
| `.dfs/items/W13.log.md` | the log, as now | `tree.py log` |

A task is **new format** when its history file exists, and old format otherwise. The two
are read side by side until every task has moved. The old archive
(`.dfs/archive/items/W13.md`) is not read once a history file exists, because migration
has copied everything in it; it is left where it is.

`W13.history.md` does not collide with the task-file pattern (`part_of` matches
`<task>.md` only), the same way `W13.log.md` does not.

### Branch parts

A branch with tag `fx` writes its own three files, mirroring today's parts:
`W13/fx.md`, `W13/fx.history.md` and `W13/fx.log.md`. Node ids in them carry the tag
(`W13.1@fx`). **There is one history per part, not one per task**, because two branches
that append to one file conflict at the end of the same section, which is the failure the
parts exist to prevent. A reader merges the parts exactly as `combine` does now: every
part's nodes, the logs by time, Goal and Summary from the first part that has a Goal.

A `Supersedes:` link names a node in its own part only. To replace a node in another part,
wait until the parts merge and link then.

## The status file

```
# W13 · <title>

## Summary          (only once the task is complete; two to four plain sentences)
## Goal
## Decisions in force
## Not taken
## Live tree        (generated)
## Raises           (generated)
```

The whole file is loaded by every session, and it is the only file the size budget
applies to (the budget keeps today's number, `state.HANDOFF_BUDGET`, 10,000 tokens). It
stays bounded because a node that is confirmed leaves the Live tree, and only its effect
stays, in one line, while that effect holds.

**Decisions in force** is kept by hand. One line per ruling or design fact that still
holds:

```
- charger is the BQ25619 (W15.87, 2026-11-25)
- four layers (answer 2026-11-25T09:14:02Z)
```

The shape is `- <the decision> (<cite>)`. The cite is a node id and the date it was
confirmed, or the word `answer` and the timestamp of the author's answer in the log. The
cite is what makes the line checkable and what `tree.py show` follows to the reason. A line
that cites several nodes takes the date of the latest. When a node is confirmed that changes a
decision, the same commit edits the line.

`check.py` holds each line to the history: it must cite a node or answer that exists, every
cited node is confirmed, and at least one is not superseded (a line that restates a fact may
cite the chain of nodes that shaped it). A line left unchanged by the commit that confirms a
node superseding one it cites is refused, so that commit has to rewrite or remove it. The
Live tree must hold exactly the open, started and parked nodes, the history may only grow
(a merge may interleave it), and the status file's token budget refuses a commit only when
what is kept by hand grew, so adding a node is never refused for size.

**Not taken** is kept by hand, one line per refuted branch and its reason, so it is not
tried again: `- <what was tried and why it failed> (W15.42, 2026-11-20)`. The cite is a
refuted node. A task with no refuted branch says `(none)`.

**Live tree** is generated by `tree.py status <task>` from the history. It holds every
open, started and parked node in full (the fields as they stand now), each under one
title line for each of its ancestors up to the task:

```
- W13.4 · charger (confirmed)
### W13.9 · pick the boost part
Parent: W13.4
Status: open
Approach: ...
```

A confirmed or refuted node is not in it, unless it is an ancestor of one that is, and
then only as its one title line. A superseded node is never in it. `started` is a mark of
the status file alone: `tree.py start` sets it there, regeneration keeps it, and it is never
written to the history, which only holds what a commit would show.

**Raises** is generated: every open raise, and every answer not yet acted on, quoted whole
from the log.

`tree.py status <task>` writes both sections from the history and the log, keeps every other
section as it is, and drops the old `## Tree` and `## Log` (the history and the log file hold
all of them). An empty section says `(none)`, or `(nothing is open or parked)`. A branch part's
status file has its own Live tree and no Raises, since the raises belong to the task. A node
under a refuted node, one cut by a correction and one a confirmed node supersedes are not
live. The chain of title lines above a live node is one line per ancestor, however long: the
longest chain of parents in the repo today is 16.

When a task has a status file with a `## Live tree`, `tree.py digest` is that file whole, and
the check's token budget counts it, so no node of the history adds to either. `tree.py start`
sets the `started` mark in the Live tree and `tree.py add` appends the new node to the history
and regenerates the file. Editing and deleting a node in this format are refused until they are
built.

## The history file

```
# W13 · <title> · history

### W13.4 · charger
Parent: W13.3
Tags: charger, power
Supersedes: W13.2
Status: open
Approach: ...
Hypothesis: ...
Status: confirmed
Evidence:
- for: ...
Determination: ...
```

One section per node, from the `### <id> · <title>` line to the next such line. The node's
whole story is in its section, and the section is the only place it is written.

**Append only.** A line, once committed, is never removed or changed. A section grows at
its end: a session appends the field it is changing, and **for a field that holds one value
(`Parent`, `Tags`, `Supersedes`, `Status`, `Approach`, `Hypothesis`, `Determination`, `Ask`,
`Corrects`) the last line wins**; `Evidence:` bullets accumulate. A reader folds the section
to the current node; `tree.py show --raw` prints the lines as written. A correction is a new
line that says what it corrects. This is how an open node is edited, and how it is
confirmed: `Status: confirmed` and `Determination:` are appended. Inserting a section into
the middle of the file is allowed (a new node goes in tree order, not at the end of the
file), and so is a line added inside a section, because only a removed or changed line
breaks the rule.

**Fields.** The fields are today's (`Parent`, `Status`, `Approach`, `Hypothesis`,
`Evidence`, `Determination`, `Ask`, `Corrects`) and two new ones:

- `Tags:` a few topic words, comma separated, such as `charger, boost, antenna` or
  `firmware/cell`. A tag is lower case letters, digits, `-`, `_` and `/`.
- `Supersedes:` the ids this node replaces, comma separated: `Supersedes: W13.2`.

**Statuses.** Stored: `open`, `parked`, `confirmed`, `refuted`. `superseded` is **derived,
never stored**: a node is superseded when a confirmed node names it in `Supersedes:`. A
refuted node stays refuted whatever names it. The status the tools show for a node is the
stored one, or `superseded` when that holds.

**The log** stays in its own file in today's format, because every tool that writes it
already does. An entry names a node when its head or body holds the node id as a whole
word; an answer names the node of the raise it answers. `tree.py show` finds log entries by
that rule, so the log needs no new syntax.

**Size.** The file grows without limit, and no check looks at its size, because nothing
reads it whole by default. If it ever becomes unwieldy it can be split by node range
behind the same `show` interface.

## Links, tags and what the briefing pulls in

- `tree.py show <id>`: the node's folded section, its children, the chain of nodes it
  supersedes and is superseded by (read in order from either end), and every log entry
  that names it.
- `tree.py tag <tag>`: the same for every node carrying the tag, oldest first.
- The briefing adds, for the node in hand: its section whole, the chain of its parents
  (one section each, folded), what it supersedes, and the recent sections of nodes that
  share a tag with it. The critic gets the same for each node it judges, and the reviewer
  the decisions with the sections of the nodes they cite.

## Settled choices

The goal's document ended with six open questions. Each is answered here, with the
reason.

1. **Decisions in force: kept by hand.** One short line per decision, written by the
   session that confirms the node and held to the history by the checks below. The
   alternative, a `Decision:` field on each confirmed node that a later node retires, cannot
   go stale, but it puts a new field into every node and gives no bound on the file's size.
   It stays an option if the hand-kept lines go stale on a real task.
2. **The briefing's history allowance: 4,000 tokens per node in hand**, on top of the
   status file. A typical section is a few hundred tokens, so this holds the node, its
   parents and a few neighbours. When over, drop in this order: tag neighbours, oldest
   first; then superseded nodes, furthest in the chain first, cut to their title and
   Determination; then parents cut to the same. The node's own section never drops, even
   if it alone is over. "A few neighbours" is the newest five (`taskhistory.PULL_NEIGHBOURS`)
   before the allowance cuts. A critic judging several nodes is given each section once, and
   the reviewer is given each decision in force with the sections it cites, what they replaced,
   and the answer it cites (no parents, no tag neighbours): `state.py` `_history_block` and
   `_decision_history`, over `taskhistory.pull`.
3. **ROADMAP §0**: the sentence "the tree reads the same from the file alone" becomes "the
   live tree reads from the status file and the whole tree from the history". Parked
   siblings stay in the Live tree, since a session unparks them. That is the author's law,
   so the last node of the task proposes the wording in a raise and no node edits
   `ROADMAP.md`.
4. **Superseded status: derived from `Supersedes:`, never stored.** There is one place
   the fact is written, so it cannot disagree with itself, and the older node, which is
   history, is not touched. It also reverses by itself: if the node that supersedes is
   later refuted, the older one reads as confirmed again.
5. **Branch parts: one history per part**, as set out under Files.
6. **A chat session that adds nodes while a runner is live on the task.** The fault is
   that both write the task's one file and the runner's commit leaves out the chat's lines.
   In this format the chat writes its own part (`<task>/chat.history.md`, ids tagged
   `@chat`), which a runner's commit by name never touches, and which the chat commits on
   its own. A `tree.py` command that does that commit is tooling, so it is not built in
   this task: the last node raises it.

## Checks (what `check.py` will refuse, for new-format tasks only)

1. Every decision line cites a node, or an answer, that exists. Every Not taken line
   cites a refuted node.
2. A node cited by a decision is confirmed and not superseded.
3. A commit that confirms a node with `Supersedes:` also removes or rewrites the decision
   lines that cite what it supersedes.
4. Every open, started or parked node appears in the Live tree, and no other node does.
5. The history file only grows: a commit that removes or changes an existing line is
   refused, except a merge that keeps both sides' lines.
6. The status file is under the budget. This is the only size rule left, and it does not
   stop a node being added, because the node's text goes to the history.

The critic, every fifth session, samples decision lines against the Evidence of the nodes
they cite.

## Moving an old task

`tree.py migrate <task>` builds the history from the task file, the archive and the log, and
refuses to write anything if a line of the old files would be lost. For each part of the task
it writes `<task>.history.md` and the merged log, and leaves the old task file and archive as
they are (`tree.py status` writes the status file from the history). What it does:

- Each node's section is its task file lines in the order written. A stub (`Approach:
  archived.`, a Determination's `(archived.)`, `Evidence: archived.`) is replaced by the
  archive's words: every archived version of the field, oldest first, so the last wins as it
  does now; the archive's `**<id> Evidence**:` items are added once each. A `Status: started` is
  written `open`, because `started` is never in the history.
- Text with no node of its own goes before the first section: the task file's other sections
  (`## Background`) and tree preamble, and any archive text that follows no node's head.
- The log is the task file's `## Log`, the archive's `**Log**:` blocks and the log file, merged
  by time, each entry once, and written to the log file.
- `taskhistory.lost` is the check: every nonblank line of the old three files is in the new
  history or log, whitespace folded. `## Goal` and `## Summary` stay in the status file and
  are not counted; neither are titles, the `**Log**:` marker, stubs and `Status: started`.
  Anything else missing is reported with its file and line, and nothing is written.

A moved task is not trimmed afterwards: `tree.py compact` and `tree.py shelve` refuse it, because
`load` reads its log from the log file alone and never reads the archive, so entries moved there
would drop out of every count.

Writing Decisions in force and Not taken, and the first `Supersedes:` and `Tags:` lines, is
judgment, so a work session does it and the author reviews it. W75's were written from its
Determinations and the commit dates of its node subjects: 15 decision lines (2,604 characters, each citing
the nodes that shaped it), no Not taken line (no branch was refuted; its one
parked node stays in the Live tree), `Tags:` on 68 nodes, and one `Supersedes:` (the node that
holds an accept while a chain runs replaces the one that merged at once). The lines are one reading of the
Determinations, so the author reviews them.

# W87 rubric · "A walk's worktree is built from git, so it fails when the project doesn't track its roadmap files"

Written from the Goal and the starting code (299a6f14), before any replay was run or scored. Seen before writing:
the original run's Summary and node titles, so clause C7 (a merge does not overwrite the author's uncommitted
edits) and C8 (a missing task file shows as missing in the status view) are what that run found; each is put as a
test of the Goal's words ("the first session can be briefed", "looks like corruption although the file is
intact") and any way of meeting a clause counts. No replay tree or replay task file was read.

At the starting commit `scripts/branch.py` `enter(task)` cuts `.dfs/worktrees/<task>` on branch `dfs/<task>` from
HEAD and symlinks the untracked `.dfs` entries (runs, artefacts, theme) into it. `items/` and `order.md` come only
from what git tracks, so when the ignore rules hide the roadmap directory (a blanket `.*` rule with a few files
force-added) a newer task file and the current `order.md` never reach the worktree. The first session then fails
in `scripts/state.py` (`dfs_state: no task file for <id>`), `scripts/run.sh` exits 2 and the walk turns itself off
without a reason; the status view (`scripts/tui.py`) lists the task with "no nodes yet".

| # | Clause (met only if wholly true) |
|---|---|
| C1 | With a blanket `.*` ignore rule and some roadmap files force-added, entering a task gives its worktree the task file as it is in the main checkout (also when it is newer than the tracked one), so `state.py --brief <task>` succeeds there. |
| C2 | Entering such a task gives the worktree the current `order.md` of the main checkout in the same way. |
| C3 | Entering a task when the roadmap directory is tracked normally (no ignore rule) behaves as before: the worktree has the tracked files, and nothing is linked over them. |
| C4 | When a worktree still lacks the task file, the chain stops before any session is started, and the stop names the cause (task file missing in the worktree), not only an exit code. |
| C5 | A chain that cannot brief a session, or a worktree that cannot be entered, records the reason in the run's record or the task's log, so the walk's "off" state shows that reason and not "the chain ended without recording why". |
| C6 | Entering a task whose force-tracked planning file has uncommitted edits in the main checkout does not crash and does not lose those edits. |
| C7 | When the branch is merged back, the author's uncommitted edits to a file the branch also changed are not overwritten by the merge: git's refusal stands, or the edits are set aside and restored. |
| C8 | The status view (`scripts/tui.py`) says the task file is missing when it is, instead of showing an empty tree ("no nodes yet") for it. |
| C9 | The new behaviour is tested: a test builds a repo with a blanket ignore rule and force-added files, enters a task, and asserts the worktree has the task file and `order.md` (at least one such assertion fails on the starting code); the existing suite for the files changed still passes. |
| C10 | The behaviour that matters is stated where the next reader looks (README, a docstring in `branch.py`, or the commit): which planning files a worktree shares with the main checkout and which it takes from git. |

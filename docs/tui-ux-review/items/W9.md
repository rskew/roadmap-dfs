# W9 · Move session storage from JSON files to SQLite

## Goal

Sessions are stored as one JSON file per session under /var/lib/gateway/sessions, and the directory now holds 2.1M files: listing it takes minutes and the nightly expiry job takes 40 minutes. Move storage to SQLite without losing any live session and without a gateway restart being needed for rollback. Done = lookups stay under 5 ms p99 at 8 concurrent writers, expiry is a single delete, and the old files can be imported and then ignored.

## Background

History: the first attempt (an LMDB spike by Dana in August) was dropped because the ops team will not run a binary dependency on the gateway hosts. SQLite ships with Python so it is allowed. Writers today are the request threads (8) and the expiry job. Readers are request threads only.

## Tree

### W9.1 · Measure the current lookup and expiry cost
Status: confirmed
Approach: Script tools/bench_sessions.py: build 200k JSON session files in a temp dir, time 10k random lookups and a full expiry sweep.
Determination: Lookup p99 is 0.9 ms (page cache warm) but expiry sweep takes 71 s at 200k files, linear, so 2.1M extrapolates to about 12 minutes warm and far worse cold; the problem is expiry and listing, not lookup.

### W9.2 · Choose the SQLite journal mode
Parent: W9.1
Status: confirmed
Approach: Create a sessions table (id TEXT PRIMARY KEY, data BLOB, expires_at INTEGER, index on expires_at) and compare journal_mode=DELETE and WAL with 8 writer threads and 8 reader threads for 30 s each on tools/bench_sessions.py --sqlite.
Hypothesis: WAL with synchronous=NORMAL keeps p99 lookup under 5 ms at 8 concurrent writers and loses at most the last few commits on power loss, which is acceptable for sessions (users log in again). Wrong if p99 exceeds 5 ms, or if the Goal's "without losing any live session" is read as surviving power loss.
Evidence:
- for: WAL, 8 writers, 8 readers, 30 s: lookup p99 1.8 ms, 41k writes/s.
- for: DELETE mode, same load: p99 22 ms, readers blocked behind writers.
- for: sqlite docs state synchronous=NORMAL in WAL can lose recent commits on power loss but never corrupts the database.
- against: the Goal says "without losing any live session"; I read that as process crashes and restarts, not power loss, which the author may not mean.
- against: bench ran on tmpfs, so fsync cost is not represented.
Determination: Use WAL with synchronous=NORMAL. The tmpfs caveat is checked in W9.3.

### W9.3 · Re-run the benchmark on a real disk
Parent: W9.2
Status: confirmed
Approach: Repeat W9.2's WAL run with the database on /var/tmp on the CI host's ext4 SSD instead of tmpfs.
Hypothesis: fsync on ext4 does not push p99 over 5 ms in WAL/NORMAL because NORMAL only syncs at checkpoint. Wrong if p99 over 5 ms.
Evidence:
- for: p99 3.1 ms, 18k writes/s on ext4 SSD.
- against: CI host is a VM; the production hosts have spinning disks according to the README of the infra repo, which I could not check.
Determination: Holds on SSD; spinning disk is unverified. Carried to W9.9.

### W9.4 · Write the import of the old JSON files
Parent: W9.3
Status: confirmed
Approach: sessions_import.py walks the directory in batches of 5000, INSERT OR IGNORE inside one transaction per batch, skipping expired files.
Determination: Imported 200k files in 38 s; re-running is a no-op, so it can be run live while the old store is still being written, as long as W9.6 dual-writes.

### W9.5 · Dual-write during rollout (SQLite first, then JSON)
Parent: W9.4
Status: refuted
Approach: In session_store.save() write to SQLite and then to the JSON file, so rollback needs no import. Lookups read SQLite then fall back to JSON.
Hypothesis: A save that succeeds in SQLite and fails in JSON (or the reverse) can be reconciled by the import in W9.4 because INSERT OR IGNORE keeps the first writer. Wrong if the two stores can disagree about a session's content.
Evidence:
- against: killing the process between the two writes (50 trials) left 7 sessions whose JSON file was older than the SQLite row; the import ignores them, so rollback would restore stale data.
- against: INSERT OR IGNORE keeps the first row, so an updated session is never refreshed on re-import.
- for: with no kills, 10k saves left both stores identical.
Determination: Refuted: the stores can disagree and the import cannot repair it. Parked alternatives in W9.6 and W9.7 take its place; revert the dual-write commit.

### W9.6 · Roll back by exporting SQLite to JSON instead of dual writing
Parent: W9.4
Status: confirmed
Approach: Single-write to SQLite; add sessions_export.py that rewrites JSON files from the database, newest row wins, to be run at rollback time.
Hypothesis: Rollback is rare and can tolerate a minutes-long export, so one store at a time is safe. Wrong if the author needs rollback within seconds.
Evidence:
- for: export of 200k sessions took 52 s.
- for: as W9.5 showed, single store means no disagreement.
Determination: Single writer plus export. Done as in W9.5's alternative.

### W9.7 · Keep the JSON store behind a read-only fallback
Parent: W9.4
Status: parked
Approach: SQLite for writes, JSON files only read when SQLite misses, for the first week after rollout.
Determination: Not first: W9.6's export covers rollback and a fallback read path costs a stat per miss; reopen if the export is judged too slow.

### W9.8 · Expiry as a single DELETE
Parent: W9.6
Status: confirmed
Approach: Replace the nightly job with DELETE FROM sessions WHERE expires_at < ? run every minute in batches of 10000.
Determination: Deleting 1M expired rows took 9 s in batches without stalling readers. Fix what W9.7 left.

# W8 · Rate limits across two gateway processes

## Summary

The gateway can now share each client's rate-limit budget across processes: set `rate_limit_shared_dir` to a directory both processes can reach and every client's tokens live in one small file there, guarded by a file lock. Tests with two real processes show they together admit no more than burst plus rate times elapsed time, and killing one process does not stall the other. Left unset, behaviour is the old per-process limiter. Files for clients that have fully refilled are cleaned up periodically; a fixed rate/2 split per process was rejected because it wastes budget when traffic is uneven.

## Goal

We are about to run two gateway processes behind the load balancer, and the rate limiter is per-process, so a client can spend twice its budget by landing on both. Make the limit hold across the two processes. No new infrastructure this quarter (no Redis, no new service): the two processes share a filesystem and a host, nothing else. Done = two processes together admit no more than rate/burst for a client, within a small tolerance, and a process dying does not wedge the other.

## Tree

### W8.1 · Pick how the two processes agree on a client's budget
Status: confirmed
Approach: Spike (outside the repo) two real processes hammering one client at rate 10, burst 20 for 4s through a per-client state file (tokens, stamp) updated under fcntl.flock, with one process SIGKILLed at 1s in a second run. Compared on paper with a static rate/2 split per process.
Hypothesis: flock on a per-client file on the shared filesystem makes the two processes spend one budget, and the kernel drops the lock of a killed holder so the survivor is never wedged. Wrong if the two admit more than burst + rate*T together, or the survivor stalls after the kill.
Evidence:
- for: two processes for 4s admitted 43+17=60 against a limit of 20+10*4=60, exactly the bound.
- for: with one process killed at 1s the survivor kept admitting (38 in total) and exited normally, no stall.
- against: static rate/2 split needs no I/O but under-admits whenever the load balancer is uneven (a client landing only on one process gets half its budget), so it is parked, not tested.
Determination: Use flock-guarded per-client state files in a shared directory. Static split stays parked (fails the Goal's "no more than rate/burst" only on the low side, but wastes budget under skew). Next: implement it behind allow_for.

### W8.2 · Implement it behind the existing limiter_for / allow_for interface
Parent: W8.1
Status: confirmed
Approach: In src/ratelimit.py add a SHARED_DIR setting (config key rate_limit_shared_dir, empty = today's in-process behaviour, set by server.py); when set, allow_for spends from a per-client file under fcntl.flock, retrying if the file was swept (unlinked) between open and lock. Stale full-bucket files are swept under their own lock. limiter_for and the in-memory path stay unchanged.
Determination: Implemented in src/ratelimit.py, src/config.py and src/server.py; the 22 existing tests still pass. Ad hoc, two processes plus a third sweeping continuously (sweep interval 0) admitted 16+34=50 against a limit of 50, so the inode recheck holds. Next: real two-process tests.

### W8.3 · Test with two real processes, including one being killed
Parent: W8.2
Status: confirmed
Approach: tests/test_ratelimit_shared.py spawns two multiprocessing processes that hammer one client for a few seconds and asserts the summed admissions are within burst + rate*T plus a small tolerance; a second test SIGKILLs one process mid-run and asserts the other keeps being served.
Determination: Added three tests (two-process budget, SIGKILL of one process, sweep keeps drained buckets); full suite passes, 25 tests. Both processes together stayed within burst + rate*T and the survivor finished on schedule and could still spend afterwards. The Goal is met.

# W1 · Bound the rate limiter's memory

## Summary

The rate limiter now drops a client's bucket once it has refilled to full, checked at most every 10 seconds, so memory stays flat while one-off client ids churn. A dropped client gets a fresh full bucket, which is identical to what it had, so a client that is mid-burst is never reset early. The Goal was fully met; no hard size cap was added because it would have to evict active clients.

## Goal

LIMITERS in ratelimit.py gets one entry per client id and never drops any. The gateway OOMs after a few weeks in prod because of one-off client ids (scanners, CI runners). Bound it. Done = memory stays flat while client ids churn, and a client that is mid-burst is never reset to a full bucket early.

### W1.2 · Make the limiter table bounded
Parent: W1.1
Status: confirmed
Approach: In src/ratelimit.py add TokenBucket.is_full(now) and a _sweep(now) run from limiter_for at most every 10s that deletes buckets whose tokens would have refilled to burst; no hard size cap.
Hypothesis: Evicting only fully-refilled buckets is enough to bound memory, because one-off ids go idle and refill within burst/rate seconds; it would be wrong if churn within one refill window can itself exhaust memory.
Evidence:
- for: test_table_stays_bounded_under_churn passes (5000 ids, table stays under 100).
- against: none found; a size cap was rejected since it would evict mid-burst clients, which the Goal forbids.
Determination: Table is bounded by clients seen in one refill window plus the sweep interval; next, pin the mid-burst guarantee with a test.

### W1.4 · Make _sweep thread-safe (concurrent requests crash and lose tokens)
Parent: W1.2
Status: confirmed
Approach: src/server.py handles each request on its own thread, but src/ratelimit.py _sweep iterates LIMITERS.items() while other threads insert in limiter_for. A scratch script (8 threads, SWEEP_INTERVAL=0, 20000 preloaded buckets) raised RuntimeError('dictionary changed size during iteration') from limiter_for, so a real request would fail with an exception once the table is large. Also a bucket can be swept after limiter_for returned it, so allow() drains an orphaned bucket and the client effectively gets a fresh full one early. Fix: guard _sweep and the get-or-create in limiter_for with a threading.Lock (and make the sweep check-and-delete under it); add a threaded test that fails on the current code.
Determination: Added a reentrant lock in src/ratelimit.py around _sweep and limiter_for, plus allow_for (lookup and spend atomically, now used by src/server.py handle) so a sweep cannot orphan a bucket. The new 8-thread test with 20000 drained buckets failed on the old code (RuntimeError) and passes now; full suite 21 passed.

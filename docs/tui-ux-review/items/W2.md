# W2 · Config typos fail loudly

## Summary

Loading a config file now reports every key the gateway does not recognise, naming the closest known key, so a typo like rate_limit_per_sce is visible at startup. By default it prints a warning and carries on, because the shipped example and the 1.x customer configs contain keys such as legacy_mode and cache_ttl that would otherwise stop their gateways on upgrade; setting GATEWAY_STRICT_CONFIG=1 makes it refuse to start instead. The Goal's "fail loudly" is therefore met as a loud warning with opt-in failure, not a hard failure for everyone.

## Goal

Config loading silently ignores keys it does not know, so a typo like rate_limit_per_sce runs on the default and nobody notices until the incident. Fail loudly at startup instead. Customers have existing config files, so this must not take anyone's gateway down on upgrade.

## Tree

### W2.1 · Detect unknown config keys
Status: confirmed
Approach: Add config.unknown_keys(file_cfg) in src/config.py returning each file key absent from DEFAULTS, paired with the closest known key (difflib) or None. Check: it flags rate_limit_per_sce and suggests rate_limit_per_sec.
Determination: Works as a pure function; load() still ignores them until W2.2 wires reporting.

### W2.2 · Report them at startup
Parent: W2.1
Status: confirmed
Approach: In src/config.py load() passes the file's unknown keys to _report(): by default a WARNING line per key on stderr (with a "did you mean" suggestion) and startup continues; with GATEWAY_STRICT_CONFIG=1 it raises UnknownKeysError. Check: loading gateway.example.json warns about legacy_mode and cache_ttl and still returns.
Hypothesis: Warning, not refusing, is the right default: gateway.example.json itself carries legacy_mode and cache_ttl (not in DEFAULTS), and README says three customers run 1.x configs, so raising by default would take their gateways down on upgrade. Wrong if the author wants hard failure for everyone.
Evidence:
- for: gateway.example.json holds legacy_mode and cache_ttl, neither in DEFAULTS, so a default-strict load would reject the shipped example.
- for: README line on three 1.x customers and the Goal's "must not take anyone's gateway down on upgrade".
- against: the Goal says "fail loudly"; a stderr warning can still be missed, which is why strict mode is offered as opt-in.
Determination: Warn by default, strict opt-in via env var. Verified below by running the example.

### W2.3 · Cover with tests
Parent: W2.2
Status: confirmed
Approach: Add four tests to tests/test_config.py: a typo warns on stderr with a suggestion and still loads; known keys are silent; gateway.example.json (legacy keys) still loads; GATEWAY_STRICT_CONFIG=1 raises UnknownKeysError. Check: python3 -m pytest -q passes.
Determination: Full suite passes; the Goal is met: typos are reported loudly at startup (strictly on request) and existing configs keep starting.
